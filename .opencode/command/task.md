Ты обязан выполнять работу СТРОГО по шагам. Пропуск шага = ошибка.

> Это одиночный путь без отдельной coder⇄reviewer петли и агента-бенчмаркера. Если задача
> крупная, спорная или производительная — используй `/feature` (полный пайплайн с ревью-петлёй
> до APPROVED и фиксацией замеров в ADR).

Задача: $ARGUMENTS

## ШАГ 0 — Изоляция ветки (ADR-021)

Переключатель фичи — сама ветка; никаких feature-flag/env/kill-switch в коде. Проверь
`git rev-parse --abbrev-ref HEAD`:

- не `main`/`master` → ты уже в worktree фичи, продолжай к ШАГУ 1.
- на `main`/`master` → `git fetch && git worktree add ../kt-<NN>-<slug> -b <NN>-<slug> origin/main`,
  зафиксируй `WT=$(cd ../kt-<NN>-<slug> && pwd)` и продолжай в ЭТОЙ же сессии (ADR-024): все команды —
  с cwd=`$WT` (параметр `workdir`) или `git -C "$WT"`, файлы — абсолютными путями под `$WT`
  (контракт WORKTREE, skill `workflow`). Не работай поверх `main`.

## ШАГ 1 — Спеки (до любого изменения кода)

1. Прочитай specs/README.md и specs/<пакет>.md для всех затрагиваемых пакетов.
2. Отредактируй спеку ПОД новую задачу ДО изменения кода: что меняется в API, поведении или инвариантах — запиши в соответствующий spec-файл.
3. Напиши пользователю одной строкой: `Спека обновлена: specs/X.md`.

## ШАГ 2 — Чек-лист

Создай todowrite со всеми шагами: спеки → код → тесты → проверки. Отмечай статус по ходу работы.

## ШАГ 3 — Код и тесты

Реализуй строго по обновлённой спеке.
Тесты: testify.Assert*, предпочтительно table-driven.
Любое отклонение кода от спеки — остановись и спроси пользователя, не решай самовольно.

## ШАГ 4 — Проверки (обязательно)

```bash
make check
```

Запускает `go fmt` → `go vet` → `go test -race` → автофиксы современных идиом (`go fix`, golangci-lint --fix) → строгий `golangci-lint`.
Если что-то упало — чини и запускай заново. Запрещено сообщать о готовности при неуспешных проверках.

## ШАГ 5 — Бенчмарки (обязательно при оптимизациях)

Если задача затрагивает hot-path (searcher/, counter/, state/, cache/, pruner/) или заявлена как оптимизация:

```bash
make bench
```

Приложи пользователю числа ДО и ПОСЛЕ. Запрещено заявлять об ускорении без замеров.

## ШАГ 6 — Закрытие ветки (ADR-021)

Только при зелёном `make check`. Зафиксируй работу в feature-ветке (`git add` поимённо + `git commit`),
затем закрой её как принято через squash в основном дереве (механика — skill `workflow` → Закрытие;
push только по запросу). Спроси tool `question`: коммитить/сливать / пропустить.
