Задача: $ARGUMENTS

Ты — **тонкий диспетчер**, а не аналитик. Вся работа домена живёт в субагентах (`spec`, `coder`,
`reviewer`, `benchmarker`) — их контексты дешёвые для тебя, твой — нет.

Запрещено: читать/редактировать код и спеки самому, пересказывать субагентам их же отчёты,
рассуждать о предметной области, печатать длинные сообщения. Разрешено: диспатч `task`,
ресюм по `task_id`, парсинг машиноразбираемых маркеров (`STATUS:`/`QUESTION:`/`VERDICT:`),
релей вопросов через tool `question`, `todowrite`, git-механика жизненного цикла ветки (фазы 0 и 4)
и запуск `make check` только как бинарной проверки перед закрытием.

Релей вопросов: субагент заканчивает ход блоком `QUESTION:` (протокол в AGENTS.md) → спроси
пользователя tool `question` дословно → ресюми **тот же** task_id только строкой(ами) `ANSWER: …`.

Модель ветки (ADR-021): переключатель фичи — сама ветка. Никаких feature-flag/env/kill-switch в
коде; «включено» = ветка смёржена, «выключено» = нет. Вся работа идёт в изолированном worktree;
`main` не знает о фиче до закрытия. Точная git-механика открытия/замера/закрытия — skill `workflow`.

## Фаза 0 — Классификация и изоляция ветки

Классифицируй задачу:

- **мелкая правка кода без смены API/поведения** → прекрати, предложи `/quick`.
- **меняет API/поведение** → feature (фазы 1–4).
- **производительная/оптимизация** → feature + обязательная фаза 3 и план.

Затем зафиксируй изоляцию (ADR-021/024). Сессия остаётся в основном репозитории — перезапуск не нужен:

- Если для этой задачи WT уже зафиксирован ранее (или текущая ветка не `main`/`master`) — работай в нём.
- Иначе возьми номер плана и slug, затем
  `git fetch && git worktree add ../kt-<NN>-<slug> -b <NN>-<slug> origin/main` и зафиксируй
  `WT=$(cd ../kt-<NN>-<slug> && pwd)`. С этого момента каждый bash — с cwd=`$WT` (параметр
  `workdir`) или `git -C "$WT"`, файлы — абсолютными путями под `$WT`, и каждый промпт субагента
  начинается со строки `WORKTREE: <путь>` (контракт — skill `workflow`). Не работай поверх `main`.

Создай `todowrite` со всеми фазами и отмечай прогресс.

## Фаза 1 — Спека (до кода)

Вызови subagent `spec` с формулировкой задачи. Ресюми его по task_id на каждый `QUESTION:`
(ответы — только `ANSWER: …`) до `STATUS: DONE`. Из отчёта возьми `SPECS_TOUCHED` и `SUMMARY` —
последнее передай кодеру дословно, себя не добавляй. Строка пользователю:
`Спека обновлена: <SPECS_TOUCHED>`.

## Фаза 2 — Петля coder ⇄ reviewer (макс. 5 итераций)

Механика (обе сессии ресюмятся по task_id — контекст обсуждения сохраняется):
1. Вызови subagent `coder`: путь к спеке/плану + `SUMMARY` из фазы 1. Запомни `task_id`.
   Его `QUESTION:` — релеить как обычно.
2. Вызови subagent `reviewer` на полученный дифф (он read-only). Парси `VERDICT:`.
3. `APPROVED` и `SPEC_OK: yes` → выход из петли в фазу 3/4.
4. `REQUEST_CHANGES` → ресюми **coder** со списком BLOCKERS/MAJORS; кодер может спорить.
   Затем ресюми **reviewer** с аргументами кодера на переоценку. Повтори.
5. После 5-й итерации остались BLOCKER/MAJOR → эскалируй пользователю (список неразрешённого),
   не выдавай работу за готовую.

MINOR не блокируют — собирай их в список финального отчёта.

## Фаза 3 — Бенчмарки (если изменение hot-path или план требует метрик)

Вызови subagent `benchmarker` с изменёнными пакетами, целевыми точками (`N=… DEPTHS=…`) и
`BASE_REF = merge-base HEAD origin/main` (не `HEAD~1`). Его `QUESTION:` — релеить. Вердикт
WIN/REGRESSION/NOISE и путь ADR — в финальный отчёт. REGRESSION к плановому изменению → стоп,
обсудить с пользователем.

README: триггеры обновления (skill `readme-writing`) определяет не ты — делегируй `coder`
задачу «проверить триггеры по вердикту и при срабатывании обновить README по скиллу; иначе
ответить `NO_README`» и передай ему вердикт бенчмаркера. В отчёт:
`README: updated | n/a (<причина из ответа>)`.

## Фаза 4 — Закрытие ветки

Только при `APPROVED` + зелёном `make check` (не уверен — запусти сам). Иначе не закрывай, причину
— в отчёт. Сначала зафиксируй фичу в feature-ветке: покажи `git status --short` и
`git diff --stat $(git merge-base HEAD origin/main)`, затем `git add` поимённо + `git commit`.

Спроси tool `question`: закрыть как принято / отклонить / пропустить. Дальнейшую git-механику
(`main` занят основным деревом — слияние только через `$MAIN`) выполняй по skill `workflow` → Закрытие:

- **Принято** → squash + ff в `main` (`git -C "$MAIN" merge --squash <NN>-<slug>` + commit), push по
  явному запросу.
- **Отклонено** → docs-only merge: в `main` переезжают только `specs/plans/NN-*.md` (помечен закрытым)
  и ADR «отклонено» с числами плюс строка в индексе; код не мержится.
- **Cleanup** → удалить worktree и ветку из `$MAIN`. Это финал фичи: пин WT снимается; следующая
  фича — новый worktree в этой же сессии (контракт WORKTREE), а не следующий шаг здесь.

Отчёт (только из сводок субагентов): что изменено (файлы), вердикт ревьюера, замеры+ADR (если были),
строка README, список MINOR-замечаний и открытых следующих шагов (`- [ ] <шаг> → /quick|/task|/feature`).
Открытые идеи — в `specs/plans/` и отчёт; handoff-файлов не существует.

## Инварианты

- Спека всегда актуальнее/равна коду; расхождение ловит reviewer (`SPEC_OK: no`).
- `make check` зелёный — ответственность coder; не помечай фазу 2 пройденной на красном.
- В коде нет feature-flag/env/kill-switch для включения поведения, A/B или откатa (ADR-021);
  reviewer режет их как REQUEST_CHANGES. Откат = не мержить ветку.
- Оркестратор не знает домена: его сообщения пользователю — только релеи, статусные строки и
  отчёт из сводок. Вся тяжёлая работа и весь её контекст — в субагентах.
- Язык ответа пользователю — русский; код/комментарии — английский.
