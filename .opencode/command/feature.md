Задача: $ARGUMENTS

Ты — оркестратор. Ведёшь работу строго по фазам. Не пропускай фазы. Пользователь общается
только с тобой (subagents автономны) — все вопросы задавай сам.

## Фаза 0 — Классификация

Определи тип задачи:
- **мелкая правка кода без смены API/поведения** → прекрати, предложи `/quick`.
- **меняет API/поведение** → feature (фазы 1–4).
- **производительная/оптимизация** → feature + обязательная фаза 3 (benchmarker) и план.

Создай `todowrite` со всеми фазами и отмечай прогресс.

## Фаза 1 — Спека (до кода)

Подгрузи skill `spec-writing` (для плана — `plan-writing`). Проведи интервью: затронутые пакеты,
контракты, инварианты, edge cases, тест-требования; для оптимизации — гипотеза/метрика успеха/порог.
Задай пользователю недостающие вопросы (tool `question`), не додумывай критичное.

Затем **обнови спеки ДО кода**: `specs/<pkg>.md`, при необходимости план `specs/plans/NN-*` и
после принятия — ADR `specs/decisions/`. Сообщите одной строкой: `Спека обновлена: specs/X.md`.

## Фаза 2 — Петля coder ⇄ reviewer (макс. 5 итераций)

Механика (обе сессии ресюмятся по task_id — контекст обсуждения сохраняется):
1. Вызови subagent `coder`: передай путь к спеке/плану + задачу. Запомни его `task_id`.
2. Вызови subagent `reviewer` на полученный дифф (он read-only). Парси `VERDICT:`.
3. Если `APPROVED` и `SPEC_OK: yes` → выходи из петли в фазу 3/4.
4. Если `REQUEST_CHANGES` → ресюми **coder** (его task_id) со списком BLOCKERS/MAJORS; кодер может
   спорить. Затем ресюми **reviewer** с аргументами кодера на переоценку. Повтори.
5. После 5-й итерации остались BLOCKER/MAJOR → эскалируй пользователю (список неразрешённого),
   не выдавай работу за готовую.

MINOR не блокируют — переносятся в финальный отчёт.

## Фаза 3 — Бенчмарки (если изменение hot-path или план требует метрик)

Вызови subagent `benchmarker` с изменёнными пакетами, целевыми точками (`N=… DEPTHS=…`) и
`BASE_REF`. Он сверяет до/после и вписывает замеры в ADR (навсегда). Его вердикт WIN/REGRESSION/NOISE
— в финальный отчёт. REGRESSION к плановому изменению → стоп, обсудить с пользователем.

Затем проверь триггеры витрины (skill `readme-writing`): если изменение/вердикт меняет CLI-дефолты,
структуру пайплайна или итоговые выводы — обнови README.md по скиллу (таблицы через
`make bench-table`, штамп коммита). Иначе README не трогать.

## Фаза 4 — Итог

Один отчёт: что изменено (файлы), вердикт ревьюера, замеры+ADR (если были), строка
`README: updated | n/a (<причина>)`, список MINOR-замечаний к улучшению в будущем, след. шаги.
Не коммить без явной просьбы.

## Инварианты

- Спека всегда актуальнее/равна коду; расхождение ловит reviewer (`SPEC_OK: no`).
- `make check` зелёный — ответственность coder; не помечай фазу 2 пройденной на красном.
- Язык ответа пользователю — русский; код/комментарии — английский.
