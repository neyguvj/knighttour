# Написание модульных спек и ADR

Спека = **эталон текущего поведения модуля**. Всё остальное (зачем так решили, замеры,
история, идеи) уходит в ADR/plans/benchmarks. Соблюдение проверяет агент `reviewer`.

## Когда применять

- Меняешь API или поведение пакета → спеку править **до** кода.
- Создаёшь новый пакет → создать `specs/<pkg>.md`.
- Принял решение с trade-off или замерами → записать ADR в `specs/decisions/NNN-slug.md`.

## Интервью (задай себе ПЕРЕД записью)

Вопросы, на которые сам не можешь ответить безопасно, — пользователю через QUESTION-релей
(протокол в AGENTS.md): пачка `QUESTION:`-блоков в конце хода, оркестратор вернёт `ANSWER:`.

1. **Границы.** Какой пакет описываем? Какие у него публичные символы (`grep -E '^func [A-Z(]'`)?
   Что он НЕ должен делать?
2. **Контракты.** Для каждого метода: предусловия, постусловия, что возвращает, потокобезопасность,
   стоимость (O/горячий путь). Какие параметры валидны (edge-значения)?
3. **Инварианты.** Что истинно всегда и от чего это зависит? (например: «хэш шарда только по State»).
4. **Зависимости.** На какие пакеты ссылается тип в сигнатурах? Чужой код в примерах НЕ пишем —
   только имя типа/пакета.
5. **Тесты.** Какими тестами поведение закреплено / должно быть закреплено? (table-driven, testify)
6. **Решения с обоснованием/замерами?** Если «раньше было иначе» или «выбрали A вместо B потому что…»
   — это НЕ в спеку, а в ADR. Ссылка `(ADR-0NN)`.

## Правила (жёсткие)

- **Один факт = одно место.** Не дублировать API из других модулей; ссылаться `specs/<pkg>.md`.
- Запрещено в модульной спеке: исторические справки («удалено», «раньше», «legacy»), таблицы
  бенчмарков, примеры кода чужих пакетов, тела методов (это реализация).
- Разрешено: публичный API своей сигнатурой + контракт, инварианты, edge cases, тест-требования.
- Сверяй сигнатуры с **кодом**, а не со старой спекой — спеки могут отставать.
- Русский язык прозы, английский для кода/имён (см. AGENTS.md).

## Шаблон модульной спеки `specs/<pkg>.md`

```markdown
# <pkg>: <одна строка — что даёт>

## Ответственность
<1–3 предложения. Что делает и чего НЕ делает.>

## Публичный API
\`\`\`go
// только свои экспортируемые символы + краткий контракт комментарием
\`\`\`

## Инварианты
- <что всегда истинно>

## Ограничения и edge cases
- <диапазоны, вырожденные входы, потокобезопасность>

## Тесты
<что покрывает пакет; имена тестов; табличные/вероятностные кейсы. Без кода тел.>

## Связанные
ADR-0NN; specs/<pkg>.md …
```

## Шаблон ADR `specs/decisions/NNN-<slug>.md`

```markdown
# ADR-NNN. <решение одной фразой>

## Статус
Принято | Отклонено | Заменено (ADR-…) | Открытые вопросы: …

## Контекст
<какая проблема подтолкнула; ограничения>

## Решение
<что выбрали и как это выражено в коде/архитектуре>

## Последствия
<плюсы/минусы; что стало нельзя/дороже>

## Замеры
<стенд, метрики до/после — фиксируются НАВСЕГДА. Если решение не про производительность — "n/a".>

## Ссылки
Код: <пути>. Спеки: <модули>. Планы: NN. Смежные ADR: NNN.
```

После добавления ADR — добавить строку в индекс `specs/decisions/README.md`.

## После записи спеки

Запустить `make check` (если менялся и код). Спека без кода — проверить, что ссылки живые и
нет запрещённого содержимого (grep на «удалено|раньше|legacy», таблицы `| ... с |`).
