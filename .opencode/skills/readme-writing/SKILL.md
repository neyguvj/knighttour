# Ведение README.md — витрины проекта

README = **текущее состояние + финальные выводы**, статья-нарратив с единым сюжетом: задача →
почему она трудна → как алгоритм шаг за шагом сокращает поиск → что показали замеры → почему
дефолты именно такие. Это не журнал и не справочник: связный текст, где каждый раздел вытекает
из предыдущего, а не набор разрозненных фактов. Мелкие оптимизации живут в ADR и витрину не
трогают. «Один факт = одно место»: детали API — в `specs/`, замеры решений — в ADR; здесь только
числа единого бенчмарка и выводы из них.

## Когда обновлять (триггеры)

Обновляй README **в той же задаче**, если выполнено хотя бы одно:

- изменился CLI (флаги, значения по умолчанию) → таблица флагов / Quick Start;
- изменилась структура пайплайна (фаза добавлена/убрана/переименована) → «Как это устроено»;
- **существенно изменился алгоритм или спека** (новый механизм сокращения поиска, изменённый
  инвариант, по-другому работает фаза или таблица) → соответствующий раздел «Как это устроено»,
  даже если замеры не менялись: README обязан описывать текущий алгоритм, а не тот, что был на
  момент последних чисел;
- вердикт benchmarker'а меняет дефолты, плато/оптимум или итоговые выводы → «Замеры» + «Вывод».

Иначе (единицы процентов без смены механизма, внутренний рефакторинг, новые флаги для
экспериментов по умолчанию off): только ADR, README не трогать. Порог: если после изменения
старый раздел README стал описывать не то, как работает код, — обновление обязательно.

## Структура (фиксированный порядок)

1. Заголовок + CI-бейдж; 1–2 абзаца: что считаем, определение открытого тура.
2. Quick Start — 2–4 рабочие команды.
3. Флаги — таблица `Флаг | Тип | По умолчанию | Описание`; значения сверяй с кодом
   (`parseArgs`, `counter.DefaultPrecomputeDepth`), не «по памяти».
4. Сборка и проверка — `make check` + таблица целей Makefile (сверять с `Makefile`).
5. «Как это устроено» — нарратив в порядке потока данных пайплайна; каждая секция —
   1–2 абзаца прозы, детали ссылкой на `specs/<pkg>.md`. Без листингов API и тел кода;
   формулы-тождества можно. Секции связаны сюжетом: первая фраза каждой — зачем предыдущего
   шага уже не хватает (что нового она добавляет к рассказу), последняя — что из этого следует
   дальше. Раздел, читаемый как изолированный список фактов, переписать мостиками; порядок
   секций менять нельзя даже если он неудобен — это порядок понимания алгоритма.
6. «Замеры» — интро (источник один: `BenchmarkCountAllTours`, стенд) → таблица на доску
   → абзац «как читать».
7. «Вывод» — плато/оптимум, почему дефолты такие; список «измеренные и отвергнутые
   оптимизации» (по одному абзацу на пункт, со ссылкой на ADR если есть).

## Правила чисел и таблиц

- Числа **только** из `BenchmarkCountAllTours`. Процедура: `make bench` /
  `make bench-size N=… > bench.log`, затем `make bench-table LOG=bench.log`; ячейки отрукописно
  не набирать и не округлять — человек только вставляет и размечает.
- Разметка: строка дефолтной глубины помечена `(дефолт)`, строка оптимума — **жирным**.
- Эталон итого — в заголовке раздела доски (1728 / 6 637 920 / …); он обязан совпадать со
  строкой `toursExpected` бенчмарка.
- Штамп свежести под разделом замеров (один на раздел, если стенд общий):
  `> Замеры: <железо>, workers=N, <benchtime>, commit <sha> (<ГГГГ-ММ-ДД>)`.
  Коммит — последний, изменивший эти числа.
- Голых таблиц не бывает: после каждой — абзац, что на ней видно (плато, meet-in-the-middle,
  лавина финального DP).
- До/после и исторические числа — в ADR; на витрине только «как сейчас» и вывод.

## Правила прозы

- Русский язык прозы и принятые термины — по скиллу `doc-style`: без кальк и телеграфных фраз,
  одно предложение — одна мысль. Имена кода остаются английскими.
- Нарратив: зачем так сделано и что сломается иначе; спек-контракты сюда не переносим.
- История («раньше», «удалено») — только когда без неё не выводится вывод, со ссылкой `(ADR-0NN)`.
- Бюджет ~250–300 строк: перелив уезжает в `specs/`, здесь остаются 1–2 предложения и ссылка.

## Чек-лист перед коммитом

- [ ] Флаги и дефолты совпадают с кодом (`main.go`, `counter.DefaultPrecomputeDepth`).
- [ ] Цели Makefile совпадают с `Makefile`.
- [ ] Таблицы отрендерены `tools/bench_table.py`, а не набраны руками; штамп коммита стоит;
      дефолт и оптимум размечены.
- [ ] Эталонные итоги в заголовках досок сверены с `toursExpected`.
- [ ] Нет дублей API пакетов (вместо них ссылки на `specs/`); нет летописи.
- [ ] «Вывод» объясняет, как читать таблицы и почему дефолты именно такие.
- [ ] «Как это устроено» совпадает с текущими спеками: ни одного механизма, которого уже нет в
      коде; читается как связный рассказ, а не набор фактов.
- [ ] Длина ≤ ~300 строк.
