# Написание планов оптимизации `specs/plans/NN-<slug>.md`

План = **гипотеза, ещё не ставшая эталоном**. Спека описывает «как есть», план — «что
попробуем и как поймём, что получилось». Реализованное решение переезжает в спеку + ADR.

## Когда применять

- Есть идея ускорения/рефактора с проверять-гипотезой (память, CPU, алгоритм).
- Прежде чем копать код под «а что если» — сначала план, даже однострочный spike.

## Интервью (до записи плана)

Вопросы пользователю — только через QUESTION-релей (протокол в AGENTS.md): пачка `QUESTION:`-блоков
в конце хода, оркестратор вернёт `ANSWER:`. Базу, метрику и порог не додумывать — спросить.

1. **Гипотеза.** Какое измеримое утверждение проверяем? («h-формы с popcount≤K повторяются
   между соседними формами шарда → tail-мемо даст hit-rate ≥ X%»)
2. **Базовые числа.** От чего меряем прирост? Какой стенд/доска/глубина (`make bench-size N=…`)?
3. **Метрика успеха.** Конкретное число до/после и порог, при котором решение принимается
   (например «≥1.7× по памяти при регрессе ≤5% по времени»). Без порога план не план.
4. **Корректность.** Почему итог (`Σ h·M`) не изменится? Нужен ли Этап 0 (измерение потенциала
   без внедрения)?
5. **Риски и откат.** Что сломается; как выключить (флаг/env/mask по умолчанию off)?
6. **Затрагиваемые спеки/ADR.** Какие модули изменятся; какой ADR появится при принятии?

## Правила

- Имя: `NN-<slug>.md`, следующий номер по максимуму в `specs/plans/`.
- Производительный план обязан содержать конкретные бенч-точки (`make bench-size N=… DEPTHS=…`)
  и порог принятия — иначе reviewer отклонит.
- План НЕ правит спеку; спека меняется только когда решение принято (см. spec-writing).
- Замеры в плане живут, пока план активен; после принятия числа кочуют в ADR навсегда.

## Шаблон плана

```markdown
# План NN. <идея одной фразой>

## Статус
Не начат | Этап 0 | В работе | Принято (→ ADR-…) | Отклонён (причина)

## Мотивация и базовые числа
<проблема + от чего меряем; стенд/доска/метрики>

## Идея / Гипотеза
<измеримое утверждение>

## Корректность
<почему итог не изменится; контрпримеры, если есть>

## Дизайн
<как устроено; структуры, API-хуки, где включается/выключается>

## Этап 0 — измерение потенциала (опц.)
<замер без внедрения: upper bound выигрыша, чтобы не пилить зря>

## Шаги
1. …
2. …

## Метрики успеха
- <метрика>: базовое → цель (порог принятия)

## Риски
- <риск → митигция/откат (флаг по умолчанию off)>

## Затрагиваемые файлы / спеки
- код: …  спеки: …  новый ADR при принятии: NNN
```

## Жизненный цикл

```
Не начат → (Этап 0) → В работе → Принято | Отклонён
                                    │           └─ записать вывод, почему нет
                                    └─ решение в спеку + ADR (замеры навсегда), план помечать "→ ADR-…"
```

При принятии: обновить затронутые модульные спеки (spec-writing), создать ADR со «Замерами»,
в плане проставить `Принято (→ ADR-NNN)` и перенести финальные числа в ADR.

Открытые следующие шаги и отложенные идеи живут в статусе плана и финальном отчёте `/feature` —
handoff-файлов не существует («один факт = одно место»).
