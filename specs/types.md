# types: единый формат статистики подзадачи

## Ответственность

`Result` — блок счётчиков одной подзадачи поиска. Горячий ход DFS увеличивает счётчики
локально у воркера, а по завершении вызывающий один раз передаёт `Result` в мониторинг через
`ReportSubtask`. Пакет задаёт единственный формат статистики подзадачи: генерационные методы
и count-фаза отчитываются одними и теми же полями.

## Публичный API

```go
type Result struct {
    TotalPathsFound int // число дополнений подзадачи; заполняет только count-DFS с обращением,
                        // генерация оставляет ноль (пути публикует контур через ReportPathsFound)

    CacheWrites int // записи весов в таблицу — вызовы Set, включая слияние под существующим ключом

    CacheHits   int // task-cache: поиска на уровне стопа завершились попаданием (только count-фаза)
    CacheMisses int // task-cache: поиска без записи (только count-фаза)

    // Отсечения по видам — значения pruner.Reason; после Finalize их сумма равна Pruned.
    Pruned            int
    PrunedDeadEnd     int // локальный тупик: изолированная клетка или недосягаемая одиночная клетка
    PrunedNoCont      int // у последней клетки нет непосещённых соседей — продолжения нет
    PrunedDisconn     int // граф над непосещёнными клетками не связен
    PrunedEndpoints   int // нарушена эвристика про концевые клетки степени один
    PrunedForcedChain int // фильтр записи в кэш (ADR-030): перегруз или цикл обязательных цепочек
}

func (r *Result) CountPrune(reason pruner.Reason) // горячий путь: ровно один инкремент поля вида
func (r *Result) Finalize() // ставит в Pruned сумму видовых счётчиков; вызывается перед возвратом Result
```

## Инварианты

- Один `Result` ведёт локально один воркер: атомарные операции не нужны, конкуренция за
  блокировки не возникает, и параллельные воркеры не делят счётчики между собой.
- `CountPrune` обновляет только видовое поле и не трогает агрегат `Pruned`: с горячего пути
  каждого отсечения снят лишний повторный разряд по общему счётчику.
- `Finalize` вычисляет `Pruned` как сумму пяти видовых счётчиков; searcher вызывает его
  перед возвратом результата из каждой публичной методы.

## Ограничения и edge cases

- Все поля экспортированы, а логика пакета сводится к инкременту и суммированию.
- `TotalPathsFound`, `CacheHits` и `CacheMisses` заполняет только count-фаза; генерационные
  методы оставляют их нулевыми.
- Нулевой `Result` корректен: счётчики начинают вести с него.
- Значение `pruner.NoReason` означает «ветвь не отсечена», и `CountPrune` его игнорирует.
- `Finalize` допустимо вызывать повторно: каждый вызов пересчитывает сумму по текущим
  видовым счётчикам.

## Тесты

`types/types_test.go`: табличный `TestResultCountPrune` — каждый вид отсекает ровно своё поле;
`pruner.NoReason` не изменяет ни один счётчик; после `Finalize` поле `Pruned` равно сумме
видов. Подтест `"mixed reasons sum up"` проверяет, что четыре разных вида дают сумму четыре.
