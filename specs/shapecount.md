# Class mode: подсчёт через классы форм (D4 ⋉ трансляции)

## Мотивация

Oracle (см. историю, удалён) мемоизировал h(U,u) таблицей классов и показал на
стенде 6×6 d18: ~250k записей, из них ~87% — нули, повторная обращаемость
классов всего ×1.16. Таблица почти не переиспользуется, но занимает память и
требует локов в хот-патте.

Наблюдение: пути симметричны обратному времени, `W(T,t) = h(reversed)`; знание
об инвариантности h к трансляциям позволяет **совсем убрать мемо-таблицу** —
каждый класс запрашивается ровно один раз по построению алгоритма.

## Математика (toждество перегруппировки)

Пусть генерация построила все префиксы глубины p с весами мультипликативности
симметрий start-орбит. Тогда при q = totalCells − p:

```
total = Σ_{листьев(T,t)} weight(T,t) · Σ_{u ∈ N(t) ∩ U} h(U,u),   U = full \ T
      = Σ_классам C=(shape,end_rel)  h(C) · M(C),                   (перегруппировка)

M(C) = Σ weight(листа) по всем листьям, чья пара (U,u) нормализуется в класс C.
```

Это точная перегруппировка суммы без допущений об инвариантности f: размещения
учтены тем, что M накапливается по фактическим размещённым листьям генерации.
Граничная проблема (дополнение не коммутирует с трансляцией) исчезает.

Следствия:
- нули h не хранятся и не пересчитываются — класс вычисляется один раз на
  финальном проходе; `h(C)=0` просто не даёт вклада;
- мемо-таблица не нужна вообще, нужна только M-аккумулятор (одна запись на
  опрошенный класс, ~8 МБ на стенде против oracle-таблица + task-cache);
- ограничение `2p ≤ totalCells` снято: режим работает при любом q.

## Компоненты

### symmetry — нормализация класса формы

Математика перенесена из oracle (`Prepare/keyOf/normEnd`): 8 ориентаций D4,
bbox к (0,0), лексикографический минимум пар `(shape, end_rel)` с tie-break по
end. API: `CanonicalizeShape(st,end) path.Path`, амортизированные
`PrepareShape(st,*ShapeCtx)` + `KeyFromPrepared(ctx,end) path.Path` (одна
нормализация маски на все концы листа). Ключ класса — единый `path.Path`
(отдельный `ShapeKey` удалён как структурный дубликат).

### cache.Accumulator — аккумулятор M

Шардированный `map[path.Path]uint64` (`Add(key, w)`, `DrainShard(i)`/`Drain()`).
Тот же тип, что и промежуточный аккумулятор gen A (см. cache.md). Без хранения
нулей по построению: запись создаётся только при Add. Потокобезопасен
(шарды под мьютексами).

**LocalSink (буфер воркера).** Прямой `Add` на стенде 6×6 d18 — ~1.5M локов
на шардах, профиль: ~26% CPU в contention + rehash под локом. Поэтому писатели
(gen A и gen B) работают через `acc.Local()` → `*LocalSink`: локальный
`map[path.Path]uint64` схлопывает дубликаты классов (~6× на стенде), при
переполнении буфера (порог) `Flush` догружает каждый уникальный ключ одним
захватом лока шарда. Семантика M аддитивна, порядок не важен; sink не
разделяется между горутинами.

### Финальный проход

M разбирается шард за шардом (`DrainShard`, без общего снимка): срез шарда
сортируется по `State` (`slices.SortFunc`), формы — это непрерывные диапазоны
`[lo, hi)` этого среза (без map/append-промежутков: аллокации группировки
O(шард) → O(число форм)); хэш шарда берёт только `State`, поэтому глобальная
сортировка не нужна вовсе (cache.md). Задачи-формы сортируются по убыванию
длины (прокси стоимости DP); воркеры берут индексы **батчами**
(`next.Add(batch)`) — атомиков на порядок меньше, очередей каналов нет.
Группировка намеренно живёт на чтении, а не на записи: сортировка шарда —
~0.3% CPU против ~20% у пути `Add`/`Flush` (подробности — counter.md).

### shapecount — вычисление h по классу

`CountShape(shape state.State, ends []int, res *types.Result) []uint64` —
DP-перечисление путей коня внутри формы с мемо `f(cur,todo)`; **одно мемо на все
концы одной формы** (подзадачи `(cur,todo)` общие). Прунер тот же
(`ShouldPruneAfterVisit`), корректность на нормализованных координатах — аргумент
инвариантности смежности (наследуется из specs/oracle.md, теперь здесь). По
умолчанию — без состояния между вызовами; опциональный persistent-уровень
описан ниже (план 03, вариант B).

**Shape-фильтр (план 02).** До выделения memo-буфера каждый конец прогоняется
через `pruner.ShapeFeasible(end, shape, mask)` (контракт — specs/pruner.md).
Маска конфигурируется `SetShapeFilter`, по умолчанию
`DefaultShapeFilter = L2ForcedChain`: этап 0 (specs/plans/02) показал, что
forced-chain убивает 53–67% нулевых форм, articulation даёт ~1 п.п. сверх
этого за полный Tarjan на конец (не включена), а endpoint-mismatch не
срабатывает никогда (покрыт корневым L1). Порог по |shape| не введён: в class
mode `|U| = s²−d ≥ s²/2 ≥ 12` при допустимых глубинах. Отсечённый конец
получает `h=0` без вызова DP; если отсечены **все** концы — форма возвращает
нулевой срез и memo-буфер не заводится вовсе, а `res.FilteredShapes++` считает
такие формы (`L2None` выключает фильтр побитово). Нулевая семантика не
меняется: фильтр даёт только доказуемые нули, итог `Σ h·M` инвариантен.
Статистика DP-прунеров (`pruned*`) остаётся отдельной от `FilteredShapes`.

**Tail-мемо (persistent level 2, план 03).** `CountShapeWithTail(shape, ends,
res, tail)` принимает необязательный `tail *TailMemo` — таблицу `f(cur,todo)`,
живущую **между вызовами одного воркера** финального прохода (`NewTail()`;
`nil` = уровень выключён, поведение побитово как без параметра).

- Ключ точный `(todo, cur)` в нормализованных координатах формы, **без
  канонизации**: значение пары зависит только от индуцированного подграфа
  `G[todo ∪ {cur}]` с отмеченным `cur`, поэтому совпадение ключа между двумя
  формами гарантирует совпадение значения (та же аргументация инвариантности,
  что у прунинга выше).
- Пишутся только записи с `popcount(todo) ≤ K` (мелкие хвосты — именно они
  повторяются между соседними формами шарда); читаются тоже только они
  (проверка по `CountBits` до обращения в таблицу). Нули сохраняются наравне
  с ненулями (прунер даёт корректный ноль дешёво, а нулевые хвосты — самое
  частое повторение).
- Хранилище — открытая адресация без штампов (пустой слот: `todo == 0`,
  состояние `todo == 0` не мемоизируется), рост удвоением до `capSlots`;
  при переполнении запись останавливается (таблица только теряет потенциал,
  но не корректность; LRU нет). Одна таблица на воркера — без локов.
- Статистика: `res.TailLookups` / `res.TailHits` (доля попаданий — метрика
  потенциала плана 03); `DPStates` по-прежнему считает только реально
  вычисленные состояния (промах по обоим уровням).

**Статистика прунинга.** Необязательный `res` (`nil` допустим) накапливает
отсечения в локальном `types.Result` (без конкурентности — счётчик один на
вызов, инкремент int на hot path): каждый сработавший прунер → `CountPrune`,
перед return — `Finalize`. Контур (`counter.processShapes`) складывает его в
монитор через `ReportSubtask` — иначе фаза `counting` показывает `pruned 0`,
хотя прунер там работает.

**Мемо-буфер.** `map[struct{State;uint8}]uint64` в профиле — главный источник
аллокаций (~12 ГБ/op на стенде 6×6 d18, ~50 КБ/форму). Заменирован на
переиспользуемую таблицу открытой адресации (плоские массивы
`keys/curs/vals/stamps`, линейная пробировка, load factor ≤ ½, рост удвоением):

- буферы живут в `sync.Pool` пакета — это не «состояние между вызовами»:
  на `Get` таблица логически пуста (инкремент поколения делает все слоты
  пустыми за O(1), нулевые значения `h=0` различимы от пустых по штампу);
- семантика `CountShape` не меняется (единственное позднее дополнение API —
  счётчик прунинга `res`); аллокации сводятся к
  росту таблиц (амортизированно редко) и буферам пула при исчерпании P;
- хэш ключа `(todo,cur)` — финализатор murmur3 над `uint64(todo)` с подмешиванием
  `cur`.

### counter — единый режим подсчёта

`ParallelCountWithDepth(ctx, monitor, workers, precomputeDepth)` — class mode на
всех допустимых глубинах (`precomputeDepth ∈ [1, total/2]`, валидация main.go):
фазы A/B пишут листьями в M через LocalSink (task-cache не строится), финальный
проход — параллельно по формам: `total += Σ h(C)·M(C)`; работа воркеров —
work-stealing батчами индексов (см. «Финальный проход»). При
`precomputeDepth ≤ TwoPhaseBaseDepth` фаза B вырождается (эмиссия из
промежуточных записей), семантика не меняется.

Legacy cache-reversal удалён вместе с `cache.Cache`.

Порога по хвосту `q` больше нет (бывш. `MaxClassTail = 18`): DP финального
прохода с общим мемо на форму и прунером недорог при любом q на досках
5×5/6×6 (замер: 6×6 depth=10, q=26 — ~0.3 с), поэтому режим привязан к
наличию фазы B генерации.

Нулевые h-формы стоят дёшево (прунер отсекает в корне DP).

## Мониторинг

`Monitor.ReportShapeStats(classes, shapes, zeroShapes int)` — вместо oracle-строки:
число классов (записей M), число форм (задач финального прохода), число форм с
h=0 по всем концам. Задачи финального прохода публикуются через `AddTasks`.

Статистика прунера из `CountShape` публикуется на каждую форму-задачу через
`Monitor.ReportSubtask(res)` — фаза `counting` показывает живую разбивку
pruned по видам, как gen A/gen B.

## Тесты (эталонные требования)

- Корректность режима: для 5×5 и 6×6 итог == известный полный перебор (5×5:
  1728 открытых; 6×6: 6 637 920) при всех тестовых глубинах `1..total/2`.
- Инвариант нормализации `CanonicalizeShape`: одинаковый ключ для всех D4/трансляций
  одной пары; полный перебор форм размера ≤ 4 совпадает с орбитами действия
  группы (миграция тестов из oracle_test.go).
- `CountShape` == брутфорс-перечисление на случайных связных масках (миграция
  property-тестов oracle), в т.ч. многоконцевой вызов с общим мемо.
- M-аккумулятор: конкурентные Add под `-race`, сумма весов инвариантна.
- Tail-мемо (план 03): значения с общим `tail` между формами совпадают со
  свежим прогоном (подзадача «пришла из другой формы»); при выключенном
  уровне (`nil`) результат побитово идентичен `CountShape`; на паре
  пересекающихся форм `TailHits > 0`, а итог `ParallelCountWithDepth` на 5×5
  не меняется (1728).
- Shape-фильтр (план 02): табличные кейсы в pruner (контрпримеры A/B/C,
  вырожденные формы 1–3 клетки); вероятностный тест «фильтр не отсекает форму
  с ненулевым h» — случайные маски против `bruteForceH`; итог
  `ParallelCountWithDepth` на 5×5/6×6 при включённом фильтре == эталону;
  убитая форма поднимает `FilteredShapes`, живая — нет.
