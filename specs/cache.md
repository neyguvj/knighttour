# Компонент Cache: Аккумулятор весов (единое хранилище)

## Назначение

Единственная потокобезопасная таблица «ключ → агрегированный вес» всего алгоритма.
Заменила собой прежний `Cache` (memo-кэш подзадач с Get/Set/Each) и отдельный
`Accumulator` класса форм: после отказа от legacy prefix-cache reversal у обоих
назначений одна семантика — **аддитивное накопление весов, чтение только после
завершения фазы записи (drain per-shard)**. Копирующий `Snapshot()` удалён: на
больших досках он удваивал пик памяти (копия всей таблицы при живых map-шардах);
вместо него таблица отдаётся наружу шард за шардом с освобождением каждого.

Два экземпляра живут в пайплайне counter.md:

1. **Промежуточный аккумулятор генерации (gen A)** — ключ: каноническая D4-пара
   `(state, end)` префикса глубины `base`; вес: `Σ orbitSize` слившихся префиксов.
2. **Аккумулятор M (gen B)** — ключ: нормализованная пара формы дополнения
   `(shape, end)` (D4 ⋉ трансляции, см. symmetry.md / shapecount.md);
   вес: `Σ weight(листа)` всех листьев, чья пара `(U, u)` нормализуется в этот класс.

## Структура данных

```go
type accShard struct {
    data map[path.Path]uint64
    mu   sync.Mutex
}

// Accumulator — шардированная (128 шардов) таблица path → вес.
// Нули по построению не хранятся: запись создаётся только при Add.
type Accumulator struct {
    shards [numAccShards]accShard
}

// Entry — одна запись таблицы (worklist фазы B, единица отдачи шарда).
type Entry struct {
    Path   path.Path
    Weight uint64
}
```

- **key**: `path.Path` — компарировая пара `(state, end)`. Для gen A это
  каноническое размещение префикса, для M — нормализованная форма; структура
  ключа едина (ShapeKey удалён как дубликат).
- **value**: `uint64` вес; сложение коммутативно, порядок слияния не важен.

### Хэширование и шардинг

```go
func accShardIndex(p path.Path) int {
    // Бесаллокационный хэш только от State: умножение на золотое сечение,
    // старшие биты. End в хэше сознательно отсутствует — инвариант:
    // все концы одной формы (одного State) лежат в одном шарде, поэтому
    // группировка по формам возможна per-shard без глобальной сортировки.
    h := uint64(p.State()) * 0x9E3779B97F4A7C15
    return int(h >> (64 - 7)) // numAccShards = 128
}
```

Инвариант «State → шард» позволяет counting-фазе counter.md обрабатывать
каждый шард независимо (drain → сортировка своего среза → DP), не строя общий
снимок. Побочный эффект: концы одной формы при генерации пишутся в один шард —
локи размывает LocalSink-бафферизация, а 128 шардов держат коллизию горячих
форм низкой.

## API

```go
func NewAccumulator() *Accumulator

func (a *Accumulator) Add(p path.Path, weight uint64) // data[k] += weight под мьютексом шарда
func (a *Accumulator) ItemsCount() int

// Drain-чтение — только после остановки всех писателей (фазы пайплайна
// барьерятся errgroup'ами). Шард залочен только на время своей отдачи.
func (a *Accumulator) NumShards() int
func (a *Accumulator) DrainShard(i int) []Entry // забирает шард i и освобождает его map
func (a *Accumulator) Drain() []Entry           // конкатенация всех шардов (для маленького worklist gen A)

func (a *Accumulator) Local() *LocalSink

type LocalSink struct{ ... } // не разделять между горутинами
func (s *LocalSink) Add(p path.Path, weight uint64)
func (s *LocalSink) Flush()
```

### LocalSink (буфер писателя)

Прямой `Add` каждого листа — лок на шард и rehash map под локом (~26% CPU в
профиле 6×6 d18). Писатели обеих фаз генерации работают через `acc.Local()`:
локальный `map[path.Path]uint64` схлопывает дубликаты ключей (~6× на стенде),
при переполнении буфера (порог `localFlushLimit = 1024`) `Flush` догружает
каждый уникальный ключ одним захватом лока шарда. `defer sink.Flush()`
гарантирует доставку остатка. Семантика аддитивна — тайминг флюша на результат
не влияет.

## Почему только аддитивное накопление, без Get/Has

- Генерация пишет префиксы/классы, потребители читают **после** завершения фазы
  записи (`DrainShard`/`Drain`), поэтому мемоизация «чти-при-промахе» не нужна.
- Отказ от `Get`/`Set`/`Each`/`GetCanonical` убрал RWMutex (хватает Mutex) и
  зависимость от `Symmetry` внутри пакета — канонизацию выполняет писатель
  (searcher), аккумулятор про симметрии ничего не знает.

## Использование в Searcher/Counter

```go
// gen A: searcher.GenerateRoots пишет канонические префиксы через sink;
// gen B: searcher.ExtendToClasses пишет классы дополнений через sink.
inter := cache.NewAccumulator()
sink := inter.Local()
defer sink.Flush()
...
entries := inter.Drain() // worklist для следующей фазы (таблица мала, depth ≤ 5)

// counting: M разбирается по шардам без общей копии — см. counter.md.
for i := range acc.NumShards() { ... acc.DrainShard(i) ... }
```

## Память

`DrainShard` отдаёт записи шарда и обнуляет его map. Плоский `Entry` стоит
24 Б против ~27–28 Б/запись в Go-map ≥1.24 (Swiss-мап: инлайн-слот 16+8,
байт метаданных, load factor ~93%; оценка заменила «~35 Б» эпохи bucket-карты —
см. пересмотр в specs/plans/01), поэтому разбор таблицы в срез **чуть дешевле**
её хранения: резидентный объём counting-фазы монотонно падает, а истинный пик
остаётся в конце фазы генерации (копирующий `Snapshot` удваивал его — удалён).
Освобождённые map'ы возвращаются сборщику мусора по мере разбора шардов.

## Хранилище: нативная Swiss-map, не self-made и не sync.Map

Решение (зафиксировано после пересмотра плана 01): шарды остаются
`map[path.Path]uint64` до тех пор, пока Этап 0 плана 01 не измерит обратное.

- **Swiss-map (Go ≥1.24)** уже делает то, что обещала «плоская таблица»:
  открытая адресация, SIMD-метаданные групп, load factor ~93%, pointer-free
  слоты без GC-скана. Своя SoA-таблица даёт ~×1.2 по памяти, а не ×2.5–3 —
  порог включения ≥1.7× при регрессе ≤5% (specs/plans/01).
- **sync.Map отклонён.** Профиль workload — аддитивные апдейты горячих общих
  ключей (`writesB` ~3.6G на 7×7 d22): atomic-add нет (CAS-цикл вокруг
  Load/Store, аллокация entry на каждый Store), указателеструктурная природа
  даёт GC-скан миллионов живых записей, контракт `DrainShard` (все концы формы
  в одном шарде, draining без общего снапшота) невыразим. sync.Map оптимизирован
  под read-mostly неизменяемых ключей — антипод нашей нагрузки.

## Тесты

- `Add`/`Drain`: суммирование весов под одним ключом, отсутствие нулевых записей,
  опустошение таблицы после drain.
- Инвариант шардинга: одинаковый `State` при разных `End` попадает в один шард.
- `LocalSink` == прямой `Add` (дубликаты, порог флюша, явный `Flush`).
- Конкурентные sinks под `-race`: сумма весов инвариантна.

## Возможные улучшения

- **Bloom Filter**: предварительная проверка наличия ключа до захвата мьютекса
  (актуально только если появятся читатели в фазе записи).
- **Compression**: сжатие ключей для экономии памяти на глубоких досках.
