# Методология бенчмарков

Единый бенчмарк `BenchmarkCountAllTours` (`counter/benchmark_test.go`) — полный
свип глубин meet-in-the-middle разреза **по убыванию** (`size²/2 .. floor`) для каждого
размера доски. Убывающий порядок: на больших досках дорогие (глубокие) разрезы
интереснее и именно они упираются в таймеры — свип отдаёт их первыми.

Это **методология**. Конкретные числа до/после решений фиксируются в ADR
(`specs/decisions/`), не здесь.

## Как запускать

```bash
make bench                 # свип 5×5/6×6 (фильтр size[56]), -benchtime=10x
make bench-deep            # + свип 7×7 (часы): фильтр size[567], -timeout=48h
make bench-size N=7 [DEPTHS=20,22]   # один размер ОТДЕЛЬНЫМ процессом
make bench-8x8 DEPTHS=32             # точечный прогон 8×8 (-timeout=24h)
make bench-table LOG=bench.log       # рендер markdown-таблиц (tools/bench_table.py)

# напрямую: без фильтра гонятся ВСЕ доски (часы/дни) — размер перечисляй явно;
# для size8 всегда добавляй и фильтр глубин (DEPTHS в make, ^depth(a|b)$ здесь):
# полный свип 32 точек × часы ≈ недели
go test -v -run='^$' -bench='BenchmarkCountAllTours/size[56]' -benchmem ./counter/
```

## Отбор досок — `-bench`-фильтры, env нет

В бенч-коде переменных окружения нет (ADR-020): что исполняется решает только `-bench`-фильтр
цели Makefile.

| Цель | Отбор |
|------|-------|
| `make bench` | `…/size[56]` — дешёвые доски, штатный прогон |
| `make bench-deep` | `…/size[567]` — + 7×7 (часы) |
| `make bench-8x8 [DEPTHS=…]` | `…/size8`; без `DEPTHS` — default-фильтр `^depth(32|30)$` (часы на точку, ADR-015) |
| `make bench-size N=… [DEPTHS=a,b]` | `…/sizeN`; `DEPTHS` транслируется в `^depth(a|b)$` — точечный набор вместо свипа (для N=8 тот же cap по умолчанию) |

Валидация глубин переехала вместе с гейтами: несопоставимая глубина молча не запускает подтестов
(exit 0 без строк `Benchmark`, ADR-020) вместо SKIP/Fail с сообщением. Якоря в фильтре обязательны:
сегменты `-bench` матчатся регуляркой без якорей, и `depth(1)` подобрал бы ещё depth10–19.
В коде остаётся одна таблица: `depthFloors` (`{7:6}`) — пол нисходящего свипа (ниже точки
неоплатны по времени, см. ниже). Cap 8×8 (`32,30`) живёт в Makefile как default-фильтр глубин
для size8-целей; произвольный точечный `DEPTHS` перезаписывает его (ADR-015).

Подтесты именуются `size{N}/depth{D}`.

Пол глубины 7×7 = 6: критерий — время. На дне кривой точка стоит ~50 мин
(доминирует count-фаза) и вниз только дорожает, память на дне ~15 МБ — пол
защищает от длительности свипа, не от ресурсов.

## Публикуемые метрики (`b.ReportMetric`)

Читаются из `FakeMonitor`-снимков **по фазам** (`Phase("gen A"/"gen B"/"counting")`).
Каждая итерация `b.Loop()` создаёт **новый** FakeMonitor (снимки аддитивны) и оборачивает
прогон в `Start(ctx)`/`Finish()` (без `Finish` длительность последней фазы не фиксируется).

| Метрика | Смысл |
|---------|-------|
| `genA_ms/op`, `genB_ms/op`, `cnt_ms/op` | тайминг фаз |
| `writesA/op`, `writesB/op` | эмиссии в промежуточную таблицу gen A и task-cache (не уникальные ключи) |
| `prunedA/op`, `prunedB/op` | отсечено прунером в генерации |
| `cacheHits/op`, `cacheMisses/op` | lookup'ы task-cache на уровне стопа в counting |
| `peakRSS_MB/op` | **максимум резидента процесса** (`syscall.Getrusage`) |
| `totalAllocMB/op` | дельта `runtime.MemStats.TotalAlloc` вокруг итерации |

Общие (`Totals()`) и пер-подзадачные (`subtasks`) метрики не публикуются: суммы видны
как A+B, а `subtasks` дублирует `tasks`.

## Единицы peak RSS

`peakRSS_MB/op` — максимум на процесс и **не убывает**: при прогоне нескольких размеров в
одном процессе цифра соответствует самому прожорливому подтесту. Для честных чисел —
один размер отдельным процессом (`make bench-size N=…`). darwin возвращает байты, linux —
КиБ; конвертируют `counter/meminfo_{darwin,linux}_test.go`, единство сторожит
`TestPeakRSSUnits`. Последний поднимает свежий процесс по внутреннему сигналу `PEAKRSS_CHILD` —
это служебный признак re-exec'а, а не ручка тюнинга (ADR-020).

## Сверка итога

Итог сверяется с `toursExpected` (5×5 — 1728, 6×6 — 6 637 920, 7×7 — 165 575 218 320);
расхождение — `b.Fatalf`. Глубина split'а на итог не влияет. Отсутствующих в таблице
размеров сверка **не** касается (разведочные прогоны, например первый 8×8).

## Дисциплина замеров

- Прогоны штатно работают с GOGC 40 — процент понижает сам конвейер (ADR-014), внешний
  env `GOGC` кодом **перезаписывается**. Контрольный прогон без понижения GC — явно
  `SetGCPercent(0)`/`-gc-percent 0`, не env.
- Любое изменение hot-path обязано прикладывать before/after числа (`make bench` /
  `make bench-size`) — нельзя заявлять выигрыш без измерения.
- A/B фичи меряется против базы `merge-base HEAD origin/main`, снятой в отдельном base-worktree с
  уникальным именем (фича живёт в своей worktree-ветке, переключателя-флага нет — ADR-021). Долгие
  точки (7×7) сериализуются глобальным `flock ../kt-bench.lock`: параллельные прогоны разных фич
  искажают тайминги и peak RSS. Механика — skill `workflow`.
- Числа решения попадают в ADR (навсегда), сюда — только изменения методологии.
- CI (`.github/workflows/test.yml`) запускает **только тесты**: бенчмарки выбираются явным
  `-bench`-фильтром и в CI появляться не должны — инвариант (отсутствие гейтов в коде его
  не меняет).
