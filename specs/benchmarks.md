# Методология бенчмарков

Единый бенчмарк `BenchmarkCountAllTours` (`counter/benchmark_test.go`) для каждого размера доски
выполняет проход по диапазону глубин meet-in-the-middle разреза **по убыванию**: от `size²/2` до
нижнего предела. Порядок выбран убывающим, потому что на больших досках глубокие разрезы дороже всех
и именно они упираются в таймеры; зато они и наиболее интересны, поэтому идут первыми.

Здесь описана только **методология**. Конкретные числа до и после решений фиксируются в ADR
(`specs/decisions/`), не в этом файле.

## Как запускать

```bash
make bench                 # доски 5×5 и 6×6 (фильтр size[56]), -benchtime=10x
make bench-deep            # плюс доска 7×7 (часы): фильтр size[567], -timeout=48h
make bench-size N=7 [DEPTHS=20,22]   # один размер отдельным процессом
make bench-8x8 DEPTHS=32             # точечный прогон 8×8 (-timeout=24h)
make bench-table LOG=bench.log       # рендер markdown-таблиц (tools/bench_table.py)

# Прямой запуск: без фильтра запускаются все доски, и это часы или дни.
# Указывайте размер явно; для size8 всегда добавляйте и фильтр глубин —
# в целях make за него отвечает DEPTHS, здесь шаблон ^depth(a|b)$.
# Полный проход по диапазону глубин для 8×8 (32 точки × часы) идёт недели.
go test -v -run='^$' -bench='BenchmarkCountAllTours/size[56]' -benchmem ./counter/

# Ген-ценз (план 19): фазы gen A и gen B пишут в сток, без task-cache и count-фазы;
# память фазы B постоянна, время растёт только с числом префиксов. Отбор точек — тот же
# фильтр -bench; тяжёлые доски под глобальным замком, как и остальные часовые точки:
flock ../kt-bench.lock go test -run='^$' -bench='BenchmarkGenCensus/size8/^depth(16|17)$' ./counter/
```

## Ген-ценз `BenchmarkGenCensus` (план 19)

Тот же отбор досок и глубин фильтром `-bench`, что у `BenchmarkCountAllTours`: подтесты
`size{N}/depth{D}`, глубины от `size²/2` до нижнего предела. Публикует только счётчики
генерации и время фаз: `genA_ms`, `genB_ms`, `writesA/B`, `prunedA/B`. Peak RSS не публикуется:
фаза B пишет в сток и почти не аллоцирует, count-фазы нет. Счётчики тождественны полному прогону
той же глубины — это закреплено тестом эквивалентности (`specs/counter.md`).

## Отбор досок — фильтры `-bench`, переменных окружения нет

В коде бенчмарка переменных окружения нет (ADR-020): что именно исполняется, решает только фильтр
`-bench` у цели Makefile.

| Цель | Отбор |
|------|-------|
| `make bench` | `…/size[56]` — дешёвые доски, штатный прогон |
| `make bench-deep` | `…/size[567]` — добавляется доска 7×7, она идёт часы |
| `make bench-8x8 [DEPTHS=…]` | `…/size8`; без `DEPTHS` действует фильтр по умолчанию `^depth(32|30)$`, на точку уходят часы (ADR-015) |
| `make bench-size N=… [DEPTHS=a,b]` | `…/sizeN`; `DEPTHS` транслируется в `^depth(a|b)$` — отдельные точки вместо полного прохода; для N=8 действует тот же фильтр по умолчанию |

Валидация глубин переехала вместе с гейтами: несопоставимая глубина молча не запускает ни одного
подтеста — код возврата 0 без строк `Benchmark`, а не SKIP или Fail (ADR-020). Якоря в фильтре
обязательны: сегменты `-bench` сопоставляются с регуляркой без якорей, поэтому `depth(1)` захватил
бы ещё depths 10–19.

В коде остаётся одна таблица — `depthFloors` (`{7:6}`); она задаёт нижний предел нисходящего прохода
по глубинам, ниже которого точки неоплатны по времени (см. ниже). Потолок для 8×8 (`32|30`) живёт в
Makefile как фильтр глубин по умолчанию для целей size8; явный `DEPTHS` перезаписывает его (ADR-015).

Подтесты именуются `size{N}/depth{D}`.

Нижний предел для 7×7 — глубина 6, и выбран он по времени. Точка на дне кривой стоит около 50 минут,
в ней доминирует count-фаза, а ниже стоимость только растёт. Память на дне — около 15 МБ, поэтому
предел защищает от длительности прохода, а не от нехватки ресурсов.

## Публикуемые метрики (`b.ReportMetric`)

Метрики читаются из снимков `FakeMonitor` **по фазам** — через `Phase("gen A")`, `Phase("gen B")` и
`Phase("counting")`. Каждая итерация `b.Loop()` создаёт **новый** FakeMonitor, потому что снимки
аддитивны. Прогон оборачивается в `Start(ctx)`/`Finish()`: без `Finish` длительность последней фазы
не фиксируется.

| Метрика | Смысл |
|---------|-------|
| `genA_ms/op`, `genB_ms/op`, `cnt_ms/op` | время фаз gen A, gen B и count-фазы |
| `writesA/op`, `writesB/op` | число записей в промежуточную таблицу (gen A) и в task-cache (gen B); считаются все записи, а не уникальные ключи |
| `prunedA/op`, `prunedB/op` | отсечения прунера в каждой генерационной фазе |
| `prunedL2A/op`, `prunedL2B/op` | из них — отсеки фильтра записей в кэш (причина ForcedChain), по фазам gen A и gen B |
| `taskEntries/op` | число класс-задач count-фазы; считается полным обходом task-cache и публикуется контуром как поле `Tasks` фазы `counting` |
| `cacheHits/op`, `cacheMisses/op` | обращения к task-cache на уровне ранней остановки счёта в count-фазе |
| `peakRSS_MB/op` | **максимум резидентной памяти процесса** (`syscall.Getrusage`) |
| `totalAllocMB/op` | приращение `runtime.MemStats.TotalAlloc` вокруг одной итерации |

Сводные метрики из `Totals()` и метрики по подзадачам не публикуются: суммы видны как A+B, а поле
`subtasks` дублирует `tasks`.

## Единицы peak RSS

`peakRSS_MB/op` — максимум на весь процесс, и он **не убывает**: при прогоне нескольких размеров в
одном процессе цифра соответствует самому прожорливому подтесту. Для честных чисел запускайте каждый
размер отдельным процессом: `make bench-size N=…`. На darwin `Getrusage` возвращает байты, на linux —
кибибайты; конвертацию выполняют `counter/meminfo_{darwin,linux}_test.go`, а единство единиц сторожит
`TestPeakRSSUnits`. Этот тест поднимает свежий процесс по внутреннему сигналу `PEAKRSS_CHILD`; это
служебный механизм re-exec, а не ручка тюнинга (ADR-020).

## Сверка итога

Итог сверяется с таблицей `toursExpected`: 5×5 — 1728, 6×6 — 6 637 920, 7×7 — 165 575 218 320. При
расхождении бенчмарк падает через `b.Fatalf`. Глубина разбиения на итог не влияет. Размеры, которых
нет в таблице, сверке **не** подлежат: это разведочные прогоны, например первый прогон 8×8.

## Дисциплина замеров

- Штатные прогоны работают с GOGC 40: процент понижает сам конвейер (ADR-014), а внешний `GOGC` из
  окружения код **перезаписывает**. Контрольный прогон без понижения GC делают явно — через
  `SetGCPercent(0)` или `-gc-percent 0`, а не через переменную окружения.
- Любое изменение горячего пути обязано прикладывать числа до и после (`make bench` или
  `make bench-size`); нельзя заявлять выигрыш без измерения.
- A/B-сравнение фичи ведут против базы `merge-base HEAD main`: локальная ветка `main` может быть
  впереди отстающего `origin/main`. Базу снимают в отдельном base-worktree с уникальным именем,
  потому что фича живёт в своей ветке и переключателя-флага нет (ADR-021).
- Долгие точки (7×7) сериализуются глобальным замком `flock ../kt-bench.lock`: параллельные прогоны
  разных фич искажают тайминги и peak RSS. Механика — в skill `workflow`, а запуск тяжёлых целей без
  flock блокирует гейт G9 (`specs/gates.md`, ADR-025).
- Числа решения попадают в ADR навсегда; в этот файл приходят только изменения методологии.
- CI (`.github/workflows/test.yml`) запускает **только тесты**. Бенчмарки выбираются явным фильтром
  `-bench` и в CI появляться не должны; это инвариант, и отсутствие гейтов в коде его не меняет.
