# План 05. Память в бенчмарке, переключатель размера 8×8 и процедура сравнения подходов

## Статус

Инфраструктура реализована (2026-09-12): метрики `peakRSS_MB/op` и
`totalAllocMB/op`, переключатель среды `BENCH_8X8`, переменная `BENCH_DEPTHS`, цели
`bench-size`/`bench-8x8`/`bench-table`, `tools/bench_table.py`; CI проверен (только `make test`).
2026-09-16 (ADR-020): переключатели среды и переопределения удалены из кода бенчмарка —
отбор досок и точечные прогоны `DEPTHS` живут в Makefile как `-bench`-фильтры; цели и
механика плановых замеров сохранены.

Отличия от текста плана: пик публикуется в МБ (`peakRSS_MB/op`) для читаемости; сверка
с `/usr/bin/time -l` выполнена на тестовом двоичном файле, который считает одну глубину:
43.8 МБ внутри против 46.1 МБ снаружи (−5%, на границе допуска). Метрика равна максимуму
процесса, поэтому она корректна только при прогоне размера отдельным процессом. Единство
единиц (байты на darwin, килобайты на linux) сторожит тест `TestPeakRSSUnits`: он запускает
подпроцесс, потому что в общем тестовом двоичном файле поле Maxrss хранит исторический
максимум других тестов.

Пункт 5 пересмотрен (ADR-015): точка 8×8 для режима классов (class mode — прежний режим
подсчёта, строивший таблицу классов форм дополнения) снята как невыполнимая, потому что
class mode заранее не помещается в память; механика переключателя и целей Makefile
сохранена для будущих прогонов обратного обхода (reversal — прежнего режима подсчёта через
общий task-cache и тождество обращения). После ADR-016 конвейер один, переменные среды
`BENCH_MODE`/`SHAPE_FILTER` удалены: `bench-8x8` остался точечным переключателем
`BENCH_8X8=1` без переключателя режима. Первый прогон 8×8 в режиме reversal — отложенная
задача вне текущих сводов; она ничего не блокирует.

## Проблема

- Бенчмарк публикует только время и счётчики (`genA_ms/op`, `writesB/op`, …). Пик памяти
  приходилось снимать вручную обёрткой `/usr/bin/time -l` — именно так выяснилось, что
  class mode на 7×7 d22 стоит 23.46 ГБ против 9.60 ГБ у reversal.
- 8×8 не замерялась никогда: нет ни переключателя размера, ни выбора точечных глубин, ни
  оценки того, сколько это стоит.
- Скрипт построения markdown-таблиц из логов бенчмарка живёт во временном каталоге и теряется.

## Дизайн

### Метрики памяти

1. `peakRSS/op` — максимум резидента процесса через `syscall.Getrusage(RUSAGE_SELF)`:
   на darwin поле `Maxrss` измеряется в байтах, а на linux — в килобайтах, поэтому
   вспомогательный код собирается под двумя тегами сборки. **Важно:** это максимум на
   процесс, а не на итерацию, значит каждый размер доски нужно запускать отдельным
   процессом (`-bench=.../size7`), иначе цифра соответствует самому прожорливому подтесту.
2. `totalAllocMB/op` — дельта `runtime.ReadMemStats().TotalAlloc` вокруг итерации:
   показатель воспроизводим и ловит шум аллокаций; он полезен для сравнения встроенной
   map Go с собственной открытой таблицей из плана 01.
3. Вспомогательные функции живут в тестовых файлах (`counter/meminfo_test.go`,
   `meminfo_darwin_test.go`, `meminfo_linux_test.go`), чтобы не тащить пакет `syscall`
   в рабочий пакет.

### Переключатели и параметры прохода по диапазону глубин

- `BENCH_8X8=1` включает размер 8 по образцу `gatedSizes`/`BENCH_DEEP`; глубины берутся из
  `depthFloors`, а нижнюю границу диапазона для 8×8 подбирает первый же прогон и фиксирует
  её в таблице.
- `BENCH_DEPTHS=30,32,...` задаёт точечный набор глубин вместо прохода по всему диапазону —
  это нужно для часовых прогонов.
- Цели Makefile:
  - `bench-size{N}` — прогон одного размера отдельным процессом ради корректного peak RSS;
  - `bench-deep` — работает как сейчас (5/6 + 7×7);
  - `bench-8x8` — задаёт `BENCH_8X8=1 BENCH_DEPTHS=…` и ставит `-timeout` на сутки.
- Проверить `.github/workflows/test.yml`: CI не должен запускать прогоны под
  переключателями; сейчас там только тесты, и это стоит зафиксировать как инвариант.

### Процедура сравнения подходов

1. Текущий вариант берётся из рабочего дерева, а эталонный — из отдельного дерева
   (`git worktree add <tmp> <commit>`), где он считается командой
   `/usr/bin/time -l ./binary -size N -precompute-depth D` (именно так получена пара
   596 с / 23.46 ГБ против 252 с / 9.60 ГБ на 7×7 d22). У старого
   CLI есть дополнительный флаг `-oracle-depth`, и процедура фиксирует его значение
   (0 = legacy reversal).
2. Обе цифры — время и RSS — заносятся в таблицу `specs/counter.md`; таблица помечает
   вариант и коммит эталона, чтобы сравнение оставалось воспроизводимым.
3. Markdown из логов строит стабильный скрипт `tools/bench_table.py`: он разбирает вывод
   `-bench`, приводит наносекунды и миллиарды к читаемым единицам и сортирует глубины по
   убыванию. Вызов живёт в Makefile: `make bench-table LOG=…`.

### Оценка стоимости 8×8 (чтобы понимать цену прогона)

Экстраполяция по замерам 7×7: стоимость одной формы растёт примерно в ×2.5 на каждую
клетку дополнения.

| доска/глубина | дополнение | форм | время на форму |
|---|---|---|---|
| 7×7 d24 | 25 | 84.8M | 2.3 мкс |
| 7×7 d20 | 29 | 44.6M | 11 мкс |
| 7×7 d14 | 35 | 3.35M | 0.31 мс |

Для 8×8 даже максимальный допустимый разрез (d=32) оставляет дополнение в 32 клетки, а
число форм на порядок больше, чем на 7×7 d22. Ожидание одно: прогон займёт часы. Поэтому
переключатель сделан точечным (`BENCH_DEPTHS`), а цель первого замера — не оптимум, а хотя
бы одна завершившаяся точка вместе с оценкой памяти.

## Метрики успеха

- В выводе бенчмарка есть `peakRSS/op` и `totalAllocMB/op`, и их значения сходятся с
  `/usr/bin/time -l` на том же прогоне (±5%).
- Есть воспроизводимая команда для замера одного размера доски и одной глубины.
- Получена первая точка 8×8 (время + память) для class mode и, если возможно, для
  эталонного reversal — с явной пометкой, где прогон уткнулся в память.
- CI не запускает прогоны под переключателями.

## Риски

- `Maxrss` — максимум процесса: при прогоне нескольких размеров в одном процессе метрика
  непригодна. Решение (отдельные запуски) должно быть в документации, иначе цифры будут
  вводить в заблуждение.
- Разные единицы darwin/linux — риск молчаливой ошибки в ×1024; его нужно покрыть тестом
  с аллокацией известного размера.
- Прогон 8×8 может остановить машину свопом или нехваткой памяти (OOM): запускать по одной
  глубине, с `ulimit -v` и ручным контролем, и обязательно фиксировать сам факт гибели как
  результат.
