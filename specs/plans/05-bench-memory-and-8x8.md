## Проблема

- Бенчмарк публикует только время и счётчики (`genA_ms/op`, `writesB/op`, …). Пик памяти
  приходилось снимать вручную обёрткой `/usr/bin/time -l` — именно так выяснилось, что
  class mode на 7×7 d22 стоит 23.46 ГБ против 9.60 ГБ у reversal.
- 8×8 не замерялась никогда: нет ни гейта по размеру, ни выбора точечных глубин, ни
  оценки, сколько это стоит.
- Скрипт рендера markdown-таблиц из логов бенчмарка живёт во временном каталоге и теряется.

## Дизайн

### Метрики памяти

1. `peakRSS/op` — максимум резидента процесса через `syscall.Getrusage(RUSAGE_SELF)`:
   на darwin `Maxrss` в байтах, на linux — в килогерцах, поэтому хелпер собирается под
   двумя build-тегами. **Важно:** это максимум на процесс, а не на итерацию, значит
   каждый размер доски нужно гонять отдельным запуском (`-bench=.../size7`), иначе цифра
   соответствует самому прожорливому подтесту.
2. `totalAllocMB/op` — дельта `runtime.ReadMemStats().TotalAlloc` вокруг итерации:
   воспроизводимо, ловит аллокационный шум (полезно для сравнения Go-map против открытой
   таблицы из плана 01).
3. Хелперы живут в тестовых файлах (`counter/meminfo_test.go`, `meminfo_darwin_test.go`,
   `meminfo_linux_test.go`), чтобы не тащить `syscall` в рабочий пакет.

### Гейты и параметры свипа

- `BENCH_8X8=1` включает размер 8 (по образцу `gatedSizes`/`BENCH_DEEP`); глубины — из
  `depthFloors`, для 8×8 пол подбирается первым же прогоном и фиксируется в таблице.
- `BENCH_DEPTHS=30,32,...` — точечный набор глубин вместо свипа (для часовых прогонов).
- Цели Makefile:
  - `bench-size{N}` — прогон одного размера отдельным процессом (корректный peak RSS);
  - `bench-deep` — как сейчас (5/6 + 7×7);
  - `bench-8x8` — `BENCH_8X8=1 BENCH_DEPTHS=…`, с `-timeout` на сутки.
- Проверить `.github/workflows/test.yml`: CI не должен запускать гейтированные прогоны
  (сейчас там только тесты — зафиксировать это как инвариант).

### Процедура сравнения подходов

1. Текущий вариант — из рабочего дерева, эталонный — из `git worktree add <tmp> <commit>`
   и `/usr/bin/time -l ./binary -size N -precompute-depth D` (именно так получена пара
   596 с / 23.46 ГБ против 252 с / 9.60 ГБ на 7×7 d22). У старого CLI есть дополнительный
   флаг `-oracle-depth` — в процедуре фиксируется его значение (0 = legacy reversal).
2. Обе цифры (время и RSS) заносятся в таблицу `specs/counter.md`; таблица помечает вариант
   и коммит эталона, чтобы сравнение оставалось воспроизводимым.
3. Рендер markdown из логов — стабильный скрипт `tools/bench_table.py` (парсит
   `-bench`-вывод, приводит наносекунды/миллиарды к читаемым единицам, сортирует глубины
   по убыванию), вызывается из Makefile: `make bench-table LOG=…`.

### Оценка стоимости 8×8 (чтобы понимать цену гейта)

Экстраполяция по замерам 7×7 (стоимость одной формы ≈ ×2.5 на каждую клетку дополнения):

| доска/глубина | дополнение | форм | время на форму |
|---|---|---|---|
| 7×7 d24 | 25 | 84.8M | 2.3 мкс |
| 7×7 d20 | 29 | 44.6M | 11 мкс |
| 7×7 d14 | 35 | 3.35M | 0.31 мс |

Для 8×8 даже максимальный валидный разрез (d=32) оставляет дополнение в 32 клетки, а
число форм на порядок больше, чем на 7×7 d22. Ожидание: один прогон — часы; поэтому
гейт точечный (`BENCH_DEPTHS`), а цель первого замера — не «оптимум», а хотя бы одна
живая точка с памятью.

## Метрики успеха

- В выводе бенчмарка есть `peakRSS/op` и `totalAllocMB/op`, значения сходятся с
  `/usr/bin/time -l` на том же прогоне (±5%).
- Есть воспроизводимая команда для замера одного размера доски и одной глубины.
- Получена первая точка 8×8 (время + память) для class mode и, если возможно, для
  эталонного reversal — с явной пометкой, где прогон уткнулся в память.
- CI не запускает гейтированные прогоны.

## Риски

- `Maxrss` — максимум процесса: при прогоне нескольких размеров в одном процессе метрика
  непригодна; решение (отдельные запуски) должно быть в доке, иначе цифры будут
  вводили в заблуждение.
- Разные единицы darwin/linux — риск молчаливой ошибки в ×1024; покрыть тестом с
  аллокацией известного размера.
- Прогон 8×8 может убить машину свопом/OOM: запускать по одной глубине, с
  `ulimit -v`/контролем вручную, и обязательно фиксировать факт гибели как результат.
