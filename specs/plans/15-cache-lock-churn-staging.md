# План 15. Убрать lock churn шардированной таблицы: батч-запись в gen B и lock-free чтение в count

## Статус

Принято (→ ADR-031, WIN): стадии 1+2; wall 7×7 d22 −15.4%, genB −18.6%, cnt −9.4%. Финальные
числа — в ADR-031 «Замеры».

## Мотивация и базовые числа

Профиль 7×7 d22 (2026-09-25, M4 Max 14 ядер, `work/genprof/NOTES.md`): wall **212.4 с**
(genA 0.8 мс, genB **135.4 с**, cnt **77.1 с**), writesB 942.6M, lookup'ов task-cache ≈ 1.95G.
Загрузка планировщика нормальная (busy P = 13.7–14/14), но ~40% CPU-семплов — runtime churn
вокруг коротких критических секций `Cache`:

- `cache.Set` в `dfsTask` — **375 с** из 716 с поддерева gen B; из них `mapassign` только 40 с,
  остальное — механика RWMutex: `Unlock→unlockSlow→semrelease` со спином на семафорных bucket-локах
  (~300 с семплов) и work-stealing backoff планировщика (`runqgrab→usleep` 522 с). Реального
  park-wait всего 20.6 с (mutex-профиль): проблема — **число lock/wake операций (942M), а не ожидание**.
- `Cache.Get` в `completions` — **176 с** из 343 с; полезный `mapaccess2` 122 с, ещё 43 с —
  `RLock/RUnlock` (atomic ping-pong по readerCount) на таблице, иммутабельной после барьера генерации.

GC (~54 цикла) и рост map — не проблема; хвост-страгглеры gen B (~15 с просадки до ~9/14) — вне объёма.

Стенд/точки: `make bench-size N=7 DEPTHS=22` (фазовые `genB_ms`, `cnt_ms`), контроль —
`make bench-size N=6 DEPTHS=14` и точка 5×5; база A/B — merge-base (ADR-021).

## Идея / Гипотеза

Число обращений к шардовым локам можно сократить на 2–3 порядка без изменения итога:
батч-запись (один цикл лока на пачку вместо лока на эмиссию) снимает wake/spin churn gen B,
а чтение post-barrier таблицы без RWMutex снимает atomic ping-pong в count-фазе.
Ожидаем `genB_ms −5%` и `cnt_ms −5%`, суммарный wall `−5%`.

## Корректность

Итог — коммутативная аддитивная свёртка (`Set`: `data[k] += w`, specs/cache.md): перенос момента
сложения из точки эмиссии во флеш батча не меняет содержимое таблицы к моменту барьера.
Count-фаза читает таблицу только после барьера генерации (specs/counter.md), писателей нет —
чтение без локов законно при предусловии «писателей нет», которое уже является инвариантом фазы
(тот же контракт, что у `Each`). Лемма звукосности гейта записи (specs/searcher.md) не затрагивается:
множество ключей и весов идентично. Частичные прогоны при отмене ctx: флеш буфера выполняется на
выходе воркера и при `ctx.Err()` — видимость записанных листьев не хуже текущей.

## Дизайн

**Стадия 1 — батч-запись gen B (`dfsTask` → `cache.Staging`).**
Писатель (воркер gen B) накапливает эмиссии в собственном `cache.Staging`: корзина по индексу
шарда (`[numShards][]Entry`, append без хеша — индекс это умножение), авто-флеш при `limit`
(фиксированная константа, кандидат 8192; оверрайдов нет — ADR-020) и явный `Flush` на выходе
воркера; флеш складывает непустые корзины под одним Lock каждого задетого шарда (дубликаты
пачки схлопываются в одно сложение). Хук включения — `Sink` (`Set(path, w)`): `*Cache` и
`*Staging` реализуют обе; `GenerateTasks`/`ExtendTask` принимают `cache.Sink`. Промежуточная
таблица gen A (малая, µs) пишется напрямую, как сейчас. Альтернатива с локальной map воркера
(дедуп до флеша) не выбрана: `mapassign` — только 40 с из стоимости Set, extra-hash и память
не оправданы; фиксируется здесь как отклонённая ветка дизайна.

**Стадия 2 — lock-free чтение count-фазы (`Cache.Reader`).**
Новый метод `func (c *Cache) Reader() *Reader` — неизменяемая ручка прямого чтения map шардов без
локов; контракт: создавать и использовать только при отсутствии писателей (гарантия барьера
вызывающего контура). `countStackTasks`/`completions` получают `*Reader` вместо `*Cache`; `Get`
с RLock остаётся для генерационной фазы (там Set конкурентен). Инвариант «видимость после барьера»
обеспечивается happens-before завершения писателей (`errgroup.Wait`) и создания Reader.

## Аллокационный бюджет

- Staging-срез: `24 Б × F × workers` = 8192·24·14 ≈ **2.75 МБ** на прогон, предвыделен один раз
  на воркера, ноль аллокаций на эмиссию (append в ёмкость). Пик таблицы не меняется (те же записи).
- `Reader` — структура-указатель на шарды, нулевые данные.
- Копий таблиц нет: чтение прямое (эталон count-фазы — live-read по инварианту фазы, ADR-013),
  запись — та же аддитивная схема, только сгруппированная по лок-захватам.

## Этап 0 — измерение потенциала (в рамках первого замера)

Гистограмма: распределение числа эмиссий на ExtendTask-задачу и доли дубликатов ключей **внутри
одной пачки F** (счётчик unique/emitted на флеш). Если unique≈emitted — сортировка по шардам даёт
ровно `lock_ops ≈ emitted/F` — гипотеза подтверждена до основной реализации.

## Шаги

1. Worktree `15-cache-lock-churn-staging` (ADR-021), база A/B — merge-base.
2. Этап 0: счётчики unique/emitted на флеш (временные, в work/ логи) + контроль HEAD ×2 на 7×7 d22.
3. Стадия 1: `cache.Sink` + `cache.Staging`, перевод searcher/counter; тесты: аддитивность и
   схлопывание дубликатов пачки, эквивалентность итога таблично (5×5 все глубины), ctx-семантика
   частичного прогона с недосбросом буфера (флеш на выходе).
4. Стадия 2: `Cache.Reader` + перевод count-фазы; тесты: hit/miss идентичен `Get`, race-чистота
   `-race`, инвариантность итога к workers.
5. Benchmarker: 7×7 d22 ×повторы (пороги ниже), контроль 6×6 d14 и 5×5; peak RSS; числа в ADR.
6. Спеки: `cache.md` (SetBatch, Reader, инварианты), `searcher.md` (эмиттер вместо прямого Set),
   `counter.md` (фазы/барьер — без изменений семантики); README не трогать (триггеры не горят).

## Метрики успеха

- 7×7 d22: `genB_ms` 135.4 с → **≤ 128.6 с (−5%)**; `cnt_ms` 77.1 с → **≤ 73.2 с (−5%)**;
  wall 212.4 с → **≤ 201.8 с (−5%)**, вне диапазона повторов контроля.
- Итог побитово неизменен (гейт `toursExpected`), peak RSS ≤ базы +100 МБ, аллокации/прогон — без
  new-O(emissions).
- Контроль 6×6 d14: регресс не хуже шума повторов.

## Риски

- Сортировка пачки по шардам добавляет O(F log F) на флеш → при F=8192 это ~мкс, дешевле lock-цикла;
  если профилем вылезет — корзины по 128 шардам за один проход.
- Reader вне локов опасен при появлении писателя после барьера → контракт документируется в спеке,
  тест с намеренным писателем не входит в API (нарушение — UB контракта, как у `Each`).
- Промежуточная таблица gen A остаётся прямым Set (фаза µs) — разнобой путей фиксируется в спеке.
- Откат = не мержить feature-ветку (ADR-021); флага в коде нет.
