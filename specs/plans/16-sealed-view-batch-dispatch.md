# План 16. Неизменяемый снимок `View` и безаллокационный канал партий для раздачи count-фазы (замена стека на условных переменных и колбэка `Each`)

## Статус

**Принято, закрыто** (2026-09-25, пользователь). Порогом принятия были читаемость API без
регресса горячего пути; приняты протокол «write → seal → read» и канал партий вместо стека.
Реализация — ветка/worktree `16-cache-view-dispatch` (ADR-021), влита через squash. Вердикт —
**WIN**: cnt 7×7 d22 −4.4%, wall −3.7%, контрольные счётчики совпали побитово; числа навсегда в
**ADR-032**. Спеки обновлены до кода: `specs/cache.md`, `specs/counter.md`; изменение
распространено на `specs/searcher.md`.

## Мотивация и базовые числа

Механика раздачи count-фазы досталась от плана 13 (ADR-019, WIN −5.6% `cnt_ms` против счёта
прямо внутри обхода `Each`). Производитель под `RLock` шарда копировал записи в общий
ограниченный стек (LIFO) с двумя условными переменными (condvar). Это около 100 строк ручной
синхронизации: остановка гортины до сигнала, широковещательное пробуждение, флаг закрытия и
частичная дозапись при неполностью свободном стеке. Вокруг неё накопился контрактный долг
пакета `cache`:

- `Each` — это колбэк под `RLock` шарда, унаследовавший оговорку ADR-013: чтение под
  блокировкой шарда законно только при отсутствии писателей. Ожидание на канале не требует
  никаких блокировок.
- API чтения раздуто: в нём числятся `Reader` (чтение без блокировок после барьера), живой `Get`
  под `RLock` (рабочий код его не вызывает — проверено grep'ом, только тесты), `ItemsCount`
  (тот же барьер, что у `Seal`) и сам `Each`. Все четыре уходят с приходом фазового протокола
  «write → seal → read».
- Поле `cacheShard.mu` было `RWMutex`: писатели gen B платили атомарной механикой учёта
  читателей на каждом `Lock`, хотя конкурентных читателей после барьера не осталось (ADR-031
  убрал чтения, но блокировки остались).

База чисел — HEAD `88310de` (ADR-031), точка **7×7 d22, workers=14** (`make bench-size N=7
DEPTHS=22`, стенд Apple M4 Max 14 CPU): wall **180.5–182.5 с**, `genB_ms` **109.8–113.1 с**,
`cnt_ms` **69.5–70.7 с**, peak RSS **5.16–5.31 ГБ** (ADR-031 §Замеры, прогоны стадии 1+2).
Перед открытием ветки обязателен свежий контроль HEAD ×2: прецеденты планов 13/15 показали
дневной дрейф в единицы процентов.

## Идея / Гипотеза

Фазовый протокол `Seal() *View` и нативный канал партий вместо стека с условными переменными
дают **ту же производительность горячего пути**. Снимок отвечает `Get`/`Len` без блокировок, а
`All(ctx) iter.Seq[Entry]` выполняет ленивый pull-обход всей таблицы без блокировок и без её
копирования (итератор сам тянет записи по одной). Средний `cnt_ms` ветки неотличим от контроля:
вне диапазона повторов — только в минус; аллокаций на запись — ноль. При этом код раздачи и API
пакета сокращаются: исчезают логика условных переменных, частичная дозапись пачки, колбэк под
блокировкой, а также живой `Get`, `Each` и `ItemsCount`. Синхронизационный бюджет не меняется:
с каждой стороны одна канальная операция приходится на `Beff` записей — это столько же, сколько
было захватов мьютекса в стеке. Переход LIFO→FIFO измерён как TIE (ADR-019, контрастная
точка).

## Корректность

- **Итог не меняется**: действует та же формула `total = Σ W(task)·f(task)`. Обход отдаёт каждую
  запись таблицы ровно один раз: map читается целиком после барьера, а писателей нет по
  предусловию `Seal`. Партия несёт `n ≤ Beff` записей, а `close` после обхода эквивалентен
  закрытому стеку.
- **Порядок FIFO** измерён как TIE относительно LIFO (ADR-019 §LIFO/FIFO: средний Δ −0.2% при
  шуме ≥1%; hits/misses от порядка не зависят). Это контрактная правка без численного риска.
- **Чтение без блокировок законно**: действует то же инвариантное предусловие фазы — писателей
  нет после барьера. Его уже держат `Reader` (ADR-031) и `Each` (ADR-013), а `Seal` концентрирует
  его в одной точке API. Появление писателя после `Seal` — data race по контракту предусловия;
  рантайм-проверки нет, как не было и раньше.
- **Отмена ctx**: `All` останавливается сам на границе шардов. Производитель завершает цикл,
  остаточную партию при отменённом ctx не отправляет и закрывает канал (`close(ch)`). Потребители
  дочитывают партии из буфера канала **без подсчёта**: при `ctx.Err()` задача пропускается. Итог
  получается частичным, но возвращается без паники. У итератора нет источника ошибок, поэтому
  правило panic-на-чужой-ошибке `checkEachError` умирает за ненадобностью.
- **Взаимоблокировка исключена**: буфер всегда не меньше одного слота (`capacity ≥ 1`).
  Производитель блокируется только на отправке, а потребители никогда не ждут производителя и
  всегда дочитывают канал до `close`.

## Дизайн

**cache — протокол write → seal → read:**

- `Seal() *View` приходит на смену `Reader()`. У `View`: `Get(p) (uint64, bool)` — чтение без
  блокировок, как у нынешнего `Reader`; `Len() int` — число записей после барьера;
  `All(ctx) iter.Seq[Entry]` — pull-обход всей таблицы без блокировок. Записи отдаются прямо из
  map шардов при предусловии «писателей нет», копирования таблицы — ноль. Цикл проверяет ctx
  между шардами, а `break` потребителя означает частичный обход. Порядок следования записей —
  по номерам шардов, внутри шарда — как их выдаёт Go map, то есть как у нынешнего `Each`.
  Повторный `Seal` даёт независимые снимки одной и той же таблицы.
- **Удалить**: `Cache.Each`, `eachShard`, живой `Cache.Get` (рабочий код его не вызывает),
  `Cache.ItemsCount` (после барьера служит `View.Len`) и `Reader`. Поле `cacheShard.mu` станет
  `Mutex` вместо `RWMutex`: блокировка нужна только писателям (`Set`, `Staging.Flush`).
- `Sink`/`Staging` не меняются. Тесты видимости `Staging` экранируются через `Seal`: до сброса
  буфера виден писательский слой пакета, после — снимок `View`.

**counter:**

- `ParallelCountWithDepth` становится тонким оркестратором: установка GOGC на время счёта +
  `generateIntermediate` (gen A) → `extendTasks` (новый метод: gen B, атомарный чанк-цикл со
  `Staging` переезжает туда без изменений семантики) → `countTasks`. Публичный API пакета не
  меняется.
- Материализация списка работ gen A: обход `view.All(ctx)` в предвыделенный срез
  `[]cache.Entry` с ёмкостью `View.Len()`.
- `countTasks`: вместо taskStack — канал партий. Элемент канала — структура
  `entryBatch { n int; items [dispatchClaimBatch]Entry }` (Beff ≤ B=16 всегда). Буфер —
  `make(chan entryBatch, ceil(capacity/Beff))`, где `capacity = max(min(consumers·K, records), 1)`;
  это прежняя ёмкость стека, пересчитанная в единицы партий. Здесь `records = view.Len()`, а
  формула `Beff` и константы K/B/C без изменений (ADR-019). Производитель ведёт единственный
  цикл по `view.All`: наполняет `items[:Beff]` и отправляет полную партию; остаток становится
  последней отправкой, после чего канал закрывается. Число потребителей прежнее: каждый читает
  `for b := range ch` и для каждой записи вызывает прежний `countOneTask`, уже без каких-либо
  блокировок. Отмена — см. раздел «Корректность». Константа `dispatchStackCapacity`
  переименовывается под новую механику; значение K=10000 не меняется, и по ADR-020 новых ручек
  не добавляем.

**searcher:** сигнатура `CountPathsWithCacheReversal(..., c *cache.Reader, ...)` меняется на
`*cache.View`; это механическое распространение переименования снимка.

## Аллокационный бюджет

Размер элемента проверен `unsafe.Sizeof`: `entryBatch = 8 + 24·B = 392 Б` (Path 16 Б, Entry 24 Б).

- Буфер канала: `⌈capacity/Beff⌉ × 392 Б`. Это одна аллокация на старте фазы и ноль аллокаций
  на запись, потому что отправка копирует структуру в предвыделенный буфер hchan.
- Худший случай (workers=14, K=10000, насыщение Beff=B=16): `⌈140 000/16⌉ = 8750` слотов × 392 Б ≈
  **3.43 МБ** против стека в 3.36 МБ. Разница +2% объясняется заголовком `n` — эффективные 24.5 Б
  на запись слота.
- Активная зона формулы (`records < B·consumers·C = 896`): там `capacity = records`, а слотов не
  больше `~2·consumers·C = 112`, то есть ≤ 44 КБ; округление целочисленного деления учтено
  множителем 2.
- Глобальная верхняя граница: `max(⌈consumers·K / B⌉, 2·consumers·C) × 392 Б`. При workers=14
  доминирует первая ветвь — **≤ ~3.4 МБ**; это шум против пика task-cache (ГБ).
- Копий таблицы нет нигде: `All` отдаёт записи прямо из map шардов, и механика эталона ADR-013
  (прямой обход без снимков) сохранена. Снимок всей таблицы и изъятие записей по-прежнему
  запрещены.

## Риски

- **Потеря гранулярности частичной дозаписи**: производитель ждёт целый свободный слот партии и
  не дописывает записи в оставшееся место. Это безопасно — буфер не меньше одного слота, и
  потребители всегда дочитывают канал, — но поведение в хвосте при полном буфере становится чуть
  грубее прежнего; его заметит метрика `cnt_ms`.
- **LIFO → FIFO**: контрастная точка измерена как TIE (ADR-019), риск закрыт заранее; hits/misses
  от порядка не зависят.
- **Удаление живых `Cache.Get`/`ItemsCount`/`Each`** — контрактная правка API пакета: тесты
  портируются через `Seal`/`View`, рабочих потребителей нет (проверено grep'ом). Гипотетический
  внешний потребитель лишается потокобезопасного чтения в середине прогона, но по факту им никто
  не пользовался.
- **Канал против одного мьютекса**: план 11 показал цену синхронизации на каждую запись (+14.5%).
  Здесь с каждой стороны одна канальная операция приходится на `Beff` записей — как раньше захваты
  стека. Ожидаем паритет; при регрессе вне полосы — отклонение: ветку не мержить, числа ложатся в
  закрытый план.
- **Обход `View.All` по map шардов**: появление писателя после `Seal` — data race по контракту
  предусловия (тот же класс риска, что был у `Reader`/`Each`). Рантайм-проверки нет; тест с
  намеренным писателем остаётся вне контракта.
- Откат = не мержить feature-ветку (ADR-021); флаг или переменная окружения в коде не появляются.
