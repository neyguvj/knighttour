# План 16. Sealed view `View` + безаллокационный батч-канал диспатча count-фазы (замена condvar-стека и колбэчного `Each`)

## Статус

**Принято, закрыто** (2026-09-25, пользователь): протокол «write → seal → read», батч-канал вместо
стека, гейт — читаемость без регресса hot-path. Реализация — ветка/worktree `16-cache-view-dispatch`
(ADR-021), влита squash-мержем; WIN: cnt 7×7 d22 −4.4%, wall −3.7%, бит-гейты идентичны — числа
навсегда в **ADR-032**. Спеки обновлены до кода (`specs/cache.md`, `specs/counter.md`,
propagated: `specs/searcher.md`).

## Мотивация и базовые числа

Механика count-диспатча досталась от плана 13 (ADR-019, WIN −5.6% `cnt_ms` против inline-Each):
продюсер под RLock шарда копирует записи в общий bounded-LIFO стек с **двумя condvar'ами** (~100
строк ручной синхронизации: park/broadcast/closed-flag, partial-push при неполном стеке). Вокруг неё
накопился контрактный долг пакета `cache`:

- `Each` — колбэк под RLock шарда с унаследованным caveat ADR-013 («блокировка продюсера законна
  только при отсутствии писателей»); блокировка на канале сегодня не требует никакого зало.
- API чтения раздут: `Reader` (безлоковый, post-barrier) + живой `Get` (RLock, в проде **не
  вызывается** — проверено grep'ом, только тесты) + `ItemsCount` (тот же барьер, что у Seal) +
  сам `Each`. Все четыре сходят с приходом фазового протокола «write → seal → read».
- `cacheShard.mu` — RWMutex: писатели gen B платят atomic readerCount-механику на каждом `Lock`,
  хотя конкурентных читателей после барьера никто не держит (ADR-031 снял чтения, локи остались).

База чисел — HEAD `88310de` (ADR-031), точка **7×7 d22, workers=14** (`make bench-size N=7
DEPTHS=22`, стенд Apple M4 Max 14 CPU): wall **180.5–182.5 с**, `genB_ms` **109.8–113.1 с**,
`cnt_ms` **69.5–70.7 с**, peak RSS **5.16–5.31 ГБ** (ADR-031 §Замеры, прогоны стадии 1+2).
Свежий контроль HEAD ×2 перед веткой — обязателен (прецеденты планов 13/15: дневной дрейф единицы
процентов).

## Идея / Гипотеза

Фазовый протокол `Seal() *View` (безлоковые `Get`/`Len` + pull-обход `All(ctx) iter.Seq[Entry]`
без локов и копий таблицы) и нативный канал батчей вместо стека с condvar'ами дают **ту же
производительность hot-path** — `cnt_ms` ветки неотличим от контроля (вне диапазона повторов —
только в минус), при нуле аллокаций на запись, — а код диспатча и API пакета сокращаются:
исчезают condvar-логика, partial-push, колбэк под залом и живой `Get`/`Each`/`ItemsCount`.
Синхронизационный бюджет не меняется: одна канальная операция на `Beff` записей с каждой стороны —
столько же, сколько захватов мьютекса в стеке; LIFO→FIFO — замеры TIE (ADR-019, контрастная точка).

## Корректность

- **Итог не меняется**: то же `total = Σ W(task)·f(task)`; каждая запись таблицы отдаётся
  обходом ровно один раз (map читается целиком после барьера, писателей нет по предусловию Seal),
  батч несёт `n ≤ Beff` записей, `close` после обхода — эквивалент закрытого стека.
- **Порядок FIFO** измерен как TIE с LIFO (ADR-019 §LIFO/FIFO: средний Δ −0.2% при шуме ≥1%,
  hits/misses от порядка не зависят) — контрактная правка без численного риска.
- **Чтение без локов законно**: то же инвариантное предусловие фазы («писателей нет после барьера»),
  которое уже держат `Reader` (ADR-031) и `Each` (ADR-013); Seal концентрирует его в одной точке API.
  Появление писателя после Seal — data race по контракту предусловия (рантайм-проверки нет, как и не
  было).
- **Отмена ctx**: `All` останавливается сам на границе шардов; продюсер дренирует цикл, хвостовой
  батч при завершённом ctx не отправляется, `close(ch)`; консьюмеры дренируют буферизованные
  батчи **без подсчёта** (`ctx.Err()` — пропуск задачи) — частичный итог без паники. У итератора нет
  источника ошибок — правило panic-на-чужой-ошибке `checkEachError` умирает за ненадобностью.
- **Дедлок исключён**: буфер ≥ 1 слота (`capacity ≥ 1`), продюсер блокируется только на отправке,
  консьюмеры никогда не ждут продюсера и всегда дренируют до `close`.

## Дизайн

**cache (протокол «write → seal → read»):**

- `Seal() *View` вместо `Reader()`; у `View`: `Get(p) (uint64, bool)` (безлоковый, как нынешний
  Reader), `Len() int` (число записей после барьера), `All(ctx) iter.Seq[Entry]` — pull-обход всей
  таблицы без локов: отдача записей из живых map под предусловием «писателей нет», ноль копий
  таблицы; проверка ctx между шардами; `break` потребителя = частичный обход; порядок — по номерам
  шардов (внутри шарда — Go map), как нынешний `Each`. Повторный `Seal` — независимые ручки над той
  же таблицей.
- **Удалить**: `Cache.Each`, `eachShard`, живой `Cache.Get` (прод не вызывает), `Cache.ItemsCount`
  (после барьера — `View.Len`), `Reader`. `cacheShard.mu`: RWMutex → Mutex — лок нужен только
  писателям (`Set`, `Staging.Flush`).
- `Sink`/`Staging` не меняются; тесты видимости Staging экранируются через Seal (до флеша —
  состояние писателя в пакете, после — View).

**counter:**

- `ParallelCountWithDepth` — тонкий оркестратор: GC-scope + `generateIntermediate` (gen A) →
  `extendTasks` (новый метод: gen B, атомарный чанк-цикл со Staging переезжает туда без изменений
  семантики) → `countTasks`. Публичный API пакета не меняется.
- Материализация worklist gen A: обход `view.All(ctx)` в предвыделенный `[]cache.Entry`
  (cap = `View.Len()`).
- `countTasks`: вместо taskStack — батч-канал. Элемент `entryBatch { n int; items [dispatchClaimBatch]Entry }`
  (Beff ≤ B=16 всегда); буфер `make(chan entryBatch, ceil(capacity/Beff))`, где `capacity =
  max(min(consumers·K, records), 1)` — прежняя ёмкость стека в батч-единицах; `records = view.Len()`,
  формула `Beff` и константы K/B/C — без изменений (ADR-019). Продюсер — единственный цикл по
  `view.All`: наполняет `items[:Beff]`, шлёт полный батч; хвост — последняя отправка; затем `close`.
  Консьюмеры (то же число) — `for b := range ch`, для каждой записи прежний `countOneTask` вне любых
  залов. Отмена — см. «Корректность». Константа `dispatchStackCapacity` переименовывается под новую
  механику (значение K=10000 не меняется; ADR-020 — ручек не добавлять).

**searcher:** сигнатура `CountPathsWithCacheReversal(..., c *cache.Reader, ...)` → `*cache.View`
(механическая пропаганда переименования ручки).

## Аллокационный бюджет

Размер элемента проверен `unsafe.Sizeof`: `entryBatch = 8 + 24·B = 392 Б` (Path 16 Б, Entry 24 Б).

- Буфер канала: `⌈capacity/Beff⌉ × 392 Б`, одна аллокация на старте фазы, ноль на запись
  (отправка копирует структуру в предвыделенный буфер hchan).
- Худший случай (workers=14, K=10000, насыщение Beff=B=16): `⌈140 000/16⌉ = 8750` слотов × 392 Б ≈
  **3.43 МБ** — против стека 3.36 МБ (разница +2% — заголовок `n`, эффективные 24.5 Б на слот-запись).
- Активная зона формулы (`records < B·consumers·C = 896`): `capacity = records`,
  `слотов ≤ ~2·consumers·C = 112` → ≤ 44 КБ (округление целочисленного деления учтено множителем 2).
- Глобальная верхняя граница: `max(⌈consumers·K / B⌉, 2·consumers·C) × 392 Б`; при workers=14
  доминирует первая ветвь — **≤ ~3.4 МБ**, шум против пика task-cache (ГБ).
- Копий таблицы нет нигде: `All` отдаёт из живых map — механика эталона ADR-013 (прямой обход без
  снимков) сохранена; снапшот/drain по-прежнему запрещены.

## Риски

- **Потеря partial-push гранулярности**: продюсер ждёт целый свободный слот батча, а не дописывает
  в оставшееся место. Безопасно (буфер ≥ 1 слота, консьюмеры всегда дренируют), но хвостовое
  поведение при полном буфере чуть грубее прежнего — заметит гейт `cnt_ms`.
- **LIFO → FIFO**: контрастная точка измерена TIE (ADR-019) — риск закрыт заранее; hits/misses от
  порядка не зависят.
- **Удаление живого `Cache.Get`/`ItemsCount`/`Each`** — контрактная правка API пакета: тесты
  портируются через Seal/View (прод-потребителей нет, проверено grep'ом); внешний потребитель
  (гипотетический) лишается конкурентно-safe чтения mid-run — по факту оно и не использовалось.
- **hchan vs один мьютекс**: план 11 показал цену per-record канала (+14.5%); здесь синхронизация —
  одна операция на `Beff` записей с каждой стороны, как захваты стека. Ожидаем паритет; при регрессе
  вне полосы — отклонение (ветку не мержить, числа в закрытый план).
- **View.All по живым map**: появление писателя после Seal = data race по контракту предусловия (тот же класс,
  что был у Reader/Each; рантайм-проверки нет, тест с намеренным писателем вне контракта).
- Откат = не мержить feature-ветку (ADR-021); флага/env в коде нет и не заводится.
