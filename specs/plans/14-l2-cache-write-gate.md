# План 14. L2-проверки прунера как гейт записи на листьях генерационного спуска

## Статус

**Закрыт 2026-09-24 — принято chain-only (→ ADR-030).** Вердикт стенда (7×7 d22, числа навсегда
в ADR-030): временной критерий («>5% выигрыша») не выполнен ни одним вариантом — лучший
chain-only +1.3% (паритет при шуме ±0.4%), articulation-only +20.1%, both +22.4%; вердикт
benchmarker'а REGRESSION. Решение пользователя — **принять chain-only ради памяти** (осознанное
отступление от временного критерия): peak RSS −48.8%, записей task-cache −30.0%, count-фаза
−16.1%. Articulation отклонена числами; compile-time маска и Tarjan удалены из кода как мёртвые,
гейт = только forced-chain. Дефолты глубины не пересматривались (re-sweep кривой с гейтом не
делался). Открытые следующие шаги: возврат к сочленениям только через более дешёвый предикт или
другую точку применения (новый план); re-sweep глубин под принятый гейт — отдельная гипотеза.

## Мотивация и базовые числа

Task-cache конвейера reversal содержит записи-префиксы, для которых count-фаза обязана
ответить `f = 0`: ключ `(S,s)` без ни одного дополнения (гамильтова пути из `s`, покрывающего
`full\S`, не существуют) даёт нулевой вклад `W·f` в итог и, более того, **никогда не
запрашивается** мемо count-фазы (лемма звукосности — `specs/searcher.md`). Такие записи — чистый
размер таблицы: память пика и обход `Each`/диспатч count-фазы.

Необходимые условия «из `cur` нет пути, покрывающего `todo`» (сочленения Tarjan lowlink +
обязательные цепочки union-find) уже были реализованы в `pruner` и удалены вместе с потребителем
class-mode (ADR-016). Прежние замеры (ADR-007, план 04) мерили их **внутри DP-рекурсии** — там
O(V+E)-проверка на каждом состоянии удорожала counting в ×2.3 (artic) / ×1.5 (chain) и была
выключена. Точка применения здесь другая: один прогон проверки **на лист генерационного спуска**
(перед `Set`), где отсечение экономит не узел рекурсии, а запись в таблицу — со всей её долей
памяти и count-работы.

Базовая линия (README, свод ADR-019), стенд 7×7 depth 22 (`make bench-size N=7 DEPTHS=22`):

| метрика | базовая линия |
|---|---|
| полный прогон | **215.10 с** |
| gen B | 121.27 с |
| counting | 93.83 с |
| writesB (Set-вызовов gen B) | 1.40 G |
| peak RSS | ~10.53 ГБ |
| taskEntries (записей task-cache) | не публиковалась — вводится этим планом (`taskEntries/op`) |

## Идея / Гипотеза

Гейт `ShouldPruneState(end, full\st)` в базовом случае `dfsTask` отсечёт **заметную долю**
записей task-cache (нулевые по `f` ключи не пишутся), что уменьшит peak RSS и время count-фазы
(меньше записей → меньше задач диспатча и count-DFS); окупается ли это ценой O(V+E) на лист в
gen B — решает стенд. Отсечение звукó: итог `Σ W·f` не меняется (лемма в `specs/searcher.md`).

## Корректность

Лемма (гейт записи, фиксируется в `specs/searcher.md`): запись `(S,s)` участвует в итоге двояко —
как задача `W·f(S,s)` и как ответ мемо задачам с остатком `S`. Если предикат гейта (необходимое
условие «из `s` есть путь, покрывающий `full\S»`) ложен, то:

1. собственный вклад нулевой (`f(S,s) = 0`, необходимое условие);
2. ключ запрашивается count-фазой тогда и только тогда, когда существует путь, покрывающий
   `full\S` и кончающийся соседом `s`; по дуальности обращения это в точности `f(S,s) > 0` —
   значит мёртвый ключ не запрашивается никогда, и отсутствие записи не добавляет ни промаха,
   ни потери;
3. предикат D4-эквивариантен (зависит только от структуры графа и маски) — «мёртвость» есть
   свойство орбиты, решение согласовано с канонизацией ключа.

Degenerate self-write `ExtendTask` (`p.State().CountBits() >= depth`) гейтом не проверяется:
такая запись — точь-в-точь лист фазы A (тот же ключ/пара), уже прошедший гейт той же проверкой.

## Дизайн

1. **Возрождение L2 в `pruner`** с `git show 895aa56^:pruner/pruner.go`: методы
   `ShouldPruneState(cur int, todo state.State) (bool, Reason)`, `articulationCut` (итеративный
   Tarjan lowlink на битмасках с уточнениями концов), `forcedChainCut` (union-find degree-2
   цепочек при зафиксированном конце), причины `Articulation`/`ForcedChain`. Обе O(V+E),
   V = |todo|+1 ≤ 64, без аллокаций (фиксированные `[64]`-массивы на стеке вызова).
   **Не возрождать**: `ShapeFeasible`, `SetL2`, публичный `L2Checks`, порог `minL2`.
   Тело `ShouldPruneState` — только L2-проверки включённого набора: повторный L0/L1 не нужен,
   единственный вызывающий уже пропустил пару `(cur,todo)` через `ShouldPruneAfterVisit` на
   спуске родителя (это же даёт связность `H = G[todo ∪ {cur}]` — предполождение lowlink).
2. **Набор проверок — неэкспортируемая compile-time константа** пакета (маска из двух бит):
   для A/B прогонов chain / articulation / both benchmarker правит константу и пересобирает;
   финальный код хардкодит принятый набор. Рантайм-ручек/env нет (ADR-020); порог `minL2` не
   нужен — остаток на листе постоянен (`totalCells − depth`, на стенде 49−22 = 27).
3. **Хук** — базовый случай `dfsTask` (`searcher/searcher.go`, ветка `CountBits >= depth`):
   перед `c.Set(s.sym.Canonicalize(st,end), weight)` вызвать
   `ShouldPruneState(end, st.Invert(totalCells))`; прунуто → `res.CountPrune(reason)` и без
   записи. Один хук покрывает обе фазы (промежуточную таблицу gen A и task-cache gen B) —
   спуск общий (ADR-018). Гейт до `Canonicalize` — отсечённые листья не тратят канонизацию.
4. **Статистика**: причины → `types.Result.PrunedArticulation/PrunedForcedChain` (+`Add`,
   `CountPrune`, сумма в `Finalize`) → разбивка монитора (порядок: `…, endpoints, artic, chain`)
   → метрики бенча `prunedL2A/op`, `prunedL2B/op` (сумма двух причин по фазам gen A / gen B).
5. **Бенч-харнес**: метрика `taskEntries/op` — число записей task-cache; счётчик уже публикуется
   (`countTasks` вызывает `AddTasks(taskCache.ItemsCount())`, снимается как `Phase("counting").Tasks`)
   — в харнесе добавляется только `ReportMetric`. Нужна обоим сторонам A/B.

## Аллокационный бюджет

Новых структур нет: гейт стейт-лесс, весь scratch (`disc/low/parent/frontier/stack/uf/…`) —
фиксированные `[64]int8`/`[64]state.State` локалы стека вызова, 0 байт на кучу, ни одного
разделяемого между воркерами состояния (параллельность gen B не меняется). Механика поднятого
кода прочитана в `895aa56^:pruner/pruner.go` — там же, где она доказала нулевые аллокации в
прежнем потребителе. Стоимость — чистый CPU на лист: O(V+E), V≈28 на стенде; именно её и
взвешивает стенд против сокращения записей.

## Шаги

1. Реализация по «Дизайну» (pruner → searcher hook → types → monitoring → benchmarks).
2. Тесты: юниты возрождённых проверок из истории (`git show 895aa56^:pruner/pruner_test.go` —
   naive-equivalence articulation, «отсечение ⟹ bruteH = 0» на walk-выборках 5×5/6×6,
   forced-chain только при зафиксированном конце, вырожденные |todo| ≤ 3 живы) + эквивариантность
   L2 по всем 8 D4; тест леммы: на 5×5 собрать множество ключей, отказанных гейтом (внутренний
   обход листьев фиксированной глубины), brute-force проверить `f(key)=0` для каждого;
   сквозные итоги (`TestParallelCountWithDepth*`, `TestReversalMatchesBruteForceAllDepths`,
   `TestWorkerInvariance`) проходят с включённым гейтом и валидируют звукосность end-to-end.
3. `make check` до зелёного.
4. Стенд (сериализация `flock ../kt-bench.lock`, база A/B — merge-base, скилл `workflow`):
   7×7 depth 22, четыре прогона — baseline (main, гейт отсутствует по построению), chain,
   articulation, both. Числа — в ADR-030 «Замеры» (навсегда).

## Метрики успеха

Стенд: `make bench-size N=7 DEPTHS=22`, полный прогон.

- **Критерий WIN**: полное время прогона лучше базовой линии 215.10 с за пределами шума —
  **более чем на 5%** (≤ ~204.3 с). Иначе — отклонение (docs-only merge, ADR-030 «отклонено»).
- Справочные метрики решения (не гейты, но объясняют вердикт): `taskEntries/op`,
  `peakRSS_MB/op`, `cnt_ms/op`, `genB_ms/op`, `writesB/op`, `prunedL2A/op`, `prunedL2B/op`.

## Риски

- **Стоимость на лист при малом сокращении** — прямой урок ADR-007 (в DP-рекурсии artic ×2.3,
  chain ×1.5). Отличие: платим один раз на лист gen B (~writesB вызовов), а не на каждый узел
  экспоненциальной рекурсии; но если доля мёртвых ключей мала — прогон дорожеет. Митигция:
  A/B по одной проверке (compile-time маска) и жёсткий порог −5% по полному времени.
- **Некорректное условие = неверный ответ**. Митигция: гейт против тестов «отсечение ⟹ h=0»,
  теста леммы на отказанных ключах и эталонов 1728 / 6 637 920 на всех допустимых глубинах.
- **Сдвиг разбивки прунинга** в живых/финальных строках монитора — обновить тесты формата
  (порядок `artic, chain` зафиксирован в спеке monitoring).
- Откат — не мержить feature-ветку (ADR-021); рантайм-переключателя нет по построению.
