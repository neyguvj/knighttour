# План 13. Count-фаза: общий lazy-batched стек задач (адаптация class mode, стратегия 3 из трёх)

## Статус

Не начат. Сравнительное исследование диспатча count-фазы (планы 11/12/13 — три стратегии,
каждая своей веткой/фичем против общего свежего контроля HEAD; по замерам лучшая вливается
в main, остальные помечаются Отклонены с числами).

## Мотивация и базовые числа

Текущий диспатч count-фазы — `Cache.Each` (ADR-013): горутина на шард под RLock, колбэк
выполняет count-DFS inline под залом; единица работы — шард целиком → последние шарды держат
воркеров поодиночке, параллелизм падает.

Механика-прародитель — class mode (ADR-010, удалён ADR-016): stage 1 дренировал шарды в
плоские срезы и резал их на задачи; stage 2 — **общий стек под мьютексом**, воркеры брали с
вершины батчами `claimBatch = 16`, пустой стек = всё разобрано (новых задач не рождалось,
сна не было). Дрейн был возможен, потому что записи изымались из map (второго экземпляра
памяти не возникало), а финальный DP читал только свои срезы.

База — HEAD с `Each` (in-place контроль, ×2 прогона до кода). Точка сравнения: **7×7 d22,
workers=14** (`make bench-size N=7 DEPTHS=22`), метрика — `cnt_ms/op`; ориентир ADR-013:
cnt ≈ 93–99 с, peak RSS (GOGC=40) 10 203 МБ.

## Идея / Гипотеза

Переносим планировщик class mode на reversal **без дрейна**: продюсеры обхода кэша складывают
копии записей пачками в общий bounded-стек (LIFO) под мьютексом, воркеры берут с вершины
батчами и считают count-DFS вне залов. Дешёвого прокси стоимости задачи в reversal нет
(в class mode им было число концов формы), поэтому **без LPT** — порядок складывания произвольный,
выигрыш даёт только динамическая батч-претензия: любой воркер берёт работу из общего стека,
хвост схлопывается. Ожидаем `cnt_ms` −5% и вне диапазона повторов контроля; относительно
плана 11 гипотеза — батч ×16 снижает синхронизационный оверхед на порядок при той же
балансировке.

## Корректность

- **Дрейн запрещён** (отличие от class mode): count-DFS читает живой task-cache через `Get`
  (мемо раннего стопа) — изъятие записей из map сломает подсчёт. Поэтому стек хранит *копии*
  (`cache.Entry`, 24 Б), а обход под RLock остаётся read-only; `Get` видит все шарды до конца
  фазы (контракт `specs/cache.md` сохраняется).
- Итог не зависит от порядка: общий `atomic.Uint64`, детерминизм `f(task)` (инвариант
  ADR-012/013). LPT снят — он был эвристикой порядка, не корректности.
- Ровно-один-раз: каждая запись кладётся один раз; стек только убывает (новых записей после
  барьера генерации нет) — пустой + барьер продюсеров = конец, как в `processShapes`.
- Блокировка продюсера на полном стеке выполняется под RLock шарда и безопасна: писателей нет,
  консьюмеры работают без залов и всегда освобождают место.
- Отмена ctx: продюсеры останавливаются (`Each` → `ctx.Err()`), флаг closed; воркеры дренируют
  стек без подсчёта (пропуск задач при `ctx.Err()`, как сейчас) — частичный итог без паники;
  чужая ошибка `Each` — panic (`checkEachError`).

## Дизайн

Пакет `cache` **не меняется** (`Each` переиспользуется как обход-продюсер). Всё в
`counter.countTasks`, форма — узнаваемая адаптация удалённых `groupShards`/`processShapes`
(см. ADR-010; код — в истории git до `895aa56`):

1. Общий стек: предвыделенный `[]cache.Entry` ёмкости `workers×K` (K ∈ {1000…10000} — ручка
   тюнинга) + мьютекс + condvar (полный/пустой/closed). Один индекс вершины; pop — срез
  `batch = min(B, размер)` за один захват мьютекса (B — второй параметр свипа, старт 16 как
   `claimBatch` class mode).
2. Продюсеры: колбэк `Each(ctx, workers, …)` накапливает записи в маленький локальный батч
   (стек-буфер продюсера, переиспользуемый) и выкладывает его одним захватом мьютекса; при
   полном стеке — wait на condvar (под RLock шарда — законно). Это снимает 131.8M одиночных
   lock/unlock до ~131.8M/B.
3. Консьюмеры: `workers` горутин крутятся на pop-батчах; каждая запись батча — прежний
   `countOneTask` (count-DFS вне залов шарда). Выход: closed && стек пуст.
4. Мониторинг без изменений семантики (`AddTasks(ItemsCount())`, отчёты из консьюмеров).

Тюнинг на 7×7 d22: K ∈ {1000, 2000, 5000, 10000} × B ∈ {8, 16, 32}. LIFO-vs-FIFO — одна
дополнительная точка свипа (у class mode LIFO работал в связке с LPT; без него порядок может
потерять актуальность — проверяем замером, не догадкой).

## Аллокационный бюджет

| структура | формула | 7×7 d22, W=14 |
|---|---|---|
| общий стек `[]Entry` cap W·K | 24 Б × K × workers | 0.34 МБ (K=1000) … 3.4 МБ (K=10000) |
| локальный батч продюсера | 24 Б × B × активные продюсеры | ≤ 8.8 КБ |

Аллокаций на запись — ноль (копия в предвыделенный массив стека; pop — срез, не new).
Одна аллокация на фазу + condvar-структуры. Пик ≤3.4 МБ — в шуме против task-cache ~10 ГБ.
Сравнение механик: class mode жил «в ноль» только благодаря дрейну (map освобождался); здесь
bounded-копия — сознательная цена отказа от дрейна; полный снапшот 131.8M×24 Б ≈ 3.2 ГБ —
запрещён (ADR-012/013) и не предлагается.

## Риски

- **Один мьютекс на всех** (продюсеры + консьюмеры): при малом B contention съедает выигрыш →
  свип B; при провале — отклонение в пользу 11/12.
- LIFO без LPT может оказаться хуже FIFO (классический стек class mode опирался на порядок
  «дорогие первыми») → отдельная точка свипа, решение по замеру.
- Продюсер под RLock ждёт на condvar полного стека — долго держит шард «открытым»; безопасно
  только при отсутствии писателей (caveat ADR-013; при будущем инкрементальном пополнении —
  пересматривать).
- Возврат формы планировщика из удалённого class mode не должен затащить мёртвый код
  (`claimBatch`/`shardJob` как таковые) — переносится только механика стека (правило AGENTS.md).
