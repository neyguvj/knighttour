# План 04. Усиленные проверки прунера внутри финального DP

## Статус

**Закрыт 2026-09-14: механизм L2 удалён вместе с потребителем (ADR-016)** —
`ShouldPruneState`, причины `Articulation`/`ForcedChain`, DP-поля `types.Result` и
соответствующие метрики больше не существуют; замеры — в ADR-007 навсегда.
Раньше план был закрыт так: этап 0 выполнен, решение принято (см. «Результаты
этапа 0») — механизм реализован, протестирован и **выключен по умолчанию** (на
досках ≤ 7×7 убыточен). Пересекается с планом 02: тот — про **весь** отказ формы
до DP, этот — про проверки **внутри** рекурсии `f(cur, todo)`. Общий знаменатель:
отсечения должны быть необходимыми условиями существования гамильтова пути.
Выводы переживают удаление: эквивалентность п.3 действующей эвристике `Endpoints`
(зафиксирована в «Результатах этапа 0» ниже), гипотеза инкрементального lowlink — там же.

## Мотивация и базовые числа

Текущий набор (`pruner.Pruner.ShouldPruneAfterVisit`, pruner/pruner.go:38): локальный
dead-end за O(deg), затем flood-fill по остатку с проверками «нет продолжения»,
связность и «вершин степени 1 больше двух / ни одна из двух не смежна с `last`».

В финальном DP он вызывается на каждом узле рекурсии (shapecount/shapecount.go:181) и
на 7×7 d22 даёт **17.27G** событий прунинга за 371 с, из них endpoints —
11.25G, disconn — 3.97G, deadend — 2.05G. То есть DP тратит миллионы вызовов на состояния,
которые можно было завершить одним-двумя проверками сильнее.

**Область включения (решение по плану): только финальный DP.** Генерационный DFS не
трогаем: `ShouldPruneAfterVisit` вызывается миллиарды раз, и удорожание узла на десятки
наносекунд окупается только при экспоненциальном сокращении дерева — это отдельное
исследование, а не часть этого плана.

## Что добавляем

### L2-проверки для состояния `(cur, todo)` (вызываются из shapecount)

1. **Сочленения (articulation points).** Необходимое условие гамильтова пути: для любой
   вершины `v` графа `G[todo ∪ {cur}]` удаление `v` оставляет не более двух компонент
   (путь проходит через `v` не более двух раз). Для состояния с фиксированным началом
   есть уточнение: если `components(G − v) == 2`, то начало обязано лежать в одной из
   них вместе с … — проверяется за тот же обход. Реализация — lowlink Тарьяна на битовых
   масках, O(V+E), без аллокаций (стек — `[]int` переиспользуемый).
2. **Обязательные цепочки (forced chains).** Вершина степени 2 обязана использовать оба
   инцидентных ребра; сжатие таких цепочек и проверка на (a) замкнутый цикл короче всего
   множества и (b) вершину с более чем двумя обязательными рёбрами.
3. **Уточнение «степень 1» под фиксированное начало.** В генерации важно, чтобы одна из двух
   вершин степени 1 была смежна с `last`; в DP начало зафиксировано (`cur`), и если
   вершин степени 1 ровно две, то **одна из них обязана быть началом**, иначе 0. Сейчас
   это условие сильнее текущего только частично — проверить на практике и, если работает,
   завести как отдельную причину.

### API и статистика

- Новые методы прунера: `ShouldPruneState(cur int, todo state.State) (bool, Reason)` —
  надстройка над существующей глобальной проверкой, **не** вызывается из searcher'а.
- Новые причины в `pruner.Reason` (`Articulation`, `ForcedChain`) → поля в `types.Result`
  (`PrunedArticulation`, `PrunedForcedChain`) + `Add`/`CountPrune`, разбивка в живой строке и
  финальном отчёте (`monitoring`), метрики бенчмарка (`prunedDP_artic/op` и т.п.).
- Порог включения: проверки L2 запускаются при `todo.CountBits() >= minL2` (стартовое
  значение — подобрать, ожидается 8–12): на мелких остатках полный перебор дешевле.

## Этап 0 — замер потенциала на реальных формах

Прежде чем включать проверку в DP, посчитать на выгрузке форм (7×7 d18–d22, 6×6 d13 —
инфраструктура из планов 02 и 05):

- сколько узлов рекурсии отсекает каждая новая проверка **сверх** текущих;
- средняя стоимость проверки на состоянии против среднего сокращения поддерева;
- итог: доля состояний DP, устранённая проверкой (цель — ≥ 15%, иначе не включаем).

Инструмент — бенчмарк пакета `shapecount` на зафиксированной выборке форм (не весь
пайплайн), с флагом включения/выключения проверки.

## Риски

- **Стоимость на узел.** L2 дороже текущего flood-fill; при низком потенциале (этап 0)
  проверка не включается вообще. Порог `minL2` и отключение по таймингу — обязательны.
- **Некорректное условие = неверный ответ.** Каждое условие сопровождается доказательством
  в спеке и тестом против наивного перебора; ни «улучшенная эвристика», ни «обычно верно»
  не принимаются.
- **Ломается статистика монитора**: новые причины сдвигают известные разбивки — обновить
  тесты `monitoring` и зафиксировать формат в спеке, чтобы старые прогоны читались.
- **Связка с планом 02**: часть проверок (степень 1 при фиксированном начале, замкнутые
  цепочки) работает и на уровне формы. Реализовывать логику один раз в `pruner`, вызывать
  либо до DP (весь отказ формы), либо внутри — но не дублировать код.

## Результаты этапа 0

Замеры на M4 Max. Инструмент — `BenchmarkCountShapeL2` (детерминированная
выборка из 24 walk-форм 6×6, размеры 14–18, свип уровней off/artic/chain/all) и
`BenchmarkCountAllToursClass/size6` на counting-тяжёлых глубинах.

Выборка форм (shapecount, ns/op; minL2 = 10):

| уровень | ns/op | dpstates/op | prunedArtic/op | prunedChain/op |
|---|---|---|---|---|
| off   | 3.98 M | 45 649 | – | – |
| artic | 5.90 M (+48%) | 44 412 (−2.7%) | 512 | – |
| chain | 4.29 M (+8%)  | 39 544 (−13.4%) | – | 1 278 |
| all   | 5.79 M (+46%) | 39 397 (−13.7%) | 332 | 1 049 |

Полный пайплайн 6×6, фаза counting (`cnt_ms/op`):

| конфигурация | depth 14 | depth 10 |
|---|---|---|
| L2 off (базовая линия) | 50.8 мс | 78.0 мс |
| artic                              | 114.4 мс (×2.25) | 180.0 мс (×2.31) |
| chain                              | 75.8 мс (×1.49)  | 119.1 мс (×1.53) |
| all                                | 118.3 мс (×2.33) | 181.4 мс (×2.32) |

Целевой стенд 7×7 depth 22 (`BENCH_DEEP=1`, `-benchtime=1x`, M4 Max):

| конфигурация | counting | полный прогон | prunedDP_artic | prunedDP_chain |
|---|---|---|---|---|
| L2 off (базовая линия) | 369.4 с | 589.7 с | – | – |
| all                                    | 860.0 с (×2.33) | 1083.2 с (×1.84) | 712.7 M | 1 490.4 M |

Отношение ×2.33 совпало с 6×6 до сотых: вывод не зависит от доски, цель «≤ 260 с»
недостижима этими проверками в текущем виде.

Вывод: **ни одна проверка не включена** (гейт «≥15% состояний, иначе не
включаем» формально проходит только chain на walk-выборке, но по времени это
чистый убыток; на реальном пайплайне оба чека проигрывают в разы). Причины:

- сочленения срабатывают редко (~1% состояний), а O(V+E)-обход Тарьяна
  выполняется на каждом состоянии с |todo| ≥ 10 — стоимость не окупается;
- обязательные цепочки отсекают чаще (в пайплайне до 0.6M событий/прогон), но
  фиксированный конец (единственная вершина степени 1 в `H`) — редкая форма, и
  для большинства состояний проверка сводится к пустому проходу по степеням;
- на досках ≤ 7×7 деревья DP слишком мелкие: удорожание узла не компенсируется
  экспоненциальным сокращением (ровно риск из раздела «Риски»).

Оставлено в коде (механизм для будущих гипотез, по умолчанию `L2None`):
`ShouldPruneState`, lowlink/UF-реализации без аллокаций, причины
`Articulation`/`ForcedChain` со сквозной статистикой (types → monitoring →
метрики `prunedDP_artic/op`, `prunedDP_chain/op`), бенчмарк свипа уровней и
полный набор тестов корректности (naive-equivalence + «отсечение ⟹ h = 0»).

Отдельная находка: уточнение п.3 («при двух degree-1 одна обязана быть
началом») логически эквивалентно действующей эвристике `Endpoints` — отдельной
реализации не потребовалось (зафиксировано в `specs/pruner.md`).

Дальнейшие гипотезы вне рамок этого плана: инкрементальный lowlink от родителя
(стоимость O(Δ) вместо O(V+E)) или применение только к формам с уже
фиксированным концом на уровне формы (связка с планом 02).
