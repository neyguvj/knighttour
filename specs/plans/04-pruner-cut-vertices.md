# План 04. Усиленные проверки `pruner` внутри финального DP

## Статус

**Закрыт 2026-09-14: механизм L2 удалён вместе со своим потребителем (ADR-016).** Метод `ShouldPruneState`, причины `Articulation` и `ForcedChain`, DP-поля в `types.Result` и соответствующие метрики больше не существуют; замеры навсегда остались в ADR-007.

До этого план был закрыт так: этап 0 выполнен, решение принято (см. «Результаты этапа 0»). Механизм реализовали, протестировали и **выключили по умолчанию** — на досках вплоть до 7×7 включительно он убыточен. План пересекается с планом 02: тот занимается отказом всей формы до DP, а этот — проверками внутри рекурсии `f(cur, todo)`. Общее у них одно: отсечение обязано быть необходимым условием существования гамильтова пути. Выводы пережили удаление: пункт 3 оказался эквивалентен действующей эвристике `Endpoints` (зафиксировано в «Результатах этапа 0» ниже), а гипотеза инкрементального lowlink — там же.

## Мотивация и базовые числа

Текущий набор проверок живёт в `pruner.Pruner.ShouldPruneAfterVisit` (pruner/pruner.go:38). Сначала он ищет локальный тупик за O(deg), затем обходит остаток в ширину (`flood-fill`) с тремя проверками: есть ли у продолжения путь, связен ли остаток и не стало ли вершин степени 1 больше двух при том, что хотя бы одна из них смежна с `last`.

В финальном DP этот метод вызывается на каждом узле рекурсии (shapecount/shapecount.go:181). На доске 7×7 d22 он даёт **17.27G** событий отсечения за 371 с, из них `endpoints` — 11.25G, `disconn` — 3.97G, `deadend` — 2.05G. Значит, DP тратит миллионы вызовов на состояния, которые одна-две более сильные проверки завершили бы сразу.

**Область включения (решение по плану): только финальный DP.** Генерационный DFS не трогаем: `ShouldPruneAfterVisit` вызывается миллиарды раз, и удорожание узла на десятки наносекунд окупается лишь экспоненциальным сокращением дерева. Это отдельное исследование, а не часть данного плана.

## Что добавляем

### L2-проверки для состояния `(cur, todo)` (вызываются из пакета `shapecount`)

1. **Точки сочленения (`articulation`)** — это вершины, удаление которых разрывает граф на части. Необходимое условие гамильтова пути таково: удаление любой вершины `v` графа `G[todo ∪ {cur}]` оставляет не более двух компонент, ведь путь проходит через `v` не более двух раз. Для состояния с фиксированным началом есть уточнение: если удаление `v` даёт ровно две компоненты (`components(G − v) == 2`), то начало обязано лежать в одной из них. Эта уточнённая проверка стоит столько же — её делает тот же обход. Реализация — алгоритм lowlink Тарьяна на битовых масках за O(V+E) без аллокаций; стек — переиспользуемый срез `[]int`.
2. **Обязательные цепочки (`forced chain`).** Вершина степени 2 обязана использовать оба инцидентных ей ребра. Такие цепочки сжимают, а затем ищут два нарушения: замкнутый цикл короче всего множества и вершину, которой нужно больше двух обязательных рёбер.
3. **Уточнение условия «степень 1» под фиксированное начало.** В генерации важно, чтобы одна из двух вершин степени 1 была смежна с `last`. В DP начало зафиксировано и равно `cur`, поэтому при ровно двух вершинах степени 1 одна из них обязана быть началом — иначе вклад равен нулю. Сейчас это условие сильнее текущего лишь частично; его планировали проверить на практике и, если работает, завести отдельной причиной.

### API и статистика

- Новый метод `pruner`: `ShouldPruneState(cur int, todo state.State) (bool, Reason)` — надстройка над существующей глобальной проверкой; из пакета `searcher` он не вызывается.
- Новые причины в `pruner.Reason` (`Articulation`, `ForcedChain`) порождают поля `PrunedArticulation` и `PrunedForcedChain` в `types.Result` с учётом через `Add`/`CountPrune`, разбивку в живой строке и финальном отчёте пакета `monitoring`, а также метрики бенчмарка вида `prunedDP_artic/op`.
- Порог включения: проверки L2 запускаются при `todo.CountBits() >= minL2`; стартовое значение подбирают, ожидается 8–12. На мелких остатках полный перебор дешевле.

## Этап 0 — замер потенциала на реальных формах

Прежде чем включать проверку в DP, её считают на выгрузке форм (7×7 d18–d22 и 6×6 d13; инфраструктура взята из планов 02 и 05):

- сколько узлов рекурсии отсекает каждая новая проверка **сверх** текущих;
- во что в среднем обходится проверка на состоянии против среднего сокращения поддерева;
- какова итоговая доля состояний DP, устранённая проверкой: цель — не менее 15%, иначе не включаем.

Инструмент — бенчмарк пакета `shapecount` на зафиксированной выборке форм, а не на всём конвейере; каждая проверка включается и выключается флагом.

## Риски

- **Стоимость на узел.** L2 дороже текущего `flood-fill`, поэтому при низком потенциале из этапа 0 проверка не включается вообще. Порог `minL2` и отключение по таймингу обязательны.
- **Некорректное условие означает неверный ответ.** Каждое условие сопровождается доказательством в спеке и тестом против наивного перебора. Ни «улучшенная эвристика», ни «обычно верно» не принимаются.
- **Ломается статистика монитора.** Новые причины сдвигают известные разбивки: нужно обновить тесты `monitoring` и зафиксировать формат в спеке, чтобы старые прогоны читались.
- **Связка с планом 02.** Часть проверок (степень 1 при фиксированном начале, замкнутые цепочки) работает и на уровне формы. Логику реализуют один раз в `pruner` и вызывают либо до DP (отказ всей формы), либо внутри него; дублировать код нельзя.

## Результаты этапа 0

Замеры на M4 Max. Инструменты: бенчмарк `BenchmarkCountShapeL2` (детерминированная выборка из 24 форм, построенных рыцарскими обходами на 6×6, размеры 14–18; прогон по каждому уровню off/artic/chain/all) и `BenchmarkCountAllToursClass/size6` на глубинах с тяжёлой count-фазой.

Отношение ×2.33 совпало между 6×6 и 7×7 до сотых: вывод не зависит от размера доски, а цель «≤ 260 с» недостижима этими проверками в текущем виде.

Вывод: **ни одна проверка не включена.** Порог принятия «не менее 15% состояний, иначе не включаем» формально проходит только chain на выборке обходов, но по времени это чистый убыток; на реальном конвейере обе проверки проигрывают в разы. Причины такие:

- точки сочленения срабатывают редко (~1% состояний), а обход Тарьяна стоимостью O(V+E) выполняется на каждом состоянии с |todo| ≥ 10 — стоимость не окупается;
- обязательные цепочки отсекают чаще (в конвейере до 0.6M событий за прогон), но фиксированный конец (единственная вершина степени 1 в `H`) — редкая форма, и для большинства состояний проверка сводится к пустому проходу по степеням;
- на досках вплоть до 7×7 включительно деревья DP слишком мелкие: удорожание узла не компенсируется экспоненциальным сокращением — ровно риск из раздела «Риски».

В коде механизм оставили для будущих гипотез, по умолчанию он выключен (`L2None`): метод `ShouldPruneState`, реализации lowlink и union-find без аллокаций, причины `Articulation`/`ForcedChain` со сквозной статистикой (от `types` через `monitoring` к метрикам `prunedDP_artic/op` и `prunedDP_chain/op`), бенчмарк перебора уровней и полный набор тестов корректности (`naive-equivalence` и «отсечение ⟹ h = 0»).

Отдельная находка: уточнение пункта 3 — «при двух вершинах степени 1 одна обязана быть началом» — логически эквивалентно действующей эвристике `Endpoints`. Отдельной реализации не потребовалось (зафиксировано в `specs/pruner.md`).

Дальнейшие гипотезы вне рамок этого плана: инкрементальный lowlink от родителя со стоимостью O(Δ) вместо O(V+E), либо применение проверок только к формам с уже фиксированным концом на уровне формы — связка с планом 02.
