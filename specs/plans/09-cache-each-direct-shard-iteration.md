# План 09. Count-фаза reversal: прямой обход шардов под RLock (Each) вместо снимков

## Статус

Принято 2026-09-13 (→ ADR-013, WIN): peak RSS 7×7 d22 −5.7% вне шума при времени в шуме,
totalAlloc −3.0 ГБ; с GOGC=40 цель ≤10.5 ГБ взята (10 203 МБ). Свипы 6×6 — все глубины
в пересечении диапазонов повторов; на 5×5 принят фиксированный +~0.1 мс/op диспатча.

После ADR-016 (пайплайн единственный): `Accumulator.NumShards` из шага 3 тоже удалён
(публичное чтение аккумулятора — только `Drain()`), env `BENCH_MODE` из базовых команд
больше не существует; текст шагов — история исполнения.

## Мотивация и базовые числа

ADR-012 снизил пик 7×7 d22 reversal с 18.9–21.4 до 16.2 ГБ (GOGC=100; 11.6 с GOGC=40),
цель ≤10.5 ГБ не взята; остаток приписан раскладке task-cache. Уточнение: эталон
`0d142f4` (9.55 ГБ) в count-фазе использовал `Cache.Each` — воркеры итерировались
**напрямую по map шарда под RLock, ноль аллокаций на диспатч**; ни полного снапшота,
ни per-shard копий. ADR-012 заменял только `Entries()` (huge-allocation ~2.1 ГБ), а не
механику обхода: текущий `SnapshotShard` по-прежнему копирует шард (~25 МБ × воркеры).
Гипотеза «эталонный пик = заслуга прямого обхода» отдельной точкой не мерилась.

База для сравнения (тот же стенд M4 Max, `BENCH_MODE=reversal make bench-size N=7
DEPTHS=22`): ADR-012 HEAD — 211.0–212.7 с / 16 202–16 258 МБ; свежий контроль HEAD
фиксируется до кода этого плана.

## Идея / Гипотеза

Нулевые аллокации диспатча (колбэк под RLock шарда, данные не копируются) снижают peak
RSS d22 относительно HEAD при времени в пределах ±5%. Побочный проверяемый тезис:
гранулярность «один шард = рабочая единица» идентична текущему курсору ADR-012, т.е.
хвост-несбаланс на малых глубинах не станет хуже (проверка — полные свипы 5×5/6×6).

## Корректность

После барьера errgroup генерации task-cache иммутабелен до конца count-фазы; колбэк
(`CountPathsWithCacheReversal`) делает только `Get`. Писателей нет → разделяемый RLock:
рекурсивный/конкурентный `Get` того же шарда из чужого воркера не блокируется (Go
RWMutex deadlock возможен только при ожидающем писателе). Итог и hits/misses
детерминированы содержимым таблицы — порядок обхода на них не влияет (тот же
тест-инвариант, что в ADR-012).

## Дизайн

**cache.Cache** (`specs/cache.md`): вместо `NumShards`/`SnapshotShard` —

```go
func (c *Cache) Each(ctx context.Context, workers int, f func(ctx context.Context, p path.Path, weight uint64) error) error
```

`errgroup` с `SetLimit(workers)`, горутина на шард: проверка ctx → RLock шарда →
`f` по каждой записи → RUnlock. Первая ошибка `f` останавливает запуск новых шардов и
возвращается из `Each` (не глотается). Данные не изымаются: `Get` видит все шарды до
конца фазы.

**counter.countTasks** (`specs/counter.md`): тело текущего `countOneTask` становится
колбэком `Each`; атомарный курсор и `countShard` удаляются (мёртвый код).
`monitor.AddTasks(taskCache.ItemsCount())` — как было.

Гранулярность не меняется (шард), поэтому отдельного фолбэка дробления в объёме нет;
lazy-batched стек остаётся зарезервированным фолбэком ADR-012 на случай, если свипы
покажут хвост.

## Шаги

1. База: HEAD, `BENCH_MODE=reversal make bench-size N=7 DEPTHS=22` ×2 (до кода).
2. Спеки до кода: `specs/cache.md`, `specs/counter.md`.
3. `cache/cache.go`: `Each`; удалить `SnapshotShard`/`NumShards` у `Cache`
   (`Accumulator.NumShards` остаётся).
4. `counter/counter.go`: `countTasks` на `Each`; удалить `countShard`/курсор.
5. Тесты: снапшот-тесты cache → Each (точное покрытие без дублей; Get видит данные во
   время итерации; отмена ctx останавливает обход); `searcher_test.go` — обход через
   Each; эквивалентность режимов 5×5/6×6 без изменений. `make check`.
6. Benchmarker: 7×7 d22 ×2 + GOGC=40 (гейты побитовые: итог, hits/misses); полные
   нисходящие свипы 5×5 и 6×6 (все глубины, ×3) — наблюдение хвоста.
7. Принятие → ADR-013 (замеры навсегда), перекрёстная ссылка из ADR-012/плана 08;
   судьба default `-mode` (шаг 7 плана 06) — по результату.

## Риски

- **Хвост на мелкой гранулярности** — та же единица работы, что у HEAD; риск не новый,
  но на малых глубинах может проявиться — поэтому полные свипы ×3; фолбэк — lazy-batched
  стек ADR-012 (отдельной итерацией по замеру).
- **Удержание RLock всю задачу шарда**: колбэк под залом; безопасно только при отсутствии
  писателей — инвариант фазы фиксируется в спеке контрактом.
- **Долгий RLock мешает будущему писателю** — в текущем пайплайне писателей в count-фазе
  нет; при появлении (инкрементальная генерация) механику пересмотреть.
- Потеря `SnapshotShard`/`NumShards` у Cache: потребители — только countTasks и тесты;
  переписываются (правило мёртвого кода).
