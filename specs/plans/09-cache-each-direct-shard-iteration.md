# План 09. Count-фаза reversal: прямой обход шардов под RLock (Each) вместо снимков

## Статус

Принято 2026-09-13 (→ ADR-013, WIN): пик RSS на 7×7 d22 снизился на −5.7% — это
вне шума, а время изменилось в пределах шума; разница totalAlloc — −3.0 ГБ.
С GOGC=40 цель ≤10.5 ГБ оказалась взята (10 203 МБ). На проходах 6×6 по всем
глубинам результаты легли в пересечение диапазонов повторов, а для 5×5 принят
фиксированный рост диспетчеризации +~0.1 мс/op.

После ADR-016 конвейер единственный, поэтому `Accumulator.NumShards` из шага 3
тоже удалён: публичное чтение аккумулятора идёт только через `Drain()`. Переменная
окружения `BENCH_MODE` в базовых командах больше не существует; текст шагов ниже —
история исполнения.

## Мотивация и базовые числа

ADR-012 снизил пик 7×7 d22 reversal с 18.9–21.4 до 16.2 ГБ (GOGC=100; 11.6 при
GOGC=40), но цель ≤10.5 ГБ взята не была, и остаток приписали раскладке
task-cache. Уточнение: эталон `0d142f4` (9.55 ГБ) в count-фазе использовал
`Cache.Each` — горутины обходили map шарда напрямую под RLock, без единого
выделения памяти на диспетчеризацию; ни полного снимка, ни копий отдельных
шардов не было. ADR-012 заменял только `Entries()` (выделение ~2.1 ГБ), а не
механику обхода: текущий `SnapshotShard` по-прежнему копирует шард
(~25 МБ на каждую горутину). Гипотезу о том, что эталонный пик — заслуга прямого
обхода, отдельной точкой не измеряли.

База для сравнения — тот же стенд M4 Max, команда `BENCH_MODE=reversal make
bench-size N=7 DEPTHS=22`: ADR-012 HEAD — 211.0–212.7 с / 16 202–16 258 МБ;
свежий контроль HEAD фиксируется до кода этого плана.

## Идея / Гипотеза

Функция обратного вызова вызывается под RLock шарда, данные не копируются, и
диспетчеризация не выделяет памяти вовсе. Гипотеза: пик RSS на d22 снизится
относительно HEAD, а время останется в пределах ±5%. Побочный проверяемый тезис:
гранулярность «один шард = рабочая единица» совпадает с гранулярностью атомарного
счётчика выданных задач из ADR-012, поэтому перекос загрузки в хвосте на малых
глубинах не станет хуже; проверка — полные проходы 5×5/6×6 по всем глубинам.

## Корректность

После барьера errgroup task-cache неизменяем до конца count-фазы, а функция
обратного вызова (`CountPathsWithCacheReversal`) делает только `Get`. Писателей
нет, поэтому обход идёт под разделяемой блокировкой: рекурсивный или конкурентный
`Get` того же шарда из чужой гортины не блокируется. Взаимоблокировка Go RWMutex
возможна только при ожидающем писателе. Итог и hits/misses определяются
содержимым таблицы, поэтому порядок обхода на них не влияет; это тот же
тест-инвариант, что в ADR-012.

## Дизайн

**cache.Cache** (`specs/cache.md`): вместо `NumShards`/`SnapshotShard` —

```go
func (c *Cache) Each(ctx context.Context, workers int, f func(ctx context.Context, p path.Path, weight uint64) error) error
```

`errgroup` с `SetLimit(workers)` запускает по горутине на шард: проверка ctx →
RLock шарда → вызов `f` для каждой записи → RUnlock. Первая же ошибка `f`
прекращает переход к следующим шардам и возвращается из `Each`, не теряясь.
Данные не извлекаются: `Get` видит все шарды до конца фазы.

**counter.countTasks** (`specs/counter.md`): тело текущего `countOneTask`
становится функцией обратного вызова для `Each`; атомарный счётчик выданных задач
и `countShard` удаляются как мёртвый код. Вызов
`monitor.AddTasks(taskCache.ItemsCount())` остаётся как был.

Гранулярность не меняется (шард), поэтому запасной план дробления в объём работы
не входит. Отложенная пакетная выдача задач (lazy-batched стек из ADR-012)
остаётся зарезервированным запасным планом на случай, если проходы по глубинам
покажут перекос хвоста.

## Шаги

1. База: HEAD, `BENCH_MODE=reversal make bench-size N=7 DEPTHS=22` ×2 (до кода).
2. Спеки до кода: `specs/cache.md`, `specs/counter.md`.
3. `cache/cache.go`: добавить `Each`; удалить `SnapshotShard`/`NumShards` у `Cache`
   (`Accumulator.NumShards` остаётся).
4. `counter/counter.go`: перевести `countTasks` на `Each`; удалить
   `countShard` и атомарный счётчик задач.
5. Тесты: тесты снимков cache переписать на Each (точное покрытие без дублей;
   `Get` видит данные во время итерации; отмена ctx останавливает обход); в
   `searcher_test.go` — обход через Each; эквивалентность режимов 5×5/6×6 без
   изменений. `make check`.
6. Benchmarker: 7×7 d22 ×2 + GOGC=40 (пороги приёмки побитовые: итог,
   hits/misses); полные нисходящие проходы 5×5 и 6×6 по всем глубинам (×3) —
   наблюдение за хвостом.
7. Принятие → ADR-013 (замеры навсегда), перекрёстная ссылка из ADR-012/плана 08;
   судьба default `-mode` (шаг 7 плана 06) — по результату.

## Риски

- **Перекос загрузки на мелкой гранулярности** — единица работы та же, что у HEAD;
  риск не новый, но на малых глубинах может проявиться, поэтому назначены полные
  проходы по всем глубинам ×3. Запасной план — отложенная пакетная выдача из
  ADR-012 (отдельной итерацией по замеру).
- **Удержание RLock всю задачу шарда**: функция обратного вызова работает под
  блокировкой; это безопасно только при отсутствии писателей, поэтому инвариант
  фазы фиксируется в спецификации как контракт.
- **Долгий RLock мешает будущему писателю** — в текущем конвейере писателей в
  count-фазе нет; при их появлении (инкрементальная генерация) механику нужно
  пересмотреть.
- Потеря `SnapshotShard`/`NumShards` у Cache: потребители — только countTasks и
  тесты, они переписываются (правило мёртвого кода).
