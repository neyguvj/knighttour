# План 08. Count-фаза reversal без полного снапшота task-cache

## Статус

Принято (→ ADR-012). Структурная цель достигена (пик −14…−24% без регресса времени,
huge-allocation устранён); RSS ≤10.5 ГБ не взят даже с GOGC=40 — остаток атрибутирован
раскладке task-cache, следующий рычаг — плотность раскладки (кандидат: план 01 для
task-cache) или GC-опция отдельным решением. Механика диспатча далее заменена прямым
обходом `Cache.Each` (план 09 → ADR-013).


## Мотивация и базовые числа

ADR-011: reversal-порт на 7×7 d22 — 213–215 с, но peak RSS **18.9–21.4 ГБ** против
эталонного `0d142f4` **9.55 ГБ** (стенд M4 Max воспроизвёл эталон: 247 с). Критерий
плана 06 «RSS ≤ 10.5 ГБ» не выполнен; перенос default `-mode` заблокирован.

Профиль расхождения: `countTasks` вызывает `Cache.Entries()` — полную копию таблицы
(131.8M записей × 16 B ≈ 2.1 ГБ) **одним huge-allocation** при живом task-cache;
опубликованный totalAlloc порта — 32.8 ГБ (у эталона не мерялся). Эталон обходил таблицу
per-shard под RLock на месте, без аллокаций в диспатче.

## Идея / Гипотеза

Избыток пика = (a) снапшот `Entries()` + раздувание хипа от его huge-allocation и
(b) GC-headroom (GOGC=100 удваивает хип на крупных всплесках). Ленивый per-shard
диспатч count-фазы (снапшард за раз, данные не изымаются) снижает peak RSS d22 до
≤ 10.5 ГБ при регрессе времени ≤ 5%.

## Корректность

После барьера errgroup генерации task-cache иммутабелен до конца count-фазы; задачи
(`CountPathsWithCacheReversal`) независимы, `Get` читает те же данные в любом порядке.
Итог и hits/misses детерминированы содержимым таблицы (не порядком воркеров) — фиксируется
тест-инвариантом. Единственное отличие от текущего порта — порядок обхода задач.

## Дизайн

**cache.Cache** (`specs/cache.md`): `Entries()` удаляется вместе с единственным
потребителем; вместо него —
```go
func (c *Cache) NumShards() int          // то же число шардов, что у Accumulator
func (c *Cache) SnapshotShard(i int) []Entry // копия шарда под RLock, ДАННЫЕ НЕ ИЗЫМАЮТСЯ
```
(в отличие от `Accumulator.DrainShard`: Get обязан видеть все шарды до конца фазы).

**counter.countTasks** (`specs/counter.md`): воркеры по атомарному курсору берут индекс
шарда, делают `SnapshotShard(i)` (~16 МБ при 131.8M/128) и выполняют все задачи шарда
самостоятельно. Доп. память ≤ workers×шард ≈ 0.2 ГБ; единый huge-allocation исчезает —
остановки только снапшардные (~16 МБ). `monitor.AddTasks(taskCache.ItemsCount())` —
один проход по длинам шардов до фазы.

## Этап 0 — измерение потенциала (до кода)

Два прогона порта на 7×7 d22 (`-mode reversal`, `/usr/bin/time -l`): контроль и `GOGC=40`.
Если GOGC=40 даёт существенное снижение пика → headroom доминирует, и в объём плана
включается опция `debug.SetGCPercent` на время count-фазы (отдельное решение с замером);
если нет → структурная копия — основной кандидат, GC не трогаем.

Результат (2026-09-13, порт ADR-011 с `Entries()`, `/usr/bin/time -l`, один прогон):

| конфигурация | wall | peak RSS | итог |
|---|---|---|---|
| контроль (GOGC=100) | 222.6 с | 21.04 ГБ | ✓ |
| `GOGC=40` | 217.1 с | **15.33 ГБ** (−27%) | ✓ |

Вывод: GC-headroom — значимый компонент (~5.7 ГБ), huge-allocation снапшота — ещё ~2–3 ГБ.
Структурного исправления может не хватить до 10.5 ГБ → **GC-опция входит в объём**: после
per-shard диспатча повторить пару прогонов с GOGC=40; если цель берётся только с ним —
принять `debug.SetGCPercent` на время count-фазы отдельным решением с замером в ADR-012.


## Шаги

1. Этап 0 (выше), числа в план.
2. Спеки до кода: `specs/cache.md` (NumShards/SnapshotShard вместо Entries),
   `specs/counter.md` (count-фаза = per-shard claim).
3. `cache/cache.go`: API + тесты (снапшот не изымает данные; Get после снапшота видит то
   же; покрытие шардов без дублей).
4. `counter/counter.go`: `countTasks` на per-shard курсор; адаптация тестов эквивалентности
   режимов и hits/misses-инварианта.
5. `make check` зелёный.
6. Benchmarker: 7×7 d22 reversal ×2 повтора (peak RSS, время), контроль 6×6 d12–d14;
   при недоборе — атрибуция остатка по Этапу 0 и решение про GC.
7. Принятие → ADR-012 (замеры навсегда); разблокировка шага 7 плана 06 (судьба default
   `-mode`). Фолбэк при хвост-несбалансе: lazy-batched стек (снапшот дробится на батчи в
   общий стек, снапшард — только когда стек пуст) — отдельной итерацией по замеру.

## Риски

- **Хвост-несбаланс per-shard inline**: при 128 шардах/14 CPU последний воркер держит до
  одного шарда (≈8% фазы). Митигция — фолбэк lazy-batched стек; решение по замеру времени.
- **Остаток RSS GC-доминанта**: Этап 0 показывает долю; `SetGCPercent` — только с явным
  замером в ADR, не «молча».
- **Потеря Entries()**: единственный потребитель — countTasks; тесты cache переписываются
  на NumShards/SnapshotShard (правило мёртвого кода — не оставлять оба).
- RLock-копия шарда конкурентна с Get того же шарда (RLock разделяемый) — писателей в
  count-фазе нет, безопасно.
