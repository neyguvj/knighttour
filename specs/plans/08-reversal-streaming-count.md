# План 08. Count-фаза reversal без полного снимка task-cache

## Статус

Принято (→ ADR-012). Структурная цель достигнута: пик снизился на −14…−24% без
регресса времени, и устранён huge-allocation — единое гигантское выделение памяти
в рантайме Go. Цель RSS ≤ 10.5 ГБ не взята даже при GOGC=40; остаток приписали
раскладке task-cache, а следующими рычагами назвали плотность раскладки и
настройку сборщика мусора. Настройку приняли позднее отдельным решением (ADR-014),
и цель была взята. Механику выдачи задач позже заменили прямым обходом `Cache.Each`
(план 09 → ADR-013). Кандидат «план 01 для task-cache» из прежней строки статуса
больше не действует: план 01 закрыт как мёртвый (ADR-016), а возвращение к плотности
раскладки требует нового плана со свежей reversal-базой.


## Мотивация и базовые числа

ADR-011 перенёс reversal на 7×7 d22 за 213–215 с, но peak RSS составил
**18.9–21.4 ГБ** против эталонных **9.55 ГБ** у `0d142f4` (стенд M4 Max
воспроизвёл эталон: 247 с). Критерий плана 06 «RSS ≤ 10.5 ГБ» не выполнен, и смена
значения `-mode` по умолчанию заблокирована.

Профиль расхождения такой: `countTasks` вызывает `Cache.Entries()` — полную копию
таблицы (131.8M записей × 16 B ≈ 2.1 ГБ) — одним huge-allocation при живом
task-cache; опубликованный totalAlloc переноса — 32.8 ГБ, а у эталона эта величина
не измерялась. Эталон обходил каждый шард напрямую под RLock, без выделений памяти
в диспетчеризации.

## Идея / Гипотеза

Излишек пика складывается из двух частей: копия таблицы из `Entries()` с
разрастанием кучи из-за её huge-allocation, и запас памяти сборщика мусора сверх
пика (GOGC=100 удваивает кучу на крупных всплесках). Гипотеза: ленивая выдача
задач count-фазы по шардам — один шард за раз, данные из таблицы не изымаются —
снизит peak RSS на d22 до ≤ 10.5 ГБ при регрессе времени ≤ 5%.

## Корректность

После барьера errgroup генерации task-cache неизменяем до конца count-фазы.
Задачи (`CountPathsWithCacheReversal`) независимы, а `Get` читает те же данные в
любом порядке. Итог и hits/misses определяются содержимым таблицы, а не порядком
воркеров; это закреплено тест-инвариантом. Единственное отличие от текущего
переноса — порядок обхода задач.

## Дизайн

**cache.Cache** (`specs/cache.md`): `Entries()` удаляется вместе с единственным
потребителем; вместо него —
```go
func (c *Cache) NumShards() int          // то же число шардов, что у Accumulator
func (c *Cache) SnapshotShard(i int) []Entry // копия шарда под RLock, ДАННЫЕ НЕ ИЗЫМАЮТСЯ
```
Это отличается от `Accumulator.DrainShard`: `Get` обязан видеть все шарды до конца
фазы, поэтому данные не извлекаются.

**counter.countTasks** (`specs/counter.md`): воркеры берут индекс шарда с атомарного
счётчика выданных задач, делают `SnapshotShard(i)` (~16 МБ при 131.8M/128) и
выполняют все задачи своего шарда самостоятельно. Дополнительная память ≤
workers×шард ≈ 0.2 ГБ; единое огромное выделение исчезает, и крупнейшим выделением
диспетчеризации остаётся снимок шарда (~16 МБ). Вызов
`monitor.AddTasks(taskCache.ItemsCount())` выполняется одним проходом по длинам
шардов до фазы.

## Этап 0 — измерение потенциала (до кода)

Выполнить два прогона переноса на 7×7 d22 (`-mode reversal`, `/usr/bin/time -l`):
контроль и `GOGC=40`. Если `GOGC=40` даст существенное снижение пика, значит
доминирует запас памяти сборщика мусора, и в объём плана включается настройка
`debug.SetGCPercent` на время count-фазы — отдельное решение с замером. Если нет —
основной кандидат остаётся структурным исправлением, а сборщик мусора не трогаем.

Результат (2026-09-13, перенос ADR-011 с `Entries()`, `/usr/bin/time -l`, один прогон):

| конфигурация | wall | peak RSS | итог |
|---|---|---|---|
| контроль (GOGC=100) | 222.6 с | 21.04 ГБ | ✓ |
| `GOGC=40` | 217.1 с | **15.33 ГБ** (−27%) | ✓ |

Вывод: запас сборщика мусора даёт ~5.7 ГБ, огромное выделение снимка — ещё
~2–3 ГБ. Структурного исправления может не хватить до 10.5 ГБ, поэтому настройка
сборщика мусора входит в объём плана: после перехода на выдачу по шардам нужно
повторить пару прогонов с GOGC=40. Если цель берётся только с ней, `debug.SetGCPercent`
на время count-фазы принимается отдельным решением с замером в ADR-012.


## Шаги

1. Этап 0 (выше), числа заносятся в план.
2. Спеки до кода: `specs/cache.md` (`NumShards`/`SnapshotShard` вместо `Entries`),
   `specs/counter.md` (count-фаза: воркеры снимают индексы шардов с атомарного счётчика).
3. `cache/cache.go`: API и тесты (снимок не изымает данные; `Get` после снимка видит
   то же; покрытие шардов без дублей).
4. `counter/counter.go`: перевести `countTasks` на атомарный счётчик индексов шардов;
   адаптировать тесты эквивалентности режимов и инвариант hits/misses.
5. `make check` зелёный.
6. Benchmarker: 7×7 d22 reversal ×2 повтора (peak RSS, время), контроль 6×6 d12–d14;
   при недоборе — приписать остаток по Этапу 0 и принять решение про сборщик мусора.
7. Принятие → ADR-012 (замеры навсегда); разблокируется шаг 7 плана 06 (судьба
   значения `-mode` по умолчанию). Запасной план при перекосе хвоста — отложенная
   пакетная выдача: снимок шарда дробится на партии в общий стек, а новый снимок
   берётся только когда стек пуст; реализуется отдельной итерацией по замеру.

## Риски

- **Перекос загрузки в хвосте при выдаче целым шардом**: при 128 шардах/14 CPU
  последний воркер держит до одного шарда (≈8% фазы). Средство — отложенная пакетная
  выдача; решение принимается по замеру времени.
- **Остаток пика создаёт сборщик мусора**: Этап 0 показывает его долю; `SetGCPercent`
  применяется только с явным замером в ADR, а не как незаметное изменение.
- **Потеря `Entries()`**: единственный потребитель — `countTasks`; тесты `cache`
  переписываются на `NumShards`/`SnapshotShard`, потому что правило мёртвого кода
  запрещает оставлять оба.
- Копия шарда под RLock совместима с `Get` того же шарда: блокировка на чтение
  разделяемая, а писателей в count-фазе нет — это безопасно.
