# План 02. Фильтр реализуемости формы перед DP (против 65% нулей)

## Статус

**Закрыт 2026-09-14: механика снята вместе с потребителем (ADR-016).** Потребителем фильтра был финальный проход пакета `shapecount`; с переходом на единственный конвейер reversal (ADR-016) он стал мёртвым кодом.

До закрытия план был выполнен целиком: Этап 0 (инструменты `counter.TestDumpZeroShapes` и `shapecount.TestShapeFeasibilityClassification`), реализация фильтров и замеры. Вердикт по трём фильтрам таков. Filter B (forced-chain — цепочки вершин степени 2, чьи рёбра обязаны входить в путь) включён по умолчанию как `DefaultShapeFilter`. Filter C (articulation — проверка точек сочленения графа) остался опцией: он даёт ~1 п.п. сверх B. Filter A (endpoint-mismatch — фиксированный конец отсутствует среди вершин степени 1) в горячем пути не включён. Его измеренная польза нулевая: случай всегда покрыт корневым `L1` — глобальной проверкой пакета `pruner` на корневом состоянии. Выигрыш по времени скромен: 2–3% count-фазы на доске 7×7, см. «Вывод».

`pruner.ShapeFeasible`, фильтровый ярус `L2` и счётчик `FilteredShapes` удалены вместе с пакетом `shapecount`. Замеры навсегда остались в ADR-008; вывод о классе `deep` пригодился плану 06.

## Мотивация и базовые числа

На доске 7×7 при глубине d22 финальный проход считает `h` для 68 379 933 форм. Это перебор с мемоизацией по дополнению префикса (далее DP). Из всех форм **44 930 025 (65.7%) дают `h == 0` по всем концам**: большинство времени DP уходит на формы, заведомо не дающие вклада. Count-фаза занимала 371 с из 596 с прогона.

Распределение нулей по глубинам (там же): zeros/shapes = 61.7% (d20), 65.7% (d22), 68.6% (d24), 50.2% (d16).

## Что заведомо НЕ поможет (зафиксировать, чтобы не пробовать снова)

**Цветовой паритет.** Граф ходов коня двудольный, и путь, покрывающий множество `U`, требует `|black − white| ≤ 1`. Но `U` — это дополнение легального префикса длины `d`, а префикс сам чередует цвета. Поэтому дисбаланс цветов дополнения всегда ≤ 1 при любом легальном префиксе, и фильтр не сработал бы никогда. Тот же аргумент объясняет строку «0 срабатываний» из README: там проверку вели на генерации.

**Дублировать проверки связности и степеней перед DP.** `CountShape` вызывает `ShouldPruneAfterVisit(cur, todo)` на входе в рекурсию (shapecount/shapecount.go:181). Тот делает обход в ширину (`flood-fill`) по `G[todo]` со счётчиком вершин степени 1 (pruner/pruner.go:68). Значит, связность и запрет «>2 вершин степени 1» уже проверяются до первого рекурсивного шага. Форма, мёртвая по этим причинам, обходится одного прохода маски, а не полного DP. Дублирование сэкономило бы лишь ×(число концов) ≈ 2.57.

Следовательно, смысл имеют только проверки **сильнее** текущего набора.

## Дизайн

### Этап 0 — измерение (без него план дальше не идёт)

Инструментировать финальный проход на реальном распределении форм и посчитать, как разбиваются нули:

1. `dead-at-root` — форму отсекает текущий `ShouldPruneAfterVisit` уже на первом вызове DP;
2. `articulation-3+` — после удаления некоторой вершины остаётся ≥ 3 компонент связности; сейчас такая проверка отсутствует;
3. `endpoint-mismatch` — в `G[U]` ровно две вершины степени 1, и фиксированный конец `u` среди них отсутствует;
4. `forced-cycle` — цепочка вершин степени 2 замыкается в цикл короче `|U|`;
5. `deep` — структурно форма жива, и ноль выясняется только после полного перебора.

Инструмент — субтест в пакете `shapecount`, который принимает дамп форм: выгрузку из прогонов 7×7 d18–d22 и 6×6 d13 в формате «`state uint64` плюс маска концов». Собранная статистика печатается по флагу. Цель — одна таблица «доля нулей по классам». Верхняя граница выигрыша любого фильтра равна сумме долей классов 2–4: класс 1 уже отсекается бесплатно.

Если классы 2–4 дадут меньше ~20% всех нулей, план закрывается. В `specs/shapecount.md` фиксируется вывод, что дешёвые проверки нули не берут, а приоритет переходит к плану 03 (переиспользование подзадач).

### Этап 1 — фильтры, не стоящие лишних проходов

Эти проверки встраиваются в уже существующий `flood-fill` пакета `pruner`, без нового обхода графа:

- **Filter A (`endpoint-mismatch`).** `flood-fill` считает `deg1Mask` и `deg1Count`; при `deg1Count == 2` добавляется проверка «фиксированный конец лежит в `deg1Mask`». Для задачи `h(U,u)` конец зафиксирован — в отличие от генерации, где важна смежность с `last`. Стоимость — пара побитовых операций по уже посчитанной маске.
- **Filter B (`forced-cycle`, частичный).** Вершины степени 2 обязательны: оба их ребра обязаны входить в путь. Прогон цепочек обязательных рёбер ищет замкнутый цикл длины < |U| за O(|U|) по тем же степеням.

### Этап 2 — сочленения (Тарьян), только если Этап 0 подтвердит пользу

- **Filter C (`articulation-3+`).** Необходимое условие: для любой вершины `v` графа `G[U]` её удаление оставляет не более 2 компонент, иначе гамильтонов путь через `v` не проходит. Реализация — алгоритм `lowlink` за один обход по битовым маскам. Проверку вызывают **один раз на форму** до перебора концов, а не на каждый узел DP.
- Нужен порог включения по `|U|`, например только для форм от 12 клеток: на мелких формах полный DP дешевле проверки.

### Интеграция

- Точка входа — `Counter.CountShape`, до создания таблицы мемоизации. Отказ по форме возвращает нулевой срез и **не** заводит буфер мемоизации: это экономит и время, и память пула.
- Причины отказа считаются отдельно от статистики отсечений DP. Новые счётчики в `types.Result` (`FilteredShapes`, при необходимости — по видам) дают разбивку в мониторе и метрику `filtered/op` в бенчмарке. По ним видно, сколько форм убито и сколько из них были бы нулями.

## Риски

- **Ложное отсечение.** Любой фильтр обязан иметь доказательство необходимости условия и тест против полного перебора. Иначе ответ перестаёт совпадать с эталоном числа туров.
- **Стоимость алгоритма Тарьяна на больших формах** (d10–d14: |U| = 35–39). Проверка может стоить дороже, чем DP с хорошим отсечением, — отсюда порог по размеру и обязательные замеры.
- **Смешивание статистики.** Фильтр меняет смысл метрики `prunedB/op`: часть ветвей перестанет доходить до `pruner`. Новую причину фиксируем в мониторинге отдельно, чтобы исторические таблицы остались сопоставимы.

## Результаты этапа 0

Инструменты:

```bash
SHAPE_DUMP=/tmp/zeros.txt SHAPE_DUMP_SIZE=6 SHAPE_DUMP_DEPTH=13 \
  go test -run TestDumpZeroShapes ./counter/          # выгрузка нулевых форм
SHAPE_CLASSIFY=/tmp/zeros.txt SHAPE_CLASSIFY_SIZE=6 \
  go test -run TestShapeFeasibilityClassification -v ./shapecount/
```

Для 7×7 предусмотрен `SHAPE_DUMP_SAMPLE`: выборку нужно держать ограниченной, потому что файл от 45M нулей огромен. Классификация для каждой нулевой формы выясняет, чем убит каждый её конец: root — текущий `ShouldPruneAfterVisit` на корневом состоянии DP; A — степени 1 в `G[shape]`; B — `forcedChainCut(end, shape∖{end})`; C — `articulationCut`.

6×6 (полные выгрузки; доли от всех нулевых форм):

| класс | d10 | d13 | d16 |
|---|---|---|---|
| dead-at-root | 0.0% | 0.0% | 0.2% |
| articulation-3+ (первый объясняющий) | 3.1% | 4.9% | 9.5% |
| endpoint-mismatch | 0.0% | 0.0% | 0.0% |
| forced-cycle | 52.9% | 48.9% | 57.5% |
| deep | 44.0% | 46.2% | 32.8% |

Суммарно по всем убитым концам: root∨B = 55.2/52.8/66.1%, root∨C = 3.1/4.9/9.8%, root∨B∨C = 56.0/53.8/67.2%. Полный алгоритм Тарьяна на каждый конец даёт прибавку C поверх B лишь ≈ 1 п.п.; это не окупается, и C остаётся опцией (`SetShapeFilter`). Фильтр A не срабатывает никогда: он доказуемо покрыт корневым `L1`. Если A убивает конец, то вершины степени 1 из `G[shape]` остаются степенью ≤ 1 и в `G[shape∖{end}]`, и эвристики концов и изолированности отсекают тот же корень. Измерение подтвердило 0.0% на всех глубинах.

Неожиданная находка: класс `dead-at-root` даёт ≈ 0. Вопреки допущению «нулевые формы и так дешевы» из shapecount.md, нули почти не ловятся корневым `L1` и сейчас платят полное DP. Именно поэтому B обещал большой выигрыш: верхняя граница (доли классов 2–4) = 54–67% нулей, порог плана «≥ 20%» превышен многократно.

Замер на 7×7 (d18–d22) оставлен за стендом `bench-deep`; распределение 6×6 устойчиво по глубинам d10–d16.

Важное уточнение к «верхней границе»: она считается по ЧИСЛУ форм, а не по времени. Классы 2–4 умирали в DP быстро — `pruner` догонял их на первых же состояниях. Поэтому выигрыш по времени заметно меньше доли таких форм; см. замеры.

## Реализация

- `pruner.ShapeFeasible(end, shape, mask)` реализует три проверки: A (`L2Endpoints`, только для инструментов), B (`L2ForcedChain`) и C (`L2Articulation`); контракт — в specs/pruner.md.
- `shapecount.Counter.SetShapeFilter` выбирает фильтр; по умолчанию стоит `DefaultShapeFilter = L2ForcedChain`. Убитый конец не входит в DP, а полностью убитая форма не заводит буфер мемоизации. Учёт ведётся в `types.Result.FilteredShapes` и попадает в мониторинг (`| filtered N`) и в бенчмарк (`filtered/op`). Настройка проброшена через `counter.Counter.SetShapeFilter`; сравнение A/B в прогоне по глубинам включалось переменной окружения `SHAPE_FILTER=off`.
- Тесты: таблица причин отказа плюс вырожденные формы; вероятностный тест «нет ложных отсечений» против `bruteH` (пакет `pruner`); эквивалентность включённого и выключенного фильтра на формах-дополнениях для префиксов, прошедших отсечение; инвариант итогов 5×5/6×6 (shapecount/counter).

## Вывод

Метрика успеха «≥40% нулей убито до DP» по ЧИСЛУ форм перевыполнена: фильтр снимает 9–11% всех форм — это нулевые цепочные формы, чьи концы не добирает корневой `L1`. Но по ВРЕМЕНИ фильтр даёт лишь 2–3% count-фазы: классы 2–4 гибнут в DP почти у корня и без него, потому что противоречие цепочки наследуется потомкам состояний. Цель «d22 ≤ 250 с» не достигнута: время нулей сосредоточено в классе `deep` (46–68% нулей), где структурные проверки бесполезны по построению. Фильтр оставлен включённым по умолчанию — плюс без регрессов, а его стоимость ~O(V+E) на конец против DP-спуска. Проверки сочленений и концов остаются только опциями для инструментов. Приоритет сокращения count-фазы переходит к плану 03 (переиспользование подзадач): таблица мемоизации хвостов уже показывает попадания именно на формах класса `deep`.
