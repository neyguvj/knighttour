# План 03. Глобальная мемоизация значений `h` вместо сброса между формами

## Статус

**Закрыт 2026-09-14: мёртв вместе с class mode (ADR-016)** — вместе с ним удалены
флаг `-tail-memo`, поле `shapecount.TailMemo` и второй финальный проход, который
их использовал. Исторический итог: вариант B реализовали и замерили как постоянную
таблицу мемоизации, живущую у одного воркера между формами; замеры на 7×7 d22
приведены в конце файла. Память уложилась в бюджет (+1.1 ГБ), доля попаданий
достигла 98%, но выигрыш времени count-фазы составил лишь −4.7%: дешёвые хвосты
не окупают стоимость обращений. Вариант A (каноническая глобальная мемоизация)
закрыт не начатым по тем же числам. Повторное использование подзадач в
действующем конвейере обеспечивает общий task-cache обратного обхода (ADR-011).

## Мотивация и базовые числа

Метод `shapecount.Counter.CountShape` брал таблицу мемоизации из пула,
**обнулял её** (`m.reset()`, shapecount/shapecount.go:162) и считал `h(shape, ·)`
для всех концов формы. Таблица жила только внутри одной формы, поэтому:

- пересекающиеся дополнения пересчитывали общие подзадачи `f(cur, todo)` заново,
  а таких много: два листа дерева генерации часто отличаются всего несколькими
  клетками;
- в count-фазе на 7×7 d22 приходилось 17.27G событий отсечения против 1.73G у
  прежнего обратного обхода (reversal) при том же дереве генерации: финальный
  проход делал на порядок больше работы, чем стоил реверсивный спуск с разделяемым
  кэшем;
- формы одного шарда обрабатывал один воркер партиями (`processShapes` брал по
  16 задач из `shardJob`), то есть локальность для повторного использования уже
  была.

Историческая подсказка: в git-истории (коммит `0d142f4`) существовал пакет
`oracle` — таблица мемоизации значений `h(U,u)` по классам формы с ключом
D4⋉трансляции, и его спека фиксировала **уменьшение таблицы ×10–20** на компактных
множествах. Режим классов (class mode) применил трансляционную нормализацию ко
всему дополнению — 27–40 клеток, где параллельные сдвиги почти не находятся, — а
не к мелким хвостам; отсюда и нулевой эффект канонизации на 7×7.

## Корректность

Значение `f(cur, todo)` зависит только от индуцированного подграфа на
`todo ∪ {cur}` с отмеченной клеткой `cur`. Ходы коня задаются разностями
координат, а путь из `cur` никогда не выходит за `todo`. Поэтому значение
инвариантно относительно D4 и параллельных переносов **пары**
`(todo ∪ {cur}, cur)` — это та же аргументация, что у `symmetry.KeyFromPrepared`
(symmetry/shape.go:78). Ключи двух разных форм сравнимы канонически, и совпадение
ключа означает совпадение значения.

## Дизайн

### Вариант B (первым) — мемоизация в абсолютных координатах между формами одного воркера

Это дешёвая половина идеи: без канонизации вообще.

1. У воркера финального прохода появляется **постоянная таблица мемоизации**
   `f(cur, todo)`, живущая между вызовами `CountShape` для его партии форм. Пул
   остаётся, но вместо `reset()` точный уровень только увеличивает поколение, а
   записи с малым `todo` сохраняются.
2. Схема двухуровневая:
   - уровень 1 — текущая таблица мемоизации формы, как тогда, с точными ключами;
   - уровень 2 — постоянная таблица воркера: в неё пишутся только записи с
     `popcount(todo) ≤ K`, а читаются всегда.
3. Запись уровня 2 годится для любой формы, содержащей данное `todo`, поэтому
   повторное использование возникает само между соседними по шарду формами. Нули
   сохраняются наравне с ненулями: ноль — корректное и дешёвое значение.
4. Память ограничивают параметр `K` и лимит числа записей на воркера. При
   переполнении запись останавливают либо сбрасывают поколение; вытеснение по
   давности (LRU) не нужен, если сбросы редки.

### Вариант A — каноническая глобальная мемоизация (вторым)

Она даёт повторное использование между формами, лежащими в разных местах доски и
в разных ориентациях.

1. Ключ — `path.Path` из `CanonicalizeShape(todo ∪ bit(cur), cur)`; значение —
   `uint64`.
2. Обращения к таблице идут **только на границе** `popcount(todo) == K`, иначе
   стоимость `PrepareShape` (O(|U|)·8) съедает выигрыш. Поддерево ниже границы
   считается локальной таблицей формы и кладётся в глобальную таблицу один раз.
3. Хранилище общее и шардированное, с открытой адресацией из плана 01. Писатели
   складывают результаты через локальные буферы по образцу `cache.LocalSink`.
   Чтение без блокировок не получается, поэтому важны редкость обращений (п. 2) и
   высокая доля попаданий.
4. Возможная реализация — воскресить удалённый пакет `oracle` (git `0d142f4`,
   `specs/oracle.md`) вместо написания нового: там уже были нормализация пары,
   статистика `lookups`/`computes`/`classes`/`zeros` и тесты инвариантности.

## Этап 0 — измерение потенциала

Прежде чем что-то строить, надо посчитать потенциал на реальном распределении
форм (выгрузки с 7×7 d18–d22 и 6×6 d13):

- доля записей `f(cur, todo)` с `popcount(todo) ≤ K` при `K = 6/8/10/12`;
- среди них доля **повторов**: (a) точных `(todo, cur)` между разными формами
  одного шарда — это потенциал варианта B, и (b) совпадений по каноническому
  классу — это потенциал варианта A;
- ожидаемая экономия = Σ (число повторов − 1) × стоимость подзадачи.

Без этих чисел план не реализуется: если повторов мало, дешевле остаться на
мемоизации для каждой формы отдельно и вкладываться в планы 02/04.

## Риски

- **Память.** Глобальная таблица на миллиарды записей убьёт эффект. Обязательны
  лимит и метрика заполненности, иначе план 01 даст обратный результат.
- **Стоимость канонизации (вариант A).** Обращение к ней допустимо только на
  границе `K`; обязателен замер до и после на мелких формах, где DP дешевле
  нормализации.
- **Конкуренция за общее хранилище.** 14 воркеров на одной таблице — это
  конкуренция за блокировку. Помогают шардирование по ключу и локальные партии
  записи; иначе остаются постоянные таблицы отдельных воркеров (вариант B) и
  меньшее повторное использование.
- **Воспроизводимость статистики.** Доля попаданий зависит от порядка обработки
  форм, поэтому тесты фиксируют этот порядок (LPT, как тогда).

## Результаты (вариант B, M4 Max 36 ГБ, 14 воркеров, 2026-09-11)

Этап 0 пропущен по решению оператора; вместо него вариант B замерили прямыми
полными прогонами `./knighttour -size 7 -precompute-depth 22 [-tail-memo K]` под
`/usr/bin/time -l`. Эталон — тот же исполняемый файл с `-tail-memo 0`.

### Выводы

- Память уложилась в бюджет плана: таблицы воркеров (~14 × ≤80 МБ занятых слотов
  при лимите `1<<23` слотов) добавили ≈ +1.1 ГиБ к пику 22.3 ГиБ; риска нехватки
  памяти нет.
- Доля попаданий на большой доске — 98% против 12–36% на мелкой: повторяемость
  мелких `(todo, cur)` между формами одного воркера действительно огромна.
- Но время почти не сдвинулось. Попадания в основном приходятся на нулевые хвосты,
  которые и без мемоизации отсекались пакетом `pruner` за O(deg), а каждый промах
  по уровню 2 стоит popcount+hash+обращение. Экономия на повторных подзадачах
  примерно равна стоимости обращений — отсюда −4.7% вместо −25%. **Доля попаданий
  без весовой стоимости подзадачи — обманчивая метрика**; этап 0 плана как раз об
  этом предостерегал.
- На мелкой доске K=12 хуже K=8, так как холодных обращений больше; на большой
  доске его не замеряли из-за цены прогона, ожидаемый эффект тот же.
- Решение: вариант B оставить выключенным по умолчанию (`-tail-memo 0`) как
  экспериментальный инструмент. Вариант A (канонизация и общая таблица) при такой
  структуре экономии только добавил бы стоимости ключу. Приоритет — планы 02/04:
  меньше состояний DP в корне, а не переиспользование хвостов.
