# План 03. Глобальное мемо значений `h` вместо сброса между формами

## Статус

**Закрыт 2026-09-14: мёртв вместе с class mode (ADR-016)** — флаг `-tail-memo`,
`shapecount.TailMemo` и второй финал, их кормивший, удалены. Исторический итог:
вариант B был реализован и замерен (persistent-мемо воркера; замеры на 7×7 d22 —
в конце файла): память в бюджете (+1.1 ГБ), hit-rate 98%, но время counting лишь
−4.7% — «дешёвые» хвосты не окупают стоимость проб. Вариант A (каноническое
глобальное мемо) закрыт не начатым по тем же числам; переиспользование подзадач
в живом конвейере даёт общий task-cache reversal (ADR-011).

## Мотивация и базовые числа

`shapecount.Counter.CountShape` берёт мемо из пула, **обнуляет его** (`m.reset()`,
shapecount/shapecount.go:162) и считает `h(shape, ·)` для всех концов формы.Memo
живёт только внутри одной формы, поэтому:

- пересекающиеся дополнения (а их много: два листа генерации часто отличаются
  несколькими клетками) пересчитывают общие подзадачи `f(cur, todo)` заново;
- в counting на 7×7 d22 приходится 17.27G событий прунинга против 1.73G у старого
  reversal при том же дереве генерации — то есть финальный проход делает на порядок
  больше работы, чем стоило реверсивному спуску с разделяемым кэшем;
- формы одного шарда обрабатываются одним воркером пачками (`processShapes` берёт
  батчами по 16 задач из `shardJob`), то есть локальность для переиспользования уже есть.

Историческое подтверждение: в git `0d142f4` был пакет `oracle` — мемо `h(U,u)` по классам
формы с ключом D4⋉трансляции; его спека фиксировала **×10–20 уменьшение таблицы** на
компактных множествах. Класс-режим применил трансляционную нормализацию к целому
дополнению (27–40 клеток, где параллельных сдвигов почти не находится), а не к мелким
хвостам — отсюда и нулевой эффект канонизации на 7×7.

## Корректность

Значение `f(cur, todo)` зависит только от индуцированного подграфа на `todo ∪ {cur}` с
отмеченной клеткой `cur`: ходы коня задаются разностями координат, а путь из `cur`
никогда не выходит за `todo`. Поэтому значение инвариантно к D4 и параллельным переносам
**пары** `(todo ∪ {cur}, cur)` — ровно та же аргументация, что у
`symmetry.KeyFromPrepared` (symmetry/shape.go:78). Ключи двух разных форм можно сравнивать
канонически, и совпадение ключа означает совпадение значения.

## Дизайн

### Вариант B (первым) — мемо в абсолютных координатах, между формами одного воркера

Дешёвая половина идеи: без канонизации вообще.

1. У воркера финального прохода появляется **постоянное** мемо `f(cur, todo)`, живущее
   между вызовами `CountShape` для своей пачки форм (пул остаётся, но вместо `reset()`
   — инкремент поколения у «точное» уровня и сохранение записей с малым `todo`).
2. Двухуровневая схема:
   - уровень 1 — текущая мемо-таблица формы (как сейчас), точные ключи;
   - уровень 2 — persistent-таблица воркера, куда пишутся только записи с
     `popcount(todo) ≤ K` и считываются всегда.
3. Так как запись уровня 2 валидна для любой формы, содержащей данное `todo`, переиспользование
   возникает автоматически между соседними по шарду формами; нули сохраняются наравне с
   ненулями (ноль — корректное значение и дешёвое).
4. Ограничение памяти: `K` + лимит числа записей на воркера (при переполнении — остановка
   записи либо сброс поколения; LRU не нужен, если сброс редкий).

### Вариант A — каноническое глобальное мемо (вторым)

Даёт переиспользование между формами, лежащими в разных местах доски и разных ориентациях.

1. Ключ — `path.Path` из `CanonicalizeShape(todo ∪ bit(cur), cur)`; значение — `uint64`.
2. Обращение **только на границе** `popcount(todo) == K`: иначе стоимость
   `PrepareShape` (O(|U|)·8) съедает выигрыш. Поддерево ниже границы считается локальным
   мемо формы и один раз кладётся в глобальную таблицу.
3. Хранилище — общее, шардированное (открытая адресация из плана 01), писатели складывают
   результаты через локальные буферы по образцу `cache.LocalSink`; чтение без локов не
   получается, поэтому важна редкость обращения (п. 2) и высокий hit-rate.
4. Возможная реализация — воскресить удалённый пакет `oracle` (git `0d142f4`,
   `specs/oracle.md`) вместо написания нового: там уже были нормализация пары, статистика
   lookups/computes/classes/zeros и тесты инвариантности.

## Этап 0 — измерение потенциала

Прежде чем что-то строить, посчитать на реальном распределении форм (выгрузка с 7×7
d18–d22 и 6×6 d13):

- доля записей `f(cur, todo)` с `popcount(todo) ≤ K` при `K = 6/8/10/12`;
- среди них доля **повторов** — (a) точных `(todo, cur)` между разными формами одного
  шарда (потенциал варианта B) и (b) совпадений по каноническому классу (потенциал
  варианта A);
- ожидаемая экономия = Σ (число повторов − 1) × стоимость подзадачи.

Без этих чисел план не реализруется: если повторова мало, дешевле остаться на per-shape
мемо и вкладываться в план 02/04.

## Риски

- **Память.** Глобальное мемо на миллиарды записей убьёт эффект; обязательны лимит и
  метрика «заполненность», иначе план 01 даёт обратный результат.
- **Стоимость канонизации** (вариант A): только на границе `K`, и обязательно с замером
  «до/после» на мелких формах, где DP дешевле нормализации.
- **Конкуренция за общее хранилище**: 14 воркеров на одной таблице — это contention;
  шардирование по ключу + локальные батчи записи, либо остаться на пер-воркеровских
  persistent-таблицах (вариант B) и принять меньшее переиспользование.
- **Детерминизм статистики**: hit-rate зависит от порядка обработки форм — фиксировать
  порядок (LPT, как сейчас) в тестах, чтобы метрики были воспроизводимы.

### Выводы

- Память — в бюджете плана: таблицы воркеров (~14 × ≤80 МБ занятых слотов при
  лимите 1<<23 слотов) добавили ≈ +1.1 ГиБ к пику 22.3 ГиБ; OOM-риска нет.
- Hit-rate 98% на большой доске против 12–36% на мелкой: повтораемость мелких
  `(todo, cur)` между формами одного воркера действительно огромна.
- Но время почти не двигается: попадания в основном «нулевые» хвосты, которые
  и без мемо отсекались прунером за О(deg), а каждый промах по уровню 2 стоит
  popcount+hash+пробу. Экономия на повторных подзадачах ≈ стоимости проб —
  отсюда −4.7% вместо −25%. **Hit-rate без весовой стоимости подзадачи —
  обманчивая метрика** (этап 0 плана это и предостерегал).
- K=12 на мелкой доске хуже K=8 (больше холодных проб), на большой не замерялся
  из-за цены прогона; ожидаемый эффект тот же.
- Решение: вариант B оставить выключенным по умолчанию (`-tail-memo 0`), как
  экспериментальный инструмент; вариант A (канонизация + общая таблица) с
  такой структурой экономии только добавит стоимости ключа. Приоритет —
  планы 02/04 (меньше состояний DP в корне, а не переиспользование хвостов).
