# План 11. Count-фаза: worker pool с буферизованным каналом на стороне counter (стратегия 1 из трёх)

## Статус

Не начат. Сравнительное исследование диспатча count-фазы (планы 11/12/13 — три стратегии,
каждая своей веткой/фичем против общего свежего контроля HEAD; по замерам лучшая вливается
в main, остальные помечаются Отклонены с числами).

## Мотивация и базовые числа

Текущий диспатч count-фазы — `Cache.Each` (ADR-013): горутина на шард под RLock, колбэк
выполняет count-DFS **inline под залом шарда**. Единица работы — шард целиком: 128 шардов /
14 воркеров ≈ 9 шардов на воркера, стоимость записей разнородна (count-DFS), поэтому к концу
фазы активные воркеры остаются поодиночке на последних шардах — параллелизм падает, хвост
растёт. ADR-012/013 фиксировали «хвост не проявился» только для гранулярности курса того дня;
наблюдение пользователя: на текущем HEAD хвост есть.

База — HEAD с `Each` (in-place контроль, ×2 прогона до кода). Стенд/методология —
`specs/benchmarks.md`, точка сравнения: **7×7 d22, workers=14** (`make bench-size N=7
DEPTHS=22`), метрика — `cnt_ms/op`; ориентир ADR-013: cnt ≈ 93–99 с, total ≈ 208–218 с,
peak RSS (GOGC=40) 10 203 МБ.

## Идея / Гипотеза

Если колбэк `Each` перестанет считать под залом и станет **продюсером**: пишет копию записи
(`cache.Entry`, 24 Б) в общий буферизованный канал, а `workers` консьюмеров считают из него —
то любой освободившийся воркер берёт следующую запись независимо от шарда, хвост «до одного
шарда» схлопывается, и `cnt_ms` падает ≥5% вне диапазона повторов контроля.

## Корректность

- Итог `Σ W(task)·f(task)` не зависит от порядка: суммирование в общий `atomic.Uint64`,
  `f(task)` детерминирован содержимым кэша (тот же инвариант, что у ADR-012/013).
- Копирование записи наружу законно после барьера генерации: писателей нет до конца count-фазы,
  данные иммутабельны; `Get` мемо раннего стопа читает живой кэш как раньше.
- Отправка в канал выполняется под RLock шарда и блокирует продюсера при переполнении —
  deadlock исключён: писателей нет (разделяемый RLock никого не ждёт), консьюмеры работают
  без залов и всегда дренируют канал; close — только после завершения всех продюсеров.
- Отмена ctx: продюсеры останавливаются (`Each` даёт `ctx.Err()`), канал закрывается,
  консьюмеры досбрасывают очередь без подсчёта (как сегодня `countOneTask` пропускает задачи
  при `ctx.Err() != nil`) — частичный итог без паники; чужая ошибка `Each` — panic по
  существующему правилу `checkEachError`.

## Дизайн

Пакет `cache` **не меняется** (`Each` остаётся эталонным и переиспользуется как обход-продюсер).
Всё изменение — в `counter.countTasks`:

1. `ch := make(chan cache.Entry, workers*K)` — единственный буфер фазы; K ∈ {1000…10000} —
   ручка тюнинга (бюджет пользователя), старт с середины диапазона.
2. До вызова `Each` стартуют `workers` консьюмеров (`errgroup`/WaitGroup): читают из `ch`,
   пока канал открыт; для каждой записи — прежний `countOneTask` (count-DFS, `w·paths` в
   общий атом). Подсчёт уходит **из-под RLock шарда** — caveat рекурсивного RLock того же
   шарда перестаёт быть нужен.
3. `taskCache.Each(ctx, workers, func(...) error { ch <- Entry{p, w}; return nil })` — обход
   остаётся zero-copy из map; копия = 24 Б в слот канала (runtime пишет значение в
   предвыделенный буфер ха́ннела, по-записной аллокации нет).
4. После возврата `Each` — `close(ch)`; Wait консьюмеров; итог — как сейчас.
5. Мониторинг: `AddTasks(taskCache.ItemsCount())`, отчёты — из консьюмеров (семиantics тот же).

Тюнинг на 7×7 d22: K ∈ {1000, 2000, 5000, 10000}; при признаках конкуренции на hchan —
шаг-фолбэк: слать пачками `[]Entry` из переиспользуемых продюсерских буферов (в объёме плана
только если замеры покают упор в sync; по умолчанию — по записи).

## Аллокационный бюджет

| структура | формула | 7×7 d22, W=14 |
|---|---|---|
| канал `chan Entry` | 24 Б × K × workers | 0.34 МБ (K=1000) … 3.4 МБ (K=10000) |

- Аллокаций на запись — ноль (слоты канала предвыделены `make`); аллокаций на фазу — одна
  (буфер канала). Пик фазы: копия ≤3.4 МБ против task-cache ~10 ГБ — в шуме peak RSS.
- Механика базы (`Each`): ноль копий, но и нет балансировки; новый дизайн сознательно берёт
  bounded-копию (≤3.4 МБ) вместо O(workers×шард) снимков ADR-012 (~350 МБ живых копий) —
  копия одна на запись, в момент передачи, без второго экземпляра.

## Шаги

1. Контроль HEAD ×2: `make bench-size N=7 DEPTHS=22` (база cnt_ms; логи в ветку).
2. Спека до кода: `specs/counter.md` (§counting — диспатч через канал, колбэк вне залов,
   семантика отмены). `specs/cache.md` — без правок (контракт `Each` не меняется).
3. Реализация в `counter/counter.go` (`countTasks` + хелперы воркеров); `cache/` не трогать.
4. Тесты (`-race`): точная доставка ровно один раз (синтетический кэш N записей, два
   продюсера через `Each`, консьюмеры считают сумму — без дублей/потерь); принудительное
   переполнение (маленький K) не дедлокается; отмена ctx → частичный итог без паники;
   инвариант итого к числу воркеров на 5×5/6×6 (`make check`).
5. Бенч: свип K на 7×7 d22 (×повторы), полный нисходящий свип 6×6, точка 5×5 (фикс-стоимость).
6. Вердикт по порогу → при WIN: merge в main + ADR-019 (замеры навсегда) + правка
   `specs/counter.md`; при проигрыше — план помечать Отклонён с числами, ветку не мержить.

## Риски

- **Синхронизационный оверхед hchan** (14 продюсеров + 14 консьюмеров на двух мьютексах
  канала) съедает выигрыш хвоста → свип K; фолбэк — пачечная отправка `[]Entry`; при новом
  провале — стратегия отклоняется в пользу 12/13.
- **Продюсер под RLock блокируется на полном канале** — сериализует обход своего шарда;
  безопасно (писателей нет), но при малом K превращает канал в узкое горло → нижняя граница
  K в свипе.
- Будущий инкрементальный писатель кэша сломает предусловие блокировок (тот же caveat, что
  ADR-013) — механику тогда пересматривать.
- Двойной пул горутин (продюсеры `Each` + консьюмеры ≈ 2×workers) — тривиально по стекам.
