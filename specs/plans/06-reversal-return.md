# План 06. Возврат reversal как основного режима подсчёта

## Статус

В работе: шаги 1–5 выполнены (порт + ADR-011, RSS-фикс плана 08 → ADR-012), шаг 6 (полный
A/B-свод 7×7) **закрыт 2026-09-13** — остаток точек снят, итоговая сводная таблица обоих
режимов в подразделе «Закрытие остатка свода 7×7» ADR-011; шаг 7 (судьба default `-mode`) **разблокирован**:
RSS-критерий ≤10.5 ГБ закрыт понижением GOGC на reversal-конвейере (ADR-014, флаг `-gc-percent`),
8×8 выведена из требований A/B-свода (ADR-015) — свод шагов 6–7 охватывает только 6×6/7×7.
Свод 6×6/7×7 (обе трубы) снят полностью. **Шаг 7 — решение принято 2026-09-13 (пользователь):
глобальный default `-mode` → `reversal` для всех размеров** (основание — итоговая таблица
свода ADR-011: на 7×7 reversal быстрее при d≥18 и всегда дешевле по памяти, на 6×6 на штатной
глубине паритет, 8×8 только reversal). Перенос дефолта в коде (main.go/спеки/README) — отдельный
коммит; **удаление class mode** (shapecount, M-аккумулятор) — ещё один отдельный будущий коммит,
этим решением не предопределено.
Перенос дефолта **в работе** (2026-09-13): спеки обновлены (main.md — дефолт `-mode`,
counter.md — дефолт свежего `NewCounter` = ModeReversal, AGENTS.md), код и README — за кодером.
Осознанно **не** меняется дефолт бенч-харнесса `BENCH_MODE` (specs/benchmarks.md остаётся
`class`): это ручка A/B-сравнимости исторических свипов, её перенос — вместе с удалением
class mode. Принят по итогам разбора планов 01–04: на стенде 7×7 d22 class mode
проигрывает эталонному reversal (git `0d142f4`) **по обеим осям** — 596 с / 23.5 ГБ
против 252 с / 9.6 ГБ при идентичном дереве генерации.

## Гипотеза

Канонизация целого дополнения (27+ клеток) не дедуплицирует почти ничего
(параллельных сдвигов на крупных формах нет — см. specs/shapecount.md, ×1.16 у
оригинального oracle), но при этом **уничтожает кросс-задачное переиспользование
подзадач**, которое давал общий task-cache reversal: 17.27G prune-событий
финального DP против 1.73G при том же дереве. Планы 02/03B/04 это косвенно
подтвердили: время нулей живёт в deep-классе, где структурные проверки (02) и
хвостовое мемо мелких todo (03B) бесполезны, а удорожание узла DP (04) убыточно.

Следовательно считать надо общим мемо по **сырым** ключам состояния (то, что умел
reversal), а не per-shape DP с обнуляемым мемо. Двухфазная генерация префиксов и
мониторинг class mode при этом сохраняются — отказывает только финальный проход.

## Дизайн

### Режим за флагом (class mode не удаляем до конца A/B)

1. CLI: `-mode class|reversal` (пока default `class`), значение в финальный отчёт.
2. Порт из `0d142f4`:
   - `cache.Cache` — шардированный task-cache `path.Path → weight`
     (`Get/GetCanonical/Set/ItemsCount`); **без** oracle-слоя
     (эталон 252 с снят при `-oracle-depth 0`);
   - `searcher.Reversal` + `CountPathsWithCacheReversal`: count-DFS по дополнению,
     остановка на hit'е кэша, запись значения при подъёме;
   - генерация подзадач глубины `precomputeDepth` → очередь задач → count-воркеры.
3. Адаптация к текущей обвязке (порт не «как есть»):
   - `types.Result`: вернуть `CacheHits/CacheMisses`, разбивку прунинга сохранить;
   - мониторинг: фазы `gen A` → `gen B` → `counting` с теми же сегментами строки,
     hits/misses в отчёт;
   - `int` → `uint64` в весах кэша (согласовать с текущим Result);
   - LocalSink не переносить молча: профиль записей reversal-кэша другой
     (hit'ы читаются в том же ране, что пишутся) — решить по первому профилю.
4. Инварианты: глубина разреза остаётся `[1, size²/2]`; канцелирование стартов
   орбитами — как сейчас; корректность = тождество обращения
   `total = Σ_tasks w · W(task)` c мемо по точному состоянию.

### Хранилище: нативная Swiss-map, не своя таблица

Task-cache портируется на `map` (Go ≥1.24 — Swiss: load factor ~93%,
pointer-free слоты). Своя плоская таблица — только если Этап 0 плана 01 покажет
≥1.7× по памяти при регрессе ≤5%; решение общее для обоих режимов. sync.Map
отклонён (аддитивные апдейты горячих ключей, GC, отсутствие per-shard drain —
см. план 01/«Риски»).

## Риски

- **Расхождение порта с эталоном** из-за «молчаливых» улучшений обвязки: порт
  делаем послойно (cache → searcher → counter), каждый слой сверяем с тестами
  эталонного коммита, адаптируя их осознанно.
- **Память task-cache на больших q** (низкие d): кэш живёт до конца count-фазы и
  не дренируется по шардам, в отличие от M; фиксировать точку OOM как результат
  A/B, а не как баг.
- **Детерминизм**: счёт в кэш идёт из разных воркеров — значения аддитивны, но
  статистика hits/misses от порядка зависит; в тестах фиксировать только итог.
- **Раздвоение кодовой базы** на время до этапа 7: оба режима обязаны переживать
  `make check` на каждом коммите.
