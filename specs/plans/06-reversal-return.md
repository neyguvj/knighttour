# План 06. Возврат reversal как основного режима подсчёта

## Статус

**Закрыт 2026-09-13.** Шаги 1–5 закрыты портом кода и ADR-011; фикс пика памяти пришёл из
плана 08 и оформлен ADR-012. Шаг 6 — полный сравнительный свод 6×6 и 7×7, его итоговая
таблица лежит в подразделе «Закрытие остатка свода 7×7» документа ADR-011. Шаг 7 — решение
пользователя (2026-09-13): глобальное значение флага `-mode` по умолчанию стало `reversal`
(обратный обход через общий task-cache и тождество обращения), и перенос закреплён коммитом
`0f70414`. Удаление режима классов (class mode — прежний режим подсчёта через таблицу
классов форм дополнения) зафиксировано ADR-016 и исполняется отдельным коммитом; объём и
основания — тоже ADR-016. Один конвейер: gen A → gen B в task-cache → count с обращениями.
Коммит удаления вычищает shapecount, M-аккумулятор, L2, DP-статистику и флаги
`-mode`/`-tail-memo`, снимает переключатель среды `BENCH_MODE` — сравнимость A/B несут
таблицы ADR-011, — переименовывает бенчмарк в `BenchmarkCountAllTours`, заново подбирает
`DefaultPrecomputeDepth` под reversal по свежим замерам и перезаписывает README-showcase по
свежему проходу по диапазону глубин. Хвост исполнения — пересмотр значений по умолчанию и
README по этому свежему проходу — в коммит удаления не вошёл; его исполняет план 10.

## Гипотеза

Канонизация целого дополнения (27+ клеток) почти ничего не дедуплицирует: параллельных
сдвигов на крупных формах нет, и оригинальный oracle даёт лишь ×1.16. При этом она
**уничтожает переиспользование подзадач между задачами**, которое давал общий task-cache
режима reversal: 17.27G событий отсечения финального DP против 1.73G при том же дереве.
Планы 02/03B/04 косвенно это подтверждают: время нулей живёт в глубоком классе задач, где
структурные проверки (план 02) и мемоизация мелких хвостовых todo (план 03B) бесполезны, а
удорожание узла DP (план 04) убыточно.

Значит, считать надо общей мемоизацией по **сырым** ключам состояния — тем, что умел
reversal, — а не отдельным DP по каждой форме с обнуляемой мемоизацией. Двухфазная
генерация префиксов (gen A и gen B) и мониторинг class mode сохраняются — отказывает только
финальный проход.

## Дизайн

### Режим за флагом (class mode не удаляем до конца A/B)

1. Флаг CLI `-mode class|reversal`, пока со значением по умолчанию `class`; выбранное
   значение попадает в финальный отчёт.
2. Порт из коммита `0d142f4`:
   - `cache.Cache` — шардированный task-cache вида `path.Path → weight` с методами
     `Get/GetCanonical/Set/ItemsCount`; **без** oracle-слоя (эталонные 252 с сняты при
     `-oracle-depth 0`);
   - `searcher.Reversal` и `CountPathsWithCacheReversal`: count-DFS по дополнению, который
     останавливается на попадании в кэш и записывает значение при подъёме;
   - генерация подзадач глубины `precomputeDepth`, затем очередь задач и count-воркеры.
3. Адаптация к текущей обвязке — порт не «как есть»:
   - в `types.Result` вернуть `CacheHits/CacheMisses`, а разбивку по причинам отсечения
     сохранить;
   - мониторинг: фазы `gen A` → `gen B` → `counting` с теми же сегментами строки, попадания
     и промахи уходят в отчёт;
   - заменить `int` на `uint64` в весах кэша, согласовав их с текущим `Result`;
   - LocalSink не переносить молча: профиль записей reversal-кэша другой (попадания
     читаются в том же интервале, в котором пишутся), и решение принимается по первому
     профилю.
4. Инварианты: глубина разреза остаётся `[1, size²/2]`; сокращение стартов орбитами
   симметрий — как сейчас; корректность даёт тождество обращения
   `total = Σ_tasks w · W(task)` при мемоизации по точному состоянию.

### Хранилище: нативная Swiss-map, не своя таблица

Task-cache портируется на встроенную `map`: Go версии не ниже 1.24 использует Swiss-карту
с коэффициентом заполнения около 93% и слотами без указателей. Свою плоскую таблицу брать
только если Этап 0 плана 01 покажет выигрыш ≥1.7× по памяти при регрессе не больше 5%;
решение общее для обоих режимов. `sync.Map` отклонён: горячие ключи требуют аддитивных
обновлений, он нагружает сборщик мусора и не освобождает память по шардам — подробности в
плане 01, раздел «Риски».

## Риски

- **Расхождение порта с эталоном** из-за незамеченных улучшений обвязки: порт делаем
  послойно (cache → searcher → counter), и каждый слой сверяем с тестами эталонного
  коммита, адаптируя их осознанно.
- **Память task-cache на больших q** (низкие d): кэш живёт до конца count-фазы и не
  освобождается по шардам, в отличие от M; точку OOM фиксируем как результат A/B, а не как
  баг.
- **Детерминизм**: записи в кэш идут из разных воркеров, значения аддитивны, но статистика
  попаданий и промахов от порядка зависит; в тестах фиксируем только итог.
- **Раздвоение кодовой базы** на время до шага 7: оба режима обязаны проходить `make check`
  на каждом коммите.
