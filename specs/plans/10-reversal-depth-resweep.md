# План 10. Пересъёмка `DefaultPrecomputeDepth` под reversal + README по свежему проходу глубин

## Статус

Принято (→ ADR-016 §«Замеры» → «2026-09-14, пересъёмка `DefaultPrecomputeDepth` под reversal»).
Исполнительный хвост ADR-016 закрыт 2026-09-14: проходы по диапазону глубин сняты,
текст README переписан как витрину под reversal-конвейер. Вердикт — **дефолты
сохранены**: на 5×5 результат NOISE/плато, а кандидаты d14 на 6×6 и d22 на 7×7
оказались быстрее вне шума, но были отклонены по потолку peak RSS. Итоговая таблица
принятых глубин (шаг 4 — без изменений, `counter/counter.go` и
`TestDefaultPrecomputeDepth` не тронуты):

| size | 5 | 6 | 7 | 8 |
|---|---|---|---|---|
| depth | 6 | 10 | 20 | 14 (заглушка без пересъёмки, ADR-015) |

Медианы, разбросы повторов и вердикты хранятся навсегда в ADR-016 §«Замеры»; логи —
`bench-logs/plan10/{sweep5,sweep6,sweep7}.log`, `make_bench.log`.

**Ревизия (2026-09-14, ADR-017):** пользователь сменил критерий принятия на «чистое
время», и правило по peak RSS из пункта 3 дизайна снято; таблица принятых значений
стала `{5: 6, 6: 14, 7: 22, 8: 14}` (кандидаты d14/d22 приняты вопреки пику).
Актуальный контракт — specs/counter.md; здесь план читается как исторический отчёт
об исполнении пересъёмки.

## Мотивация и базовые числа

Дефолты глубины meet-in-the-middle заданы таблицей `defaultPrecomputeDepths`
(`counter/counter.go`, контракт — specs/counter.md) по замерам **class-режима**. После
ADR-016 конвейер остался один (reversal), а его профиль иной. По ADR-011 окно минимума
reversal на 6×6 лежит в d12–d14 против штатного 10; на 7×7 при d ≥ 18 reversal быстрее
class на 29–63%, поэтому плато class-режима 19–23 на него не переносится. Стенд —
Apple M4 Max (14 ядер); прогоны штатные: GOGC=40 задаёт конвейер (ADR-014), переменную
окружения `GOGC` не подменять.

База сравнения — текущие дефолты на reversal: точки d6 (5×5), d10 (6×6) и d20 (7×7)
из этого же прохода по диапазону глубин, иначе сравнение некорректно.

## Идея / Гипотеза

Как минимум на 6×6 действующий дефолт 10 проигрывает времени минимума окна d12–d14
≥ 5%. На 7×7 минимум окна d14…d22 может сдвинуться относительно 20. На 5×5 точка d6
попадает в плато, и смена не требуется. Таблица заменяется по замерам; иначе
фиксируется вывод «осталось».

## Корректность

Глубина разреза на итог не влияет (тест инвариантности `counter/counter_test.go`,
тождество `Σ W·f` — specs/counter.md); меняются только время и память. 8×8 не
пересъёмляется: доска вне штатных прогонов (ADR-015), и значение 14 остаётся
консервативной заглушкой.

## Дизайн

Изменения в коде сводятся к четырём числам: таблица в `counter/counter.go`, тест
`TestDefaultPrecomputeDepth` и контрактная таблица specs/counter.md. Замерные точки
(методология — specs/benchmarks.md):

1. `make bench-size N=5` и `N=6` — полные нисходящие проходы по диапазону глубин,
   по 3 повтора (у малых досок шум велик); peak RSS корректен только так, потому что
   каждый размер доски прогоняется отдельным процессом.
2. 7×7 точечно: `make bench-size N=7 DEPTHS=14,16,18,20,22` — запуск требует явного
   разрешения `BENCH_DEEP`, точка занимает часы, объём окна задан ADR-016; не менее
   2 повторов на глубину.
3. Правило принятия: принимается глубина минимума времени, если её отрыв от текущего
   дефолта превышает разброс повторов (ориентир >3% для 5×5/6×6). В пределах шума
   дефолт сохраняется, а вывод пишется в ADR-016. Peak RSS принятой глубины не выше
   пика текущего дефолта вне шума.

## Шаги

1. Проход по диапазону глубин для 5×5/6×6 (пункт 1 дизайна); логи — в один файл,
   рендер таблиц — `make bench-table`.
2. Проход по диапазону глубин для 7×7 (пункт 2) — в тот же лог.
3. Принятие глубин по правилу; правка таблицы `counter/counter.go`, теста

   `make check`.
4. Числа до и после пишутся в резерв подраздела «Замеры» ADR-016 (навсегда); здесь
   остаётся только итоговая таблица принятых значений.
5. README: полная перезапись по скиллу `readme-writing` под единственный
   reversal-конвейер, потому что прежний текст описывал режим class и был
   невоспроизводим. Нужны таблица CLI без `-mode`/`-tail-memo`, повествование без
   «двух финалов», таблицы из свежего единого лога `make bench` и штамп свежести.
   Триггер скилла срабатывает: изменились дефолты, структура и выводы.
6. Всё записывается одним коммитом вместе с вердиктом бенчмаркера; иначе README
   снова отстаёт от чисел.

## Метрики успеха

| метрика | база (текущий дефолт на reversal) | цель / порог |
|---|---|---|
| 6×6, время на принятой глубине | прогон d10 этого прохода | −≥5% против d10, иначе вывод «10 остаётся» |
| 7×7, время на принятой глубине | прогон d20 этого прохода | минимум d14…d22; в шуме d20 — сохраняем 20 |
| 5×5, время на принятой глубине | прогон d6 | подтверждение плато (±шум) или смена на минимум |
| peak RSS принятой глубины | пик текущего дефолта (bench-size) | не выше вне шума |
| README | таблицы class-прогонов | воспроизводимы из одного свежего `make bench`-лога |

## Риски

- **Цена прохода по 7×7**: каждая глубина стоит часы. Помогают точечные глубины,
  фоновый запуск и `bench-size` отдельными процессами; недобор повторов не
  маскировать — писать в план.
- **Шум малых досок**: обязательны ×3 повтора и медиана; на границе шума сохраняется
  старое значение (консервативное правило выше).
- **Расхождение README и дефолтов**: шаги 3–5 исполняются одним коммитом; частичная
  правка запрещена триггером `readme-writing`.
- **Сдвиг поведения CLI**: принятые глубины меняют значение `-precompute-depth` по
  умолчанию — это ожидаемое изменение (ADR-016, «Последствия»).
