# План 01. Плоская таблица классов вместо Go-map (память аккумулятора M)

## Статус

**Закрыт 2026-09-14: мёртв вместе с class mode (ADR-016).** Аккумулятор M второго финала,
`dfsEmit`, `ShapeCtx`, `CountShape`, `groupSorted` удалены — Stage 2 нечего точить, Этап 0
не проводился. Все числа файла — class-mode стенд, для живого конвейера не применимы.
Идея плотной раскладки выживает лишь как спящий рычаг task-cache (помечен в статусе
плана 08); её возрождение требует нового плана с reversal-базой, а не реанимации этого.

Пересмотр предпосылки (проверка `go.mod`): стенд измерялся на Go ≥1.25, т.е.
хранилище уже на **Swiss-map** (она с Go 1.24). Оценка «~50 Б/запись» —
арифметика старой bucket-реализации (`hmap`/`bmap`), к Swiss-map неприменима:
открытая адресация, группы по 16 слотов с SIMD-метаданными, load factor до
~93%, инлайн pointer-free слоты (у `path.Path→uint64` нет указателей — GC их
не сканирует). Честная оценка: slot 16+8 Б + байт метаданных ÷ 0.93 ≈
**27–28 Б/запись**, а не 50. Ожидаемый выигрыш своей SoA-таблицы при честном
load factor линейной пробировки (~0.75): (8+1+8)/0.75 ≈ 23 Б/запись — **×1.2,
а не ×2.5–3**. Stage 1 понижён до «под вопросом»: сначала Этап 0 ниже.
Главные потребители пика 23.46 ГБ, вероятно, не бакеты, а пики удвоений,
второй живой набор при drain и DP-мемо воркеров — требует проверки.

## Базовые числа (для проверки эффекта)

Один и тот же стенд (Apple M4 Max, 14 ядер), доска 7×7, `-precompute-depth 22`,
class mode против старого reversal из git `0d142f4`:

| метрика | class mode | reversal (git) |
|---|---|---|
| время прогона | 596 с | 252 с |
| пик RSS (`/usr/bin/time -l`) | **23.46 ГБ** | 9.60 ГБ |
| gen B | 224.6 с, writes 3 591 773 354 | 141 с, writes 1 397 913 888 |
| counting | 371 с | 107.9 с |
| записей в хранилище | 284 359 145 классов | 131 814 325 задач |

Дерево поиска идентично (разбивка прунинга gen B совпадает счёт в счёт), поэтому весь
разрыв — ключи, хранилище и финальный проход.

## Гипотеза

Измеренный пик объясняют представлением M: `map[path.Path]uint64` (16-байтный ключ),
плоские срезы при `DrainShard` в финальном проходе и DP-мемо воркеров. Первичная
оценка карты «~50 Б/запись» на Go ≥1.24 несостоятельна (см. «Статус»): Swiss-map
стоит ~27–28 Б/запись для данной пары типов, т.е. 284M записей → ~7.6 ГБ, а не 14.
Что занимает остальные гигабайты — предмет Этапа 0.

Открытая адресация с ключом, разложенным по массивам (`keys []state.State`,
`ends []uint8`, `vals []uint64`, `stamps []uint32`), укладывает запись в ~17–21 Б;
против Swiss-map это **×1.2**, а не ×2.5–3, и выкупается только попутными
свойствами: штампы вместо очистки (тот же приём, что в `shapecount.memoTable`),
управляемый рост без пиков удвоения, упаковка. Реализуется **только при
подтверждении Этапом 0**.

Основной носитель выигрыша — **Stage 2** (сокращение ЧИСЛА записей в 2.57 раза),
ортогональный выбору хранилища и одинаково работающий поверх нативного map:
`map[state.State]uint32` → арена пар `(end, weight)` вместо своей таблицы.

Второй эффект — не память, а число эмиссий: `searcher.dfsEmit` (searcher/searcher.go:95)
пишет на листе по ключу на каждый `u ∈ N(t) ∩ U`, средний fan-out 2.57. Если хранить
весы концов формы вместе (Stage 2), записей становится в 2.57 раза меньше, а gen B
получает столько же единиц работы, сколько было у reversal-варианта.

## Этап 0 — проверка предпосылки Stage 1 (прежде чем что-то строить)

1. Микробенч пакета `cache`: вставка ~100M ключей реального распределения (дамп
   6×6 d13 из инфраструктуры плана 02) — нативный `map[path.Path]uint64` против
   прототипа SoA-таблицы; метрики: пик RSS, Б/запись, throughput.
2. Разложить пик реального прогона по потребителям (инфраструктура плана 05:
   `totalAllocMB/op`, peak RSS; точки 6×6 d13/d18): сколько дают map M, удвоения,
   срез `DrainShard`, DP-мемо воркеров.
3. **Порог включения Stage 1:** измеренное преимущество по памяти ≥ 1.7× при
   регрессе скорости ≤ 5% на всём свипе. Иначе Stage 1 закрывается с выводом в
   этом файле, Stage 2 реализуется поверх нативной Swiss-map.

## Дизайн

### Stage 1 — плоская таблица, ключ прежний `(state, end)` (условный: только по итогам Этапа 0)

1. Новый тип `cache.flatShard` вместо `accShard{data map[path.Path]uint64}`:
   - массивы `states []state.State`, `ends []uint8`, `weights []uint64`,
     `stamps []uint32`, счётчик занятых `n`, поколение `gen`;
   - хэш — существующий мультипликативный по `State` (важно: **только по `State`**,
     инвариант «все концы одной формы в одном шарде» из specs/cache.md обязан
     сохраниться, на нём держится группировка финального прохода без глобальной
     сортировки);
   - `Add(state, end, weight)` — поиск с линейной пробировкой и сложением веса при
     совпадении ключа; рост при `n*2 >= cap` (rehash c перестановкой в новое поколение);
   - начальный размер шарда — из эвристики по числу задач генерации, чтобы не
     проходить через серию удвоений (сейчас Go-map растёт сам и это стоит пика).
2. `DrainShard(i)` возвращает плоский срез записей (`[]Entry`), карта/массивы
   освобождаются сразу — текущее поведение карты нужно сохранить по семантике,
   но без второго живого представления.
3. `LocalSink` остаётся: локальный буфер схлопывает дубликаты до захвата лока; его
   внутреннее представление тоже переводится на плоскую карту (или остаётся map —
   решить по профилю, он мал).
4. Публичный API (`Add`, `Local`, `DrainShard`, `Drain`, `ItemsCount`, `NumShards`) не
   меняется → `counter` и `searcher` правятся минимально (только конструкторы/вызовы).

### Stage 2 — shape-major: одна запись на форму + вектор весов по концам

Требует, потому что веса разных концов одной формы **различаются** (их приносят разные
листья), поэтому «битовая маска концов» без весов некорректна.

1. Значение шарда — `(ends []uint8, weights []uint64)` при одном `state`:
   добавление ищет конец в маленьком массиве (длина ≈ 2.5, линейно).
2. `dfsEmit` делает **одну** эмиссию на лист: подготовленный `ShapeCtx` уже есть,
   концы — биты `cand`, веса одинаковы внутри листа.
3. Финальный проход: запись формы = `(shape, ends, weights)`, задача shape'а не
   меняется; `CountShape` возвращает `h` по концам, в контрибуции
   `Σ h[k]·weights[k]` (counter/counter.go:296 уже суммирует по концам).
4. `groupSorted` упрощается: группировка по `State` превращается в «одна запись —
   одна форма», сортировка внутри шарда остаётся только для порядка LPT по числу
   концов.

## Риски

- **Отклонённая альтернатива — sync.Map.** Профиль workload — аддитивные апдейты
  горячих общих ключей (`writesB` ~3.6G): atomic-add у sync.Map нет (нужен CAS-цикл
  вокруг Load/Store, аллокация entry на каждый Store), указателеструктурная природа
  даёт GC-скан миллионов живых записей, контракт `DrainShard` (все концы формы в
  одном шарде, draining без общего снапшота) невыразим без глобальной остановки.
  Текущая схема «шарды + LocalSink» остаётся; зафиксировать отказ и в specs/cache.md.
- **Кластеринг при плохом хэше.** Ключи — маски дополнений, старшие биты могут быть
  почти постоянны; нужен тест распределения на реальных ключах и, при необходимости,
  перемешивание (`splitmix64`) перед взятием маски бакета.
- **Пики при росте.** Удвоение открытой таблицы на 284M записей кратковременно
  держит две таблицы: стартовать с оценки размера (по `ItemsCount` прошлых прогонов
  либо по числу эмиссий), расти арифметически, а не геометрически после порога.
- **Регресс скорости на малых досках.** Swiss-map оптимизирована (SIMD-метаданные,
  load factor ~93%); на 5×5/6×6 таблица мала и своя версия может оказаться медленнее
  — обязательна сравнительная таблица по всему свипу, не только по 7×7.
- **Stage 2 меняет контракт `CountShape`.** Тесты shapecount (инвариантность к D4 и
  трансляциям, нули вне формы) должны пережить перенос весов без ослабления проверок.
