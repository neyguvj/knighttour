# План 01. Плоская таблица классов вместо Go-map (память аккумулятора M)

## Статус

**Закрыт 2026-09-14: мёртв вместе с class mode (ADR-016).** Классовый режим (`class`) — прежняя схема подсчёта по классам форм; после её удаления единственным конвейером остался reversal, счёт через обращение тура. Удалены аккумулятор M второго финала и всё его окружение: `dfsEmit`, `ShapeCtx`, `CountShape`, `groupSorted`. Для Stage 2 точить нечего, Этап 0 так и не проводился. Все числа этого файла сняты на стенде классового режима; к живому конвейеру они неприменимы.

Идея плотной раскладки остаётся лишь отложенным резервом task-cache — она помечена в статусе плана 08. Её возрождение требует нового плана с базой на режиме reversal, а не реанимации этого документа.

Пересмотр предпосылки по проверке `go.mod`: стенд измерялся на Go ≥1.25, то есть хранилище уже работало на **Swiss-map** (она действует с Go 1.24). Оценка «~50 Б/запись» — арифметика старой реализации карты (`hmap`/`bmap`), к Swiss-map она неприменима. Swiss-map использует открытую адресацию: группы по 16 слотов снабжены SIMD-метаданными, коэффициент заполнения доходит до ~93%. Слоты без указателей лежат в самом массиве: пара `path.Path→uint64` не содержит указателей, и сборщик мусора её не сканирует. Честный подсчёт даёт слот 16+8 Б + байт метаданных ÷ 0.93 ≈ **27–28 Б/запись**, а не 50. Собственная таблица с раскладкой «отдельный массив на каждое поле» при честном коэффициенте заполнения линейной пробировки (~0.75) дала бы (8+1+8)/0.75 ≈ 23 Б/запись — это **×1.2, а не ×2.5–3**. Поэтому Stage 1 понижен в статусе до «под вопросом»: сначала выполняется Этап 0 ниже. Главными потребителями пика 23.46 ГБ, вероятно, были не бакеты карты, а пики удвоений, второй живой набор при вычитывании (`DrainShard`) и таблицы мемоизации воркеров — это требует проверки.

## Базовые числа (для проверки эффекта)

Замеры сняты на одном и том же стенде (Apple M4 Max, 14 ядер) для доски 7×7 с `-precompute-depth 22`: классовый режим против старого режима reversal из коммита git `0d142f4`.

| метрика | class mode | reversal (git) |
|---|---|---|
| время прогона | 596 с | 252 с |
| пик RSS (`/usr/bin/time -l`) | **23.46 ГБ** | 9.60 ГБ |
| gen B | 224.6 с, writes 3 591 773 354 | 141 с, writes 1 397 913 888 |
| counting | 371 с | 107.9 с |
| записей в хранилище | 284 359 145 классов | 131 814 325 задач |

Дерево поиска идентично: разбивка отсечений gen B совпадает счёт в счёт. Поэтому весь разрыв создают ключи, хранилище и финальный проход.

## Гипотеза

Гипотеза того времени: измеренный пик объясняет представление аккумулятора M — `map[path.Path]uint64` с 16-байтным ключом, плоские срезы при `DrainShard` в финальном проходе и таблицы мемоизации воркеров. Первичная оценка карты «~50 Б/запись» для Go ≥1.24 несостоятельна (см. «Статус»): Swiss-map стоит ~27–28 Б/запись для данной пары типов, то есть 284M записей потянули бы ~7.6 ГБ, а не 14. Что занимает остальные гигабайты — предмет Этапа 0.

План предполагал открытую адресацию с ключом, разложенным по массивам (`keys []state.State`, `ends []uint8`, `vals []uint64`, `stamps []uint32`). Такая раскладка укладывает запись в ~17–21 Б; против Swiss-map это **×1.2**, а не ×2.5–3. Выкупаться план мог только попутными свойствами: штампы вместо очистки (тот же приём, что в `shapecount.memoTable`), управляемый рост без пиков удвоения и упаковка. Реализация допускалась **только при подтверждении Этапом 0**.

Главным источником выигрыша считался **Stage 2**: он сокращает число записей в 2.57 раза. Он не зависит от выбора хранилища и одинаково работает поверх нативной `map`: значение `map[state.State]uint32` заменяется ареной пар `(end, weight)` вместо собственной таблицы.

Второй эффект касался не памяти, а числа записей в таблицу: `searcher.dfsEmit` (searcher/searcher.go:95) писал на листе по записи на каждый `u ∈ N(t) ∩ U`, среднее число таких записей — 2.57. Если хранить веса всех концов формы вместе (Stage 2), записей станет в 2.57 раза меньше, и gen B получит столько же единиц работы, сколько было у варианта reversal.

## Этап 0 — проверка предпосылки Stage 1 (прежде чем что-то строить)

1. Микроизмерение пакета `cache`: вставка ~100M ключей реального распределения (дамп 6×6 d13 из инфраструктуры плана 02); нативная `map[path.Path]uint64` сравнивается с прототипом таблицы с раскладкой по полям. Метрики: пик RSS, Б/запись и пропускная способность.
2. Разложить пик реального прогона по потребителям (инфраструктура плана 05: `totalAllocMB/op`, peak RSS; точки 6×6 d13/d18): сколько дают карта M, удвоения, срез `DrainShard` и таблицы мемоизации воркеров.
3. **Порог включения Stage 1:** измеренное преимущество по памяти ≥ 1.7× при регрессе скорости ≤ 5% на всех точках прогона по глубинам. Иначе Stage 1 закрывается с выводом в этом файле, а Stage 2 реализуется поверх нативной Swiss-map.

## Дизайн

### Stage 1 — плоская таблица, ключ прежний `(state, end)` (условный: только по итогам Этапа 0)

1. Новый тип `cache.flatShard` вместо `accShard{data map[path.Path]uint64}`:
   - массивы `states []state.State`, `ends []uint8`, `weights []uint64`,
     `stamps []uint32`, счётчик занятых `n`, поколение `gen`;
   - хэш — существующий мультипликативный, и важно: **только по `State`**. Инвариант specs/cache.md «все концы одной формы в одном шарде» обязан сохраниться. На нём держится группировка финального прохода без глобальной сортировки;
   - `Add(state, end, weight)` ищет слот линейной пробировкой и складывает вес при совпадении ключа; рост происходит при `n*2 >= cap` с повторным хешированием в новое поколение;
   - начальный размер шарда задаётся эвристикой по числу задач генерации, чтобы не проходить через серию удвоений. Сейчас `map` растёт сама, и именно это стоит пика.
2. `DrainShard(i)` возвращает плоский срез записей (`[]Entry`), а карта и массивы освобождаются сразу. Семантику текущего поведения карты нужно сохранить, но без второго живого представления.
3. `LocalSink` остаётся: локальный буфер объединяет повторяющиеся ключи ещё до захвата блокировки. Его внутреннее представление тоже переводится на плоскую карту либо остаётся `map` — это решается по профилю, буфер мал.
4. Публичный API (`Add`, `Local`, `DrainShard`, `Drain`, `ItemsCount`, `NumShards`) не меняется, поэтому `counter` и `searcher` правятся минимально: только конструкторы и вызовы.

### Stage 2 — хранение по формам: одна запись на форму и вектор весов по концам

Stage 2 нужен потому, что веса разных концов одной формы **различаются**: их приносят разные листья. Поэтому битовая маска концов без весов дала бы некорректный счёт.

1. Значением шарда становятся `(ends []uint8, weights []uint64)` при одном `state`; добавление ищет конец линейным проходом по маленькому массиву (длина ≈ 2.5).
2. `dfsEmit` делает на листе **одну** запись: подготовленный `ShapeCtx` уже готов, концы — это биты `cand`, а веса внутри листа одинаковы.
3. В финальном проходе запись формы — это `(shape, ends, weights)`, и принадлежность задачи форме не меняется. `CountShape` возвращает `h` по концам, а вклад задачи равен `Σ h[k]·weights[k]`; counter/counter.go:296 уже суммирует по концам.
4. `groupSorted` упрощается: группировка по `State` сводится к тому, что одной форме соответствует одна запись. Сортировка внутри шарда остаётся только для порядка LPT по числу концов.

## Риски

- **Отклонённая альтернатива — `sync.Map`.** Профиль нагрузки — аддитивные обновления горячих общих ключей (`writesB` ~3.6G). Операции атомарного сложения у `sync.Map` нет: потребовался бы цикл атомарного сравнения и обмена вокруг `Load`/`Store`, и каждый `Store` аллоцировал бы запись. Карта хранит данные по указателям, поэтому сборщик мусора сканировал бы миллионы живых записей. Контракт `DrainShard` (все концы формы в одном шарде, вычитывание без общего снимка) было бы невыразим без глобальной остановки. Текущая схема «шарды + `LocalSink`» остаётся; отказ зафиксировать и в specs/cache.md.
- **Скопление записей при плохом хэше.** Ключи — маски дополнений, и старшие биты могут быть почти постоянными. Нужен тест распределения на реальных ключах; при необходимости добавляется перемешивание (`splitmix64`) перед вычислением индекса слота.
- **Пики при росте.** Удвоение открытой таблицы на 284M записей кратковременно держит две таблицы сразу. Поэтому стартовать нужно с оценки размера (по `ItemsCount` прошлых прогонов либо по числу записей в таблицу), а после порога расти арифметически, а не геометрически.
- **Регресс скорости на малых досках.** Swiss-map сильно оптимизирована: SIMD-метаданные и коэффициент заполнения ~93%. На 5×5/6×6 таблица мала, и своя версия может оказаться медленнее. Сравнительная таблица обязательна по всем точкам прогона, а не только по 7×7.
- **Stage 2 меняет контракт `CountShape`.** Тесты shapecount — инвариантность к D4 и трансляциям, нули вне формы — должны пережить перенос весов без ослабления проверок.
