# План 17. Единый переиспользуемый пул воркеров: пакет `workerpool` поверх трёх фаз counter

## Статус

Закрыт: принят (WIN) — реализован и смержен в main, числа гейта в ADR-033.
Предыдущая попытка той же идеи на устаревшей базе отменена целиком — её дизайн не наследуется.

## Мотивация и базовые числа

Логика многопоточности реализована в `counter/counter.go` трижды, каждый раз по-своему:

1. **gen A** (`generateIntermediate`) — `errgroup.WithContext` + `SetLimit(workers)`, по `g.Go` на
   стартовую группу; ~10 задач, фаза µs–ms.
2. **gen B** (`extendTasks`) — `errgroup.WithContext` + `min(len(entries), workers)` горутин с
   внутренним циклом: атомарный курсор `nextEntry.Add(1)` (претензия на порядки дешевле числа
   задач — ADR-031) + собственный `cache.Staging` на воркера с deferred `Flush`.
3. **counting** (`countTasks`) — ручной `sync.WaitGroup` + zero-alloc `chan entryBatch`
   (392 Б/слот, whole-slot backpressure, FIFO, одна канальная операция на `Beff` записей — ADR-032).

Три написанных вручную барьера и две вариации «команда горутин + ctx + ожидание» — дублирование
механики при том, что доменных ошибок на этом пути нет (`searcher` возвращает `Result`, все
`return nil`/`_ = g.Wait()` константны). Цель — вынести механику «фиксированная команда воркеров,
пропагация ctx, барьер Wait» в отдельный пакет, оставив каждой фазе её **измеренную** доставку
работы. Это рефакторинг без смены поведения: ни ускорения, ни сокращения аллокаций заявляем —
гейт только на паритет и бит-идентичность.

База чисел — локальный main `3c6546d` (ADR-032 в базе; origin/main отстаёт и не база). Ожидаемая
полоса контроля (прогоны ветки ADR-032, тот же код): точка **7×7 d22, workers=14** — wall
**174.7–179.8 с**, `genB_ms` **108.3–112.1 с**, `cnt_ms` **66.4–67.7 с**, peak RSS ~5.1–5.3 ГБ,
allocs/op ≈ 92 860 1xx. Свежий контроль main ×2 перед веткой обязателен (дневной дрейф — прецеденты
планов 13/15/16). Бит-эталоны: итог **165 575 218 320**; hits/misses counting
**364 804 607 / 1 584 519 460**; `writesB` 942 644 146; `prunedL2B` 455 269 742; `taskEntries`
92 315 032 (ADR-032 §Корректность).

## Идея / Гипотеза

Механика «N горутин + ctx + барьер» сворачивается в два примитива пакета `workerpool` —
претензию индексов атомарным курсором (`Run`) и fan-out поверх буферизованного канала (`Fanout`) —
при том что **все три фазы проходят через них без изменения наблюдаемого поведения**: бит-гейты
итогов побитово идентичны, а `cnt_ms`/`genB_ms`/wall ветки — в полосе свежего контроля main или
лучше (гипотеза паритетная; ускорение не заявляется).

## Корректность

- **Итог не меняется**: фазы сохраняют свои функции работы и порядок суммирования (`atomic.Uint64`,
  коммутативность сложения весов); расписание (какая горутина какую задачу/индекс берёт) итога не
  касается — тот же инвариант, что закрепляет тест инвариантности к числу воркеров.
- **От error-обвязки отказываемся осознанно**: на всём пути ошибок нет (все `g.Go` возвращают nil,
  `Wait` игнорируется), errgroup-семантика «первая ошибка отменяет остальных» неиспользуема;
  dead-code-правило AGENTS запрещает «на будущее». Следствие — пакет `golang.org/x/sync`
  исключается из `go.mod` (других потребителей в репозитории нет, проверено grep'ом).
- **Отказ от производного ctx эквивалентен**: сегодня `errgroup.WithContext` создаёт `gctx`,
  отменяемый на Wait; наблюдателем отмены он стать не может — к моменту Wait все воркеры уже
  завершены барьером, ошибок нет. Пул передаёт воркерам родительский `ctx` как есть; семантика
  частичного прогона (завершившийся ctx → досрочный выход фазы без паники) обеспечивается тем же,
  чем сейчас: проверкой ctx в цикле претензий и внутри `countOneTask`.
- **Проверка ctx до претензии вместо после**: текущий gen B снимает индекс и лишь затем смотрит ctx
  (снятый неотработанный индекс бесследно теряется). Пул проверяет ctx **до** снятия — курсор
  отличается значением, число обработанных задач и частичный итог те же (претензия side-effect-free).
- **Fanout сохраняет канальный контракт ADR-032 дословно**: буфер ≥ 1 слота; продюсер блокируется
  только на отправке до целого свободного слота; консьюмеры ничего не ждут от продюсера и всегда
  дренируют до `close` — дедлок исключён той же аргументацией. Отмена: `produce` завершается сам
  (обход `All` встаёт на границе шардов), канал закрывается, консьюмеры дренируют буфер без подсчёта
  (`ctx.Err()`-пропуск в `countOneTask`) — частичный итог без паники.
- **Каждая запись доставляется ровно один раз**: обход `View.All` остаётся единственным продюсером,
  `close` — после его возврата; инвариант переезжает из `countTasks` в контракт `Fanout` и
  покрывается тестом пакета.

## Дизайн

Новый пакет **`workerpool`** (дженерик-механика, ничего не знает о cache/counter/мониторе):

```go
// Pool — конфигурация команды воркеров (workers ≥ 1 — контракт вызывающей стороны,
// в main.go валидируется). Горутин живут внутри одного вызова метода; состояние
// между вызовами — только число воркеров.
type Pool struct{ workers int }

func New(workers int) *Pool

// Run запускает min(workers, max(n,0)) горутин-воркеров и ждёт их (барьер).
// Каждый воркер крутит цикл претензий над idx — бесконечным итератором индексов
// 0..n-1, снимаемых атомарным курсором (один Add(1) на задачу); итерация
// прекращается, когда работа кончилась или ctx завершён (проверка до снятия).
// Тело воркера отделено от тела задачи: per-worker инициализация/завершение
// (например батч-писатель с deferred Flush) живёт в worker вокруг цикла.
func (p *Pool) Run(ctx context.Context, n int, worker func(ctx context.Context, idx iter.Seq[int]))

// Fanout — продюсер→консьюмеры поверх одного буферизованного канала: consumers
// горутин дренируют канал до close; produce вызывается в горутине вызывающего
// сразу после старта консьюмеров; по возврату produce канал закрывается, Fanout
// ждёт завершения консьюмеров. Число консьюмеров — параметр (фазовый clamp
// max(min(workers, records), 1) считает вызывающий). Контракт отсутствия дедлока:
// produce блокируется только на отправке; consume ничего не ждёт от produce и
// всегда дренирует до close. Пакет не создаёт производных контекстов — семантика
// отмены в produce/consume.
func (p *Pool) Fanout[T any](ctx context.Context, consumers, bufSize int,
    produce func(ctx context.Context, out chan<- T),
    consume func(ctx context.Context, batch T))
```

**Покрытие фаз (механика доставки каждой — своя, измеренная):**

- **gen A** → `Run`: `n = len(groups)`; тело воркера — прежний цикл по `idx` с
  `searcher.GenerateTasks(ctx, intermediate, ...)` + отчёты монитора. Конкурентный потолок тот же
  (`min(workers, n)` против `SetLimit(workers)`), `gctx` заменяется на ctx (см. Корректность).
- **gen B** → `Run`: `n = len(intermediate)`; тело воркера — создание `taskCache.NewStaging(...)`,
  deferred `Flush`, цикл по `idx` с прежним телом задачи. Атомарный курсор — ровно нынешний
  `Add(1)`-механизм (ADR-031), Staging — per-worker и закрывается на всех путях выхода.
- **counting** → `Fanout[entryBatch]`: `consumers`/`bufSize = ⌈capacity/Beff⌉` считает counter;
  `produce` = нынешняя `dispatchEntries` (единственный обход `view.All`, батчи по `Beff`, whole-slot
  backpressure, хвост при живом ctx); `consume` = тело нынешнего `for b := range ch`: по записям
  батча — `countOneTask` вне любых залов. `entryBatch` остаётся типом counter (в нём `cache.Entry` и
  потолок B); пул параметризован им конкретно — **никаких `any`/интерфейсов на горячей границе**.

**Граница ответственности**: ручки и формулы фазы (`K=10000`, `B=16`, `C=4`, `effectiveBatch`,
clamp консьюмеров, `capacityPerConsumer` — тестовая ручка) остаются в `counter` (фазовая политика);
пул владеет только механикой (спавн, курсор, канал+close, барьер). Публичный API `counter` не меняется.

## Аллокационный бюджет

Новых структур на горячем пути нет; всё добавляемое — на старте фазы:

- `Pool` — 8 Б × 1 конвейер; курсор `atomic.Int64` — 8 Б × 1 вызов `Run`; замыкания worker/итератора
  — O(1) на воркера (порядка сотни байт × workers), по одному за вызов.
- `Fanout`: буфер канала — та же единственная аллокация фазы `⌈capacity/Beff⌉ × 392 Б`
  (формула и значение не меняются; `make` переезжает в пул), ноль аллокаций на запись/батч —
  конкретная instantiation `T = entryBatch`, копия в слот hchan как сегодня.
- Ожидание по allocs/op: дельта против контроля — O(workers) единиц (замыкания), т.е. шум против
  ~92.86M; рост аллокаций **на запись** — ровно ноль. Копий таблицы/снимков не появляется
  (механика эталона ADR-013/032 сохранена: один обход живых map, доставка батчами).

## Шаги

1. План (этот файл) — до кода.
2. **Спеки до кода (G12)**, отдельным коммитом: создать `specs/workerpool.md` (ответственность,
   API+контракты Run/Fanout, инварианты отсутствия дедлока и exact-once, edge cases, тесты);
   правка `specs/counter.md` (§фазы — механика через примитивы пула, формулы/ручки те же; «Связанные»);
   строки `specs/README.md` (компоненты + «Все фазы параллельны…»); §Project Structure `AGENTS.md`.
3. Реализация пакета `workerpool` + юнит-тесты (`-race`, синтетические, без зависимостей):
   Run — clamp `min(workers,n)`, `n ≤ 0` (ноль горутин), каждый индекс ровно один раз при конкурентном
   съёме, завершившийся ctx (отмена/дедлайн) — досрочный выход без паники и без повторной обработки,
   барьер Wait; Fanout — exact-once доставка, принудительный backpressure (bufSize = 1 слот) без
   дедлока, завершение produce → close → дренаж, ранняя отмена ctx в produce.
4. Перешивка `counter/counter.go`: `generateIntermediate`/`extendTasks` → `Run`, `countTasks` →
   `Fanout[entryBatch]`; удалить импорт `errgroup`, ручной `WaitGroup` и цикл-обвязку; из `go.mod`/`go.sum`
   — `golang.org/x/sync`. Тесты counter не меняются по смыслу (публичный API + внутренние ручки
   `effectiveBatch`/`capacityPerConsumer` сохранены); существующие тесты диспатча (exact-once,
   форсированный overflow, отмена → частичный итог) проходят как были.
5. `make check` зелёно на каждом коммите кода.
6. Бенч-гейт (ниже): контроль main ×2 + ветка ×3 чередованием, 7×7 d22, flock `../kt-bench.lock`,
   отдельные процессы; затем сани́ти-прогон `make bench` (5×5/6×6) control vs ветка.
7. Вердикт: паритет взят → **ADR-033** с числами навсегда + строка в индекс + фактические спеки
   (`workerpool.md`, `counter.md`) + squash-merge; регресс вне полосы → план закрыть с числами,
   ветку не мержить (docs-only). README-витрину не трогать (триггеры readme-writing не горят:
   CLI, структура конвейера и вердикты дефолтов те же).

## Метрики успеха

| метрика | база (свежий контроль main ×2) | цель / порог принятия |
|---|---|---|
| итог 7×7 | 165 575 218 320 | побитово — жёстко, все прогоны |
| hits/misses counting | 364 804 607 / 1 584 519 460 | побитово — жёстко |
| `writesB`, `prunedL2B`, `taskEntries` | 942 644 146 / 455 269 742 / 92 315 032 | побитово — жёстко |
| `cnt_ms` 7×7 d22, workers=14 | полоса контроля (ожидание ~66–68 с) | средний ветки **в полосе повторов контроля или лучше**; вне полосы только в минус |
| `genB_ms`, wall | полоса контроля (~108–112 / ~175–180 с) | то же (паритет; гипотеза не про ускорение) |
| peak RSS, totalAlloc | полоса контроля | в полосе (новых структур на горячем пути нет) |
| allocs/op | ≈ 92.86M | рост ≤ O(workers) единиц (замыкания пула); ноль новых аллокаций на запись/батч |
| `make bench` 5×5/6×6 | main control | ни одна глубина не выбивается за шум повторов (~±2%) |
| `make check` (fmt/vet/-race/lint) | зелёно | зелёно — жёстко |

Принцип решения — полный гейт методологии ADR-019/032 относительно main; «рефакторинг дороже
шума» = отклонение, флага для включения старого пути нет и не заводится (ADR-021).

## Риски

- **Разрыв измеренных оптимизаций ADR-031/032** — главный риск. Митигция — список «что не меняется»,
  против которого reviewer сверяет diff: атомарная претензия `Add(1)` на задачу (не канал и не семафор);
  per-worker Staging с deferred Flush на всех путях; элемент канала — конкретный `entryBatch` 392 Б,
  батч-доставка `Beff`, whole-slot backpressure без partial-fill; единственный продюсер `View.All`;
  FIFO; формулы буфера/батча и clamp консьюмеров в counter; отсутствие новых залов/атомиков на пути
  задачи. Любая «унификация» доставки до per-record или через `any` — BLOCKER (урок плана 11:
  per-record канал стоил +14.5%).
- **Скрытая смена семантики errgroup** (отмена производного ctx, error-борн барьер) — зафиксирована в
  Корректности как ненаблюдаемая; ревьюитер проверяет отсутствие потребителей `gctx` после барьера.
- **Ген A: перестановка per-group `g.Go` на claim-loop** — результат порядково-независим, фаза
  1.3–1.7 мс (шум `genA_ms`); альтернатива «оставить errgroup для gen A» убивает цель единого пула.
- **Дженерик-инстанцирование** — одна instantiation на фазу, compile-time; рантайм-эквивалентность
  подтверждает гейт allocs/op.
- **G12 (спеки до кода)**: спека `workerpool.md` коммитится раньше пакета.
- Откат = не мержить feature-ветку (ADR-021); переключателя в коде нет.
