# План 17. Единый переиспользуемый пул воркеров: пакет `workerpool` поверх трёх фаз counter

## Статус

Закрыт: принят (WIN) — реализован и влит в main, числа порога принятия зафиксированы в **ADR-033**.
Предыдущая попытка той же идеи на устаревшей базе отменена целиком; её дизайн не наследуется.

## Мотивация и базовые числа

Логика многопоточности реализована в `counter/counter.go` трижды, каждый раз по-своему:

1. **gen A** (`generateIntermediate`) — `errgroup.WithContext` + `SetLimit(workers)`, по одному `g.Go`
   на стартовую группу; задач ~10, длительность фазы µs–ms.
2. **gen B** (`extendTasks`) — `errgroup.WithContext` + `min(len(entries), workers)` горутин с
   внутренним циклом. Цикл выдаёт индексы через атомарный счётчик `nextEntry.Add(1)`: снятие индекса
   на порядки дешевле исполнения задачи (ADR-031); у каждого воркера собственный `cache.Staging` с
   отложенным `Flush` на выходе.
3. **count-фаза** (`countTasks`) — ручной `sync.WaitGroup` и канал `chan entryBatch` без аллокаций:
   392 Б на слот, противодавление канала с ожиданием целого слота, порядок FIFO, одна канальная
   операция на `Beff` записей (ADR-032).

Три написанных вручную барьера и две вариации «команда горутин с ctx и ожиданием» дублируют
механику, хотя доменных ошибок на этом пути нет: `searcher` возвращает `Result`, а все `return nil`
и `_ = g.Wait()` константны. Цель — вынести механику «фиксированная команда воркеров с передачей
ctx и барьером Wait» в отдельный пакет; каждой фазе остаётся её измеренная доставка работы. Это
рефакторинг без смены поведения: ни ускорения, ни сокращения аллокаций не заявляем, порог принятия
— только паритет и побитовая идентичность.

База чисел — локальный main `3c6546d`: ADR-032 уже входит в него, а `origin/main` отстаёт и базой
не является. Ожидаемая полоса контроля взята из прогонов ветки ADR-032 на том же коде. Точка
**7×7 d22, workers=14**: wall **174.7–179.8 с**, `genB_ms` **108.3–112.1 с**, `cnt_ms` **66.4–67.7 с**,
peak RSS ~5.1–5.3 ГБ, allocs/op ≈ 92 860 1xx. Свежий контроль main ×2 перед открытием ветки
обязателен: планы 13/15/16 оставляли прецеденты дневного дрейфа. Побитовые эталоны: итог
**165 575 218 320**; hits/misses count-фазы **364 804 607 / 1 584 519 460**; `writesB` 942 644 146;
`prunedL2B` 455 269 742; `taskEntries` 92 315 032 (ADR-032 §Корректность).

## Идея / Гипотеза

Механика «N горутин с ctx и барьером» сворачивается в два примитива пакета `workerpool`: выдачу
индексов воркерам через атомарный счётчик (`Run`) и разворачивание потока потребителей поверх
буферизованного канала (`Fanout`). Все три фазы проходят через них без изменения наблюдаемого
поведения. Гипотеза паритетная: итоги побитово идентичны, а `cnt_ms`/`genB_ms`/wall ветки лежат в
полосе свежего контроля main или лучше; ускорение не заявляется.

## Корректность

- **Итог не меняется**: фазы сохраняют свои функции работы и порядок суммирования (`atomic.Uint64`,
  коммутативность сложения весов). Расписание — какая горутина какой индекс возьмёт — на итог не
  влияет; это тот же инвариант, который закрепляет тест независимости от числа воркеров.
- **От обвязки с ошибками отказываемся осознанно**: на всём пути ошибок нет (все `g.Go` возвращают
  nil, `Wait` игнорируется), поэтому семантика errgroup «первая ошибка отменяет остальных»
  неиспользуема. Правило мёртвого кода из AGENTS запрещает держать код «на будущее». Следствие —
  пакет `golang.org/x/sync` исключается из `go.mod`: других потребителей в репозитории нет, это
  проверено grep'ом.
- **Отказ от производного ctx эквивалентен**: сегодня `errgroup.WithContext` создаёт `gctx`,
  отменяемый на `Wait`, но наблюдателем отмены он стать не может — к моменту `Wait` барьер уже
  завершил всех воркеров, и ошибок нет. Пул передаёт воркерам родительский `ctx` как есть.
  Семантика частичного прогона (отменённый контекст — досрочный выход фазы без паники)
  обеспечивается тем же, чем и сейчас: проверкой `ctx` перед каждым снятием индекса и внутри
  `countOneTask`.
- **Проверка ctx до снятия индекса вместо проверки после**: нынешний gen B сначала снимает индекс
  и лишь затем смотрит на `ctx`, и снятый неотработанный индекс бесследно теряется. Пул проверяет
  `ctx` до снятия; счётчик при этом отличается значением, но число обработанных задач и частичный
  итог те же — снятие индекса не имеет побочных эффектов.
- **`Fanout` сохраняет канальный контракт ADR-032 дословно**: буфер не меньше одного слота;
  производитель блокируется только на отправке, дожидаясь целого свободного слота; потребители
  ничего не ждут от производителя и всегда дочитывают канал до `close`. Взаимоблокировка исключена
  той же аргументацией. При отмене `produce` завершается сам (обход `All` останавливается на
  границе шардов), канал закрывается, а потребители дочитывают буфер без подсчёта: внутри
  `countOneTask` пропуск задачи даёт проверка `ctx.Err()`. Частичный итог возвращается без паники.
- **Каждая запись доставляется ровно один раз**: обход `View.All` остаётся единственным
  производителем, а `close` наступает после его возврата. Инвариант переезжает из `countTasks` в
  контракт `Fanout` и покрывается тестом пакета.

## Дизайн

Новый пакет **`workerpool`** — дженерик-механика, которая ничего не знает о `cache`, `counter` и
мониторе:

```go
// Pool — конфигурация команды воркеров (workers ≥ 1 — контракт вызывающей стороны,
// в main.go валидируется). Горутин живут внутри одного вызова метода; состояние
// между вызовами — только число воркеров.
type Pool struct{ workers int }

func New(workers int) *Pool

// Run запускает min(workers, max(n,0)) горутин-воркеров и ждёт их (барьер).
// Каждый воркер крутит цикл снятия индексов над idx — бесконечным итератором
// индексов 0..n-1, выдаваемых атомарным счётчиком (один Add(1) на задачу); цикл
// прекращается, когда работа кончилась или ctx завершён (проверка до снятия).
// Тело воркера отделено от тела задачи: инициализация и завершение каждого воркера
// (например писатель партий с отложенным Flush) живут в worker вокруг цикла.
func (p *Pool) Run(ctx context.Context, n int, worker func(ctx context.Context, idx iter.Seq[int]))

// Fanout — доставка значений от производителя потребителям поверх одного буферизованного
// канала: consumers горутин дочитывают канал до close; produce вызывается на горутине
// вызывающего сразу после старта потребителей; по возврату produce канал закрывается, и
// Fanout ждёт завершения потребителей. Число потребителей — параметр (ограничение значения
// диапазоном для фазы, max(min(workers, records), 1), считает вызывающий). Контракт
// отсутствия взаимоблокировки: produce блокируется только на отправке; consume ничего не
// ждёт от produce и всегда дочитывает канал до close. Пакет не создаёт производных
// контекстов — семантика отмены живёт в produce/consume.
func (p *Pool) Fanout[T any](ctx context.Context, consumers, bufSize int,
    produce func(ctx context.Context, out chan<- T),
    consume func(ctx context.Context, batch T))
```

**Покрытие фаз**: каждая фаза сохраняет свою измеренную механику доставки.

- **gen A** → `Run`: `n = len(groups)`; тело воркера — прежний цикл по `idx` с
  `searcher.GenerateTasks(ctx, intermediate, ...)` и отчётами монитора. Потолок конкурентности тот
  же: `min(workers, n)` против прежнего `SetLimit(workers)`. `gctx` заменяется на ctx — обоснование
  в разделе «Корректность».
- **gen B** → `Run`: `n = len(intermediate)`; тело воркера создаёт `taskCache.NewStaging(...)`,
  регистрирует отложенный `Flush` и идёт по `idx` с прежним телом задачи. Атомарный счётчик — ровно
  нынешний механизм `Add(1)` (ADR-031); `Staging` у каждого воркера свой, и он закрывается на всех
  путях выхода.
- **count-фаза** → `Fanout[entryBatch]`: значения `consumers` и `bufSize = ⌈capacity/Beff⌉` считает
  `counter`. `produce` — нынешняя `dispatchEntries`: единственный обход `view.All`, партии по `Beff`,
  противодавление канала с ожиданием целого слота, хвостовая партия при живом ctx. `consume` — тело
  нынешнего `for b := range ch`: для каждой записи партии вызывается `countOneTask`, уже без каких-либо
  блокировок. `entryBatch` остаётся типом пакета `counter` (в нём лежат `cache.Entry` и потолок B);
  пул параметризован этим конкретным типом — никаких `any` и интерфейсов на горячей границе.

**Граница ответственности**: ручки и формулы фазы (`K=10000`, `B=16`, `C=4`, `effectiveBatch`,
ограничение числа потребителей диапазоном, `capacityPerConsumer` — тестовая ручка) остаются в
`counter`, потому что это фазовая политика. Пул владеет только механикой: запуск горутин, счётчик
индексов, канал с `close`, барьер ожидания. Публичный API `counter` не меняется.

## Аллокационный бюджет

Новых структур на горячем пути нет; всё добавляемое аллоцируется один раз на старте фазы:

- `Pool` занимает 8 Б × 1 конвейер. Счётчик индексов `atomic.Int64` занимает 8 Б × 1 вызов `Run`.
  Замыкания `worker` и итератора — O(1) на воркера, порядка сотни байт × workers, по одному за вызов.
- Буфер канала в `Fanout` — та же единственная аллокация фазы `⌈capacity/Beff⌉ × 392 Б`: формула и
  значение не меняются, переезжает только `make`. Аллокаций на запись или партию — ноль: это
  конкретная подстановка типа `T = entryBatch`, и копия в слот hchan лежит там же, где сегодня.
- Ожидание по `allocs/op`: дельта против контроля — O(workers) единиц (замыкания), то есть шум
  против ~92.86M; рост аллокаций на запись — ровно ноль. Копий таблицы или снимков не появляется:
  механика эталона ADR-013/032 сохранена — один обход живых map и доставка партиями.

## Шаги

1. План (этот файл) — до кода.
2. **Спеки до кода (G12)**, отдельным коммитом: создать `specs/workerpool.md` (ответственность,
   API и контракты `Run`/`Fanout`, инварианты отсутствия взаимоблокировки и доставки ровно один раз,
   edge cases, тесты); правка `specs/counter.md` — раздел о фазах описывает механику через примитивы
   пула, формулы и ручки те же, плюс раздел «Связанные»; строки `specs/README.md` (компоненты и
   «Все фазы параллельны…»); §Project Structure в `AGENTS.md`.
3. Реализация пакета `workerpool` и юнит-тестов (`-race`, синтетических, без зависимостей). Для
   `Run`: ограничение `min(workers,n)`, случай `n ≤ 0` (ноль горутин), каждый индекс ровно один раз
   при конкурентном съёме, уже отменённый ctx (отмена или дедлайн) — досрочный выход без паники и
   без повторной обработки, барьер `Wait`. Для `Fanout`: доставка ровно один раз, принудительное
   противодавление канала (`bufSize` = один слот) без взаимоблокировки, завершение `produce` →
   `close` → полное дочитывание буфера, ранняя отмена ctx в `produce`.
4. Перевод `counter/counter.go` на пул: `generateIntermediate`/`extendTasks` переходят на `Run`,
   `countTasks` — на `Fanout[entryBatch]`. Удаляются импорт `errgroup`, ручной `WaitGroup` и
   вспомогательные циклы-обвязки; из `go.mod`/`go.sum` уходит `golang.org/x/sync`. Тесты counter не
   меняются по смыслу: публичный API и внутренние ручки `effectiveBatch`/`capacityPerConsumer`
   сохранены, а существующие тесты раздачи (доставка ровно один раз, принудительное переполнение
   буфера, отмена → частичный итог) проходят без изменений.
5. `make check` зелёный на каждом коммите кода.
6. Бенч-проверка (метрики ниже): контроль main ×2 и ветка ×3 чередованием на 7×7 d22 под
   `flock ../kt-bench.lock`, каждая точка в отдельном процессе; затем короткий прогон `make bench`
   (5×5/6×6), сравнивающий контроль и ветку.
7. Вердикт: паритет взят — **ADR-033** с числами навсегда, строка в индекс, фактические спеки
   (`workerpool.md`, `counter.md`) и squash-merge. Регресс вне полосы — план закрывается с числами,
   ветка не мержится (переносится только документация). README-витрину не трогать: триггеры
   readme-writing не горят — CLI, структура конвейера и вердикты дефолтов те же.

## Риски

- **Разрыв измеренных оптимизаций ADR-031/032** — главный риск. Митигация — список «что не
  меняется», против которого reviewer сверяет diff: атомарное снятие индекса одним `Add(1)` на
  задачу, а не каналом и не семафором; у каждого воркера свой `Staging` с отложенным `Flush` на всех
  путях выхода; элемент канала — конкретный `entryBatch` на 392 Б; доставка партиями по `Beff` с
  ожиданием целого свободного слота без дозаписи остатка; единственный производитель — `View.All`;
  порядок FIFO; формулы буфера и партий и ограничение числа потребителей остаются в `counter`; на
  пути задачи не появляется новых блокировок и атомарных операций. Любая «унификация» доставки до
  одной записи или через `any` — blocker (урок плана 11: канал с доставкой по одной записи стоил
  +14.5%).
- **Скрытая смена семантики errgroup** (отмена производного ctx, барьер, переносящий ошибки) —
  зафиксирована в разделе «Корректность» как ненаблюдаемая; reviewer проверяет, что после барьера
  потребителей `gctx` не осталось.
- **gen A: замена отдельных `g.Go` по группам на цикл со снятием индексов.** Результат от порядка не
  зависит, а фаза идёт 1.3–1.7 мс — это шум метрики `genA_ms`. Альтернатива «оставить errgroup для
  gen A» убивает цель единого пула.
- **Подстановка типов дженериков** выполняется по одному разу на фазу и разрешается на этапе
  компиляции; эквивалентность в рантайме подтверждает метрика `allocs/op`.
- **G12 (спеки до кода)**: спека `workerpool.md` коммитится раньше пакета.
- Откат = не мержить feature-ветку (ADR-021); переключателя в коде нет.
