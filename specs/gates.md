# gates: жёсткие гейты агентского пайплайна (ADR-022)

## Ответственность

Превращает обязательные правила проекта в непроходимые проверки уровня инструмента — такие,
которые модель не может проигнорировать текстом ответа. Два слоя:

- **permission-конфиг** (`opencode.json` в корне, frontmatter агентов в `.opencode/agent/`) —
  декларативные `allow | ask | deny` по паттернам bash-команд и путей edit; `deny` не обходится
  даже в `--auto`;
- **plugin-хуки** (`.opencode/plugins/gates.ts`, `tool.execute.before`) — stateful-проверки,
  недоступные паттернам (состояние ветки, истории прогонов); намеренное исключение `GateError`
  блокирует вызов инструмента.

Гейт существует ровно в одном из двух слоёв; текст в AGENTS.md остаётся объяснением «зачем»,
а не механизмом.

## Слой permission: матчинг путей (ADR-026)

Паттерны permission компилируются в полностью анкорированный regex по всему subject'у
(`^…$`, флаг `s`): `*` → `.*` — любая последовательность символов (включая `/` и переводы строк),
`?` → `.`; совпадает вся строка целиком, вхождение подстрокой — нет; **last-match-wins**,
catch-all `"*"` ставится первым.
Разрешён `~/`/`$HOME/` в начале паттерна — раскрывается в абсолютный путь при загрузке конфига.

Форма subject'а зависит от разрешения (opencode 1.18):

- `edit` (покрывает `edit`/`write`/`apply_patch`) — **путь файла относительно корня проекта
  сессии** (`instance.worktree`). Файлы соседнего worktree выглядят как `../kt-*/…`;
  абсолютные и тильдовые паттерны под это разрешение не матчатся никогда (под subject-строку
  с `..` они бьются только литералом).
- `external_directory` — абсолютный glob `<родительский каталог>/*`; здесь `~/work/kt-*/**`
  из корневой `opencode.json` уместен и достаточен (G2).

Порядок правил для агента: встроенные дефолты → глобальный/проектный `opencode.json` →
frontmatter агента; последние выигрывают. Следствия:

- `"*": deny` во frontmatter не поднять allow'ем из `opencode.json` (он стоит левее) — ролевые
  исключения пишутся в том же frontmatter после catch-all;
- feature-worktree по контракту сосед main-дерева (`../kt-<NN>-<slug>`), поэтому запись агента
  в него открывается относительным паттерном `../kt-*/<ролевой каталог>/**`; запись в само
  основное дерево — относительным `specs/**`/`work/**` (сессия живёт в main, ADR-024);
- Совпадение — матчинг строк: permission не проверяет существование пути и не знает про
  «активность» worktree — stateful-часть остаётся за plugin-слоем (G8).

## Plugin-ядро (`.opencode/plugins/gates.ts`)

Единый модуль плагина opencode — точка подключения всех stateful-гейтов. opencode загружает
файлы из `.opencode/plugins/` автоматически при старте сервера.

Контракт ядра:

- Модуль экспортирует ровно одну функцию-плагин: `export const GatesPlugin: Plugin` (тип —
  `@opencode-ai/plugin`). Матчеры и хелперы не экспортируются: загрузчик считает каждую
  экспортированную функцию плагином.
- Ядро регистрирует по одному обработчику `tool.execute.before`, `tool.execute.after`,
  `command.execute.before` и `event` и диспетчирует вызовы по списку гейтов в порядке регистрации.
  Гейт — элемент списка формы:

  ```ts
  interface Gate {
    id: string                  // ID из реестра («G7»)
    before?(call): void         // наблюдение args до исполнения; может бросить GateError
    after?(call): void          // наблюдение результата (для утилит — фиксация успеха)
    onEvent?(event): void       // события шины opencode (например file.edited)
    onCommand?(invocation): void // запуск slash-команды {name, sessionID}, до первого хода модели
  }
  ```

- Намеренная блокировка — исключение `GateError` с текстом-инструкцией для модели; оно
  прекращает вызов инструмента (текст возвращается модели как ошибка инструмента).
  Неожиданное внутреннее исключение гейта логируется (`client.app.log`) и не влияет на вызов:
  fail-closed только для `GateError`, баг гейта — fail-open.
- Состояние гейтов — память процесса плагина: между серверами/перезапусками не разделяется.

Новый гейт = новый элемент списка + строка в реестре; ядро при этом не меняется.

## Гейт G7: make check перед git commit (ADR-023)

Пассивный трекинг «зелёного штампа»: плагин ничего не исполняет сам — он запоминает факт
успешного `make check` и требует штамп свежим к моменту `git commit`.

- **Штамп.** Источник: завершение команды `make check` в инструменте `bash` с положительным
  подтверждением exit code 0 из результата инструмента (без подтверждения — не ставится).
  Инвокация распознаётся токен-матчером по сегментам команды; допускаются флаги `make`,
  `-C <dir>`, env-префиксы. Exit-код относится ко всей строке: подтверждение действительно,
  только если после инвокации `make check` все оставшиеся разделители — `&&` (после `; | ||`
  и переводов строк код принадлежит более позднему сегменту — успех не подтверждён).
- **Инвалидация.** Штамп снимается вызовами инструментов `edit` / `write` / `patch`
  (в opencode ≥1.18 id патчера — `apply_patch`) и событием шины `file.edited`. Изменения файлов через `bash` штамп не снимают — зафиксированное
  ограничение v1.
- **Проверка.** Вызов `bash`, содержащий инвокацию `git commit` (токен-матчер: бинарь `git` +
  субкоманда `commit`; допускаются глобальные флаги `-C`, `-c k=v`, `--git-dir=…`, env-префиксы;
  команда режется по shell-разделителям `&& || ; |` и переводам строк, сегменты проверяются
  отдельно), без действующего штампа блокируется `GateError` с инструкцией: сначала выполнить
  `make check` и повторить коммит (или использовать самогейдящуюся цепочку).
- **Самогейдящаяся цепочка.** Команда пропускается без штампа, если инвокация `make check`
  связана с инвокацией `git commit` путём строго из `&&`: все разделители между их сегментами —
  `&&`, и check стоит раньше. Тогда коммит физически не состоится на красной проверке — гарантия
  эквивалентна раздельному выполнению. Разделители `; | ||` и переводы строк связь не дают
  (коммит может состояться при красном check).
- **Ложные срабатывания.** Матчер консервативен: безобидные команды, текстом содержащие
  `git commit`, могут блокироваться (переформулировка ничего не стоит). Ложные пропуски —
  только невидимые матчеру пути (алиасы, коммит из скрипта, `git merge --squash`, cherry-pick);
  они вне скоупа v1.

## Гейт G8: main read-only при активном feature-worktree (ADR-024)

Сессия оркестратора живёт в основном дереве и не перезапускается между фичами; изоляция фичи —
worktree, а не процесс. Пока гейт считает worktree активным, править основное дерево нельзя —
страховка от «забыл workdir/абсолютный путь» в контракте WORKTREE (skill `workflow`).

- **Активные worktree.** Множество строится из наблюдаемых bash-команд с exit 0: инвокация
  `git … worktree add <path>` добавляет разрешённый абсолютный `<path>` (база относительности —
  параметр `workdir` инструмента, иначе cwd процесса; `git -C <dir>` задаёт базу),
  `git … worktree remove <path>` убирает. Не-нулевой exit ничего не меняет.
- **Самоизлечение.** Перед каждой проверкой несуществующие пути молча выпадают из множества:
  worktree, удалённый вне сессии (ручной терминал), перестает блокировать main при первой же правке.
- **Проверка.** Инструменты `edit`/`write` (поле `filePath`) и `patch`/`apply_patch` (строки
  `*** Update|Add|Delete File:` текста патча) с целью внутри корня основного дерева (git worktree
  сервера), пока множество непусто, блокируются `GateError` со списком активных worktree.
  Относительные пути инструментов разрешаются от корня проекта — это и есть основное дерево.
- **Что не блокируется.** Bash-правки основного дерева (как в G7 — матчер снимает «забыл», а не
  отражает злоумышленника); git-операции закрытия (`git -C "$MAIN" merge --squash` — bash, не
  edit-инструмент); `/quick` на `chore/<slug>` без отдельного worktree (множество пусто).

## Гейт G9: тяжёлые бенчи только под flock (ADR-025)

Долгие замеры (7×7/8×8, часы на точку) при параллельных прогонах разных фич искажают тайминги и
peak RSS; дисциплина сериализации глобальным lock'ом `../kt-bench.lock` задана в AGENTS.md и skill
`workflow`. Текст не снимает «забыл flock» — гейт блокирует инвокации без обёртки. В отличие от G7/G8
он **stateless**: только наблюдатель `before` на bash, ни штампов, ни множеств, exit code не читается —
решение по одной строке команды.

- **Тяжёлая инвокация.** Сегмент команды (разбиение и токенизация как в G7) под гейтом, если:
  - содержит соседние токены `make` + цель `bench-deep`, `bench-8x8` или `bench-size` (флаги `make`
    и `-C <dir>` допускаются; критерий — имя цели, значения `N=`/`DEPTHS=` не разбирать);
  - либо `go test` с флагом `-bench`/`--bench` (flag-пакет Go эквивалентен; формы `-bench <значение>`
    и `-bench=<значение>`) выбирает тяжёлую доску: значение после снятия кавычек содержит size-сегмент
    `size<N>`/`size[...]` с 7 или 8 — независимо от упоминания имени бенчмарка (единственный
    size-сегментированный бенч репозитория — `BenchmarkCountAllTours`, ложный блок анонимного селектора
    в безопасную сторону); иначе, если значение матчит все доски (`.`) либо упоминает этот бенчмарк без
    size-сегмента — тоже тяжёлое. Прочие значения не классифицируются; анонимные селекторы без
    size-сегмента (`-bench=depth22`) — принятый край вне матчера.
- **Что не блокируется никогда.** `make bench` (доски 5×5/6×6, минуты) — явное исключение; остальные
  цели `make` и все не-bash инструменты вне гейта. `make bench-size N=5` блокируется несмотря на лёгкую
  доску: лёгкий замер в контеншене с долгим искажается так же, а свободный lock бесплатен.
- **Защита сегмента.** Сегмент проходит, если до тяжёлой инвокации в том же сегменте стоит вызов
  `flock` (приближение обёртки: тяжёлая цель — аргумент flock). Флаги flock пропускаются (`-n`, `-s` и
  т.п.; значения флагов с параметром вида `-w` потребляют следующий токен), первый не-флаг его аргументов —
  lock-файл.
- **Канонический lock.** Защита признаётся только когда lock-файл разрешается в
  `<родитель-основного-дерева>/kt-bench.lock`: относительный аргумент flock резолвится от параметра
  `workdir` инструмента, иначе от cwd процесса плагина (та же база, что у G8). В каноническом написании
  `../kt-bench.lock` это один файл для main и всех соседних worktree; иной lock-файл (например локальный
  для worktree) прогоны не сериализует и защиты не даёт.
- **Блокировка.** Вся bash-инвокация блокируется `GateError` с инструкцией: повторить как
  `flock ../kt-bench.lock make bench-size N=<n> DEPTHS=<d>` из корня worktree, с пометкой, что короткому
  `make bench` lock не нужен.
- **Консервативность матчера.** Обёртки (`sudo`, `env`, `time`) не скрывают тяжёлую инвокацию (пара
  `make`+цель ищется по сегменту) и не мешают проходу: flock остаётся валиден на любой позиции сегмента.
  Текстовые упоминания тяжёлых целей отдельными словами (echo, grep) могут дать ложный блок — тот же
  принятый класс, что у G7 (переформулировка ничего не стоит); разбора кавычек нет.

## Гейт G10: тул в tools/ заводится вместе с карточкой

Правило «один инструмент = код + карточка + строка индекса» задано текстом (AGENTS.md
«Shared tools», skill `tools`, `specs/tools/README.md`); гейт снимает «забыл карточку». Как и G9 —
**stateless**: решение по состоянию файловой системы в момент вызова, ни штампов, ни множеств.

- **Субъект.** Инструменты `edit`/`write` (поле `filePath`) и `patch`/`apply_patch` (строки путей
  текста патча) — извлечение целей как в G8. Цель резолвится в абсолютный путь самим гейтом:
  относительная — от корня проекта сервера, абсолютная — as-is (контракт WORKTREE: субагент пишет
  в активный worktree абсолютным путём; permission-subject ADR-026 хукам недоступен). Под гейт
  попадает любой `.py` под каталогом `tools/` на любой глубине.
- **Новый vs правка.** Если файл цели существует на момент вызова — это правка, гейт пропускает
  молча (редактирование существующего тула свободно; `apply_patch` Update/Delete цели по определению
  существуют). Не существует — новый тул, проверяется. Переименование = создание нового пути:
  карточка переименовывается тем же усилием.
- **Структурная привязка к дереву.** Гейту не нужно знать, в каком он checkout: для цели вида
  `<X>/tools/…py` карточка и индекс ищутся в `<X>/specs/tools/` — в том же дереве, куда идёт запись
  (worktree проверяется по своей копии, main — по своей). Макет без `specs/tools/` под правами G2
  не ожидается; блок с инструкцией при его отсутствии корректен.
- **Поиск карточки.** Python-имя snake_case, имя карточки kebab-case (`bench_table.py` ↔
  `bench-table.md`). Карточка считается существующей, если найден любой из `specs/tools/<stem>.md`
  или `specs/tools/<stem c подчёркиваниями→дефисы>.md`; индекс считается упомянутым, если текст
  `specs/tools/README.md` содержит одну из этих основ имени (подстрока). Обе проверки — состояния,
  а не формата: строку индекса нельзя завести, не назвав тул, и шаблонный ряд skill `tools` не
  обязан линковать карточку.
- **Блокировка.** Отсутствие карточки или упоминания в индексе на момент записи `.py` — `GateError`
  с инструкцией: сначала создать карточку по шаблону skill `tools` и строку в индексе, затем
  повторить запись. Порядок «карточка+индекс → код» задаётся инструкцией; транзакционности нет —
  «то же изменение» stateless-хук наблюдать не может, значимо состояние на момент записи `.py`,
  промежуток между карточкой и кодом допустим.
- **Что вне гейта.** Не-`.py` файлы под `tools/` (ресурсы — на ревьюере); скрипты в `work/<task>/`
  и где угодно вне `tools/` (одноразовые — законны); сами карточка и индекс (обычная запись specs);
  обратный порядок — удаление тула без удаления карточки/строки — остаётся ревьюеру.

## Гейт G11: транзитные артефакты только в work/

Правило «все временные артефакты — под `work/<task>/`» задано текстом (AGENTS.md
«Working scratch space», `work/README.md`). Гейт снимает «записал лог в корень». Stateless,
субъект и резолв путей — как в G10.

- **Принадлежность репозиторию.** Цель под гейтом, если какой-то предок каталога цели содержит
  `.git` (каталог в main или файл worktree). Найденный корень — базис проверки; `.git` нет — вне
  территории гейта (там `external_directory`/G2). Обход вверх выполняется только для целей из
  класса расширений, стоимость пренебрежима.
- **Разрешённая зона.** `<корень>/work/**` пишется как есть (включая трекаемый `work/README.md`).
- **Класс блокируемого — только по расширению**, без разбора содержимого: edit/write несут текст,
  «бинарность по содержанию» под этим инструментом бессмысленна, а сборочные артефакты приходят
  через bash (см. ниже). Класс: `.log` (главный — в `.gitignore` его нет, он грязит `git status`);
  бинарники/исполняемые и кэши `.exe`, `.dll`, `.so`, `.dylib`, `.test`, `.out`, `.pyc`. Список
  зеркалит артефактные строки `.gitignore` плюс `.log`; наличие расширения в `.gitignore` от блока
  не освобождает — правило «транзит живёт в work/», игнорирование git его не отменяет. Класс статичен:
  прочие расширения (`.status`, `.csv`, …) вне гейта — расширение списка только решением, а не матчером.
- **Правка без исключения** (в отличие от G10): цель класса вне `work/` блокируется и когда файл
  уже существует — существование мусор не легитимирует.
- **Легальные пути не затронуты:** `Makefile`, `.gitignore`, `go.sum`, исходники и документация —
  другие расширения или без них.
- **Блокировка.** `GateError` с инструкцией: перенести запись в `work/<task>/…`; если артефакт
  стал переиспользуемым скриптом — skill `tools`.
- **Bash-перенаправления** (`make bench > root.log`, `go build -o prog`) — принятый непрозрачный
  класс, как у G7/G8: гейт покрывает инструменты edit/write/patch; цель — снять «забыл, куда пишу»,
  а не перехватить терминал.

## Гейт G12: спеки до кода

Правило «спека пакета обновлена ДО любого изменения его Go-кода» задано текстом (AGENTS.md
«Mandatory workflow», ШАГ 1 `/task`, Фаза 1 `/feature`); reviewer ловит нарушение постфактум
(`SPEC_OK: no`). Гейт снимает «кодер начал с кода». Приоритет контракта — **ноль ложных блоков на
легальных путях** (`/quick`, чисто-спековые правки, тесты к уже описанному поведению): ложный блок
дороже пропуска, агент начнёт обходить гейт.

- **Субъект.** Инструменты `edit`/`write` (поле `filePath`) и `patch`/`apply_patch` (строки путей
  текста патча) — извлечение и резолв целей как в G8/G10/G11 (ADR-026: плагин резолвит сам,
  permission-subject хукам недоступен). Под гейт — цели `*.go`; **вне гейта**: `_test.go` (тесты
  сопровождают код; добавление тестов к уже описанному поведению легально без правки спеки —
  территория ревьюера), `work/**` (scratch-территория, обратная сторона G11), `testdata/`, цели вне
  дерева репозитория (walk-up до `.git` как в G11; там G2). Правка `.md` — не Go: работа `spec` и
  `benchmarker` гейтом не затронута.
- **Пакет → спека.** Каталог цели относительно корня дерева записи: файл в корне → `specs/main.md`
  (корневой пакет `main`), `<dir>/…go` → `specs/<dir>.md`; вложенный каталог даёт путь целиком
  (`specs/<rel-путь>.md`) — раскладка репозитория одноуровневая, коллизий имён нет. **Спеки нет —
  это блок** с инструкцией «сначала создай спеку» (AGENTS.md workflow шаг 2: нового пакета без спеки
  быть не должно), а не свобода.
- **Условие «спека обновлена» — git-состояние на момент вызова**, проверяется в дереве цели записи
  (`git -C <root>`), достаточно одного из:
  1. *грязная*: `status --porcelain -- specs/<pkg>.md` непусто (правка в рабочем дереве или индексе,
     включая untracked — свежесозданная спека нового пакета);
  2. *изменена от базы ветки*: `diff --name-only <mb> -- specs/<pkg>.md` непусто, `mb` =
     `merge-base HEAD origin/main` (канон A/B-базы из skill `workflow`; далее `main`, если
     `origin/main` не резолвится; если и `main` нет — проверка пропускается: неразрешимая база не
     должна давать ложный блок).
  Покрытие: порядок «спека→код» в `/task`/`/feature` (спека грязная), контрольный коммит середи
  ветки и рестарт сервера после него (history-проверка, состояние читается с диска, не из памяти).
- **Стоимость и кэш.** Каждый git-вызов ≈8 мс (замер в этом репозитории, ADR-028) — при частоте
  edit-инструмента стоимость вторична; тем не менее **позитивные** вердикты кэшируются в памяти
  процесса по паре (корень дерева, путь спеки), **негативные не кэшируются никогда** — появившаяся
  спека пропускает следующую проверку без инвалидации. Кэш сбрасывается целиком событием шины
  `vcs.branch.updated` (излишняя инвалидация дешёва). Ветка, сменённая вне сессии без порождения
  события, оставляет протухший позитив (пропуск вместо блока) — принятый класс G7/G8.
- **Обход `/quick`.** Триггер — хук `command.execute.before` (`{command, sessionID, arguments}`;
  срабатывает до хода модели, метка гарантированно предшествует первой правке команды):
  `command == "quick"` помечает сессию `sessionID`, имена `task`/`feature` метку **снимают**
  (перезапуск команды в той же сессии меняет режим). Время жизни — память процесса, пока жива
  сессия. `/quick` правит код в своей сессии без субагентов — попадает ровно под свою метку; сессии
  субагентов `/feature` имеют другие `sessionID` и метки не имеют → гейт для них активен. Отклонены:
  событие шины `command.executed` (в opencode 1.18.31 публикуется **после завершения всего хода**
  команды — probe-замер: `before` → tool-вызовы → `executed`; первая же правка `/quick` ложно
  блокировалась бы, нарушение приоритета «ноль ложных блоков»), сигнал «ветка `chore/*`»
  (git-процесс на каждый edit + «сидит на chore вручную» даёт обход + дрейф вне сессии) и глобальный
  флаг процесса (утёк бы в последующие `/feature`; см. ADR-028).
- **Блокировка.** `GateError` с инструкцией: сначала обновить `specs/<pkg>.md` (контракт под изменение
  или пояснительная строка «поведение/API не меняются»), либо оформить код-only правку через `/quick`
  на `chore/<slug>`; ссылка ADR-028. **Режима warn нет**: предупреждение — текст, а гейты существуют
  потому, что текст не снимает «забыл» (ADR-022); переключатель — ветка (ADR-021): стал шумить —
  ветка закрывается как rejected.
- **Независимость.** Состояние G12 (метки сессий, кэш) не пересекается с G7/G8/G9/G10/G11 и они его
  не читают. Bash-правки Go (`sed -i`, `go fmt` внутри `make check`) — принятый непрозрачный класс
  G7/G8: цель — снять «забыл спеку» у видимых путей агента, не перехватить терминал.

## Инварианты

- Ни один агент-субагент (`spec`, `coder`, `reviewer`, `benchmarker`) не запускает других
  субагентов — оркестрация остаётся у команды-диспетчера.
- Права на запись минимальны для роли: read-only агенты не пишут, документальные агенты пишут
  только в свою область документации.
- На вызов инструмента влияет только намеренный `GateError`; сбой внутренней логики гейта не
  должен ломать работу инструментов (логируется).
- Зелёный штамп живёт только в памяти процесса плагина: рестарт сервера ⇒ штампа нет, коммит
  требует свежей проверки. Штамп глобален для процесса (не делится по `sessionID`): в `/feature`
  `coder` гоняет `make check` в своей сессии, а коммитит оркестратор в своей.
- Изменения permission-конфига и файлов `.opencode/plugins/*` применяются с рестартом
  opencode-сессии.

## Ограничения и edge cases

- Матчинг путей permission (формы subject'а, порядок правил, тильда) — в секции
  «Слой permission: матчинг путей»; там же причина, по которой G3/G4 используют относительные
  `../kt-*` паттерны вместо `~/work/kt-*` (ADR-026).
- Слой permission не знает состояния (ветка, результат `make check`) — для таких проверок
  предназначен plugin-слой.
- `ask` проходим пользователем (и авто-режимом); `deny` непроходим ни для кого, кроме правки
  самого конфига человеком.
- G7 оперирует строкой команды модели: обход скриптом/алиасом возможен и принят — цель гейта
  снять «забыл прогнать», а не отразить злоумышленника. Пользовательский терминал вне слоя
  плагина (это территория git hooks).
- Подтверждение успеха берётся из метаданных результата bash-инструмента (opencode 1.18.x:
  `metadata.exit` — число; при abort/kill равно `null`, при таймауте отсутствует); если формат
  метаданных изменится в новой версии opencode — штамп перестанет ставиться: отказ безопасный
  (коммит блокируется, а не пропускается).
- Подтверждение exit code — механизм after-наблюдателей (G7/G8): обёртка `cmd; echo "exit=$?"` прячет
  внутренний сбой за итоговым нулём (найдено приёмкой G8). Гейту G9 это не применимо — он stateless и
  exit code не читает; уязвимы только state-гейты.
- `flock(1)` отсутствует в базовом userland darwin: без него каноническая команда падает в runtime
  (command not found) — это вопрос настройки окружения (пробы по AGENTS.md «Shell environment»), а не
  исключение из гейта; G9 проверяет форму инвокации, не наличие утилиты.
- `cd` внутри команды матчером не отслеживается: относительный lock-аргумент резолвится от `workdir`
  инструмента. Каноническое написание, запущенное из другого каталога, бьёт по иному файлу — принятый
  edge, WORKTREE-контракт требует cwd=`$WT`.
- Относительные `../kt-*` паттерны G3/G4 резолвятся от корня проекта сессии; контракт предполагает,
  что opencode запущен в main-дереве (ADR-024). Запуск сессии внутри worktree переопределяет, что для
  неё «main»: `specs/**` накроет сам worktree, а основное дерево станет `../knighttour/…` и закроется.
- Удалённый worktree формально остаётся под паттерном (permission — матчинг строк без проверки
  существования): запись в `<удалённый kt-*>/specs/…` воссоздала бы каталоги. Принято; WORKTREE-контракт
  требует путь из свежего `git worktree add`, а G8 самоизлечивает своё множество (это влияет только на
  блокировку main).
- Чужой каталог вне `~/work/kt-*` (например `~/work/<other>`): `external_directory` даёт ask (G2), а
  edit-слой G3/G4 — deny, и `--auto` его не снимает; двойная защита проверена эмпирически (ADR-026).
- Plugin-хуки получают аргументы инструментов до любых преобразований permission-слоя: формы
  subject'а ADR-026 им недоступны, поэтому G8/G10/G11/G12 резолвят цели сами (относительные — от корня
  проекта сервера, абсолютные as-is). Структурная привязка G10 (`<X>/tools ↔ <X>/specs/tools`) и
  walk-up `.git` у G11 привязывают проверку к дереву цели записи, а не к дереву сессии.
- Текстовое упоминание имени тула в `specs/tools/README.md` вне строки таблицы выводит G10 из блока
  (подстрока найдена) — малозначимый край, строка индекса остаётся зоной ревьюера; обратный порядок
  G10 (удалён тул, карточка осталась) гейтом не проверяется в принципе.
- G12 при сбое git-вызова (таймаут, повреждённый refs) пропускает правку: для шумного гейта ложный
  блок дороже пропуска, а внутренний сбой по контракту ядра fail-open; неразрешимая база ветки
  (`origin/main`/`main` отсутствуют) — тот же проход.
- Инвалидация кэша G12 best-effort: событие `vcs.branch.updated` не несёт ни сессии, ни дерева, а
  смена ветки вне поля зрения плагина его не порождает — протухший позитив (лишний проход) принят;
  обратного (ложный блок после смены ветки) конструкция не даёт: негативы не кэшируются.
- Обход G12 меткой `/quick` живёт в сессии, получившей команду: субагенты унаследовать его не могут
  (другой `sessionID`); снятие — только `/task`/`/feature` в той же сессии или рестарт процесса. Это
  осознанно слабее «флага на задачу»: `/quick` — волевое действие пользователя, а не классификация
  каждой правки.

## Тесты

Конфиг не имеет кода; проверка гейта ручная: попытка заблокированного действия в сессии
opencode должна давать блок/ask. Для plugin-гейта приёмка — воспроизводимые сценарии,
зафиксированные в ADR фичи.

Сценарии приёмки G7 (ADR-023):

1. свежая сессия → `git commit -m x` → блок `GateError` с инструкцией;
2. зелёный `make check` → тот же commit проходит;
3. зелёный, затем любое редактирование файла через edit/write → commit снова блокируется;
4. одна команда `make check && git commit -m x` без предварительного штампа → проходит;
5. красная `make check` (сломанный тест) → commit остаётся заблокированным;
6. `git -C <worktree> commit ...` детектируется как коммит;
7. негативные контроли: `git status`, `git log --oneline` не блокируются; не-`bash` инструменты
   гейтом не затрагиваются.

Сценарии приёмки G8 (ADR-024):

1. без активных worktree → edit файла основного дерева проходит;
2. зелёный `git worktree add <путь>` → edit/write основного дерева блокируется `GateError`
   (в т.ч. относительный путь инструмента), edit файлов внутри worktree — проходит;
3. `apply_patch` со `*** Update File: <main/…>` блокируется;
4. зелёный `git worktree remove <тот же путь>` → правка main снова проходит;
5. worktree из множества удалён с диска → на следующей правке самоизлечение, main не заблокирован;
6. красный (`exit != 0`) `git worktree add` множество не пополняет;
7. красная команда `git commit` G7-гейтом блокируется независимо от состояния G8.

Сценарии приёмки G9 (ADR-025):

1. `make bench-deep` без flock → `GateError` с инструкцией и канонической командой;
2. `flock ../kt-bench.lock make bench-deep` проходит из корня репозитория/worktree; абсолютный путь
   к тому же lock-файлу — тоже;
3. исключения: `make bench`, `make check`, `make bench-table LOG=…` проходят без lock'а;
4. `make bench-size N=7 DEPTHS=22 > work/x/log 2>&1` → блок; с flock-префиксом — проход (и при `N=5`:
   решает имя цели);
5. цепочки: `cd <wt> && make bench-8x8` → блок (второй сегмент не защищён);
   `flock ../kt-bench.lock make bench-size N=7; echo done` → проход;
6. прямой `go test -run='^$' -bench='BenchmarkCountAllTours/size7' ./counter/` без flock → блок, с
   flock → проход; значения `size[56]`, `size6/depth14` проходят без lock'а; `-benchtime=10x` не путается
   с `-bench`; равносильная двойная черта `--bench='BenchmarkCountAllTours/size7'` (и пробельная форма) —
   тоже блок, с flock → проход; анонимный селектор `-bench=size7` — блок, `-bench=size[56]` и
   принятый край `-bench=depth22` (без size-сегмента) — проход;
7. `flock ./.bench.lock make bench-deep` — неканонический lock-файл → блок;
8. негативные контроли: `git status`, `go test ./...` (без `-bench`), не-bash инструменты не блокируются;
   G9 не трогает состояние G7/G8 и не зависит от него.

Сценарии приёмки G10 (ADR-027):

1. запись нового `tools/new_tool.py` без карточки → `GateError` с инструкцией «сначала карточка +
   строка индекса»;
2. созданы карточка `specs/tools/new-tool.md` и строка в индексе (в любом порядке между собой) →
   повторная запись проходит;
3. правка существующего `tools/bench_table.py` проходит, ничего не требуя; `apply_patch`
   `*** Update File:` по нему — тоже;
4. карточка есть, упоминания в индексе нет → блок; добавлена строка → проход;
5. «переименование»: запись `tools/renamed_tool.py` (старый файл на месте) без карточки → блок;
   с переименованными карточкой и строкой индекса → проход;
6. `apply_patch` `*** Add File: tools/x.py` без карточки → блок;
7. worktree-контекст: запись `<wt>/tools/x.py` требует карточку в `<wt>/specs/tools/`, а не в main
   (структурная привязка); отсутствие карточки только в main — не блок;
8. негативные контроли: запись самой карточки и индекса, `work/<task>/script.py`, не-`.py` под
   `tools/` — проходят; G10 stateless и не влияет на состояние G7/G8/G9.

Сценарии приёмки G11 (ADR-027):

1. запись `bench.log` в корень репозитория и в любой каталог вне `work/` → `GateError` с инструкцией
   про `work/<task>/`;
2. запись `work/<task>/run.log` проходит; правка `work/README.md` — проходит;
3. бинарники по расширению: `prog.exe`, `libfoo.so`, `x.out` вне `work/` → блок;
4. негативные контроли: `Makefile`, `.gitignore`, `go.sum`, `*.go`, `*.md` — проходят;
5. `apply_patch` `*** Add File: junk.log` → блок; правка уже существующего вне `work/` лога (созданного
   через bash) — тоже блок (правки без исключения);
6. запись `.log` за пределами репозитория (без `.git`-предка) — гейт не срабатывает (территория G2);
7. `make bench > root.log` через bash — не блокируется (принятый непрозрачный класс, зафиксирован);
   G11 stateless и не влияет на состояние других гейтов.

Сценарии приёмки G12 (ADR-028; применяются со свежим процессом opencode):

1. чистое дерево, ветка от `main`: edit `<pkg>/x.go` → `GateError` с инструкцией (спека/`/quick`);
2. правка `specs/<pkg>.md` (dirty) → тот же edit проходит; новый пакет: `foo/foo.go` без спеки →
   блок, после создания `specs/foo.md` — проход;
3. контрольный коммит всего изменения (`git add -A && git commit`) → правки кода проходят по
   history-проверке (merge-base), не требуя грязной спеки; рестарт сервера после коммита — тоже;
4. живьём `/quick <мелкая правка>`: в сессии, выполнившей команду, edit `.go` без изменения спек
   проходит, в том числе внутри самого хода команды (обход по хуку `command.execute.before`);
   затем в той же сессии запущенные `/task`/`/feature`
   метку снимают — следующий edit кода без спеки блокируется;
5. негативные контроли: `_test.go`, `work/<task>/scratch.go`, `.md`, не-Go, запись вне репозитория —
   не блокируются; чисто-спековая сессия (только `.md`) гейтом не затронута;
6. worktree-контекст: edit `<wt>/<pkg>/x.go` проверяет спеку дерева `<wt>`, а не main (walk-up до
   `.git` цели); правка G7/G8/G9/G10/G11-территорий не меняет состояние G12 и наоборот.

Сценарии приёмки G3/G4 (ADR-026; применяются со свежим процессом opencode):

1. сессия в main при активном feature-worktree: агент `spec` пишет по абсолютному пути
   `<worktree>/specs/<pkg>.md` — разрешено (файл создан);
2. тот же агент в корень worktree (`<worktree>/README.md`) — блокируется G3 (`deny`);
3. тот же агент в `~/work/<other>/specs/x.md` — блокируется G3 даже в `--auto`
   (external ask автопроходится, edit-нет);
4. `spec` пишет `specs/**` основного дерева: без активных worktree — разрешено; при активном —
   блокируется G8 (гейт не сломан: permission пропускает, plugin снимает);
5. `benchmarker`: `<worktree>/specs/decisions/NNN-*.md` и `<worktree>/work/<task>/log` — разрешено;
   `<worktree>/counter/*.go` — блокируется G4; base-worktree `../kt-base-<slug>` попадает под
   `../kt-*` (замеры пишутся в ADR основного дерева/worktree фичи, не в базу);
6. негативный контроль: `reviewer`/`coder` не затронуты (G5/G6 без изменений).
