# gates: жёсткие гейты агентского пайплайна (ADR-022)

## Ответственность

Модуль превращает обязательные правила проекта в непроходимые проверки уровня инструмента. Такую
проверку модель не может обойти текстом ответа. Механизмов два:

- **permission-конфиг** — `opencode.json` в корне и frontmatter агентов в `.opencode/agent/`. Он
  декларирует `allow | ask | deny` по паттернам bash-команд и путей edit; `deny` не обходится
  даже в режиме `--auto`.
- **plugin-хуки** — `.opencode/plugins/gates.ts`, хук `tool.execute.before`. Они выполняют
  проверки с состоянием (состояние ветки, истории прогонов), недоступные паттернам. Намеренное
  исключение `GateError` блокирует вызов инструмента.

Каждый гейт живёт ровно в одном из двух слоёв. Текст в AGENTS.md объясняет «зачем» и не является
механизмом.

## Слой permission: сопоставление путей (ADR-026)

Паттерны permission компилируются в регулярное выражение, привязанное к началу и концу строки
(`^…$`, флаг `s`). Звёздочка `*` означает любую последовательность символов — включая `/` и
переводы строк; вопросительный знак `?` — один символ. Совпадает только вся строка целиком;
вхождение подстрокой не считается. Правило выбора — **last-match-wins**: общее правило `"*"`
ставится первым. Паттерн может начинаться с `~/` или `$HOME/`; при загрузке конфига этот префикс
раскрывается в абсолютный путь.

Форма проверяемой строки (subject) зависит от разрешения — opencode 1.18:

- Разрешение `edit` покрывает инструменты `edit`/`write`/`apply_patch`. Его subject — **путь файла
  относительно корня проекта сессии** (`instance.worktree`). Файлы соседнего worktree выглядят как
  `../kt-*/…`. Абсолютные и тильдовые паттерны под это разрешение не совпадают никогда: subject
  с `..` побивает только литерал.
- Разрешение `external_directory` получает абсолютный glob вида `<родительский каталог>/*`; здесь
  префикс `~/work/kt-*/**` из корневой `opencode.json` уместен и достаточен (G2).

Порядок правил для агента такой: встроенные значения по умолчанию, затем глобальный и проектный
`opencode.json`, затем frontmatter агента; последнее перечисленное выигрывает. Следствия:

- Правило `"*": deny` из frontmatter нельзя перекрыть разрешением allow из `opencode.json` — оно
  стоит левее. Ролевые исключения пишут в том же frontmatter после catch-all.
- Feature-worktree по контракту соседствует с main-деревом под именем `../kt-<NN>-<slug>`. Поэтому
  запись агента в него открывает относительным паттерном `../kt-*/<ролевой каталог>/**`; запись в
  само основное дерево открывают относительными `specs/**`/`work/**`, ведь сессия живёт в main (ADR-024).
- Сопоставление работает со строками: permission не проверяет существование пути и не знает про
  «активность» worktree. Проверки с состоянием остаются за plugin-слоем (G8).

## Plugin-ядро (`.opencode/plugins/gates.ts`)

Это единый модуль плагина opencode и точка подключения всех гейтов с состоянием. opencode
загружает файлы из `.opencode/plugins/` автоматически при старте сервера.

Контракт ядра:

- Модуль экспортирует ровно одну функцию-плагин: `export const GatesPlugin: Plugin` (тип —
  `@opencode-ai/plugin`). Правила сопоставления и вспомогательные функции не экспортируются:
  загрузчик считает плагином каждую экспортированную функцию.
- Ядро регистрирует по одному обработчику `tool.execute.before`, `tool.execute.after`,
  `command.execute.before` и `event`. Вызовы диспетчируются по списку гейтов в порядке
  регистрации. Гейт — элемент списка следующей формы:

  ```ts
  interface Gate {
    id: string                  // ID из реестра («G7»)
    before?(call): void         // наблюдение args до исполнения; может бросить GateError
    after?(call): void          // наблюдение результата (для утилит — фиксация успеха)
    onEvent?(event): void       // события шины opencode (например vcs.branch.updated)
    onCommand?(invocation): void // запуск slash-команды {name, sessionID}, до первого хода модели
  }
  ```

- Намеренная блокировка — это исключение `GateError` с текстом-инструкцией для модели. Оно
  прекращает вызов инструмента, а текст возвращается модели как ошибка инструмента. Неожиданное
  внутреннее исключение гейта логируется через `client.app.log` и не влияет на вызов: безопасный
  отказ в сторону запрета действует только для `GateError`, а баг гейта операцию пропускает.
- Состояние гейтов живёт в памяти процесса плагина и не разделяется между серверами и
  перезапусками.

Новый гейт — это новый элемент списка и строка в реестре; ядро при этом не меняется.

## Гейт G7: make check перед git commit (ADR-023; v2 — ADR-029)

Гейт пассивно отслеживает подтверждение зелёной проверки — далее штамп. Плагин не исполняет
проверки сам: он запоминает факт успешного `make check` вместе с отпечатком содержимого дерева,
в котором прогон запускался. В момент создания коммита плагин сверяет содержимое целевого дерева
с этим множеством. Штамп — не булев флаг, а множество отпечатков. Вызов, создающий коммит, легален
тогда и только тогда, когда проверяемое содержимое совпадает с содержимым зелёной проверки.

- **Отпечаток.** Это хэш содержимого всех нетигируемых путей дерева — `tracked ∪ untracked`.
  Git-исключения (`work/**`) и артефакты сборки в отпечаток не входят: они не участвуют в сборке
  и тестах. Для каждого пути учитываются и рабочая копия, и индекс (staged-blob). Легальность
  штампа асимметрична, ведь коммит берёт содержимое из индекса. Рабочая копия обязана совпасть
  с проверенной. Запись индекса может либо не двигаться, либо перейти ровно к проверенному
  содержимому: `git add` между проверкой и коммитом легален. Любой иной ход индекса — блок; это
  чужое содержимое или выпадение записи через `git rm --cached`.
- **Штамп.** Это множество отпечатков в памяти процесса. Оно пополняется завершением команды
  `make check` в инструменте `bash`, когда результат инструмента подтверждает exit code 0; без
  подтверждения пополнения нет. Множество конечно: при переполнении вытесняется древнейший
  отпечаток (FIFO), и цена вытеснения — ровно один лишний прогон `make check`. Вызов команды
  распознаётся разбором по токенам по сегментам команды; допускаются флаги `make`, `-C <dir>` и
  env-префиксы. Exit-код относится ко всей строке. Подтверждение действительно, только если после
  `make check` остались лишь разделители `&&`: после `;`, `|`, `||` и переводов строк код
  принадлежит более позднему сегменту, и успех не подтверждён. Отпечаток берётся из дерева, где
  прогон физически запускался. Базой служит параметр `workdir` инструмента, иначе cwd процесса
  плагина; `make -C <dir>` меняет базу; далее идёт walk-up до `.git`, как в G11. Если репозиторий
  по пути не найден, штамп не ставится.
- **Вызовы, создающие коммит.** Под гейт попадают сегменты bash, порождающие коммит: явный
  `git commit` и авто-commit субкоманд `merge`, `cherry-pick`, `revert`, `rebase`, `am`. Сегмент
  вне гейта, когда субкоманда заведомо не создаёт коммита: любая из них с `--no-commit`, а также
  `merge --squash` и `merge --ff-only` — fast-forward только перемещает указатель. Разбор по
  токенам работает как в v1: двоичная утилита `git`, глобальные флаги `-C`, `-c k=v`,
  `--git-dir=…`, env-префиксы. Команда режется по shell-разделителям `&& || ; |` и переводам
  строк; сегменты проверяются отдельно. Формы освобождения распознаются вне кавычек, группировка
  аргументов как в shell. Литерал внутри закавыченного сообщения не освобождает:
  `merge -m "…--ff-only…"` остаётся под гейтом. При небалансированной кавычке освобождения нет —
  консервативно.
- **Проверка.** Создающий вызов пропускается, только если отпечаток его целевого дерева в момент
  вызова совпадает с одним из зелёного множества. Иначе плагин бросает `GateError` с инструкцией
  выполнить `make check` и повторить. Для авто-commit субкоманд инструкция дополнительно указывает
  корректный двухшаговый путь: `--no-commit`/`--squash` → `make check` → явный `git commit`.
  Блокировка поднимается до исполнения команды, поэтому весь вызов не запускается: пристыкованный
  к создающему вызову `git add` тоже не отработает, и стейдж переносится в повтор. Целевое дерево
  определяется по git-флагу `-C <dir>`, иначе по `workdir` инструмента или cwd процесса. Разбор не
  отслеживает `cd` внутри команды — принятый край, тот же класс, что у G9. При нескольких создающих
  вызовах в команде каждый проверяется по своему дереву.
- **Самогейдящаяся цепочка.** Как в v1: вызов пропускается без штампа, если он связан с ранее
  стоящим `make check` цепочкой строго из `&&`, и check идёт раньше. Разделители `; | ||` и
  переводы строк связь не дают. Для авто-commit субкоманд исключение формально: check до merge не
  аттестует результат merge. Блок на незелёном дереве и инструкция разворачивают к двухшаговому
  пути.
- **Инвалидаций как механизма нет.** Любую правку файлов заметит рассогласование отпечатка в
  момент коммита. Речь о правках инструментов `edit`/`write`/`patch` (в opencode ≥1.18 id патчера —
  `apply_patch`), о bash-правках (`sed -i`, редиректы, скрипты) и о внешнем редакторе. Пара «правка
  и откат» штамп восстанавливает: значима эквивалентность содержимого, а не факт обращения
  инструмента.
- **Отказы.** Если отпечаток не вычислился — нет git, таймаут git-вызова, цель вне репозитория —
  подтверждения нет, и коммит блокируется. Безопасный отказ в сторону запрета стоит один прогон
  `make check`; направление то же, что у правила «без подтверждения — нет штампа».
- **Стоимость.** Плагин проходит содержимое дерева один раз при штамповке и один раз при каждой
  попытке коммита; замеры — в ADR-029. Синхронные git/fs-вызовы в плагине — прецедент G12
  (ADR-028). Кэша отпечатков нет, потому что значима свежесть сравнения.
- **Ложные срабатывания и принятые пропуски.** Правило сопоставления консервативно, как в v1:
  безобидные команды, текстом содержащие `git commit`, могут блокироваться, а переформулировка
  ничего не стоит. Принятые пропуски v2: алиасы и коммит из скрипта — класс осознанного обхода,
  невидимый разбору; пользовательский терминал; обёртка `cmd; echo "exit=$?"`, прячущая сбой за
  итоговым нулём.

## Гейт G8: main read-only при активном feature-worktree (ADR-024)

Сессия оркестратора живёт в основном дереве и не перезапускается между фичами; изоляция фичи —
worktree, а не процесс. Пока гейт считает хотя бы один worktree активным, править основное дерево
нельзя. Это страховка от забывчивости с `workdir` и абсолютным путём в контракте WORKTREE
(skill `workflow`).

- **Активные worktree.** Множество строится из наблюдаемых bash-команд с exit 0. Вызов
  `git … worktree add <path>` добавляет разрешённый абсолютный `<path>`, а
  `git … worktree remove <path>` убирает его. Базой относительности служит параметр `workdir`
  инструмента, иначе cwd процесса; `git -C <dir>` задаёт базу. Не-нулевой exit ничего не меняет.
- **Самокоррекция множества.** Перед каждой проверкой несуществующие пути молча выпадают из
  множества. Worktree, удалённый вне сессии в ручном терминале, перестаёт блокировать main при
  первой же правке.
- **Проверка.** Пока множество непусто, гейт блокирует цели внутри корня основного дерева
  (git worktree сервера) через `GateError` со списком активных worktree. Под блок попадают
  инструменты `edit`/`write` с полем `filePath` и `patch`/`apply_patch` со строками
  `*** Update|Add|Delete File:` текста патча. Относительные пути инструментов разрешаются от
  корня проекта — это и есть основное дерево.
- **Что не блокируется.** Bash-правки основного дерева: как в G7, это защита от забывчивости, а
  не от злонамеренного обхода. Также вне блока git-операции закрытия — `git -C "$MAIN" merge
  --squash` это bash, а не edit-инструмент. Вне блока и `/quick` на `chore/<slug>` без отдельного
  worktree, потому что множество пусто.

## Гейт G9: тяжёлые бенчи только под flock (ADR-025)

Долгие замеры досок 7×7 и 8×8 занимают часы на точку. Параллельные прогоны разных фич искажают
тайминги и peak RSS, поэтому AGENTS.md и skill `workflow` задали сериализацию глобальным файлом
`../kt-bench.lock`. Документация сама по себе страхует от забывчивости слабо, поэтому гейт
блокирует вызовы команд без обёртки flock. В отличие от G7/G8 этот гейт **stateless**: у него
только наблюдатель `before` на bash. Он не хранит штампов и множеств и не читает exit code;
решение принимается по одной строке команды.

- **Тяжёлый вызов команды.** Сегмент команды под гейтом, если (разбиение и разбор по токенам как
  в G7):
  - сегмент содержит соседние токены `make` и цель `bench-deep`, `bench-8x8` или `bench-size`.
    Флаги `make` и `-C <dir>` допускаются; решает имя цели, значения `N=`/`DEPTHS=` не
    разбираются;
  - либо запущен `go test` с флагом `-bench` или `--bench`; двойная черта эквивалентна одинарной,
    формы `-bench <значение>` и `-bench=<значение>` тоже. Вызов считается тяжёлым, если значение
    после снятия кавычек содержит size-сегмент `size<N>` или `size[...]` с 7 или 8. Упоминание
    имени бенчмарка роли не играет: `BenchmarkCountAllTours` — единственный size-сегментированный
    бенч репозитория, и ложный блок анонимного селектора падает в безопасную сторону. Если
    значение совпадает со всеми досками (`.`) или упоминает этот бенчмарк без size-сегмента,
    вызов тоже тяжёлый. Прочие значения не классифицируются; анонимные селекторы без size-сегмента
    вроде `-bench=depth22` остаются принятым краем вне правила сопоставления.
- **Что не блокируется никогда.** `make bench` — явное исключение, его доски 5×5 и 6×6 стоят
  минуты. Остальные цели `make` и все не-bash инструменты вне гейта. `make bench-size N=5`
  блокируется несмотря на лёгкую доску: лёгкий замер искажается от соседства с долгим так же, а
  свободный lock ничего не стоит.
- **Защита сегмента.** Сегмент проходит, если до тяжёлого вызова в нём стоит вызов `flock` — это
  приближение обёртки, где тяжёлая цель является аргументом flock. Флаги flock пропускаются
  (`-n`, `-s`), а флаг с параметром вида `-w` потребляет следующий токен. Первый не-флаг среди
  аргументов flock считается lock-файлом.
- **Канонический lock.** Защита признаётся, только когда lock-файл разрешается в
  `<родитель-основного-дерева>/kt-bench.lock`. Относительный аргумент flock резолвится от
  параметра `workdir` инструмента, иначе от cwd процесса плагина — та же база, что у G8.
  Каноническое написание `../kt-bench.lock` означает один файл для main и всех соседних worktree.
  Иной lock-файл, например локальный для worktree, прогоны не сериализует и защиты не даёт.
- **Блокировка.** Весь вызов bash блокируется исключением `GateError` с инструкцией. Повторить
  нужно так: `flock ../kt-bench.lock make bench-size N=<n> DEPTHS=<d>` из корня worktree.
  Инструкция помечает, что короткому `make bench` lock не нужен.
- **Консервативность правила сопоставления.** Обёртки `sudo`, `env` и `time` не скрывают тяжёлый
  вызов и не мешают проходу: пара `make` и цели ищется по всему сегменту, а flock действенен на
  любой позиции сегмента. Текстовые упоминания тяжёлых целей отдельными словами в `echo` или
  `grep` могут дать ложный блок — это тот же принятый класс, что у G7, где переформулировка ничего
  не стоит. Разбора кавычек нет.

## Гейт G10: тул в tools/ заводится вместе с карточкой

Правило «один инструмент = код + карточка + строка индекса» задано текстом (AGENTS.md
«Shared tools», skill `tools`, `specs/tools/README.md`). Гейт страхует от забывчивости: карточка
появляется вместе с кодом. Как и G9, гейт **stateless**: решение принимается по состоянию
файловой системы в момент вызова, штампов и множеств нет.

- **Субъект.** Инструменты `edit`/`write` (поле `filePath`) и `patch`/`apply_patch` (строки путей
  текста патча) — цели извлекаются как в G8. Гейт сам резолвит цель в абсолютный путь:
  относительную — от корня проекта сервера, абсолютную — без изменений. По контракту WORKTREE
  субагент пишет в активный worktree абсолютным путём, а permission-subject из ADR-026 хукам
  недоступен. Под гейт попадает любой `.py` под каталогом `tools/` на любой глубине.
- **Новый файл или правка.** Если файл цели существует на момент вызова, это правка, и гейт
  молча пропускает её. Редактирование существующего тула свободно; цели `apply_patch` с
  Update/Delete существуют по определению. Несуществующий файл — новый тул, он проверяется.
  Переименование равно созданию нового пути: карточка переименовывается тем же усилием.
- **Структурная привязка к дереву.** Гейту не нужно знать, в каком checkout он работает. Для цели
  вида `<X>/tools/…py` карточка и индекс ищутся в `<X>/specs/tools/` — в том же дереве, куда идёт
  запись. Worktree проверяется по своей копии, main — по своей. Макета без `specs/tools/` под
  правами G2 ожидать не приходится, и блок с инструкцией при его отсутствии корректен.
- **Поиск карточки.** Имя Python-файла пишется в snake_case, имя карточки — в kebab-case:
  `bench_table.py` соответствует `bench-table.md`. Карточка считается найденной, если существует
  `specs/tools/<stem>.md` или `specs/tools/<stem с подчёркиваниями, заменёнными дефисами>`.
  Индекс считает упоминание найденным, когда текст `specs/tools/README.md` содержит одну из этих
  основ имени как подстроку. Обе проверки смотрят состояние, а не формат: строку индекса нельзя
  завести, не назвав тул, и шаблонный ряд skill `tools` не обязан линковать карточку.
- **Блокировка.** Если карточки или упоминания в индексе нет в момент записи `.py`, гейт бросает
  `GateError` с инструкцией. Сначала нужно создать карточку по шаблону skill `tools` и строку в
  индексе, затем повторить запись. Порядок «карточка+индекс → код» задаёт инструкция;
  транзакционности нет. Stateless-хук не может наблюдать «то же изменение», значимо состояние на
  момент записи `.py`, а промежуток между карточкой и кодом допустим.
- **Что вне гейта.** Не-`.py` файлы под `tools/`: ресурсы остаются на ревьюере. Скрипты в
  `work/<task>/` и где угодно вне `tools/` — одноразовые записи законны. Сами карточка и индекс —
  обычная запись specs. Обратный порядок, то есть удаление тула без удаления карточки и строки,
  остаётся ревьюеру.

## Гейт G11: транзитные артефакты только в work/

Правило «все временные артефакты — под `work/<task>/`» задано текстом (AGENTS.md
«Working scratch space», `work/README.md`). Гейт страхует от записей логов в корень репозитория.
Он stateless; субъект и резолв путей — как в G10.

- **Принадлежность репозиторию.** Цель под гейтом, если какой-то предок каталога цели содержит
  `.git` — каталог в main или файл worktree. Найденный корень становится базисом проверки. Без
  `.git` цель вне территории гейта, там правят `external_directory` и G2. Обход вверх выполняется
  только для целей из класса расширений, и его стоимость пренебрежима.
- **Разрешённая зона.** `<корень>/work/**` пишется как есть, включая трекаемый `work/README.md`.
- **Класс блокируемого определяется только расширением**, содержимое не разбирается. Инструменты
  edit/write несут текст, поэтому «бинарность по содержанию» под ними бессмысленна, а сборочные
  артефакты приходят через bash (см. ниже). В класс входят `.log` — главный нарушитель, которого
  нет в `.gitignore`, и он грязит `git status`. Сюда же относятся двоичные, исполняемые файлы и
  кеш байткода: `.exe`, `.dll`, `.so`, `.dylib`, `.test`, `.out`, `.pyc`. Список зеркалит
  артефактные строки `.gitignore` плюс `.log`. Присутствие расширения в `.gitignore` от блока не
  освобождает: транзит живёт в `work/`, и игнорирование git этого не отменяет. Класс статичен;
  прочие расширения вроде `.status` и `.csv` вне гейта, и список расширяют отдельным решением, а
  не автоматически.
- **Правка без исключения**, в отличие от G10: цель класса вне `work/` блокируется, даже когда
  файл уже существует. Существование не легитимизирует мусор.
- **Легальные пути не затронуты:** `Makefile`, `.gitignore`, `go.sum`, исходники и документация
  имеют другое расширение или не имеют его вовсе.
- **Блокировка.** Гейт бросает `GateError` с инструкцией: перенести запись в `work/<task>/…`.
  Если артефакт стал переиспользуемым скриптом — обращаться к skill `tools`.
- **Bash-перенаправления** вида `make bench > root.log` и `go build -o prog` — принятый
  непрозрачный класс, как у G7/G8. Гейт покрывает инструменты edit/write/patch; его цель —
  страховать от забывчивости о месте записи, а не перехватывать терминал.

## Гейт G12: спеки до кода

Правило «спека пакета обновлена ДО любого изменения его Go-кода» задано текстом (AGENTS.md
«Mandatory workflow», ШАГ 1 `/task`, Фаза 1 `/feature`). Reviewer ловит нарушение постфактум
через `SPEC_OK: no`. Гейт страхует от начала работы с кода. Приоритет контракта — **ноль ложных
блоков на легальных путях**: нельзя задевать `/quick`, чисто-спековые правки и тесты к уже
описанному поведению. Ложный блок дороже пропуска, потому что агент начнёт обходить гейт.

- **Субъект.** Инструменты `edit`/`write` (поле `filePath`) и `patch`/`apply_patch` (строки путей
  текста патча); извлечение и резолв целей — как в G8/G10/G11. По ADR-026 плагин резолвит сам, а
  permission-subject хукам недоступен. Под гейт идут цели `*.go`. **Вне гейта:** `_test.go`,
  потому что тесты сопровождают код, и их добавление к уже описанному поведению легально без
  правки спеки — это территория ревьюера; также `work/**` как scratch-территория и обратная
  сторона G11, `testdata/` и цели вне дерева репозитория. Walk-up до `.git` работает как в G11, а
  дальше правит G2. Правка `.md` — не Go: работа `spec` и `benchmarker` гейтом не затронута.
- **Пакет → спека.** Каталог цели берётся относительно корня дерева записи. Файл в корне даёт
  `specs/main.md`, то есть корневой пакет `main`. Путь `<dir>/…go` даёт `specs/<dir>.md`;
  вложенный каталог даёт путь целиком `specs/<rel-путь>.md`. Раскладка репозитория одноуровневая,
  поэтому коллизий имён нет. **Отсутствие спеки — это блок** с инструкцией «сначала создай
  спеку»: шаг 2 workflow в AGENTS.md не допускает нового пакета без спеки, и свободы здесь нет.
- **Условие «спека обновлена» — git-состояние на момент вызова.** Проверка идёт в дереве цели
  записи через `git -C <root>`, и достаточно одного из двух условий:
  1. *грязная*: вывод `status --porcelain -- specs/<pkg>.md` непустой. Учитываются правка в
     рабочем дереве и в индексе, включая untracked — так проходит свежесозданная спека нового
     пакета;
  2. *изменена от базы ветки*: вывод `diff --name-only <mb> -- specs/<pkg>.md` непустой, где `mb`
     — `merge-base HEAD main`, канон A/B-базы из skill `workflow`. Если локальный `main` не
     резолвится, берётся `origin/main`; если нет и его, проверка пропускается. Неразрешимая база
     не должна давать ложный блок.
  Покрытие: порядок «спека→код» в `/task` и `/feature` даёт грязную спеку; контрольный коммит
  середи ветки и рестарт сервера после него проверяются по истории. Состояние читается с диска, а
  не из памяти.
- **Стоимость и кэш.** **Положительные** вердикты кэшируются в памяти процесса по паре
  (корень дерева, путь спеки). **Отрицательные** вердикты не кэшируются никогда: появившаяся спека
  пропускает следующую проверку без инвалидации. Замеры стоимости git-вызовов и экономику кэша
  содержит ADR-028. Кэш целиком сбрасывается событием шины `vcs.branch.updated`, потому что
  лишняя инвалидация дешёва. Если ветку сменили вне сессии без порождения события, остаётся
  протухший положительный вердикт — пропуск вместо блока. Это принятый класс G7/G8.
- **Обход `/quick`.** Триггер — хук `command.execute.before` с аргументами
  `{command, sessionID, arguments}`; он срабатывает до хода модели, поэтому метка гарантированно
  предшествует первой правке команды. При `command == "quick"` метка ставится на сессию
  `sessionID`. Имена `task` и `feature` **снимают** метку: перезапуск команды в той же сессии
  меняет режим. Время жизни — память процесса, пока жива сессия. `/quick` правит код в своей
  сессии без субагентов и попадает ровно под свою метку. Сессии субагентов `/feature` имеют
  другие `sessionID`, меток не имеют, и гейт для них активен. Альтернативные механизмы обхода
  отклонены; probe-замеры и обоснования — в ADR-028.
- **Блокировка.** Гейт бросает `GateError` с инструкцией: сначала обновить `specs/<pkg>.md` —
  контракт под изменение или пояснительная строка «поведение/API не меняются». Альтернатива —
  оформить код-only правку через `/quick` на `chore/<slug>`. Инструкция ссылается на ADR-028.
  **Режима warn нет**: предупреждение — это текст, а гейты существуют именно потому, что текст не
  страхует от забывчивости (ADR-022). Переключателем служит ветка согласно ADR-021: стал шумить —
  ветка закрывается как rejected.
- **Независимость.** Состояние G12 — метки сессий и кэш — не пересекается с G7/G8/G9/G10/G11, и
  они его не читают. Bash-правки Go (`sed -i`, `go fmt` внутри `make check`) — принятый
  непрозрачный класс G7/G8: цель — страховать от забывчивости про спеку на видимых путях агента, а
  не перехватывать терминал.

## Инварианты

- Ни один агент-субагент (`spec`, `coder`, `reviewer`, `benchmarker`) не запускает других
  субагентов; оркестрация остаётся у команды-диспетчера.
- Права на запись минимальны для роли: read-only агенты не пишут, а документальные агенты пишут
  только в свою область документации.
- На вызов инструмента влияет только намеренный `GateError`. Сбой внутренней логики гейта не должен
  ломать работу инструментов; он логируется.
- Множество зелёных отпечатков живёт только в памяти процесса плагина. Рестарт сервера означает
  пустое множество, и коммит требует свежей проверки. Множество глобально для процесса и не
  делится по `sessionID`: в `/feature` агент `coder` гоняет `make check` в своей сессии, а
  коммитит оркестратор в своей. Легальность коммита решает совпадение содержимого дерева с одним
  из отпечатков, а не автор или место прогона.
- Изменения permission-конфига и файлов `.opencode/plugins/*` применяются после рестарта
  opencode-сессии.

## Ограничения и edge cases

- Сопоставление путей в permission-слое — формы строки subject, порядок правил и тильду — описывает
  секция «Слой permission: сопоставление путей (ADR-026)». Там же причина, по которой G3/G4
  используют относительные паттерны `../kt-*` вместо `~/work/kt-*`.
- Слой permission не знает состояния — ветки или результата `make check`. Для таких проверок
  предназначен plugin-слой.
- `ask` проходим пользователем, в том числе авто-режимом. `deny` непроходим ни для кого, кроме
  человека, который правит сам конфиг.
- G7 v2 оперирует строкой команды и содержимым дерева. Обход алиасом или коммитом из скрипта
  возможен и принят — это класс осознанного обхода. Цель гейта — страховать от забывчивости
  прогнать проверку, а не защищать от злонамеренного обхода. Пользовательский терминал вне слоя
  плагина; это территория git hooks.
- Игнорируемые файлы (`work/**`, артефакты сборки) вне отпечатка G7: они не участвуют в сборке и
  тестах. Тест, читающий gitignore-нные данные, тоже вне гарантии гейта.
- Целевое дерево коммита в G7 резолвится текстом команды через git-`-C`, иначе через
  `workdir`/cwd инструмента. `cd` внутри команды не отслеживается — принятый класс G9, а
  WORKTREE-контракт требует cwd=`$WT`.
- Подтверждение успеха берётся из метаданных результата bash-инструмента. В opencode 1.18.x это
  `metadata.exit`: число; при abort или kill равно `null`, при таймауте отсутствует. Если новый
  opencode изменит формат метаданных, штамп перестанет ставиться. Отказ безопасен в сторону
  запрета: коммит блокируется, а не пропускается.
- Подтверждение exit code — механизм after-наблюдателей G7/G8. Обёртка `cmd; echo "exit=$?"`
  прячет внутренний сбой за итоговым нулём; это нашли на приёмке G8. Гейту G9 он не применим: тот
  stateless и exit code не читает. Уязвимы только гейты с состоянием.
- `flock(1)` отсутствует в базовом userland darwin. Без него каноническая команда падает в
  runtime с command not found — это вопрос настройки окружения по пробам AGENTS.md «Shell
  environment», а не исключение из гейта. G9 проверяет форму вызова команды, а не наличие
  утилиты.
- Правило сопоставления не отслеживает `cd` внутри команды: относительный lock-аргумент
  резолвится от `workdir` инструмента. Каноническое написание, запущенное из другого каталога,
  бьёт по иному файлу — принятый edge; WORKTREE-контракт требует cwd=`$WT`.
- Относительные паттерны `../kt-*` у G3/G4 резолвятся от корня проекта сессии. Контракт
  предполагает, что opencode запущен в main-дереве (ADR-024). Запуск сессии внутри worktree
  переопределяет, что для неё является «main»: `specs/**` накроет сам worktree, а основное дерево
  станет `../knighttour/…` и закроется.
- Удалённый worktree формально остаётся под паттерном, потому что permission сопоставляет строки
  без проверки существования. Запись в `<удалённый kt-*>/specs/…` воссоздала бы каталоги. Это
  принято: WORKTREE-контракт требует путь из свежего `git worktree add`, а G8 выполняет
  самокоррекцию своего множества. То влияние касается только блокировки main.
- Чужой каталог вне `~/work/kt-*`, например `~/work/<other>`: `external_directory` даёт ask (G2),
  а edit-слой G3/G4 даёт deny, и `--auto` его не снимает. Двойная защита проверена эмпирически
  (ADR-026).
- Plugin-хуки получают аргументы инструментов до любых преобразований permission-слоя. Формы
  строки subject из ADR-026 им недоступны, поэтому G8/G10/G11/G12 резолвят цели сами:
  относительные — от корня проекта сервера, абсолютные — без изменений. Структурная привязка G10
  (`<X>/tools ↔ <X>/specs/tools`) и walk-up до `.git` у G11 привязывают проверку к дереву цели
  записи, а не к дереву сессии.
- Текстовое упоминание имени тула в `specs/tools/README.md` вне строки таблицы выводит G10 из
  блока, потому что подстрока найдена. Это малозначимый край, и строка индекса остаётся зоной
  ревьюера. Обратный порядок G10 — тул удалён, карточка осталась — гейт не проверяет в принципе.
- При сбое git-вызова (таймаут, повреждённые refs) G12 пропускает правку. Для шумного гейта
  ложный блок дороже пропуска, а внутренний сбой ядро по контракту пропускает. Неразрешимая база
  ветки — отсутствие `origin/main` и `main` — даёт тот же проход.
- Инвалидация кэша G12 работает best-effort. Событие `vcs.branch.updated` не несёт ни сессии, ни
  дерева, а смена ветки вне поля зрения плагина его не порождает. Протухший положительный вердикт
  — лишний проход — принят. Обратного не случается: ложного блока после смены ветки конструкция не
  даёт, потому что отрицательные вердикты не кэшируются.
- Обход G12 меткой `/quick` живёт в сессии, получившей команду: субагенты унаследовать его не
  могут, так как у них другой `sessionID`. Снятие — только `/task` или `/feature` в той же сессии
  либо рестарт процесса. Это осознанно слабее «флага на задачу»: `/quick` — волевое действие
  пользователя, а не классификация каждой правки.

## Тесты

Конфиг не имеет кода; проверка гейта ручная: попытка заблокированного действия в сессии opencode
должна давать блок или ask. Для plugin-гейта приёмка состоит из воспроизводимых сценариев,
зафиксированных в ADR фичи.

Сценарии приёмки G7 (ADR-023; дополнения v2 — ADR-029):

1. Свежая сессия → `git commit -m x` → блок `GateError` с инструкцией.
2. Зелёный `make check` → тот же коммит проходит.
3. Зелёный прогон, затем любое редактирование файла через edit/write → коммит снова блокируется.
4. Одна команда `make check && git commit -m x` без предварительного штампа → проходит.
5. Красная `make check` (сломанный тест) → коммит остаётся заблокированным.
6. `git -C <worktree> commit ...` детектируется как коммит.
7. Негативные контроли: `git status` и `git log --oneline` не блокируются; не-`bash` инструменты
   гейтом не затрагиваются.
8. v2: зелёный прогон, затем правка файла через bash (`sed -i`, редирект) → коммит блокируется из
   за рассогласования отпечатка.
9. v2: правка через bash и возврат к исходному содержимому → коммит проходит; значима
   эквивалентность содержимого, а не факт правки.
10. v2: `git add` уже проверенного содержимого между check и коммитом → проходит. Подготовку в
    индекс содержимого, отличного от проверенной рабочей копии, — правка через bash, затем
    `git add`, затем откат копии — блокируется.
11. v2 close-flow: зелёный прогон в worktree, затем `git -C "$MAIN" merge --squash <ветка>`. Если
    main не ушёл, пост-squash содержимое равно зелёному отпечатку, и коммит проходит. Если main
    ушёл вперёд → блок; после `make -C "$MAIN" check` → проходит.
12. v2 авто-commit: на незелёном дереве команды `git merge <ветка>`, `git cherry-pick <c>`,
    `git revert <c>` и `git am x.patch` → блок с инструкцией двухшагового пути; на зелёном они
    проходят. `git merge --squash`, `git merge --no-commit` и `cherry-pick --no-commit` вне гейта
    и не блокируются.
13. v2 отказ в сторону запрета: git мгновенно недоступен при попытке коммита — сломанный PATH или
    цель вне репозитория → блок.

Сценарии приёмки G8 (ADR-024):

1. Без активных worktree → edit файла основного дерева проходит.
2. Зелёный `git worktree add <путь>` → edit/write основного дерева блокируется `GateError`,
    включая относительный путь инструмента; edit файлов внутри worktree проходит.
3. `apply_patch` со строкой `*** Update File: <main/…>` блокируется.
4. Зелёный `git worktree remove <тот же путь>` → правка main снова проходит.
5. Worktree из множества удалён с диска → при следующей правке срабатывает самокоррекция, и main
    не заблокирован.
6. Красная команда `git worktree add` с `exit != 0` множество не пополняет.
7. Красная команда `git commit` блокируется G7-гейтом независимо от состояния G8.

Сценарии приёмки G9 (ADR-025):

1. `make bench-deep` без flock → `GateError` с инструкцией и канонической командой.
2. `flock ../kt-bench.lock make bench-deep` проходит из корня репозитория или worktree;
    абсолютный путь к тому же lock-файлу — тоже.
3. Исключения: `make bench`, `make check` и `make bench-table LOG=…` проходят без lock'а.
4. `make bench-size N=7 DEPTHS=22 > work/x/log 2>&1` → блок; с flock-префиксом — проход, и при
    `N=5` тоже: решает имя цели.
5. Цепочки: `cd <wt> && make bench-8x8` → блок, потому что второй сегмент не защищён.
    `flock ../kt-bench.lock make bench-size N=7; echo done` → проход.
6. Прямой `go test -run='^$' -bench='BenchmarkCountAllTours/size7' ./counter/` без flock → блок,
    с flock → проход. Значения `size[56]` и `size6/depth14` проходят без lock'а. Флаг
    `-benchtime=10x` не путается с `-bench`. Равносильная двойная черта
    `--bench='BenchmarkCountAllTours/size7'` и пробельная форма — тоже блок, с flock → проход.
    Анонимный селектор `-bench=size7` → блок; `-bench=size[56]` проходит, как и принятый край
    `-bench=depth22` без size-сегмента.
7. `flock ./.bench.lock make bench-deep` — неканонический lock-файл → блок.
8. Негативные контроли: `git status`, `go test ./...` без `-bench` и не-bash инструменты не
    блокируются. G9 не трогает состояние G7/G8 и не зависит от него.

Сценарии приёмки G10 (ADR-027):

1. Запись нового `tools/new_tool.py` без карточки → `GateError` с инструкцией «сначала карточка +
    строка индекса».
2. Созданы карточка `specs/tools/new-tool.md` и строка в индексе, в любом порядке между собой →
    повторная запись проходит.
3. Правка существующего `tools/bench_table.py` проходит и ничего не требует; `apply_patch` со
    строкой `*** Update File:` по нему — тоже.
4. Карточка есть, упоминания в индексе нет → блок; после добавления строки → проход.
5. «Переименование»: запись `tools/renamed_tool.py` при старом файле на месте без карточки →
    блок; с переименованными карточкой и строкой индекса → проход.
6. `apply_patch` со строкой `*** Add File: tools/x.py` без карточки → блок.
7. Контекст worktree: запись `<wt>/tools/x.py` требует карточку в `<wt>/specs/tools/`, а не в
    main — это структурная привязка; отсутствие карточки только в main — не блок.
8. Негативные контроли: запись самой карточки и индекса, `work/<task>/script.py` и не-`.py` под
    `tools/` проходят. G10 stateless и не влияет на состояние G7/G8/G9.

Сценарии приёмки G11 (ADR-027):

1. Запись `bench.log` в корень репозитория и в любой каталог вне `work/` → `GateError` с
    инструкцией про `work/<task>/`.
2. Запись `work/<task>/run.log` проходит; правка `work/README.md` — проходит.
3. Двоичные файлы по расширению: `prog.exe`, `libfoo.so` и `x.out` вне `work/` → блок.
4. Негативные контроли: `Makefile`, `.gitignore`, `go.sum`, `*.go` и `*.md` проходят.
5. `apply_patch` со строкой `*** Add File: junk.log` → блок; правка уже существующего вне `work/`
    лога, созданного через bash, — тоже блок, так как правки без исключений.
6. Запись `.log` за пределами репозитория, без `.git`-предка: гейт не срабатывает, это территория
    G2.
7. `make bench > root.log` через bash не блокируется — принятый непрозрачный класс, зафиксирован.
    G11 stateless и не влияет на состояние других гейтов.

Сценарии приёмки G12 (ADR-028; применяются со свежим процессом opencode):

1. Чистое дерево, ветка от `main`: edit `<pkg>/x.go` → `GateError` с инструкцией про спеку или
    `/quick`.
2. Правка `specs/<pkg>.md` до грязного состояния → тот же edit проходит. Новый пакет:
    `foo/foo.go` без спеки → блок; после создания `specs/foo.md` — проход.
3. Контрольный коммит всего изменения через `git add -A && git commit` → правки кода проходят по
    history-проверке от merge-base и не требуют грязной спеки; рестарт сервера после коммита —
    тоже.
4. Живьём `/quick <мелкая правка>`: в сессии, выполнившей команду, edit `.go` без изменения спек
    проходит, в том числе внутри самого хода команды — обход по хуку `command.execute.before`.
    Затем `/task` или `/feature`, запущенные в той же сессии, метку снимают, и следующий edit кода
    без спеки блокируется.
5. Негативные контроли: `_test.go`, `work/<task>/scratch.go`, `.md`, не-Go и запись вне
    репозитория не блокируются. Чисто-спековая сессия, где только `.md`, гейтом не затронута.
6. Контекст worktree: edit `<wt>/<pkg>/x.go` проверяет спеку дерева `<wt>`, а не main, через
    walk-up до `.git` цели. Правки территорий G7/G8/G9/G10/G11 не меняют состояние G12 и наоборот.

Сценарии приёмки G3/G4 (ADR-026; применяются со свежим процессом opencode):

1. Сессия в main при активном feature-worktree: агент `spec` пишет по абсолютному пути
    `<worktree>/specs/<pkg>.md` — разрешено, файл создан.
2. Тот же агент пишет в корень worktree, `<worktree>/README.md` → блокируется G3 (`deny`).
3. Тот же агент пишет в `~/work/<other>/specs/x.md` → блокируется G3 даже в `--auto`: внешний ask
    автопроходится, но edit-слой отказывает.
4. `spec` пишет `specs/**` основного дерева: без активных worktree — разрешено; при активном →
    блокируется G8. Гейт не сломан: permission пропускает, а plugin убирает блокировку.
5. Для `benchmarker` разрешены `<worktree>/specs/decisions/NNN-*.md` и
    `<worktree>/work/<task>/log`; `<worktree>/counter/*.go` блокируется G4. Base-worktree
    `../kt-base-<slug>` попадает под паттерн `../kt-*`: замеры пишутся в ADR основного дерева или
    worktree фичи, а не в базу.
6. Негативный контроль: `reviewer` и `coder` не затронуты, G5/G6 без изменений.
