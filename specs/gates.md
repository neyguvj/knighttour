# gates: жёсткие гейты агентского пайплайна (ADR-022)

## Ответственность

Превращает обязательные правила проекта в непроходимые проверки уровня инструмента — такие,
которые модель не может проигнорировать текстом ответа. Два слоя:

- **permission-конфиг** (`opencode.json` в корне, frontmatter агентов в `.opencode/agent/`) —
  декларативные `allow | ask | deny` по паттернам bash-команд и путей edit; `deny` не обходится
  даже в `--auto`;
- **plugin-хуки** (`.opencode/plugins/gates.ts`, `tool.execute.before`) — stateful-проверки,
  недоступные паттернам (состояние ветки, истории прогонов); намеренное исключение `GateError`
  блокирует вызов инструмента.

Гейт существует ровно в одном из двух слоёв; текст в AGENTS.md остаётся объяснением «зачем»,
а не механизмом.

## Реестр включённых гейтов

| ID | Слой | Что блокирует | Где задано |
|----|------|---------------|-----------|
| G1 | permission (global) | `git push` / `git -C … push` — только подтверждение пользователя | `opencode.json → permission.bash` |
| G2 | permission (global) | доступ к путям вне worktree: allow только `~/work/knighttour/**` и `~/work/kt-*/**`, иначе ask | `opencode.json → permission.external_directory` |
| G3 | permission (agent `spec`) | edit/write вне `specs/**`, `work/**` и `~/work/kt-*/specs/**`, `~/work/kt-*/work/**`; запуск субагентов | `.opencode/agent/spec.md` |
| G4 | permission (agent `benchmarker`) | edit/write вне `specs/decisions/**`, `work/**` и `~/work/kt-*/specs/decisions/**`, `~/work/kt-*/work/**`; запуск субагентов | `.opencode/agent/benchmarker.md` |
| G5 | permission (agent `reviewer`) | любые правки (уже было) + запуск субагентов | `.opencode/agent/reviewer.md` |
| G6 | permission (agent `coder`) | запуск субагентов | `.opencode/agent/coder.md` |
| G7 | plugin (`gates.ts`) | `git commit` без свежего зелёного `make check` (ADR-023) | `.opencode/plugins/gates.ts` |
| G8 | plugin (`gates.ts`) | правку основного дерева при активном feature-worktree (ADR-024) | `.opencode/plugins/gates.ts` |
| G9 | plugin (`gates.ts`) | `make bench-deep`/`bench-8x8`/`bench-size` и прямой `go test -bench` на тяжёлые доски без flock глобального lock'а (ADR-025) | `.opencode/plugins/gates.ts` |

## Plugin-ядро (`.opencode/plugins/gates.ts`)

Единый модуль плагина opencode — точка подключения всех stateful-гейтов. opencode загружает
файлы из `.opencode/plugins/` автоматически при старте сервера.

Контракт ядра:

- Модуль экспортирует ровно одну функцию-плагин: `export const GatesPlugin: Plugin` (тип —
  `@opencode-ai/plugin`). Матчеры и хелперы не экспортируются: загрузчик считает каждую
  экспортированную функцию плагином.
- Ядро регистрирует по одному обработчику `tool.execute.before`, `tool.execute.after` и `event`
  и диспетчирует вызовы по списку гейтов в порядке регистрации. Гейт — элемент списка формы:

  ```ts
  interface Gate {
    id: string                  // ID из реестра («G7»)
    before?(call): void         // наблюдение args до исполнения; может бросить GateError
    after?(call): void          // наблюдение результата (для утилит — фиксация успеха)
    onEvent?(event): void       // события шины opencode (например file.edited)
  }
  ```

- Намеренная блокировка — исключение `GateError` с текстом-инструкцией для модели; оно
  прекращает вызов инструмента (текст возвращается модели как ошибка инструмента).
  Неожиданное внутреннее исключение гейта логируется (`client.app.log`) и не влияет на вызов:
  fail-closed только для `GateError`, баг гейта — fail-open.
- Состояние гейтов — память процесса плагина: между серверами/перезапусками не разделяется.

Новый гейт = новый элемент списка + строка в реестре; ядро при этом не меняется.

## Гейт G7: make check перед git commit (ADR-023)

Пассивный трекинг «зелёного штампа»: плагин ничего не исполняет сам — он запоминает факт
успешного `make check` и требует штамп свежим к моменту `git commit`.

- **Штамп.** Источник: завершение команды `make check` в инструменте `bash` с положительным
  подтверждением exit code 0 из результата инструмента (без подтверждения — не ставится).
  Инвокация распознаётся токен-матчером по сегментам команды; допускаются флаги `make`,
  `-C <dir>`, env-префиксы. Exit-код относится ко всей строке: подтверждение действительно,
  только если после инвокации `make check` все оставшиеся разделители — `&&` (после `; | ||`
  и переводов строк код принадлежит более позднему сегменту — успех не подтверждён).
- **Инвалидация.** Штамп снимается вызовами инструментов `edit` / `write` / `patch`
  (в opencode ≥1.18 id патчера — `apply_patch`) и событием шины `file.edited`. Изменения файлов через `bash` штамп не снимают — зафиксированное
  ограничение v1.
- **Проверка.** Вызов `bash`, содержащий инвокацию `git commit` (токен-матчер: бинарь `git` +
  субкоманда `commit`; допускаются глобальные флаги `-C`, `-c k=v`, `--git-dir=…`, env-префиксы;
  команда режется по shell-разделителям `&& || ; |` и переводам строк, сегменты проверяются
  отдельно), без действующего штампа блокируется `GateError` с инструкцией: сначала выполнить
  `make check` и повторить коммит (или использовать самогейдящуюся цепочку).
- **Самогейдящаяся цепочка.** Команда пропускается без штампа, если инвокация `make check`
  связана с инвокацией `git commit` путём строго из `&&`: все разделители между их сегментами —
  `&&`, и check стоит раньше. Тогда коммит физически не состоится на красной проверке — гарантия
  эквивалентна раздельному выполнению. Разделители `; | ||` и переводы строк связь не дают
  (коммит может состояться при красном check).
- **Ложные срабатывания.** Матчер консервативен: безобидные команды, текстом содержащие
  `git commit`, могут блокироваться (переформулировка ничего не стоит). Ложные пропуски —
  только невидимые матчеру пути (алиасы, коммит из скрипта, `git merge --squash`, cherry-pick);
  они вне скоупа v1.

## Гейт G8: main read-only при активном feature-worktree (ADR-024)

Сессия оркестратора живёт в основном дереве и не перезапускается между фичами; изоляция фичи —
worktree, а не процесс. Пока гейт считает worktree активным, править основное дерево нельзя —
страховка от «забыл workdir/абсолютный путь» в контракте WORKTREE (skill `workflow`).

- **Активные worktree.** Множество строится из наблюдаемых bash-команд с exit 0: инвокация
  `git … worktree add <path>` добавляет разрешённый абсолютный `<path>` (база относительности —
  параметр `workdir` инструмента, иначе cwd процесса; `git -C <dir>` задаёт базу),
  `git … worktree remove <path>` убирает. Не-нулевой exit ничего не меняет.
- **Самоизлечение.** Перед каждой проверкой несуществующие пути молча выпадают из множества:
  worktree, удалённый вне сессии (ручной терминал), перестает блокировать main при первой же правке.
- **Проверка.** Инструменты `edit`/`write` (поле `filePath`) и `patch`/`apply_patch` (строки
  `*** Update|Add|Delete File:` текста патча) с целью внутри корня основного дерева (git worktree
  сервера), пока множество непусто, блокируются `GateError` со списком активных worktree.
  Относительные пути инструментов разрешаются от корня проекта — это и есть основное дерево.
- **Что не блокируется.** Bash-правки основного дерева (как в G7 — матчер снимает «забыл», а не
  отражает злоумышленника); git-операции закрытия (`git -C "$MAIN" merge --squash` — bash, не
  edit-инструмент); `/quick` на `chore/<slug>` без отдельного worktree (множество пусто).

## Гейт G9: тяжёлые бенчи только под flock (ADR-025)

Долгие замеры (7×7/8×8, часы на точку) при параллельных прогонах разных фич искажают тайминги и
peak RSS; дисциплина сериализации глобальным lock'ом `../kt-bench.lock` задана в AGENTS.md и skill
`workflow`. Текст не снимает «забыл flock» — гейт блокирует инвокации без обёртки. В отличие от G7/G8
он **stateless**: только наблюдатель `before` на bash, ни штампов, ни множеств, exit code не читается —
решение по одной строке команды.

- **Тяжёлая инвокация.** Сегмент команды (разбиение и токенизация как в G7) под гейтом, если:
  - содержит соседние токены `make` + цель `bench-deep`, `bench-8x8` или `bench-size` (флаги `make`
    и `-C <dir>` допускаются; критерий — имя цели, значения `N=`/`DEPTHS=` не разбирать);
  - либо `go test` с флагом `-bench`/`--bench` (flag-пакет Go эквивалентен; формы `-bench <значение>`
    и `-bench=<значение>`) выбирает тяжёлую доску: значение после снятия кавычек содержит size-сегмент
    `size<N>`/`size[...]` с 7 или 8 — независимо от упоминания имени бенчмарка (единственный
    size-сегментированный бенч репозитория — `BenchmarkCountAllTours`, ложный блок анонимного селектора
    в безопасную сторону); иначе, если значение матчит все доски (`.`) либо упоминает этот бенчмарк без
    size-сегмента — тоже тяжёлое. Прочие значения не классифицируются; анонимные селекторы без
    size-сегмента (`-bench=depth22`) — принятый край вне матчера.
- **Что не блокируется никогда.** `make bench` (доски 5×5/6×6, минуты) — явное исключение; остальные
  цели `make` и все не-bash инструменты вне гейта. `make bench-size N=5` блокируется несмотря на лёгкую
  доску: лёгкий замер в контеншене с долгим искажается так же, а свободный lock бесплатен.
- **Защита сегмента.** Сегмент проходит, если до тяжёлой инвокации в том же сегменте стоит вызов
  `flock` (приближение обёртки: тяжёлая цель — аргумент flock). Флаги flock пропускаются (`-n`, `-s` и
  т.п.; значения флагов с параметром вида `-w` потребляют следующий токен), первый не-флаг его аргументов —
  lock-файл.
- **Канонический lock.** Защита признаётся только когда lock-файл разрешается в
  `<родитель-основного-дерева>/kt-bench.lock`: относительный аргумент flock резолвится от параметра
  `workdir` инструмента, иначе от cwd процесса плагина (та же база, что у G8). В каноническом написании
  `../kt-bench.lock` это один файл для main и всех соседних worktree; иной lock-файл (например локальный
  для worktree) прогоны не сериализует и защиты не даёт.
- **Блокировка.** Вся bash-инвокация блокируется `GateError` с инструкцией: повторить как
  `flock ../kt-bench.lock make bench-size N=<n> DEPTHS=<d>` из корня worktree, с пометкой, что короткому
  `make bench` lock не нужен.
- **Консервативность матчера.** Обёртки (`sudo`, `env`, `time`) не скрывают тяжёлую инвокацию (пара
  `make`+цель ищется по сегменту) и не мешают проходу: flock остаётся валиден на любой позиции сегмента.
  Текстовые упоминания тяжёлых целей отдельными словами (echo, grep) могут дать ложный блок — тот же
  принятый класс, что у G7 (переформулировка ничего не стоит); разбора кавычек нет.

## Инварианты

- Ни один агент-субагент (`spec`, `coder`, `reviewer`, `benchmarker`) не запускает других
  субагентов — оркестрация остаётся у команды-диспетчера.
- Права на запись минимальны для роли: read-only агенты не пишут, документальные агенты пишут
  только в свою область документации.
- На вызов инструмента влияет только намеренный `GateError`; сбой внутренней логики гейта не
  должен ломать работу инструментов (логируется).
- Зелёный штамп живёт только в памяти процесса плагина: рестарт сервера ⇒ штампа нет, коммит
  требует свежей проверки. Штамп глобален для процесса (не делится по `sessionID`): в `/feature`
  `coder` гоняет `make check` в своей сессии, а коммитит оркестратор в своей.
- Изменения permission-конфига и файлов `.opencode/plugins/*` применяются с рестартом
  opencode-сессии.

## Ограничения и edge cases

- Паттерны permission матчат строку инструмента/команды простыми wildcard'ами (`*`, `?`);
  last-match-wins, catch-all `"*"` ставится первым.
- Слой permission не знает состояния (ветка, результат `make check`) — для таких проверок
  предназначен plugin-слой.
- `ask` проходим пользователем (и авто-режимом); `deny` непроходим ни для кого, кроме правки
  самого конфига человеком.
- G7 оперирует строкой команды модели: обход скриптом/алиасом возможен и принят — цель гейта
  снять «забыл прогнать», а не отразить злоумышленника. Пользовательский терминал вне слоя
  плагина (это территория git hooks).
- Подтверждение успеха берётся из метаданных результата bash-инструмента (opencode 1.18.x:
  `metadata.exit` — число; при abort/kill равно `null`, при таймауте отсутствует); если формат
  метаданных изменится в новой версии opencode — штамп перестанет ставиться: отказ безопасный
  (коммит блокируется, а не пропускается).
- Подтверждение exit code — механизм after-наблюдателей (G7/G8): обёртка `cmd; echo "exit=$?"` прячет
  внутренний сбой за итоговым нулём (найдено приёмкой G8). Гейту G9 это не применимо — он stateless и
  exit code не читает; уязвимы только state-гейты.
- `flock(1)` отсутствует в базовом userland darwin: без него каноническая команда падает в runtime
  (command not found) — это вопрос настройки окружения (пробы по AGENTS.md «Shell environment»), а не
  исключение из гейта; G9 проверяет форму инвокации, не наличие утилиты.
- `cd` внутри команды матчером не отслеживается: относительный lock-аргумент резолвится от `workdir`
  инструмента. Каноническое написание, запущенное из другого каталога, бьёт по иному файлу — принятый
  edge, WORKTREE-контракт требует cwd=`$WT`.

## Тесты

Конфиг не имеет кода; проверка гейта ручная: попытка заблокированного действия в сессии
opencode должна давать блок/ask. Для plugin-гейта приёмка — воспроизводимые сценарии,
зафиксированные в ADR фичи.

Сценарии приёмки G7 (ADR-023):

1. свежая сессия → `git commit -m x` → блок `GateError` с инструкцией;
2. зелёный `make check` → тот же commit проходит;
3. зелёный, затем любое редактирование файла через edit/write → commit снова блокируется;
4. одна команда `make check && git commit -m x` без предварительного штампа → проходит;
5. красная `make check` (сломанный тест) → commit остаётся заблокированным;
6. `git -C <worktree> commit ...` детектируется как коммит;
7. негативные контроли: `git status`, `git log --oneline` не блокируются; не-`bash` инструменты
   гейтом не затрагиваются.

Сценарии приёмки G8 (ADR-024):

1. без активных worktree → edit файла основного дерева проходит;
2. зелёный `git worktree add <путь>` → edit/write основного дерева блокируется `GateError`
   (в т.ч. относительный путь инструмента), edit файлов внутри worktree — проходит;
3. `apply_patch` со `*** Update File: <main/…>` блокируется;
4. зелёный `git worktree remove <тот же путь>` → правка main снова проходит;
5. worktree из множества удалён с диска → на следующей правке самоизлечение, main не заблокирован;
6. красный (`exit != 0`) `git worktree add` множество не пополняет;
7. красная команда `git commit` G7-гейтом блокируется независимо от состояния G8.

Сценарии приёмки G9 (ADR-025):

1. `make bench-deep` без flock → `GateError` с инструкцией и канонической командой;
2. `flock ../kt-bench.lock make bench-deep` проходит из корня репозитория/worktree; абсолютный путь
   к тому же lock-файлу — тоже;
3. исключения: `make bench`, `make check`, `make bench-table LOG=…` проходят без lock'а;
4. `make bench-size N=7 DEPTHS=22 > work/x/log 2>&1` → блок; с flock-префиксом — проход (и при `N=5`:
   решает имя цели);
5. цепочки: `cd <wt> && make bench-8x8` → блок (второй сегмент не защищён);
   `flock ../kt-bench.lock make bench-size N=7; echo done` → проход;
6. прямой `go test -run='^$' -bench='BenchmarkCountAllTours/size7' ./counter/` без flock → блок, с
   flock → проход; значения `size[56]`, `size6/depth14` проходят без lock'а; `-benchtime=10x` не путается
   с `-bench`; равносильная двойная черта `--bench='BenchmarkCountAllTours/size7'` (и пробельная форма) —
   тоже блок, с flock → проход; анонимный селектор `-bench=size7` — блок, `-bench=size[56]` и
   принятый край `-bench=depth22` (без size-сегмента) — проход;
7. `flock ./.bench.lock make bench-deep` — неканонический lock-файл → блок;
8. негативные контроли: `git status`, `go test ./...` (без `-bench`), не-bash инструменты не блокируются;
   G9 не трогает состояние G7/G8 и не зависит от него.
