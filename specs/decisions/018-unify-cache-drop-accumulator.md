# ADR-018. Одна таблица `cache.Cache`: `Accumulator` и `LocalSink` удалены

## Статус

Принято (2026-09-14, пользователь). Заменяет ADR-002 (аддитивный `Accumulator` + `LocalSink`
как отдельная таблица gen A); снимает drain-чтение из ADR-004 (шард-хэш по `State` остаётся в
силе). Механика task-cache (`Set`/`Get`/`Each`, RWMutex, без дренажа) — ADR-011/ADR-012/ADR-013 —
не меняется.

## Контекст

В пакете `cache` жили две шардированные таблицы «ключ → вес»: `Accumulator` (аддитивный `Add`,
чтение только `Drain()`, писатели через `LocalSink`) для промежуточной таблицы gen A и `Cache`
(task-cache: `Set`/`Get`/`Each`). Дублирование почти полное:

- **`Cache.Set` уже аддитивен** (`data[k] += w`, нулевой вес — no-op), т.е. семантически это тот
  же `Accumulator.Add`, только с защитой от нуля; отдельная add-операция не требовалась.
- `dfsGen` (путь `Accumulator`) и `dfsTask` (путь `Cache`) — байт-в-байт идентичные спуски кроме
  строки записи (`sink.Add` против `c.Set`); после унификации совпадают и `GenerateRoots`, и
  `GenerateTasks`.
- `LocalSink` стал рудиментом: горячий путь gen B пишет в task-cache прямым `Set` ещё с ADR-011,
  а единственный оставшийся потребитель sink — фаза A, которая идёт мкс–мс (дерево глубины
  `TwoPhaseBaseDepth=5`, ~десяток стартовых групп). Замер ADR-002 о contention прямого Add
  относился к профилю генерации task-cache (миллиарды записей), а не к gen A.

Приоритет задачи — упрощение и устранение дублирования; производительность gen A не критична
(слова пользователя). Пик RSS процесса — живая task-cache (ADR-014), путь которого изменение не
задевает.

## Решение

Один тип `cache.Cache` на обе роли пайплайна:

- **Удалены** `Accumulator`, `LocalSink`, `NewAccumulator`, `Add`, `Local`, `Flush`, `Drain`,
  `drainShard`, `localFlushLimit`. Общий `shardIndex`/`numShards` переезжают в `cache.go`;
  `Entry` остаётся как запись-элемент worklist фазы B.
- **Промежуточная таблица gen A** — отдельный `Cache`: фаза A пишет прямым `Set`, затем после
  барьера errgroup обходом `Each` (писателей уже нет → предусловие выполнено) материализуется в
  `[]cache.Entry` и выбрасывается. Таблица мала, поэтому освобождение — обычным GC; пошардовый
  дренаж (`drainShard`) не нужен, а копирующий снимок больших таблиц по-прежнему запрещён
  (ADR-004/ADR-012/ADR-013) — он касается только task-cache, обходимой прямым `Each`.
- **`searcher`**: `GenerateRoots` и `dfsGen` удалены; остаётся единственный генерационный спуск
  `GenerateTasks(ctx, *cache.Cache, start, orbitSize, depth)` (тот же код, что был у `dfsTask`) +
  `ExtendTask`. Фаза A вызывает `GenerateTasks` с промежуточным `Cache`, фаза B — `ExtendTask` с
  task-cache.
- **`counter.generateIntermediate`**: `NewAccumulator` → `NewCache`, `sink.Add` → прямой `Set`
  внутри `GenerateTasks`, `Drain()` → сборка `[]Entry` через `Each(ctx, 1, …)` (одна горутина —
  без мьютекса на общий срез).

Аддитивность и коммутативность сложения сохранены → итог не зависит от тайминга записей и числа
воркеров; защита `Set` от нуля лишь убирает латентную возможность завести ключ с весом 0, которую
`Accumulator.Add` не отсекал (на практике веса — размеры орбит ≥ 1, так что поведение совпадает).

## Последствия

- В пакете одна таблица вместо двух; `searcher` теряет один дублирующий спуск и один публичный
  метод; исчезает отдельный тестовый файл `cache/accumulator_test.go` (покрытие sink больше не
  нужно — его нет).
- Фаза A платит шард-локом на лист вместо локального схлопывания дублей; при ms-масштабе фазы и
  уже принятом прямом `Set` в миллиардном gen B это несущественно.
- Чтение промежуточной таблицы — материализация среза при живой таблице (пик +O(записей));
  допустимо только для малой gen A и прямо запрещено для task-cache (зафиксировано в
  `specs/cache.md`).

## Замеры

n/a по производительности: изменения вне горячего пути (gen A ≪ конвейера), путь task-cache/пик
RSS не затронуты. Ожидание benchmarker — NOISE на всех досках; отдельного A/B не заводится.
Решение принято по соображениям простоты/устранения дублирования (явный приоритет пользователя).
