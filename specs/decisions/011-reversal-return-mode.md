# ADR-011. Возврат reversal как второго режима подсчёта (флаг `-mode`)

## Статус

Принято (реализация по плану 06). A/B-замеры сняты 2026-09-12 (см. «Замеры»); перенос
default `-mode` заблокирован критерием RSS до плана 08 / ADR-012.

## Контекст

На стенде 7×7 d22 class mode проигрывает эталонному reversal (git `0d142f4`) по обеим
осям: 596 с / 23.5 ГБ против 252 с / 9.6 ГБ при идентичном дереве генерации. Канонизация
целого дополнения не дедуплицирует почти ничего, но уничтожает кросс-задачное
переиспользование подзадач общего task-cache (17.27G prune-событий финального DP против
1.73G). Планы 02/03B/04 подтвердили: время живёт в deep-классе, где структурные проверки
и хвостовое мемо бесполезны.

## Решение

Reversal портируется на текущую обвязку вторым режимом за флагом `-mode class|reversal`
(дефолт — `class` до вердикта A/B-свода). Двухфазная генерация и мониторинг общие;
отличается финал: gen B пишет сырые канонические префиксы в возвращённый `cache.Cache`
(task-cache), count-фаза идёт DFS'ом со стопом на уровне `totalCells − d` и ответом
`Σ Get(canon(U,u))/orbitSize`.

Осознанные отступления от эталона (`0d142f4`):
- `cache.Cache` **не знает о симметриях** (эталон держал `*symmetry.Symmetry` и канонизировал
  в Get/Set); единый `Get` вместо пары `Get/GetCanonical`, писатель канонизует сам;
- веса `uint64` вместо `int`; шарды 128 с хэшем по State (общий хелпер с Accumulator)
  вместо 64 по state+end;
- oracle-слой не переносится (эталонный прогон снят при `-oracle-depth 0`);
- генерация пишет в task-cache прямым `Set` (верный порт; LocalSink — только если профиль
  покажет contention на локах шардов);
- count-dispatch — чанк-воркеры с атомарным индексом по `Entries()` вместо per-shard `Each`.

## Последствия

- До этапа 7 плана живут два режима; оба обязаны переживать `make check`.
- Task-cache не дренируется по шардам и живёт до конца count-фазы — на низких глубинах
  дороже M; точка OOM — результат A/B, не баг.
- Статистика hits/misses зависит от порядка воркеров; тесты фиксируют только итог.

**Вердикт.** WIN против базы (`9800c64`, class-only): на целевой 7×7 d22 reversal-порт быстрее
class в **2.65×** (215 с против 569 с) при RSS на 11% ниже и побитово точном итоге; быстрее и
эталонного git (−13…−14% при повторах ±1%). Критерий плана «RSS ≤10.5 ГБ» **не выполнен**:
пик порта 18.9–21.4 ГБ — ×2 к эталону стенд-в-стенд; вероятные причины (не исправлять задним
числом, проверять отдельной задачей): копия `Entries()` (~3.2 ГБ при 131.8M записей) при живом
task-cache + GC-headroom (totalAlloc 32.8 ГБ против неизмеренного у эталона). До решения по RSS
перенос default `-mode` (шаг 7 плана) не проводить.

**Точка перегиба class↔reversal.** На 6×6 reversal дешевле только в окне d12–d14 (−11…−16%);
вне его быстрее class, а на d≤3 class платит памятью (680 МБ против плоских 37 МБ). На 7×7
reversal монотонно дешевеет с ростом d до 22 (d18: 464 с / 4.2 ГБ → d22: 215 с / ~19–21 ГБ —
экономия времени покупается пиком).

**Pending (бюджет свода исчерпан):** class 7×7 d18/d14, reversal 7×7 d14 (оценочно часы и
риск своппинга по кривой task-cache); повторный эталон — не требуется (воспроизведён).
