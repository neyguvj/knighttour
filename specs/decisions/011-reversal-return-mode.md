# ADR-011. Возврат reversal как второго режима подсчёта (флаг `-mode`)

## Статус

Принято; реализация сделана по плану 06. A/B-замеры сняты 2026-09-12 (см. раздел «Замеры»).
Перенос значения `-mode` по умолчанию заблокирован критерием RSS до плана 08 и ADR-012.

Дополнено 2026-09-13: остаток A/B-свода по 7×7 снят (нижний подраздел раздела «Замеры»),
и свод шага 6 плана 06 закрыт. ADR-014 сняла блокировку значения `-mode` по умолчанию,
вызванную RSS. По итогам свода принято решение шага 7 (2026-09-13, пользователь):
**глобальное значение `-mode` по умолчанию → `reversal`**. Перенос этого значения в коде —
отдельный коммит; судьба режима class (его удаление) — отдельное будущее решение.

## Контекст

На стенде 7×7 при глубине 22 режим class проигрывает эталонному reversal (git `0d142f4`)
по обеим осям: 596 с и 23.5 ГБ против 252 с и 9.6 ГБ при идентичном дереве генерации.
Канонизация дополнения целиком почти ничего не дедуплицирует, но уничтожает переиспользование
подзадач между задачами внутри общего task-cache: 17.27G событий отсечений финального
динамического программирования против 1.73G. Планы 02, 03B и 04 подтвердили, что время живёт
в глубоких классах задач, где структурные проверки и хвостовая мемоизация бесполезны.

## Решение

Reversal перенесён на текущую обвязку вторым режимом за флагом `-mode class|reversal`;
значение по умолчанию — `class` до вердикта A/B-свода. Двухфазная генерация (`gen A` + `gen B`)
и мониторинг у режимов общие, отличается только финал. Gen B пишет сырые канонические префиксы
в возвращаемый `cache.Cache` (task-cache). Count-фаза идёт поиском в глубину с ранней остановкой
на уровне `totalCells − d`, а ответ равен `Σ Get(canon(U,u))/orbitSize`.

Осознанные отступления от эталона (`0d142f4`):

- `cache.Cache` **не знает о симметриях** (эталон держал `*symmetry.Symmetry` и канонизировал
  в `Get`/`Set`); единый `Get` заменяет пару `Get`/`GetCanonical`, и писатель канонизует сам;
- веса имеют тип `uint64` вместо `int`; шардов 128 с хэшем по State (вспомогательная функция
  общая с Accumulator) вместо 64 с хэшем по state+end;
- слой oracle не переносится: эталонный прогон снят при `-oracle-depth 0`;
- генерация пишет в task-cache прямым вызовом `Set` — это точный перенос эталона; `LocalSink`
  вводить только если профиль покажет конкуренцию за блокировки шардов;
- раздачу count-фазы ведут чанк-воркеры с атомарным индексом по `Entries()` вместо обхода
  `Each` по каждому шарду.

## Последствия

- До этапа 7 плана живут оба режима, и каждый обязан проходить `make check`.
- Task-cache живёт до конца count-фазы и, в отличие от аккумулятора M (таблицы весов финала
  режима class), не вычитывается по шардам; на низких глубинах он из-за этого стоит дороже.
  Появление точки OOM — результат A/B-сравнения, а не дефект.
- Статистика hits/misses зависит от порядка воркеров, поэтому тесты фиксируют только итог.

### 2026-09-12, A/B-свод (benchmarker). Стенд: Apple M4 Max, 14 CPU, 36 ГБ, Go 1.25.4 darwin/arm64

worktree `0d142f4`: его двоичный файл из `go run` замеряли через `/usr/bin/time -l`.
Порт — рабочее дерево поверх коммита `9800c64`.

**Вердикт.** WIN против базы (`9800c64`, только режим class): на целевой 7×7 d22 порт reversal
быстрее режима class в **2.65×** (215 с против 569 с), RSS ниже на 11%, а итог побитово точен;
порт обгоняет и эталонный git — −13…−14% при повторах ±1%. Критерий плана «RSS ≤10.5 ГБ»
**не выполнен**: пик порта составляет 18.9–21.4 ГБ — это в 2 раза выше эталона на одном стенде.
Вероятные причины (не исправлять задним числом, проверять отдельной задачей): копия `Entries()`
(~3.2 ГБ при 131.8M записей) поверх живого task-cache и запас памяти, который сборщик мусора
держит сверх пика; totalAlloc — 32.8 ГБ против неизмеренного у эталона. Пока вопрос с RSS не
решён, перенос значения `-mode` по умолчанию (шаг 7 плана) проводить нельзя.

**Точка перегиба между режимами.** На 6×6 режим reversal дешевле только в окне d12–d14
(−11…−16%); вне его быстрее режим class, а на d≤3 режим class платит памятью: 680 МБ против
плоских 37 МБ. На 7×7 режим reversal монотонно дешевеет с ростом глубины до 22 (d18:
464 с / 4.2 ГБ, затем d22: 215 с / ~19–21 ГБ) — экономию времени покупают пиком памяти.

**Отложено (бюджет свода исчерпан).** Остались три точки: class на 7×7 d18 и d14, reversal на
7×7 d14; по оценке — часы на точку и риск свопинга из-за роста task-cache. Повторный эталон не
требуется, он воспроизведён. *(Закрыто прогоном 2026-09-13 ниже: оценки оказались
пессимистичны в разы, риск не проявился.)*

### 2026-09-13, закрытие остатка свода 7×7 (benchmarker). Стенд: Apple M4 Max, 14 CPU, 36 ГБ, macOS 26.3.1, Go 1.25.4 darwin/arm64

HEAD `76ca1c6`: база и замер идут на одном дереве, поэтому это не сравнение ревизий, а снятие
отложенных **абсолютных точек** свода (см. «Отложено» выше). Метод: `BENCH_MODE=class|reversal
make bench-size N=7 DEPTHS=<d>`, каждая точка отдельным процессом при `-benchtime=1x`; точки
идут строго последовательно на праздном стенде, своп за время всех прогонов не использовался.
Режим reversal считается со значением `-gc-percent 40` по умолчанию: ADR-014 понижает GOGC на
время самого конвейера. Режим class сборщик мусора не трогает. Внешний `GOGC` не выставлен.
Проверка `toursExpected`: **все прогоны точны** (165 575 218 320).

GOGC=100): на HEAD время выросло на 6.1%, а RSS упал на 38.4%. У каждого режима по одному

¹ — данные ADR-011 (2026-09-12); код пути class с тех пор не менялся: ADR-012, ADR-013 и
ADR-014 трогали только reversal. ² — верификация ADR-014 (n=6, медиана) на том же коде

Итог totalAlloc по своду: у режима class — 342 ГБ (d18) и 3.87 ТБ (d14), у reversal — 8.3 ГБ
(d18) и 1.05 ГБ (d14). На низких глубинах режим class расходует терабайты памяти на
кратковременные аллокации, тогда как профиль reversal плоский по всем точкам.

**Выводы для шага 7.** Решение о значении `-mode` по умолчанию здесь не принимается — оно вне
полномочий замера.

1. Память. На всём измеренном окне [14, 22] режим reversal дешевле режима class по пику на
   каждой глубине (−51…−95%). Пик reversal растёт с глубиной из-за task-cache; пик class тоже
   растёт, но изначально выше на порядок и сопровождается терабайтными объёмами мусора.
2. Время. На 7×7 точка перегиба лежит между d14 и d18: при d ≥ 18 режим reversal быстрее
   (−29…−63%), а на d14 — медленнее (+23%). Тренд ADR-011 «reversal монотонно дешевеет к d22»
   подтверждён: 1 282 → 493 → 212 с. Глубина по умолчанию для доски 7×7 равна 20, то есть
   лежит в зоне выигрыша reversal; точку d20 не измеряли, а между d18 и d22 оба режима
   монотонны.
3. Шум. У режима class разброс составляет ±0.5% по времени и ±5% по RSS, у reversal — ±1.6%
   по времени; счётчики hits/misses детерминированы содержимым побитово (на d18 они совпали
   даже с прогоном эпохи `Entries()`). Все выводы выше лежат вне шума: Δ(d14, +23%) и
   Δ(d18, −29%) многократно превышают разброс повторов.

**Вердикт: WIN относительно ожиданий ADR-011.** Все три отложенные точки сняты с повторами,
проверки точности пройдены, тренды подтверждены; заявленный риск (часы на точку и свопинг) не
проявился. Новых аномалий нет — кроме зафиксированных +6.1% на d18 относительно точки эпохи
`Entries()`.
