# ADR-001. Классовый режим: подсчёт через классы форм вместо таблицы мемоизации и обращения тура

## Статус

Принято. Открытые вопросы: память M (план 01), гипотеза возврата reversal (план 06).

## Контекст

Прежний эталонный подход (oracle) мемоизировал функцию `h(U,u)` в таблице классов
и опирался на обращение тура (prefix-cache reversal). Замер на стенде 6×6 d18
дал ~250k записей, из них ~87% — нули, а класс обращался к таблице в среднем
всего ×1.16 раза. Таблица почти не переиспользовалась, но занимала память и
требовала блокировок на горячем пути. Обращение тура страдало пограничной
проблемой: дополнение множества посещённых клеток не коммутировало с
трансляцией. Оно также связывало глубину спуска условием `2p ≤ totalCells`.

## Решение

Таблицу мемоизации убрали полностью. Сумму перегруппировали по классам форм —
этот счёт и называют классовым режимом:

```
total = Σ_листьев(T,t) weight(T,t) · Σ_{u ∈ N(t)∩U} h(U,u)
      = Σ_классам C   h(C) · M(C),        U = full \ T,
M(C)  = Σ weight(листа) по листьям, чья пара (U,u) нормализуется в C.
```

Каждый класс вычисляется динамическим программированием ровно один раз на
финальном проходе. Размещения учтены тем, что накопитель M пополняется по
фактическим листьям генерации. Ограничение `2p ≤ totalCells` снято. Конвейер
стал таким: gen A → gen B → count-фаза (`specs/counter.md`).

## Последствия

- Плюсы: в горячем DFS больше нет таблицы мемоизации и блокировок обращения
  тура; нули h не хранятся; корректность даёт точная перегруппировка суммы без
  допущений.
- Минусы: на каждый опрошенный класс приходится одна запись M, и память растёт
  с глубиной — отсюда потолок `size²/2`. На 7×7 d22 время пока хуже обращения
  тура (см. замеры); оптимизацию вынесли в планы 01/05/06.

## Замеры

Статистика oracle на 6×6 d18: ~250k классов, ~87% нули, переиспользование ×1.16.

Сравнение классового режима и обращения тура (git `0d142f4`), Apple M4 Max,
14 ядер, 7×7 d22:

| метрика | class mode | reversal |
|---|---|---|
| время прогона | 596 с | 252 с |
| пик RSS | **23.46 ГБ** | 9.60 ГБ |
| gen B | 224.6 с, writes 3 591 773 354 | 141 с, writes 1 397 913 888 |
| counting | 371 с | 107.9 с |
| записей в хранилище | 284 359 145 классов | 131 814 325 задач |

Дерево поиска идентично: разбивка отсечений gen B совпадает счёт в счёт.
Разрыв объяснён представлением M и финальным проходом (план 01).
