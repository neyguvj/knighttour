# ADR-023. Гейт G7 «make check перед git commit»: пассивный зелёный штамп вместо прогона внутри хука

## Статус
Принято; реализовано на feature-ветке `02-gates-plugin-core` (`.opencode/plugins/gates.ts`, фича F2).
Процессное, замеры n/a.

## Контекст
ADR-022 заложил двухслойную схему гейтов. Правило «make check до git commit» требует состояния, а
паттерны permission состояния не хранят — такому правилу доступен только plugin-слой. Требовалось
выбрать механику: плагин может (а) блокировать коммит с текстом-инструкцией, чтобы модель сама
запустила `make check`, или (б) запускать `make check` прямо в момент коммита и по коду возврата
решать, пускать коммит или нет.

## Решение
Выбран вариант (а) — пассивное ведение зелёного штампа (контракт — specs/gates.md):

- штамп ставится в хуке `tool.execute.after` на bash-команду `make check`, только когда получен
  положительный ответ, что команда завершилась с кодом 0; подтверждения нет — штампа нет, отказ
  безопасен в сторону блокировки;
- штамп сбрасывают инструменты `edit`/`write`/`patch` и событие шины `file.edited`; изменения
  файлов через bash штамп не снимают. Это осознанное ограничение v1: полный контроль файловой
  системы дороже, чем ложно-зелёный риск, который он закрывает;
- при блокировке выполняется `throw GateError` с инструкцией: модель получает его как ошибку
  инструмента, сама запускает `make check` и видит вывод;
- сделано исключение для цепочки `make check && git commit …`, где проверка стоит в строке раньше
  коммита: оператор `&&` уже гарантирует, что при красной проверке коммита не будет, и повторный
  контроль избыточен;
- ядро плагина устроено просто: один экспорт `GatesPlugin` и диспетчер по списку гейтов
  `{id, before, after, onEvent}`. Намеренные блокировки выражаются только через `GateError`;
  внутренние ошибки гейтов протоколируются и не ломают вызовы инструментов. Новый гейт — элемент
  списка, ядро при этом не меняется. Feature-flag включения отсутствует: переключателем служит
  ветка (ADR-021);
- состояние живёт в памяти процесса плагина, одно на все сессии сервера. В `/feature` агент `coder`
  засчитывает проверку в своей сессии, а коммитит оркестратор в своей: штамп на каждую сессию
  разрушил бы этот поток. Параллельные worktree — отдельные процессы opencode, и состояние они
  не делят.

## Последствия
- (+) хук не блокирует сессию на минуты: `go test -race` и lint исполняет сама модель, и она видит
  вывод. Стоимость гейта на каждый вызов — сопоставление строки команды с образцом.
- (-) обход остаётся возможен невидимыми путями: скрипт, алиас, `git merge --squash`, cherry-pick.
  Это принято: цель гейта — убрать забывчивость модели, а не перехватывать злоумышленника.
  Пользовательский терминал гейт не затрагивает.
- (-) остался ложно-зелёный сценарий v1: правка файлов через bash между проверкой и коммитом
  не обнаруживается.
- (-) перезапуск opencode теряет штамп: первый коммит после него требует свежей проверки.
- Каждое следующее правило с состоянием (проверка, что коммит идёт не в `main`, flock для тяжёлых
  бенчей и т. д.) становится элементом списка гейтов и строкой реестра; ядро не правится.

## Замеры
n/a — процессное решение, вне горячего пути кода.

## Проверка
Приёмка прошла на харнессе уровня хуков плагина (Node ≥23.6; `tool.execute.before/after` и `event`
вызываются напрямую). Прогон охватил сценарии 1–7 из specs/gates.md, кейсы разделителей (`; `,
перевод строки, `|`, `||` разрывают и действие исключения для цепочки проверки вместе с коммитом,
и подтверждение штампа; обычная `&&`-цепочка пропускается), негативные контроли сопоставления
команды и устойчивость к битым args/metadata — прогон 2026-09-16: ALL PASSED. Загрузка
`.opencode/plugins/` реальным `opencode serve` 1.18.31 подтверждена (проба через `client.app.log`,
ошибок загрузки нет); `tsc --strict` проходит чисто. Ручную приёмку в живой сессии делает
оркестратор при закрытии ветки.
