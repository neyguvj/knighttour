# ADR-023. Гейт G7 «make check перед git commit»: пассивный зелёный штамп вместо инлайн-прогона

## Статус
Принято; реализовано на feature-ветке `02-gates-plugin-core` (`.opencode/plugins/gates.ts`, фича F2).
Процессное, замеры n/a.

## Контекст
ADR-022 заложил двухслойную схему гейтов; правило «make check до git commit» stateful и
permission-паттернам недоступно. Требовалось выбрать механику plugin-слоя: плагин может
(а) блокировать коммит с текстом-инструкцией, чтобы модель сама прогнала `make check`, или
(б) прогонять `make check` инлайн в момент коммита и пускать/не пускать по коду возврата.

## Решение
(a) Пассивный трекинг зелёного штампа (контракт — specs/gates.md):

- штамп ставится по `tool.execute.after` на bash-команду `make check` только при
  положительном подтверждении exit code 0; отсутствие подтверждения = нет штампа
  (fail-safe в сторону блокировки);
- инвалидация — инструменты `edit`/`write`/`patch` и событие шины `file.edited`; мутации
  файлов через bash штамп не снимают (осознанное ограничение v1: полный трекинг файловой
  системы дороже ложно-зелёного риска, который он закрывает);
- блокировка — `throw GateError` с инструкцией: модель получает её как ошибку инструмента,
  сама запускает `make check` и видит вывод;
- исключение для самогейдящейся цепочки `make check && git commit …` (check текстово раньше
  commit): `&&` уже гарантирует «красно ⇒ коммита нет», повторный контроль избыточен;
- скелет ядра: один экспорт-плагин (`GatesPlugin`), диспетчер по списку гейтов
  `{id, before, after, onEvent}`; намеренные блокировки — только `GateError`, внутренние баги
  гейтов логируются и не ломают вызовы инструментов; новые гейты — элемент списка, ядро
  неизменно; feature-flag включения отсутствует (ADR-021: переключатель — ветка);
- состояние — память процесса плагина, одно на все сессии сервера: в `/feature` `coder`
  считает проверку в своей сессии, а коммитит оркестратор в своей; per-session штамп развалил бы
  этот поток. Параллельные worktree'ы — отдельные opencode-процессы, состояния не делят.

## Последствия
- (+) нет минутных блокировок хука (`go test -race` + lint исполняет модель и видит вывод);
  стоимость гейта на вызов — матчинг строки команды.
- (-) обход возможен невидимыми путями (скрипт, алиас, `git merge --squash`, cherry-pick):
  принято — цель снять «забыл», не злоумышленника; пользовательский терминал не затрагивается.
- (-) ложно-зелёный сценарий v1: правка файлов через bash между проверкой и коммитом не
  детектируется.
- (-) рестарт opencode теряет штамп: первый коммит после рестарта требует свежей проверки.
- Каждое следующее stateful-правило (ветка-не-main, flock для тяжёлых бенчей и т.д.) —
  элемент списка гейтов + строка реестра, без правки ядра.

## Замеры
n/a (процессное решение, не hot-path).

## Проверка
Харнесс приёмки на уровне хуков плагина (Node ≥23.6, вызов `tool.execute.before/after`/`event`
напрямую): сценарии 1–7 из specs/gates.md + кейсы разделителей (`; `, newline, `|`, `||` разрывают
и самогейдинг, и подтверждение штампа; `&&`-цепочка пропускает), негативные контроли матчера и
устойчивость к битым args/metadata — прогон 2026-09-16: ALL PASSED. Загрузка `.opencode/plugins/`
реальным `opencode serve` 1.18.31 подтверждена (probe через `client.app.log`, ошибок загрузки нет);
`tsc --strict` чисто. Ручная приёмка в живой сессии — за оркестратором при закрытии ветки.
