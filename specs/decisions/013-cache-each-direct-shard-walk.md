# ADR-013. Count-фаза reversal: прямой обход шардов task-cache под RLock (`Cache.Each`) вместо снимков

## Статус

Принято (WIN; план 09). Замеры сняты 2026-09-13 (см. «Замеры»): peak RSS 7×7 d22 −5.7%
за пределы шума при времени в шуме повторов; аллокационный шум снимков снят ровно в
размер предсказания (−3.0 ГБ). С GOGC=40 цель ADR-012 «≤10.5 ГБ» взята впервые (10 203 МБ). Открытые вопросы:
GC-опция (`SetGCPercent` на фазу) как способ забрать 10.5 ГБ на дефолтном GOGC; перенос
default `-mode` (шаг 7 плана 06) — по-прежнему отдельное решение.

## Контекст

ADR-012 убрал полный снапшот `Entries()` (~2.1–3.2 ГБ одной аллокацией), но count-диспатч
остался на per-shard копиях: воркеры по атомарному курсору звали `SnapshotShard(i)` —
~16–25 МБ живой копии на воркера плюс повторная проходка всех 131.8M записей (ещё ~3 ГБ
аллокационного шума за фазу). Пик 7×7 d22 застыл на 16.2 ГБ (GOGC=100) / 11.6 ГБ (GOGC=40);
цель ≤10.5 ГБ не бралась, остаток был атрибутирован раскладке task-cache.

Уточнение гипотезы: эталон `0d142f4` (9.55 ГБ) в count-фазе ходил **напрямую по map шарда
под RLock** (`Cache.Each`) — ноль аллокаций на диспатч, ни курсора, ни копий. Тезис
«эталонный пик = заслуга прямого обхода» отдельной точкой не мерился (план 09).

## Решение

`Cache.SnapshotShard`/`Cache.NumShards` удалены; вместо них

```go
func (c *Cache) Each(ctx context.Context, workers int, f func(ctx context.Context, p path.Path, weight uint64) error) error
```

— `errgroup.SetLimit(workers)`, горутина на шард: проверка ctx → RLock шарда → `f` по каждой
записи → RUnlock; данные не изымаются (`Get` видит все шарды до конца фазы), первая ошибка
`f` останавливает запуск новых шардов и возвращается. `workers < 1` клампится внутрь `Each`
в число шардов (`errgroup.SetLimit(0)` паркует первый `Go` навсегда; «без лимита» у errgroup —
только отрицательное значение). `counter.countTasks`: тело воркера стало колбэком `Each`,
курсор и `countShard` удалены; не-`Canceled` ошибка из `Each` — panic (по контракту
недостижима, молча частичный результат хуже).

Предусловие зафиксировано в спеке контрактом: на время фазы писателей нет (фазовый барьер
errgroup генерации) — иначе ожидающий `Set` заблокирует разделяемый RLock того же шарда
внутри колбэка.

## Последствия

- Диспатч count-фазы не аллоцирует: пик фазы — стеки воркеров вместо O(workers×шард);
  снят ровно объём копий (см. замеры, B/op −3.16 ГБ при неизменном allocs/op).
- Гипотеза подтверждена частично: прямой обход снимает ~0.94 ГБ пика на дефолтном GOGC и
  выводит GOGC=40 на 10.2 ГБ (эталонные 9.55 ГБ того же порядка) — но остаток до 10.5 ГБ
  на **дефолтном** GOGC по-прежнему раскладка task-cache + GC-headroom, не диспатч.
- Идеал ADR-012 (≤10.5 ГБ) теперь достижим дешёвой GC-опцией (GOGC=40 на фазу —
  время бесплатно); её принятие — отдельное решение, здесь фиксируется только рычаг.
- Стоимость на мелких досках: `g.Go` на каждый из 128 шардов с семафором errgroup вместо
  пула из 14 воркеров даёт фиксированные ~+0.1 мс/op на фазах порядка долей миллисекунды
  (5×5 — целиком; см. свип). Абсолютно ничтожно; при желании удешевляется пулом, тянущим
  индексы шардов, — отдельной точкой не мерялось.
- Долгий RLock на всё время задачи шарда безопасен только при отсутствии писателей; при
  будущем инкрементальном пополнении кэша механику пересмотреть (риск плана 09).

Ни одной глубины вне пересечения собственных диапазонов повторов — хвост-несбаланс на
гранулярности шарда (та же единица работы, что у курсора ADR-012) не проявился. d15–d17
шумны в обе стороны и на базе (d16: 86.5–135.0 при n=5); медианный +22% на d16 при
перекрывающихся диапазонах — не регресс, но глубина помечена к наблюдению.

**Свип 5×5, reversal, d12…d1.** HEAD ×5 и BASE ×4 прогона (то же чередование); гейт итога
пройден везде; peak RSS процесса в свипе 13–15 МБ HEAD / 12–14 МБ BASE. Все глубины —
суб-миллисекундные оп'ы; систематически **HEAD ≈ BASE + 0.05…0.2 мс/op** (например d12:
медиана 0.6 [0.5..0.7] против 0.4 [0.4..0.4]; d8: 0.4 против 0.3; d1: 0.6 [0.5..0.7]
против 0.5 [0.5..0.6]). Фиксированная стоимость диспатча `Each` (запуск 128 горутин через
семафор errgroup против 14 воркеров с курсором) на фазах в доли миллисекунды; на d3/d4 —
в шуме, на половине глубин диапазоны формально не пересекаются. Абсолютная цена <0.3 мс
на прогон всего размера — принята как ничтожная (см. «Последствия»).

**Вердикт: WIN.** Peak RSS 7×7 d22 снижен за пределы шума (−5.7% при разбросе повторов
≤0.2% и непересекающихся диапазонах), время в пределах шума (гейт ±5%), аллокационный шум
снимков снят ровно как предсказано (−3 018 МБ totalAlloc, −3 164 МБ B/op при неизменном
allocs/op), побитовые гейты (итог, hits/misses) пройдены во всех прогонах. Идеал ADR-012
≤10.5 ГБ достигнут при GOGC=40 (10 203 МБ, время бесплатно); на дефолтном GOGC остаток
по-прежнему атрибутирован раскладке task-cache. Регресс мелких досок (+~0.1 мс/op на 5×5)
— принятая стоимость; фолбэк lazy-batched стек не требуется (на 6×6 глубины быстрее базы
чаще, чем медленнее).
