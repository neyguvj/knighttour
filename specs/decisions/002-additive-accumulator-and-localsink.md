# ADR-002. Единое хранилище: аддитивный Accumulator вместо memo-Cache; писатели через LocalSink

## Статус

Принято.

## Контекст

Исторически было два хранилища: memo-кэш подзадач `cache.Cache`
(Get/Set/Each под RWMutex, пережил отказ от reversal без потребителей) и
аддитивный аккумулятор класса форм. После перехода на class mode (ADR-001)
чтение нужно строго **после** завершения фазы записи — мемоизация
«чти-при-промахе» не нужна никому.

Прямой `Add` каждого листа в шардированную таблицу: лок на шард + rehash map
под локом; профиль 6×6 d18 — ~26% CPU в contention. Нагрузка аддитивная по
горячим общим ключам (`writesB` ~3.6G на 7×7 d22).

## Решение

Одна структура `cache.Accumulator`: шардированная (128 шардов)
`map[path.Path]uint64` с семантикой `Add(k, w)` — «data[k] += w», чтение только
drain'ом после барьера фазы. Прежний `Cache` (Get/Set/Each + RWMutex) удалён:
хватает Mutex, исчезла зависимость пакета от `Symmetry` (канонизацию выполняет
писатель).

Писатели обеих генерационных фаз работают через `acc.Local()` → `LocalSink`:
пер-горутиновый буфер `map[path.Path]uint64` схлопывает дубликаты ключей, при
переполнении (порог `localFlushLimit = 1024`) `Flush` догружает каждый
уникальный ключ одним захватом лока. `defer sink.Flush()` гарантирует доставку;
семантика аддитивна — тайминг флюша на результат не влияет. Sink не разделять
между горутинами.

## Последствия

- Меньше локов и аллокаций rehash'а; дубли схлопываются до захвата лока.
- Чтение возможно только между фазами (барьер errgroup) — совместимо с пайплайном.
- Нули по построению не хранятся: запись создаётся только при `Add`.

## Замеры

- Профиль 6×6 d18: contention + rehash под локом при прямом Add — ~26% CPU.
- LocalSink схлопывает дубликаты ключей ~×6 на стенде (6×6).
- Объём записей: `writesB` ~3.6G на 7×7 d22 (метрика монитора, не уникальные ключи).
