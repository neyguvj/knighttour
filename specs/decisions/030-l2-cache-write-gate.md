# ADR-030. L2-проверки прунера — гейт записи на листьях генерационного спуска

## Статус

Принято (chain-only, 2026-09-24). По времени — **паритет с базовой линией** (лучший вариант
chain-only: +1.3% при шуме ±0.4%; временной критерий плана 14 «>5% выигрыша» не выполнен),
принято **осознанно ради памяти**: peak RSS −48.8%, записей task-cache −30.0%, totalAlloc −35.6%,
count-фаза −16.1%. Articulation отклонена стендом числами (см. «Замеры»). Дефолты глубины не
пересматривались: re-sweep кривой глубин после включения гейта **не делался** — точка 7×7 d22
снята с ним, дефолт d22 оставлен как есть (пересъёмка — отдельная гипотеза, если понадобится).

Вердикт benchmarker'а по временному критерию был REGRESSION с рекомендацией отклонения; решение
пользователя — принять chain-only ради памяти, это зафиксированное **отступление от критерия
плана**, а не его reinterpretация.

## Контекст

Проверки необходимых условий гамильтова пути (сочленения Tarjan lowlink, обязательные цепочки
union-find) жили в `pruner` как ярус L2 и были удалены вместе с их потребителем — class-mode
(ADR-016). Прежнее применение — внутри экспоненциальной DP-рекурсии — оказалось убыточным
(O(V+E) на состояние: counting ×2.3 artic / ×1.5 chain, ADR-007). В конвейере reversal остались
записи task-cache с нулевым числом дополнений `f`: они раздувают таблицу (пик RSS — узкое место
ADR-012/013) и count-фазу, ничего не внося в итог.

## Решение

Гейт записи в базовом случае общего генерационного спуска `dfsTask`: перед
`Set(Canonicalize(st,end), weight)` — `pruner.ShouldPruneState(end, full\st)`, прунуто → записи
нет. Один хук покрывает промежуточную таблицу gen A и task-cache gen B; degenerate self-write
`ExtendTask` не гейтится (ключ уже прошёл гейт фазой A). Звукосность — лемма в
`specs/searcher.md` (нулевой вклад + «мёртвый ключ никогда не запрашивается» из дуальности
обращения + D4-эквивариантность).

Принятый набор проверок — **только forced-chain** (`forcedChainCut`, причина `ForcedChain`):
механизм A/B (compile-time маска `l2Gate` и `articulationCut` с Tarjan lowlink) после вердикта
стенда вычищен из кода как мёртвый (правило «dead code удаляется в той же правке, что его
осиротило»); возвращаться к сочленениям — только с новым планом и более дешёвым предиктом.
Рантайм-ручек нет (ADR-020). Статистика: поле `types.Result.PrunedForcedChain`, разбивка
монитора `…, endpoints, chain`, метрики `prunedL2A/op`, `prunedL2B/op` (имена сохранены — «L2»
это ярус гейта; содержательно теперь только цепочки); бенч-харнес публикует `taskEntries/op`.

## Последствия

- Каждый лист генерации платит O(V+E) (V = totalCells−depth+1): genB +14.9% на 7×7 d22 —
  цена, оплаченная памятью; полное время остаётся паритетным (+1.3%).
- Task-cache содержит только ключи с ненулевым потенциалом → `writesB` и `taskEntries` меньше
  числа листьев; peak RSS конвейера на 7×7 d22 вдвое ниже (5.33 ГБ против 10.41).
- Разбивка прунинга монитора расширена (`…, endpoints, chain`).

## Замеры

Прогон 2026-09-24 (benchmarker). Стенд: Apple M4 Max (14 ядер), 36 ГБ, go1.25.4 darwin/arm64;
машина простаивала до старта. Точка: `make bench-size N=7 DEPTHS=22`, каждый прогон отдельным
процессом, workers=14 (default), GOGC 40 (понижается конвейером). Прогоны строго сериализованы
под глобальным lock `../kt-bench.lock` (на darwin-хосте нет flock(1) — использован mkdir-shim
с тем же lock-путём). База — merge-base `2bb0646` из отдельного worktree, с единственной
backport-строкой харнеса `taskEntries/op` (в поведении базы не меняет ничего; удалённый worktree).
Варианты — compile-time маска `l2Gate` (A/B-механизм того этапа): chain-only / articulation-only /
both (закоммичен на момент замера).

Корректность: все прогоны PASS с сверкой харнеса 7×7 = 165 575 218 320; `cacheHits` идентичен
во всех конфигурациях (364.80M) — звукó гейта подтверждено на точке (мёртвые ключи не
запрашиваются: промахи падают, попадания не меняются).

Шум: baseline и chain сняты по 2 раза; разброс полного времени ≤ ±0.4%, детерминированные
счётчики (writesB, taskEntries, hits/misses) совпадают побитово. Остальные конфигурации — по
одному прогону; их отклонения (+20%/+22%) на порядок выше шума.

Отдельные прогоны полного времени (ns/op): baseline 198.36 / 199.13; chain 200.55 / 202.01;
articulation 238.71; both 243.17. `cacheMisses`: baseline 1.773G, chain/both ≈ 1.584G (−10.6%),
articulation 1.763G (−0.5%). `genA_ms` — микроскопичен везде (0.77–0.88 мс база vs 1.9–2.7 мс
гейт); `prunedL2A = 0` во всех гейтнутых конфигурациях: на листьях gen A (~2.4K writes) гейт не
сработал ни разу, вся работа — листья gen B.

Интерпретация критерия (план 14: «более чем на 5% лучше базовой линии»). Историческая цифра
плана 215.10 с (README/ADR-019) не сопоставима напрямую: свежий замер той же базы merge-base на
этом стенде — 198.74 с (дрейф стенда ~8%), и буквальный порог «≤ 204.3 с» база проходит уже
сейчас. Решение — только против baseline, снятого в той же сессии: лучший вариант chain-only
замедляет (+1.3% при шуме ±0.4%), committed both — на +22.4%. Ни один вариант не выполнил
критерий >5% выигрыша.

Наблюдения (справочные): гейт вдвое режет память (task-cache-записей −30%, peak RSS −50%,
totalAlloc −36%) и count-фазу (−17%), но O(V+E)-проверка на каждый лист gen B дороже:
genB +14.9% (chain) / +53.3% (both) съедают экономию cnt с запасом. Articulation — главный
расточитель: добавляет к chain ещё +43 с genB ради −0.3M записей (+20.1% одна, articulation-only);
именно поэтому она отклонена, а принят chain-only.

**Вердикт benchmarker'а по временному критерию плана: REGRESSION** (рекомендация — отклонение).
**Итоговое решение (пользователь): принято chain-only** — память как самостоятельная цель
(ADR-012/013 держат RSS узким местом); время — паритет. Articulation и both отклонены числами;
механизм маски удалён из кода, принятое состояние — forced-chain (см. «Решение»). Глубинный
re-sweep с гейтом не выполнялся; дефолт d22 не пересматривался.
