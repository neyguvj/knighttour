# ADR-010. Count-фаза: два этапа на шард, стек партий по LPT; группировка при чтении

## Статус

Принято (профиль 2026-09).

## Контекст

Финальная фаза счёта разбирает аккумулятор M — десятки миллионов записей — и считает
`total += Σ h(C)·M(C)` по формам. Возникают два вопроса. Первый: где группировать концы
в форму — при записи в аккумулятор или при чтении из него. Второй: как раздавать задачи-формы
воркерам, чтобы дорогой шард не вызывал простоя остальных и не держал лишней памяти.

## Решение

**(1) Группировка при чтении, а не при записи.** В аккумуляторе лежит плоская таблица
`path.Path → weight`; форма собирается сортировкой разобранного шарда по `State`.
Соблазн хранить вложенное значение «State → концы» отклонён — см. замеры.

**(2) Два этапа на каждый шард, без общего снимка M** (опирается на ADR-004):

- **Первый этап — группировка.** `min(workers, NumShards())` горутин берут индексы шардов
  общим атомарным счётчиком выданных задач. Каждая горутина вызывает `DrainShard(i)`,
  сортирует полученный срез по `State` и режет его на диапазоны форм; из диапазона
  получается задание `{entries, tasks}`. Все задания известны заранее, и они складываются
  в стек **по убыванию суммарного числа концов** — это эвристика LPT (Longest Processing
  Time): долгая работа берётся первой.
- **Второй этап — раздача.** Воркеры берут с вершины стека партии под мьютексом, по 16
  элементов за раз (`claimBatch = 16`); внутри одного задания индексы берутся его
  собственным атомарным счётчиком. Пустой стек означает, что вся работа разобрана. Ожидание новых
  задач не нужно: они не появляются, поэтому прежние `sync.Cond` и счётчик горутин,
  читавших шарды, убраны.

## Последствия

- В памяти живёт примерно по одному срезу шарда на активного воркера; даже дорогой шард
  не оставляет остальных праздными.
- Внутри задания формы упорядочены по убыванию числа концов — это прокси стоимости
  динамического программирования.
- Сложность планировщика (`sync.Cond`, счётчик горутин, читавших шарды) убрана, а
  утилизация воркеров не потеряна.

## Замеры

Профиль 6×6 d18 (2026-09): вся count-фаза занимает ~8% CPU конвейера, из них сортировка
группировки — ~0.3%, тогда как путь записи (`Accumulator.Add`/`LocalSink.Flush`) — ~20%.
Вложенное значение добавило бы аллокацию на каждую форму: 7×7 d20 — это 44.6M форм,
т. е. ≈ 150M мелких аллокаций плюс ещё один указатель на форму в каждом цикле сборщика
мусора. Потребовалась бы и семантика слияния под блокировкой шарда, хотя `LocalSink`
всё равно остался бы `map[Path]uint64`. Обход класса по плоскому срезу локален по памяти,
чего блуждание по указателям среди 44M бакетов не даёт.
