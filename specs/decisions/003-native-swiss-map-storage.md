# ADR-003. Хранилище M — нативная Swiss-map; своя плоская таблица и sync.Map отклонены

## Статус

Принято (пересмотр плана 01). Этап 0 плана 01 может пересмотреть порог включения
собственной таблицы.

## Контекст

Пик RSS классового режима на доске 7×7 d22 составил 23.46 ГБ (замеры ADR-001), и
главный потребитель — аккумулятор M, аддитивный накопитель классов форм (ADR-002)
с ~284M записей. План 01 изначально предлагал заменить его собственной плоской
таблицей в раскладке SoA (отдельный массив на каждое поле) и оценивал Go-map в
«~50 Б/запись».

## Решение

Шарды остаются `map[path.Path]uint64` до тех пор, пока Этап 0 плана 01 не измерит
обратное.

- **Swiss-map (Go ≥ 1.24)** уже даёт свойства «плоской таблицы»: открытая
  адресация, поиск по метаданным групп одной SIMD-инструкцией, load factor ~93% и
  слоты без указателей — такую карту сборщик мусора не сканирует (у
  `path.Path→uint64` указателей нет). Честная оценка: слот 16+8 Б плюс байт
  метаданных, делённые на 0.93, дают ≈ **27–28 Б/запись**, а не 50. Своя SoA-таблица
  при load factor ~0.75 стоит (8+1+8)/0.75 ≈ 23 Б/запись — выигрыш **×1.2, а не
  ×2.5–3**.
    Порог включения собственной таблицы: выигрыш по памяти ≥1.7× при регрессе по
    времени ≤5%.
- **`sync.Map` отклонён.** Нагрузка представляет собой аддитивные обновления
  горячих общих ключей. Атомарного сложения в его API нет — остаются цикл на CAS и
  аллокация entry при Store; контейнер построен из указателей, поэтому сборщик
  мусора сканирует миллионы живых записей; наконец, контракт «все концы одной формы
  лежат в одном шарде, шард вычитывается до конца без общего снимка» на нём
  невыразим. `sync.Map` оптимизирован для сценариев, где чтения преобладают, а
  ключи не меняются, — это противоположность нашей нагрузке.

## Последствия

- Нулевой код хранилища, память ~27–28 Б/запись. Запаса в ×1.2 не хватает, чтобы
  окупить риски, поэтому оптимизация перенесена в Этап 0 плана 01. Профиль пика
  показывает: возможно, главные потребители — удвоение map при росте и таблицы
  мемоизации воркеров, а не само хранилище.

## Замеры

Оценка Swiss-map 27–28 Б/запись получена расчётом от структуры слота Go ≥ 1.24;
она заменила оценку «~50 Б», полученную для классической организации map через
корзины (buckets).
Теперь 284M записей весят ~7.6 ГБ, а не 14. Порог пересмотра: ×1.7 при регрессе
≤5% (specs/plans/01).
