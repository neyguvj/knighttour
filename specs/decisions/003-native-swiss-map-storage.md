# ADR-003. Хранилище M — нативная Swiss-map; своя плоская таблица и sync.Map отклонены

## Статус

Принято (пересмотр плана 01). Этап 0 плана 01 может пересмотреть порог включения
собственной таблицы.

## Контекст

Пик RSS class mode на 7×7 d22 — 23.46 ГБ (замеры ADR-001), главный потребитель —
аккумулятор M (~284M записей). План 01 изначально предлагал свою плоскую SoA-таблицу
с оценкой «~50 Б/запись» для Go-map.

## Решение

Шарды остаются `map[path.Path]uint64` до тех пор, пока Этап 0 плана 01 не измерит
обратное.

- **Swiss-map (Go ≥ 1.24)** уже даёт свойства «плоской таблицы»: открытая адресация,
  SIMD-метаданные групп, load factor ~93%, pointer-free слоты без GC-скана
  (у `path.Path→uint64` нет указателей). Честная оценка: slot 16+8 Б + байт
  метаданных ÷ 0.93 ≈ **27–28 Б/запись**, а не 50. Своя SoA-таблица при load factor
  ~0.75: (8+1+8)/0.75 ≈ 23 Б/запись — выигрыш **×1.2, а не ×2.5–3**.
    Порог включения собственной таблицы: ≥1.7× по памяти при регрессе ≤5% по времени.
- **sync.Map отклонён.** Нагрузка — аддитивные апдейты горячих общих ключей:
  atomic-add нет (CAS-цикл + аллокация entry на Store), указателеструктурная природа
  даёт GC-скан миллионов живых записей, контракт «все концы формы в одном шарде,
  drain без общего снапшота» невыразим. sync.Map оптимизирован под read-mostly
  неизменяемых ключей — антипод нагрузки.

## Последствия

- Нулевой код хранилища, память ~27–28 Б/запись; запас на ×1.2 не окупает риски —
  экономия перенесена в Этап 0 плана 01 (профиль пика: возможно, главные потребители
  — удвоения map и DP-мемо воркеров, а не бакеты).

## Замеры

Оценка Swiss-map 27–28 Б/запись (расчёт от структуры слота Go ≥1.24) заменила
«~50 Б» эпохи bucket-карты; 284M записей → ~7.6 ГБ, а не 14. Порог: ×1.7 при
регрессе ≤5% (specs/plans/01).
