# ADR-034. Склейка task-cache по маске: ключ — каноническая маска, значение — гистограмма «класс конца → W»

## Статус

**Принято, гейты взяты (второй стенд, 2026-09-28).** План 18, итерация 2 (вариабельная упаковка
значения). Вердикт benchmarker'а: **WIN** — peak RSS **−47.7%** при гейте «−≥25%», wall **−13.6%**
при регрессе ≤+5%, `cnt_ms` −32.9%; полосы контроля и ветки полностью разделены по обеим метрикам,
бит-гейты (итог/`writesB`/`prunedL2B`) идентичны во всех прогонах обеих итераций (восьми).

История: первый стенд шага 5 (фиксированный inline kcap=7) дал **REGRESSION** — peak **+84.1%**
при тех же временных выигрышах; механизм провала (постоянная оплата 7 слотов на маску) подтверждён
итерацией 2, развернувшей пик на −70.5% относительно первого стенда. Числа первого стенда
сохранены ниже как история. Закрытие — squash-merge ветки `18-merge-by-mask` (orchestrator).

## Контекст

Task-cache хранил по записи на каноническую пару `(state, end)`; классы концов одной маски
читаются пачкой и дублируют ключ. Гипотеза плана 18: одна запись на маску с гистограммой классов
даёт падение записей `Σk → #масок` и peak RSS **−≥25%** при регрессе wall ≤5%. Этап 0 (7×7,
генерация без счёта): d21 — записей 81 015 580 / масок 32 560 903 / c̄ = 2.4881; d20 —
60 470 692 / 34 520 087 / c̄ = 1.7518; тренд по глубине растущий ⇒ экстраполяция d22: c̄ ≥ ~2.5,
масок ≈ записей/2.5 ≈ 37 М. Расчёт экономии (раскладка (a)) предполагал **вариабельное** значение
`V(k) = 8·(1+k)` слов; inline-ёмкость kcap = p95(d21) = 7.

Реализация первой итерации ветки: `Value{count; pairs [kcap]uint64; spill []uint64}` —
**фиксированный** inline массив на 7 классов (88 Б хендл, specs/cache.md «copies are cheap»), pack
`(rep:8 | W:56)`. Именно она и провалила гейт памяти (первый стенд ниже); итерация 2 заменила её
вариабельной упаковкой.

## Решение

Принято: task-cache хранит **одну запись на каноническую маску** `K` со значением-гистограммой
«класс конца → W» в **вариабельной упаковке** (итерация 2, specs/cache.md): pointer-free
`map[uint64]uint64`, теговое слово значения — MSB=0 при k=1 (`inline rep:8 | W:56`), MSB=1 при
k≥2 (`slab-ref k:7 | idx:56`) в per-shard append-only `[]uint64` slab под Mutex писателей; рост —
in-place внутри `cap(k)=2^⌈log2 k⌉` или copy-on-append релокация в ёмкость следующего класса с
переработкой освобождаемого блока через корзины той же ёмкости. Внешние контракты
(`Sink.Set` rep<128, `View.Get/Value.Weight`, разворот `All`, `Len`, `Staging`) семантически не
изменились; итог бит-идентичен (бит-гейты восьми прогонов).

Фактическая плотность (второй стенд, нормировка peak на класс-записи): **60.5 → 31.7 Б/запись
(−47.7%)**; на маску — 58.1 Б при формуле спеки `18.3 + 8·cap(k)` (медиана k=2 ⇒ cap в основном 2,
≈34.3 Б/маску таблицы, остальное — рабочий набор и GOGC-слак, масштабирующиеся с таблицей).
Пересмотр плотности слота ADR-003: свис-слот пары (27–28 Б/запись) заменён теговым словом + slab;
верхняя граница «не дороже базы ни при каком k» выдержана на реальном распределении d22.

## Замеры

Стенд (общий для обеих итераций): Apple M4 Max (14 ядер), workers=14, GOGC 40 конвейером; точка
`make bench-size N=7 DEPTHS=22` (`-benchtime=1x`, отдельный процесс на прогон), прогоны
сериализованы глобальным lock'ом `../kt-bench.lock` (mkdir-shim — на darwin нет flock(1)). База
A/B — merge-base `b62a6a8` (tip локального main), отдельный base-worktree. Протокол каждого
стенда: база ×2, ветка ×2.

GOGC-слак сжимаются пропорционально таблице.

Сверка с первым стендом (тот же код склейки, только упаковка значения): маски те же
50 322 844; peak **9455 → 2787 МиБ (−70.5%)**, totalAlloc 20 426 → 12 609 МБ. Механизм провала
первого стенда — **подтверждён**: постоянная оплата фиксированного inline kcap=7 при медиане k=2;
вариабельная упаковка убрала её и на фактическом c̄=1.83 (без экстраполированных 2.5) выигрывает
у пары почти вдвое.

### Бит-гейты (все прогоны обеих итераций, восемь)

Итог 165 575 218 320 (`toursExpected`, enforced харнессом — PASS везде); `writesB` 942 644 146;
`prunedL2B` 455 269 742; `writesA` 2364; `prunedA` 373; `prunedB` 2 637 875 620 — идентичны.
`cacheHits/cacheMisses` 364 804 607 / 1 584 519 460 — **совпали побитово**, хотя план объявлял их

сохранила числа.

### Записи против экстраполяции Этапа 0

`taskEntries` ветки = **50 322 844 масок** (семантика метрики изменена: было — пары). Факт d22:
c̄ = 92 315 032 / 50 322 844 = **1.8345**, record-count reduction 45.5%. Это **ниже** d21 (2.4881)
и между d20 и d21: число масок по глубине non-monotonic — 34.5M (d20) → 32.6M (d21) → **50.3M
(d22)**, т.е. +54% на шаге d21→d22 вместо экстраполированного роста c̄. Прогноз масок ≈ 37.1 М
превзойдён на **+36%**. Экстраполяция «глубже ⇒ больше c̄ ⇒ больше экономии» на d22 не подтвердилась.

### Плотность слота (история, по первому стенду; итоговая фактическая — во «Втором стенде» и «Решении»)

Процессные байты на логическую единицу (peak RSS включает рабочий набор и GOGC-слак, отношение
сторон корректно как верхняя оценка):

| сторона | peak / taskEntries | перпенормировка на пару записей |
|---|---|---|
| база (пары) | 5135 МиБ / 92 315 032 = **58.3 Б/пару** | 58.3 Б/запись |
| ветка (маски) | 9455 МиБ / 50 322 844 = **196.9 Б/маску** | 107.4 Б/запись (+84%) |

Формулы: план (a) при фактическом k̄=1.83 — `(8+8(1+k)+1)/0.93` ≈ **34.1 Б/маску**; фиксированный
inline kcap=7 как реализовано — ключ 8 + хендл 88 + метаданные, /(≈0.93) ≈ **104 Б/маску**.
Мерный коэффициент (196.9/34.1 ≈ 5.8 против плановых, 196.9/104 ≈ 1.9 — остальное рабочий набор и
GOGC-слак) указывает: таблица платит фиксированную раскладку, а не вариабельную из расчёта плана.
Две независимые причины провала гейта: **(i)** фактический c̄(d22)=1.83 вместо экстраполяции ≥2.5;
**(ii)** постоянная оплата 7 слотов на каждую маску при медиане k=2 (d21) — даже при c̄=2.49
фиксированная раскладка дала бы ≈104 Б/маску против 66.9 Б/пару-эквивалента, т.е. плановая
экономия требовала вариабельного значения, а не inline-kcap+spill.

### Развязанный TODO плана: запас разряда веса `W < 2^56` при writesB ~ 1e9

Каждый вклад `Set(K, rep, w)` несёт вес стартовой группы: `GenerateTasks` сеет `orbitSize ≤ 8`,
`dfsTask`/`ExtendTask` передают weight неизменным вдоль всего спуска — вклад > 8 конструктивно
невозможен. Значит для любого слота `W_r ≤ ΣW ≤ 8 × writesB = 8 × 942 644 146 = 7.54×10⁹ ≈ 2³³`.
Запас 56-битного поля упаковки `(rep:8 | W:56)` — **≈ 9.6×10⁶× (2²³)**; переполнение потребовало бы
роста writesB на семь порядков при том же орбитальном весе. Runtime-проверки не нужны
(specs/cache.md) — запас подтверждён по факту прогона d22.

## Последствия

- Пик конвейера 7×7 d22 падает с ~5.3 до ~2.8 ГиБ (−47.7%) при wall −13.6% — принятая форма
  таблицы стоит дешевле парной и быстрее на count-фазе; headroom к 8×8-точкам существенно вырос.
- `taskEntries/op` меняет семантику: число масок, не пар (50 322 844 против 92 315 032); исторические
  сравнения по этой метрике требуют перпенормировки на c̄.
- Урок упаковки: плановая формула экономии верна только для вариабельного значения; фиксированный
  inline-ёмкости (p95) платит за хвост распределения на каждой записи — первый стенд это показал
  числами (+84.1% против прогноза −40%).
- Экстраполяция c̄ по глубине (Этап 0) ненадёжна: d20→d21 росла (1.75→2.49), d22 откатилась до
  1.83; прогнозы «по тренду» в будущих планах — только с нижней оценкой.
- Откат = не мержить ветку `18-merge-by-mask` (ADR-021); переключателя в коде нет.
