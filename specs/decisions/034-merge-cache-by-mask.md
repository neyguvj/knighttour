# ADR-034. Объединение записей task-cache по маске: ключ — каноническая маска, значение — гистограмма «класс конца → W»

## Статус

**Принято, пороги выдержаны (второй стенд, 2026-09-28).** Это план 18, итерация 2 с вариабельной
упаковкой значения. Вердикт benchmarker'а — **WIN**: peak RSS снизился на **−47.7%** при пороге
«−≥25%», wall сократился на **−13.6%** при допустимом регрессе ≤+5%, `cnt_ms` — на −32.9%.
Полосы контроля и ветки полностью разделены по обеим метрикам. Проверки побитового совпадения
(итог, `writesB`, `prunedL2B`) пройдены: значения идентичны во всех восьми прогонах обеих итераций.

История: первый стенд шага 5 с фиксированной встроенной ёмкостью kcap=7 дал **REGRESSION** — peak
вырос на **+84.1%** при тех же выигрышах по времени. Итерация 2 подтвердила механизм провала:
каждая маска постоянно оплачивала 7 слотов; относительно первого стенда пик развернулся на −70.5%.
Числа первого стенда сохранены ниже как история. Закрытие — squash-merge ветки `18-merge-by-mask`,
выполненный оркестратором.

## Контекст

До этого task-cache хранил по одной записи на каждую каноническую пару `(state, end)`. Классы
концов одной маски читаются пачкой и каждый раз дублируют ключ. Гипотеза плана 18: одна запись на
маску с гистограммой классов сокращает число записей с `Σk` до числа масок и даёт −≥25% peak RSS
при регрессе wall не больше 5%. Этап 0 измерил генерацию без счёта на доске 7×7: для d21 —
81 015 580 записей, 32 560 903 маски, среднее c̄ = 2.4881; для d20 — 60 470 692 записи,
34 520 087 масок, c̄ = 1.7518. С глубиной c̄ растёт, поэтому по экстраполяции для d22 ждали
c̄ ≥ ~2.5 и около 37 М масок (записи / 2.5). Расчёт экономии раскладки (a) предполагал
**вариабельное** значение `V(k) = 8·(1+k)` слов; встроенная ёмкость kcap = p95(d21) = 7.

Первая итерация ветки реализовала значение как `Value{count; pairs [kcap]uint64; spill []uint64}` —
**фиксированный** встроенный массив на 7 классов с упаковкой `(rep:8 | W:56)`. Структура значения
стоила 88 Б, и спека считала такую копию дешёвой (specs/cache.md). Именно эта реализация и
провалила проверку памяти (первый стенд ниже); итерация 2 заменила её вариабельной упаковкой.

## Решение

Принято: task-cache хранит **одну запись на каноническую маску** `K` со значением-гистограммой
«класс конца → W» в **вариабельной упаковке** (итерация 2, specs/cache.md). Карта не содержит
указателей ни с одной стороны пары: `map[uint64]uint64`. Старший бит значения — тег формы: при
k=1 он равен 0, это форма `inline` (`rep:8 | W:56`); при k≥2 он равен 1, это ссылка на slab
(`k:7 | idx:56`). Slab — срез
`[]uint64` того же шарда с дозаписью в конец, под мьютексом писателей. Рост записи происходит на
месте внутри `cap(k)=2^⌈log₂ k⌉`, либо через copy-on-append: блок переезжает в ёмкость следующего
класса, а освобождённый блок попадает в корзину той же ёмкости и используется повторно. Внешние
контракты (`Sink.Set` с rep<128, `View.Get` и `Value.Weight`, разворот `All`, `Len`, `Staging`)
семантически не изменились; итог совпадает побитово во всех восьми прогонах.

Фактическая плотность второго стенда, если нормировать peak на класс-запись:
**60.5 → 31.7 Б/запись (−47.7%)**. На маску приходится 58.1 Б; формула спеки `18.3 + 8·cap(k)`
при медиане k=2 (значит, ёмкость в основном 2) даёт ≈34.3 Б на маску таблицы. Остальное — рабочий
набор и запас кучи между сборками GC, они растут вместе с таблицей.

Это пересматривает плотность слота из ADR-003: слот пары в Swiss-map (27–28 Б/запись) заменён
теговым словом и slab. Верхняя граница «не дороже базы ни при каком k» выдержана на реальном
распределении d22.

## Замеры

Стенд общий для обеих итераций: Apple M4 Max (14 ядер), workers=14, GOGC 40 понижен конвейером.
Точка — `make bench-size N=7 DEPTHS=22` с `-benchtime=1x`, каждый прогон в отдельном процессе.
Прогоны сериализованы общей файловой блокировкой `../kt-bench.lock`: на darwin нет утилиты
flock(1), поэтому используется подделка через mkdir. База A/B — merge-base `b62a6a8`, вершина
локального main на тот момент, в отдельном base-worktree. Протокол каждого стенда: база ×2,
ветка ×2.

тоже разделены полностью, временной порог ≤+5% выдержан с запасом. **cnt сократился на −32.9%**
([46.00; 46.19] против [67.40; 69.96]): выигрыш первого стенда (−27.6%) не только сохранён, но и
увеличен примерно на 5 п.п., потому что slab читается подряд. Gen B по средним дал −1.7% (попарно

шум. `totalAllocMB` снизился на **−9.2%** (первый стенд давал +47.0%), `B/op` — на −9.2%, а
`allocs/op` составил 92.60M против 92.86M (−0.3%).

Плотность считана по тем же процессным пикам при МиБ=2²⁰: у базы **60.5 Б/пару**, у ветки
**58.1 Б/маску**, то есть **31.7 Б на запись-пару (−47.7%)**. Формула спеки `18.3 + 8·cap(k)` при
d22-распределении (c̄=1.83, медиана k=2, поэтому ёмкость в основном 2) даёт ≈34 Б на маску таблицы
и прогноз экономии −27..−42%. Мерный пик (−47.7%) оказался лучше полосы прогноза: рабочий набор и
запас кучи между сборками GC сжались пропорционально таблице.

Сверка с первым стендом — тот же код объединения, изменилась только упаковка значения: масок те же
50 322 844; peak упал с **9455 до 2787 МиБ (−70.5%)**, totalAlloc — с 20 426 до 12 609 МБ.
Механизм провала первого стенда **подтверждён**: каждая маска постоянно оплачивала фиксированную
встроенную ёмкость kcap=7 при медиане k=2. Вариабельная упаковка убрала эту плату и на фактическом
c̄=1.83 — без экстраполированных 2.5 — выигрывает у попарной раскладки почти вдвое.

### Побитовые сверки (все прогоны обеих итераций, восемь)

Итог 165 575 218 320 совпадает с `toursExpected` — харнесс проверял это во всех прогонах, везде
PASS. Значения `writesB` 942 644 146, `prunedL2B` 455 269 742, `writesA` 2364, `prunedA` 373 и
`prunedB` 2 637 875 620 идентичны во всех прогонах. `cacheHits/cacheMisses`
364 804 607 / 1 584 519 460 **совпали побитово**, хотя план не включал их в проверяемые величины
(«Get на маску»): единица счёта осталась классовой (спека), а биекция «пара ↔ класс» сохранила
числа.

### Число записей против экстраполяции этапа 0

`taskEntries` ветки равно **50 322 844 маскам**: семантика метрики изменена, раньше это были пары.
Фактическое значение d22: c̄ = 92 315 032 / 50 322 844 = **1.8345**, сокращение числа записей на
45.5%. Это **ниже** d21 (2.4881) и лежит между d20 и d21. Число масок по глубине не монотонно:
34.5M (d20) → 32.6M (d21) → **50.3M (d22)**, то есть +54% на шаге d21→d22 вместо экстраполированного
роста c̄. Прогноз ≈ 37.1 М масок превзойдён на **+36%**. Экстраполяция «глубже ⇒ больше c̄ ⇒ больше
экономии» на d22 не подтвердилась.

### Плотность слота (история, по первому стенду; итоговая фактическая — во «Втором стенде» и «Решении»)

Это процессные байты на логическую единицу. Peak RSS включает рабочий набор и запас кучи между
сборками GC, поэтому отношение сторон корректно как верхняя оценка:

| сторона | peak / taskEntries | перпенормировка на пару записей |
|---|---|---|
| база (пары) | 5135 МиБ / 92 315 032 = **58.3 Б/пару** | 58.3 Б/запись |
| ветка (маски) | 9455 МиБ / 50 322 844 = **196.9 Б/маску** | 107.4 Б/запись (+84%) |

Формулы: плановая раскладка (a) при фактическом k̄=1.83 даёт `(8+8(1+k)+1)/0.93` ≈
**34.1 Б/маску**; фиксированная встроенная ёмкость kcap=7, как было реализовано, — ключ 8 Б +
структура значения 88 Б + метаданные, и после деления на ≈0.93 получаем ≈ **104 Б/маску**. Мерный
коэффициент 196.9/34.1 ≈ 5.8 против плановых, а 196.9/104 ≈ 1.9 — остальное объясняется рабочим
набором и запасом кучи. Это значит, что таблица платила фиксированную раскладку, а не вариабельную
из расчёта плана. У провала порога памяти две независимые причины: **(i)** фактический
c̄(d22)=1.83 вместо экстраполяции ≥2.5; **(ii)** каждая маска постоянно оплачивала 7 слотов при
медиане k=2 (d21). Даже при c̄=2.49 фиксированная раскладка дала бы ≈104 Б/маску против 66.9 Б на
пару-эквивалент: плановая экономия требовала вариабельного значения, а не схемы
`inline-kcap+spill`.

### Закрытый TODO плана: запас разряда веса `W < 2^56` при writesB ~ 1e9

Каждый вклад `Set(K, rep, w)` несёт вес стартовой группы: `GenerateTasks` сеет `orbitSize ≤ 8`,
а `dfsTask` и `ExtendTask` передают weight неизменным вдоль всего спуска, поэтому вклад больше 8
конструктивно невозможен. Значит, для любого слота `W_r ≤ ΣW ≤ 8 × writesB = 8 × 942 644 146 =
7.54×10⁹ ≈ 2³³`. Поле `W:56` упаковки `(rep:8 | W:56)` даёт запас **≈ 9.6×10⁶× (2²³)**:
переполнение потребовало бы роста writesB на семь порядков при том же орбитальном весе. Проверки
в рантайме не нужны (specs/cache.md) — запас подтверждён фактом прогона d22.

## Последствия

- Пик конвейера 7×7 d22 падает с ~5.3 до ~2.8 ГиБ (−47.7%) при wall −13.6%: принятая форма таблицы
  дешевле парной и быстрее в count-фазе. Запас памяти до точек 8×8 существенно вырос.
- Метрика `taskEntries/op` меняет семантику: теперь это число масок, а не пар (50 322 844 против
  92 315 032). Исторические сравнения по этой метрике требуют пересчёта с учётом c̄.
- Урок упаковки: плановая формула экономии верна только для вариабельного значения. Фиксированная
  встроенная ёмкость по p95 оплачивает хвост распределения на каждой записи; первый стенд показал
  это числами: +84.1% против прогноза −40%.
- Экстраполяция c̄ по глубине (этап 0) ненадёжна: от d20 к d21 значение выросло (1.75→2.49), а на
  d22 откатилось до 1.83. Прогнозы по тренду в будущих планах стоит давать только с нижней оценкой.
- Откат — просто не мержить ветку `18-merge-by-mask` (ADR-021); переключателя в коде нет.
