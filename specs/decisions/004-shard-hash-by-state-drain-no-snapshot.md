# ADR-004. Хэш шарда только по State; чтение drain'ом без копирующего Snapshot

## Статус

Принято.

## Контекст

Аккумулятор M на больших досках занимает гигабайты (ADR-001). Наивное чтение —
копирующий `Snapshot()` всей таблицы в срез для обхода counting-фазой. Дополнительно
нужно группировать записи по форме (все концы одного State обрабатываются вместе,
одно memo на форму).

## Решение

Индекс шарда = старшие 7 бит мультипликативного хэша **только от `State`**
(`h = uint64(state) * 0x9E3779B97F4A7C15`, сдвиг). `End` в хэше сознательно
отсутствует.

Инвариант: **все концы одной формы (одного State) лежат в одном шарде.** Поэтому
counting-фаза обрабатывает каждый шард независимо (`DrainShard(i)` → сортировка
своего среза по `State` → DP), не строя общий снимок. Копирующий `Snapshot()` удалён:
он удваивал пик памяти (копия всей таблицы при живых map-шардах).

## Последствия

- Пик counting монотонно падает: разбор шарда в плоский срез (`Entry` = 24 Б) чуть
  дешевле хранения (~27–28 Б/запись, ADR-003); освобождённые map'ы уходят GC.
- Глобальная сортировка не нужна вовсе — группировка по формам within-shard.
- Побочный эффект: концы одной формы пишутся в один шард — локализацию локов
  размывает LocalSink (ADR-002), а 128 шардов держат коллизию горячих форм низкой.

## Замеры

`Snapshot` удваивал пик генерации — удалён. `Entry`(24 Б) против map (~27–28 Б/запись,
Swiss-map): разбор таблицы в срез дешевле хранения, резидентный объём counting падает.
Сортировка группировки ~0.3% CPU фазы (профиль 6×6 d18).
