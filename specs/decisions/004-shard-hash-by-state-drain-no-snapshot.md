# ADR-004. Хэш шарда только по State; вычитывание шарда до конца без копирующего Snapshot

## Статус

Принято.

## Контекст

На больших досках аккумулятор M занимает гигабайты (ADR-001). Наивное чтение —
копирующий `Snapshot()`: он складывает всю таблицу в срез, а затем обходит его
count-фаза. Дополнительно записи нужно группировать по форме: все концы одного
`State` обрабатываются вместе, и значение динамического программирования считается
один раз на форму.

## Решение

Индекс шарда — старшие 7 бит мультипликативного хэша **только от `State`**
(`h = uint64(state) * 0x9E3779B97F4A7C15`, сдвиг). Поле `End` в хэше сознательно
отсутствует.

Инвариант: **все концы одной формы (одного State) лежат в одном шарде.** Поэтому
count-фаза обрабатывает каждый шард независимо. Метод `DrainShard(i)` вычитывает
содержимое шарда, сортирует свой срез по `State` и запускает динамическое
программирование; общий снимок не строится. Копирующий `Snapshot()` удалён: он
удваивал пик памяти, потому что к живым map-шардам добавлялась копия всей таблицы.

## Последствия

- Пик count-фазы монотонно падает: разбор шарда в плоский срез стоит чуть дешевле
  хранения — `Entry` = 24 Б против ~27–28 Б/запись (ADR-003). Освобождённые map
  переходят сборщику мусора.
- Глобальная сортировка не нужна вовсе: группировка по формам происходит внутри
  каждого шарда.
- Побочный эффект: концы одной формы пишутся в один шард, поэтому локализация
  попаданий в блокировки, которую даёт `LocalSink` (ADR-002), размывается. Зато
  128 шардов держат вероятность столкновения горячих форм в одном шарде низкой.

## Замеры

`Snapshot` удваивал пик генерации и был удалён. Сравнение `Entry` (24 Б) с
хранением в map (~27–28 Б/запись, Swiss-map): разбор таблицы в срез дешевле хранения,
поэтому резидентный объём памяти на count-фазе падает. Сортировка группировки
занимает ~0.3% CPU фазы (профиль 6×6 d18).
