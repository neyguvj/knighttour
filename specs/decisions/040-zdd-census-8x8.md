# ADR-040. Ценз ZDD для 8×8: нуль-супрессированная диаграмма не проходит по памяти, план 23 закрыт

## Статус

Отклонено (2026-10-20). Вердикт ценза Этапа 0 — **NO-GO**: предсказанный пик памяти 8×8 —
полоса от ~0,5 ТБ до десятков ТБ при пороге ~28 ГБ; порог нарушен на полтора–три порядка при
любой модели роста, согласованной с измерениями. План 23 закрыт как направление счёта; пакет
`zdd` и ценз остаются в `main` как постоянный инструмент методологии (см. «Последствия»).

## Контекст

Дорожная карта закрыла 8×8 по всем ветвям: reversal — по времени (ADR-036), frontier DP —
по памяти (ADR-038), отсечения и переиспользование остатка count-фазы — числами (ADR-037,
ADR-039). Класс методов решения остался необследованный: в литературе 8×8 досчитали
бинарными и нуль-супрессированными диаграммами решений. Гипотеза плана 23: глобальное
переиспользование узлов через уникальную таблицу опускает пик живых узлов на порядки ниже
пика состояний frontier DP, и счёт 8×8 влезает в ~28 ГБ за время меньше 30 суток.

Этап 0 построил фронтьерный ценз-движок (пакет `zdd`: арена узлов, уникальная
таблица, таблица мемоизации состояний, мягкий байтовый потолок `ErrOverCap`) и измерил его
на досках 5×5–7×7. Числа этого ADR решают судьбу направления.

## Решение

Решения о мерже нет: вердикт Этапа 0 — отклонить. Ключевое измеренное открытие ценза —
**редукция узлов реальна, но память занимает не она**. Диаграмма действительно мала: на
6×6 Paths в живой диаграмме 248 418 узлов против пика 108 642 911 состояний frontier DP
(в ×437 раз меньше). Однако счёт ведёт таблица мемоизации: в неё попадает каждое
посещённое состояние фронтьера, включая тупиковые, которых нуль-супрессирование не
оставляет узлами. Отношение записей мемоизации к живым узлам измерено ≈10³ (полное построение
6×6 Paths: 250 059 810 против 248 418), и по объёму она превосходит послойный пик
frontier DP: ×2,3 на Paths и ×8,2 на Cycles той же доски. Модель памяти из плана
(40–48 Б на живой узел) опровергнута; бюджет считается зарезервированными байтами
`liveBytes` ≈61 Б на запись мемоизации при полосе пика RSS 1,5–2,4× от зарезервированного.

## Последствия

- Отклонено направление счёта 8×8, а не инструмент: пакет `zdd`, спека `specs/zdd.md` и обвязка
  ценза `BenchmarkZDDCensus` мержатся и остаются в `main` как постоянный инструмент методологии
  (прецедент ADR-039, где `BenchmarkMemoReuseCensus` пережил отказ). Ценз переиспользуем на новом
  железе или других depths без возобновления плана.
- 8×8 корректно закрыта и для ZDD: у каждого класса методов есть числовое замыкание —
  reversal по времени, frontier DP и ZDD по памяти, отсечения и второй уровень мемоизации
  по эффективности.
- Узловая редукция не сокращает объём работы: посещённых состояний столько же порядков, что
  у послойного обхода, но удерживаются они целиком. Отказ от удержания (послойное освобождение
  таблицы мемоизации) вернул бы метод к памяти frontier DP, но потерял бы переиспользование подзадач —
  единственный источник его преимущества. Усовершенствования такого рода в плане не значатся.
- Порог продолжения плана пересматривать не для чего: он нарушен консервативной границей
  с запасом в десятки раз.

## Замеры

Стенд: Apple M4 Max (14 ядер), 36 ГБ, macOS, go1.25.4 darwin/arm64. Дата прогона — 2026-10-20.
Отбор точек фильтром `-bench` (ADR-020): `make bench-zdd-census N=5`,
`go test -bench='BenchmarkZDDCensus/size6/cycles'`; тяжёлые точки — зонды с временным
понижением внутреннего рычага `arenaCap` до 8 GiB (временный probe-файл в пакете `zdd`,
удалён после съёмки; сырые логи в `work/plan23/`, не коммитятся). Каждый тяжёлый прогон —
свой процесс под `flock ../kt-bench.lock`. Построение детерминировано: счётчики узлов и записей мемоизации
воспроизводимы бит-в-бит, плавает только wall-время. Счёт полных точек сверен с эталонами
`docs/requirements.md` (5×5 Paths ×2 = 1728; 6×6 Cycles ×2 = 19 724 — совпали).

### Экстраполяция на 8×8 и вердикт по порогам

Модель — байтовый бюджет `liveBytes`, узлы в прогнозе не участвуют. Анкеры роста:
записи мемоизации Paths narrow 3,165·10⁴ (5×5) → 2,50·10⁸ (6×6), то есть r(5→6)=7,9·10³;
плотность записей на уровне масштабируется с шириной разреза с коэффициентом
g≈2,4–4,9 на единицу ширины (пары: Paths 5×5/6×6 по доскам, row/narrow 5×5 внутри доски).

- Центральная оценка (g=4,9, ширина 12→16): записи ≈1,4·10¹¹ → liveBytes ≈8,8 ТБ →
  пик RSS ≈16 ТБ.
- Консервативная нижняя полоса модели (g=2,4): записи ≈8,3·10⁹ → liveBytes ≈0,5 ТБ →
  RSS ≈1 ТБ — всё ещё в ~35 раз выше порога.
- Демпфированная модель по доскам (r(6→7)=r(7→8)=√7900≈89): записи ≈2·10¹² → liveBytes
  ≈120 ТБ → RSS ≈220 ТБ. Без демпфирования рост уходит в петабайты — порядок совпадает с
  оценкой frontier DP (2–4 ПБ).
- Единственная модель, проходящая порог (RSS ≤28 ГБ ⇒ записи ≤ ~2,6·10⁸), требует нулевого
  роста состояний от 6×6 к 8×8. Она противоречит измерениям: на обрыве зонда 7×7 узлы уже
  ×2,6 полного 6×6 при незавершённом фронте, а записи на пиковых уровнях 7×7 (2,8·10⁷) не
  ниже пиковых уровней полного 6×6; ширина разреза при этом растёт (+2 на доску), а плотность
  состояний по ширине экспоненциальна.

Время: измеренная пропускная способность ≈2·10⁶ состояний/с даёт полосе памяти полосу
времени от часов (центральная модель) до десятков суток и лет (демпфированная и выше);
порог <30 суток выполняется лишь моделями, которые уже превысили память машины минимум
в ~35 раз. Память нарушает порог на всей согласованной полосе — вердикт держится на ней,
как и в ADR-038.

**ВЕРДИКТ: NO-GO.** Порог плана (пик ≤ ~28 ГБ **и** < 30 суток) не выполнен консервативной
границей с запасом ≥×35; план 23 закрывается как направление счёта, инструмент остаётся в `main`.
