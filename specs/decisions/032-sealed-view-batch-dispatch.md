# ADR-032. Sealed `View` (протокол write → seal → read) и безаллокационный батч-канал диспатча count-фазы

## Статус

Принято, гейт взят (2026-09-25). План 16. Вердикт benchmarker'а: **WIN** — `cnt_ms` всех трёх
прогонов ветки ниже полосы контроля базы только в минус (средний −4.4%), регресса нет ни по одной
метрике; бит-гейты идентичны во всех прогонах.

## Контекст

Механика count-диспатча досталась от плана 13 (ADR-019): продюсер под RLock шарда копировал записи
в общий bounded-LIFO стек с двумя condvar'ами (~100 строк ручной синхронизации, partial-push).
Вокруг неё накопился контрактный долг пакета `cache`: колбэк `Each` под RLock с унаследованным
caveat ADR-013; раздутое API чтения (`Reader` + живой `Get`, не вызываемый из прода, + `ItemsCount`);
`cacheShard.mu` — RWMutex с atomic readerCount-механикой на каждом `Lock` писателя, хотя конкурентных
читателей после барьера генерации никто не держит (ADR-031 снял чтения, локи остались).

## Решение

1. **`Cache.Seal() *View`** вместо `Reader()`: безлоковые `Get`/`Len` + pull-обход
   `All(ctx) iter.Seq[Entry]` по живым map без локов и копий таблицы (механика эталона ADR-013);
   предусловие «писателей нет после барьера» сконцентрировано в одной точке API. Удалены `Each`,
   `eachShard`, живой `Get`, `ItemsCount`, `Reader`; `cacheShard.mu`: RWMutex → Mutex (лок нужен
   только писателям).
2. **Батч-канал вместо condvar-стека** в `countTasks`: элемент `entryBatch { n int; items [16]Entry }`
   (392 Б, `unsafe.Sizeof`), буфер `⌈capacity/Beff⌉` слотов при прежней ёмкости `capacity =
   max(min(consumers·K, records), 1)` и неизменных K/B/C (ADR-019); одна канальная операция на `Beff`
   записей с каждой стороны — столько же синхронизаций, сколько захватов мьютекса в стеке; ноль
   аллокаций на запись. Порядок LIFO → FIFO — TIE по замерам ADR-019. Отмена: `All` встаёт на границе
   шардов, консьюмеры дренируют буфер без подсчёта.
3. **Оркестрация**: `ParallelCountWithDepth` thin — `generateIntermediate` → `extendTasks` →
   `countTasks`; worklist gen A материализуется обходом `view.All`. Публичный API `counter` не меняется;
   в `searcher` механическая пропаганда `*cache.Reader` → `*cache.View`.

Аллокационный бюджет подтверждён мером: `totalAllocMB` идентичен базе, аллокаций на ветке даже
чуть меньше (см. Замеры).

## Последствия

- `specs/cache.md`: протокол write/seal/read (`Seal`/`View`), удаления; `specs/counter.md`: §counting
  на батч-канале; `specs/searcher.md`: ручка `*cache.View`.
- Исчезли condvar-логика, partial-push, колбэк под залом, живой `Get`/`Each`/`ItemsCount`;
  mid-run конкурентное чтение таблицы API больше не предоставляет (прод-потребителей не было).
- Наружу от канальной границы — worst-case ~3.4 МБ буфера при workers=14 против стека 3.36 МБ (+2%).

## Замеры

Стенд: Apple M4 Max (14 ядер), workers=14, GOGC=40 конвейером; точка `make bench-size N=7
DEPTHS=22` (`-benchtime=1x`, отдельный процесс на прогон), прогоны сериализованы flock'ом
(`../kt-bench.lock`). База A/B — коммит отрыва `88310de` (merge-base с локальным main; ADR-031),
отдельный base-worktree. Протокол: контроль базы ×2, затем ветка ×3. Логи: `work/plan16/{base1,base2,br1..3}.log`.

`genA_ms` — 1.3–1.7 мс на всех прогонах (шум). Против средних базы: **cnt −4.4%**, gen B −3.4%,
wall −3.7%; peak RSS в полосе контроля (средний −0.1%), totalAlloc побитово тот же, аллокаций на
запись нет — ветка даже легче на ~550 allocs/op (удалённый condvar-механизм), B/op в шуме ±0.1%.

Гейт плана: полоса контроля `cnt` = [68.03; 72.63] с; все три прогоны ветки ([66.37; 67.69] с) —
вне полосы **только в минус**. Отделение подтверждается историческими числами той же ревизии из
ADR-031 (стадии 1+2 = `88310de`: cnt 70.69 / 69.47): из пяти известных прогонов базы минимум —
68.03, максимум ветки 67.71 — разделение полное (3/5 ниже всех). Величина выигрыша сопоставима с
дневным дрейфом (разброс самого контроля ±3.2%, контроль n=2), поэтому формулировка гейта —
«паритет или лучше», и он взят; ускорение не заявляется как цель (гипотеза была паритетной).
gen B ниже полосы контроля во всех прогонах — согласуется с предсказанием «RWMutex → Mutex
писателю только в пользу».

### Корректность (бит-гейты, все прогоны)

Итог 165 575 218 320 (`toursExpected`, enforced харнессом); hits/misses counting побитово
`364 804 607 / 1 584 519 460`; `writesB` 942 644 146; `prunedL2B` 455 269 742; `taskEntries`
92 315 032 — идентично базе во всех пяти прогонах. Примечание: число misses `1 772 741 575`,

(гейт применён к фактическому числу базы).
