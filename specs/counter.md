# counter: оркестрация подсчёта

## Ответственность

Высокоуровневый контур подсчёта: две генерационные фазы строят task-cache, затем count-фаза
считает дополнения с ранней остановкой по точному состоянию (ADR-011). Конвейер единственный —
ADR-016. Механику параллелизма фаз берёт на себя пакет `workerpool` (`Run`/`Fanout`,
specs/workerpool.md); симметрии стартов и мониторинг общие для всех фаз.
`ParallelCountWithDepth` — тонкий оркестратор: он выставляет GOGC и последовательно вызывает три
шага — `generateIntermediate`, `extendTasks`, `countTasks`.

## Публичный API

```go
const TwoPhaseBaseDepth = 5             // глубина промежуточной таблицы фазы gen A
const DefaultGCPercentReversal = 40     // GOGC на время всего конвейера (ADR-014)

func DefaultPrecomputeDepth(size int) int // контрактные значения из таблицы ниже;
                                          // для неизвестных досок — TwoPhaseBaseDepth+1

func NewCounter(g *graph.Graph) *Counter

// Параллельный подсчёт всех открытых туров. precomputeDepth — глубина разреза
// meet-in-the-middle, main.go валидирует её в [1, size²/2]. Итог накапливается
// в atomic.Uint64.
func (c *Counter) ParallelCountWithDepth(ctx context.Context, monitor monitoring.Monitor,
    workers, precomputeDepth int) uint64

// То же на глубине по умолчанию для данной доски.
func (c *Counter) ParallelCount(ctx context.Context, monitor monitoring.Monitor, workers int) uint64

// Ген-ценз (план 19): фазы gen A и gen B пишут в сток cache.NullSink — task-cache не
// заводится, count-фаза не идёт. Снимки монитора по генерационным фазам равны снимкам
// полного прогона той же глубины. Верхняя граница глубины size²/2 не применяется: условие
// дуальности относится к count-фазе, которой здесь нет.
func (c *Counter) CensusWithDepth(ctx context.Context, monitor monitoring.Monitor,
    workers, censusDepth int)

// Диагностика:
func (c *Counter) SetGCPercent(p int)   // GOGC на время конвейера (ADR-014): при p > 0 значение
                                        // ставится на входе и восстанавливается на выходе;
                                        // p <= 0 — не трогать GC рантайма. Значение по умолчанию —
                                        // DefaultGCPercentReversal.
```

`DefaultPrecomputeDepth` возвращает глубину с минимальным временем работы на измеренном окне
глубин; критерий выбора — «чистое время» (ADR-017). Пояснения к строкам таблицы: `5: 6` — это
плато d2..d12, неразличимое над шумом повторов, поэтому смену не оценивали (ADR-016); `8: 14` —
placeholder без пересъёмки (ADR-015). Сами замеры живут в ADR-016 §«Замеры» и плане 10.

| size | 5 | 6 | 7 | 8 |
|---|---|---|---|---|
| depth | 6 | 14 | 22 | 14 |

Память не ограничивает выбор глубины: пик RSS — справочная метрика (ADR-017). Пониженный GOGC на
время конвейера сохраняется (ADR-014).

## Алгоритм (три фазы)

### gen A (`generateIntermediate`)

Воркеры идут параллельно по каноническим стартовым группам через `workerpool.Pool.Run`: воркеров
`min(workers, len(groups))`, каждый снимает индекс задачи с общего атомарного счётчика. Каждая
задача — вызов `searcher.GenerateTasks(ctx, intermediate, canonical, orbitSize, a)`, где
`a = min(precomputeDepth, TwoPhaseBaseDepth)`. Таблица `intermediate` — экземпляр `cache.Cache`
(маска → гистограмма «класса конца», specs/cache.md). Воркеры пишут в неё напрямую через `Set`;
промежуточное буферизование записей здесь не нужно, потому что таблица мала, а фаза занимает мкс–мс.

Барьер `Run` останавливает всех писателей, после чего таблица опечатывается (`Seal`), и обход
`All(ctx)` строит список работ для gen B **развёрнутым**: по одному `cache.Entry{Mask, Rep, Weight}`
на класс. Ёмкость среза берётся от `View.Len()` — это число масок, то есть только нижняя оценка,
ведь классов не меньше масок. Промежуточная таблица больше не нужна, и её забирает сборщик мусора
(ADR-018).

### gen B (`extendTasks`)

Снова `workerpool.Pool.Run`, теперь по списку работ: воркеров `min(len(entries), workers)`, индексы
задач снимаются с того же атомарного счётчика. Каждая задача — вызов
`searcher.ExtendTask(ctx, staging, e, precomputeDepth)` на развёрнутой записи `e`.

Воркер создаёт собственный `cache.Staging` (пакетная запись в таблицу, ADR-031) и сливает его в
task-cache при выходе из цикла обработки задач. Автослияние наступает по лимиту буфера
(`stagingFlushLimit = 8192`), а обязательный `Flush` выполняется на любом пути выхода — в том числе
при уже отменённом ctx. Так видимость записанных листьев не хуже, чем при прямой записи. При
`precomputeDepth ≤ TwoPhaseBaseDepth` фаза вырождается: каждая запись передаётся в таблицу как есть
(тоже через `Staging`). Листья обеих таблиц проходят фильтр записей в кэш в `dfsTask`
(specs/searcher.md, ADR-030): классы с нулевым числом дополнений не пишутся, поэтому task-cache
содержит только задачи с ненулевым потенциалом вклада в итог.

### Count-фаза (`countTasks`)

Диспатч идёт через `workerpool.Fanout[entryBatch]` поверх безаллокационного канала пачек (план 16,
план 17). После барьера генерации task-cache опечатывается один раз (`Seal`). Один и тот же
неизменяемый снимок `View` даёт и таблицу мемоизации для ранней остановки счёта (`Get`), и обход
производителя (`All(ctx)`); писателей больше нет — это предусловие `Seal` (specs/cache.md).
Производитель обходит **развёрнутые** записи: задача count-фазы — пара `(mask, rep как конец)`, а
вес `Weight` контур умножает сам.

`records = view.Len()` — число масок, а не задач, потому что классов не меньше масок. Эта величина
служит нижней оценкой только формулам фазы, а корректность от её точности не зависит:

- число потребителей: `max(min(workers, records), 1)` — контур счёта ограничивает значение
  диапазоном, чтобы потребитель был хотя бы один;
- эффективный размер пачки считается один раз на старте фазы:
  `Beff = min(B, max(1, records/(consumers·C)))`. Здесь `B` — потолок пачки (фиксированное
  значение 16), а `C = 4` — нижняя граница числа отправок на потребителя (ADR-019);
- ёмкость канала в записях: `capacity = max(min(consumers·K, records), 1)`, где `K` — глубина
  очереди на потребителя (фиксированное значение 10000 — измеренная точка, ADR-019); буфер канала —
  `ceil(capacity/Beff)` слотов, он выделяется одной аллокацией на старте фазы.

Элемент канала — пачка: заголовок `n` плюс массив из `B` копий `cache.Entry`; весь элемент занимает
392 Б, а `Entry` — 24 Б (маска 8 + тег класса 1 + вес 8 с упаковкой в слово). Всегда выполняется
`Beff ≤ B`. Формулы K/B/C выведены из этого размера и не зависят от формата значения таблицы
(план 18).

Производитель — единственный владелец обхода `All`: он наполняет `items[:Beff]` и отправляет полную
пачку; хвост (`n < Beff`) становится последней отправкой, а при завершившемся ctx не отправляется.
Затем канал закрывается. Потребители читают пачки циклом `for b := range ch` и для каждой записи
вызывают `searcher.CountPathsWithCacheReversal(ctx, e, view, precomputeDepth)` не беря мьютексов,
складывая `e.Weight · paths` в общий `atomic.Uint64`. Порядок доставки — FIFO обхода; контрастную
точку LIFO измерили как TIE (ADR-019). Противодавление канала: на полном канале производитель
блокируется до целого свободного слота и начинает заполнять новую пачку с нуля, дописывать
незаполненную он не станет. Дедлок исключён: буфер всегда не меньше одного слота, потребители ничего
не ждут от производителя и дочитывают канал до close.

Производитель регистрирует задачи фазы инкрементально: перед **каждой** отправкой пачки он вызывает
`monitor.AddTasks(n)` на число записей пачки. К концу фазы `Tasks` равно точному числу класс-задач и
совпадает с `Completed`. Регистрация строго до отправки даёт `completed ≤ tasks` в любой момент
фазы: прогресс не превышает 100%, а оценка оставшегося времени считается по полному знаменателю и
не обнуляется преждевременно. При завершившемся ctx хвостовая неотправленная пачка остаётся
зарегистрированной, но не выполненной; для partial-run это ожидаемый прогресс ниже 100%.

Весь конвейер работает под пониженным GOGC (`SetGCPercent`, ADR-014): значение применяется на входе
и восстанавливается при выходе. Пиком фазы остаётся живая task-cache, а запас памяти над ней стоит
слишком дорого.

### Ген-ценз (`CensusWithDepth`, план 19)

Тот же генерационный спуск, но фаза B пишет в `cache.NullSink`: фабрика писателя на воркер
возвращает сток со пустой заменой вместо `Staging`. Task-cache не заводится, `Seal` и count-фаза
не выполняются, поэтому память фазы B постоянна. Счётчики записей и отсечений считает спуск в
`types.Result`, потому снимки монитора фаз gen A и gen B совпадают с полным прогоном той же
глубины. GOGC применяется как в полном прогоне, чтобы время gen B оставалось сравнимым.
Глубина ценза ограничена только размером доски (валидацией вызывающего контура): без count-фазы
условие дуальности `2d ≤ size²` не действует.

## Инварианты и корректность

- Каждое класс-размещение глубины `a` проходит ровно через один слот `(K, rep)`: граф и pruner
  симметричны относительно `D4`. Итог подчиняется тождеству `total = Σ_tasks W(task)·f(task)` на
  множестве канонических префиксов (ADR-011); задача — развёрнутый `cache.Entry`, пара
  `(mask, rep как end)`.
- Общий счёт ведёт `atomic.Uint64`; обе таблицы шардированы. gen A пишет напрямую через `Set`, а
  gen B — через собственный `Staging` каждого воркера: разделяемого буфера нет, у каждого воркера
  свой. Итог не зависит от числа воркеров и глубины разреза (тест инвариантности). Порядок доставки
  записей потребителям (FIFO, гранулярность пачки) на итог тоже не влияет.
- Бюджет диспатча count-фазы — предвыделенный буфер канала: `⌈capacity/Beff⌉ × 392 Б` одной
  аллокацией на старте фазы и ноль аллокаций на запись. Синхронизация стоит одну канальную операцию
  на `Beff` записей с каждой стороны. Пока формула активна (малые таблицы), число отправок
  производителя не больше примерно `consumers·C + 1` независимо от размера таблицы. При workers = 14
  и K = 10000 худший случай — `⌈140 000/16⌉ × 392 Б ≈ 3.4 МБ`; этот объём незаметен на фоне пика
  task-cache.
- Глубина разреза сверху ограничена `size²/2`: дальше лежит точка дуальности обращения
  (`2d ≤ totalCells`), и разрез лишь повторяет двойственный ему разрез перевёрнутого тура.

## Ограничения и edge cases

- Завершившийся контекст — внешняя отмена **или** истечение deadline (`ctx.Err() != nil`) — на любом
  обходе `All` конвейера (построение списка работ в gen A, обход производителя в count-фазе) даёт
  частичный результат без паники. В count-фазе это значит: обход останавливается сам на границе
  шардов, хвостовая пачка не отправляется, канал закрывается, а потребители дочитывают буферизованные
  пачки **без подсчёта** (задача пропускается при `ctx.Err() != nil`) — итог частичный. Иных
  источников ошибок у обхода нет (specs/cache.md).
- Task-cache живёт до конца count-фазы и не освобождается по шардам; на низких глубинах (большое q)
  счёт дорожает. Пониженный GOGC на время конвейера — штатное поведение по умолчанию (ADR-014).
- Две конкурентные трубы в одном процессе восстанавливают GC-процент в порядке «последний пишет»:
  значение глобально для рантайма, а тесты идут последовательно.

## Тесты

`counter/counter_test.go`:

- Итог против эталона на всех допустимых глубинах: `TestParallelCountWithDepthMatchesReference`
  (5×5 = 1728; 6×6 = 6 637 920 на выборке глубин), плюс `TestSequentalCount`, `TestParallelCount` и
  `TestParallelCountWithDepth`.
- Инвариантность к числу воркеров — `TestWorkerInvariance`; последовательный запуск совпадает с
  параллельным.
- Упаковка task-cache не теряет и не дублирует вклады: `TestTaskCacheWeightConservation7x7` сверяет
  ΣW по класс-слотам с brute-force обходом листьев, прошедших фильтр записей в кэш;
  per-task reversal-эквивалентность закреплена brute-force таблицей 5×5 (specs/searcher.md).
- gen A: веса классов списка работ кратны орбите и сохраняются при слиянии групп
  (`TestGenerateIntermediateWeightsMatchOrbits`); записи останавливаются на base-глубине
  (`TestGenerateIntermediateStopsAtBaseDepth`).
- Контрактные глубины таблицы — `TestDefaultPrecomputeDepth`.
- Мониторинг: count-фаза публикует hits/misses в свои счётчики (`TestCountingPublishesHitsMisses`);
  отсечения count-DFS с разбивкой по причинам попадают в фазу `counting`
  (`TestCountingPhaseReportsPruning`); фильтр записей в кэш работает в обеих генерационных фазах и
  не работает в счётной (`TestGenerationPhasesReportWriteGate`).
- Канал пачек доставляет каждый развёрнутый класс таблицы ровно один раз, без дублей и потерь: итог
  равен последовательному Σ W·f(task), число завершённых задач равно зарегистрированным `AddTasks` и
  числу классов обхода `All`, но не меньше `View.Len()`, при нескольких значениях workers
  (`TestCountTasksDeliversEachEntryOnce`). Spy-монитор пинит инвариант прогресса: на каждом репорте
  завершения задачи `completed ≤ tasks` (`TestCountingProgressNeverExceedsRegistered`). Принудительное
  противодавление (K = 1 и буфер в один слот — каждая отправка ждёт дочитывания) не дедлокается и не
  меняет итог (`TestDispatchEntriesExactOnceUnderBackpressure`, `TestCountTasksForcedOverflow`).
- Формула `Beff` закреплена табличным тестом границ: доставка по одной записи при записях ≤
  consumers·C и потолок B при записях ≥ B·consumers·C (`TestEffectiveBatch`); малая таблица
  (записей < B) доставляется по одной записи в пачке.
- Завершившийся контекст (отмена и дедлайн — таблица) даёт частичный итог без паники
  (`TestTerminatedContextPartialRun`); отмена ровно в момент первого засчитанного таска при
  workers = 1 оставляет ровно одну завершённую задачу счётной фазы
  (`TestCancelDuringCountingGivesPartialTotal`).
- GC-ручка (ADR-014): итог не зависит от `SetGCPercent(0|40)`, а после завершения конвейера процент
  рантайма восстановлен (`TestGCPercentAppliesAndRestores`).
- Ген-ценз (план 19): табличный тест на 5×5 (все глубины) и 6×6 (выборка) — снимки `FakeMonitor`
  ценза по фазам gen A и gen B равны снимкам полного прогона той же глубины
  (`TestCensusMatchesFullRunGeneration`); отменённый ctx даёт частичный снимок без паники
  (`TestCensusTerminatedContextIsPartial`).
