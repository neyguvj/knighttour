# counter: оркестрация подсчёта

## Ответственность

Высокоуровневый контур подсчёта: двухфазная генерация префиксов в task-cache и count-фаза
с ранним стопом через мемо по точному состоянию (ADR-011, единственный конвейер — ADR-016).
Механика параллелизма фаз — пакет `workerpool` (`Run`/`Fanout`, specs/workerpool.md), симметрии
стартов и мониторинг — общие для фаз. `ParallelCountWithDepth` — тонкий оркестратор: GC-scope и
три шага `generateIntermediate` → `extendTasks` → `countTasks`.

## Публичный API

```go
const TwoPhaseBaseDepth = 5                 // глубина промежуточной таблицы фазы A
const DefaultGCPercentReversal = 40         // GOGC на время конвейера (ADR-014)

func DefaultPrecomputeDepth(size int) int   // контрактные значения таблицы ниже;
                                            // fallback TwoPhaseBaseDepth+1 для неизвестных досок

func NewCounter(g *graph.Graph) *Counter

// Параллельный подсчёт всех открытых туров; разрез meet-in-the-middle на precomputeDepth
// (валидируется в main.go в [1, size²/2]). Суммирование — atomic.Uint64.
func (c *Counter) ParallelCountWithDepth(ctx context.Context, monitor monitoring.Monitor,
    workers, precomputeDepth int) uint64

// Обёртка: глубина по умолчанию для текущей доски.
func (c *Counter) ParallelCount(ctx context.Context, monitor monitoring.Monitor, workers int) uint64

// Диагностика:
func (c *Counter) SetGCPercent(p int)       // GOGC на время конвейера (ADR-014);
                                            // p > 0 — debug.SetGCPercent(p) на входе и
                                            // восстановление прежнего при выходе;
                                            // p == 0 — не трогать. Значение по умолчанию —
                                            // DefaultGCPercentReversal
```

Контрактные значения `DefaultPrecomputeDepth` — глобальный минимум времени на измеренном
окне глубин (критерий «чистое время» — ADR-017; замеры пересъёмки — ADR-016 §«Замеры», план 10;
`5: 6` — плато d2..d12, неразличимое над шумом повторов, смена не оценима, ADR-016;
`8: 14` — placeholder без пересъёмки, ADR-015):

| size | 5 | 6 | 7 | 8 |
|---|---|---|---|---|
| depth | 6 | 14 | 22 | 14 |

Память не ограничивает выбор глубины (пик RSS — справочная метрика, ADR-017); пониженный
GOGC на время конвейера сохраняется (ADR-014).

## Алгоритм (три фазы)

1. **gen A** (`generateIntermediate`) — параллельно по каноническим стартовым группам через
   `workerpool.Pool.Run` (`min(workers, len(groups))` воркеров, задачи тянутся атомарным курсором):
   `searcher.GenerateTasks(ctx, intermediate, canonical, orbitSize, a)`, где
   `a = min(precomputeDepth, TwoPhaseBaseDepth)` и `intermediate` — экземпляр `cache.Cache`
   (маска → гистограмма «класс конца», specs/cache.md); воркеры пишут напрямую через `Set`
   (промежуточная буферизация записей не нужна: таблица мала, фаза — мкс/мс). Писателей
   останавливает барьер `Run`, затем таблица запечатывается (`Seal`) и worklist фазы B
   материализуется обходом `All(ctx)` **развёрнуто** — по одному `cache.Entry{Mask, Rep,
   Weight}` на класс; ёмкость среза от `View.Len()` (число масок) — только нижняя оценка,
   классов ≥ масок; сама таблица затем выбрасывается (ADR-018).
2. **gen B** (`extendTasks`) — `workerpool.Pool.Run` по worklist (`min(len(entries), workers)`
   воркеров, задачи тянутся атомарным курсором), каждая задача — `searcher.ExtendTask(ctx,
   staging, e, precomputeDepth)` c развёрнутой записи `e`;
   собственный `cache.Staging` (батч-запись, ADR-031) создаётся и флешится в теле воркера вокруг
   цикла по курсору: флеш по лимиту буфера и обязательный `Flush` на выходе воркера — в том числе
   при отменённом ctx, чтобы видимость записанных листьев не хуже прямой записи. При
   `precomputeDepth ≤ TwoPhaseBaseDepth` фаза вырождается — запись самой записи (тоже через
   Staging). Листья обеих таблиц проходят
   L2-гейт записи в `dfsTask` (specs/searcher.md, ADR-030): классы с нулевым числом дополнений
   не пишутся — task-cache содержит только задачи с ненулевым потенциалом вклада в итог.
3. **counting** (`countTasks`) — диспатч через `workerpool.Fanout[entryBatch]` поверх
   безаллокационного батч-канала (план 16; план 17): `produce` — обход-продюсер, `consume` —
   счёт одной пачки; `close` канала — по возврате produce, дренаж до close — за пулом. После
   барьера генерации task-cache запечатывается один раз (`Seal`): тот же `View` даёт и мемо
   раннего стопа (`Get`), и обход-продюсер (`All(ctx)`); писателей больше нет по предусловию
   `Seal` (specs/cache.md). Продюсер обходит **развёрнутые** записи `Entry{Mask, Rep, Weight}`
   (по одной на класс); задача count-фазы — пара `(mask, rep как конец)`, вес `Weight` контур
   умножает сам. `records = view.Len()` — число **масок**, а не задач (классов ≥ масок): это
   нижняя оценка **только** для формул фазы — консьюмеры `min(workers, records) ≥ 1` (clamp считает
   counter — фазовая политика), корректность от точности оценки не зависит. Эффективный батч `Beff = min(B, max(1, записей/(консьюмеры·C)))` считается один раз
   на старте фазы; `B` — потолок батча (фиксированно 16), `C = 4` — нижняя граница числа снятий
   на консьюмера (ADR-019). Элемент канала — батч: заголовок `n` + массив `B` копий `cache.Entry`
   (392 Б); всегда `Beff ≤ B`. `Entry` — 24 Б (маска 8 + тег класса 1 + вес 8 с упаковкой в
   слово), формулы K/B/C выведены из этого размера и от формата значения таблицы не зависят
   (план 18). Буфер предвыделен: `ceil(capacity/Beff)` слотов, где
   `capacity = max(min(консьюмеры·K, записей), 1)`, `K` — глубина на консьюмера (фиксированное
   значение 10000 — измеренная точка ADR-019). Продюсер — единственный обход `All`: наполняет
   `items[:Beff]` и шлёт полный батч; хвост (`n < Beff`) — последняя отправка (не отправляется при
   завершившемся ctx); затем `close(ch)`. Консьюмер: `for b := range ch`, для каждой записи батча —
   `searcher.CountPathsWithCacheReversal(ctx, e, view, precomputeDepth)` **вне любых залов**,
   складывая `e.Weight · paths` в общий `atomic.Uint64`. Порядок доставки — FIFO обхода (контрастная точка
   LIFO/FIFO измерена TIE, ADR-019). Backpressure: продюсер на полном канале блокируется до целого
   свободного слота и продолжает с нового батча (дописывания в оставшееся место нет); дедлок
   исключён — буфер ≥ 1 слота, консьюмеры ничего не ждут от продюсера и всегда дренируют.
    Задачи фазы регистрирует продюсер инкрементально: перед **каждой** отправкой батча —
    `monitor.AddTasks(n)` на число записей батча. По завершении фазы `Tasks` равно точному числу
    класс-задач и совпадает с `Completed`. Регистрация строго до отправки даёт `completed ≤ tasks`
    в любой момент фазы: прогресс не превышает 100%, ETA не прилипает к `0s`. При завершившемся ctx
    хвостовой неотправленный батч остаётся зарегистрированным, но не выполненным — для partial-run
    это ожидаемый прогресс < 100%.

Весь конвейер работает под пониженным GOGC (`SetGCPercent`, ADR-014): значение применяется на
входе и восстанавливается при выходе — пик фазы это живая task-cache, headroom над ней дорог.

## Инварианты и корректность

- Каждый класс-размещение глубины `a` проходит ровно через один слот `(K, rep)`
  (D4-эквивариантность графа/прунера); тождество итога `total = Σ_tasks W(task)·f(task)` на
  множестве канонических префиксов (ADR-011), задача — развёрнутый `cache.Entry`,
  `(mask, rep как end)`.
- Общий счёт — `atomic.Uint64`; обе таблицы шардированы; gen A пишет прямо через `Set`,
  gen B — через per-worker Staging (разделяемого буфера нет, каждый воркер — свой). Итог не
  зависит от числа воркеров и глубины разреза (тест инвариантности); порядок доставки записей
  консьюмерам (FIFO, батч-гранулярность) на итог не влияет.
- Бюджет диспатча count-фазы — предвыделенный буфер канала: `⌈capacity/Beff⌉ × 392 Б` одной
  аллокацией на старте фазы, ноль аллокаций на запись; синхронизация — одна канальная операция
  на `Beff` записей с каждой стороны. Пока формула активна (малые таблицы), число отправок
  продюсера ≤ ~`консьюмеры·C + 1` независимо от размера таблицы. workers = 14, K = 10000:
  худший случай `⌈140 000/16⌉ × 392 Б ≈ 3.4 МБ`, шум против пика task-cache.
- Глубина разреза сверху ограничена `size²/2`: точка дуальности обращения (`2d ≤ totalCells`),
  глубже — дублирование двойственного разреза.

## Ограничения и edge cases

- Завершившийся контекст — внешняя отмена **или** истечение deadline (`ctx.Err() != nil`) — на
  любом обходе `All` конвейера (материализация worklist gen A, обход-продюсер count) даёт
  частичный результат без паники. В count-фазе это означает: обход останавливается сам на
  границе шардов, хвостовой батч не отправляется, канал закрывается, консьюмеры дренируют
  буферизованные батчи **без подсчёта** (пропуск задачи при `ctx.Err() != nil`) — частичный итог.
  Иных источников ошибок у обхода нет (specs/cache.md).
- Task-cache живёт до конца count-фазы и не дренируется по шардам; на низких глубинах
  (большое q) счёт дорожает. Пониженный GOGC на время конвейера — штатное поведение
  по умолчанию (ADR-014).
- Две конкурентные трубы в одном процессе восстанавливают GC-процент в порядке
  «последний пишет» — значение глобально для рантайма; тесты последовательны.

## Тесты

`counter/counter_test.go`: итог на всех допустимых глубинах == эталон (5×5 = 1728,
6×6 = 6 637 920); плюс таблично малые глубины 7×7 — консервация ΣW по класс-слотам
task-cache против brute-force обхода гейтованных листьев (`TestTaskCacheWeightConservation7x7`):
упаковка «маска + класс» не теряет и не дублирует вклады; per-task reversal-эквивалентность
закреплена brute-force таблицей 5×5 (specs/searcher.md); sequential == parallel;
инвариантность к числу воркеров; `TestDefaultPrecomputeDepth`; веса классов промежуточного
worklist кратны орбите и останавливаются на base-глубине; counting публикует hits/misses в
счётчики фазы `counting`. Батч-канал диспатча доставляет каждый развёрнутый класс таблицы ровно
один раз без дублей и потерь (итог == последовательный Σ W·f(task), завершённых задач == число
классов обхода `All` == зарегистрированных `AddTasks` и не меньше `View.Len()`, несколько значений
workers); spy-монитор пинит инвариант прогресса — на каждом репорте завершения задачи
`completed ≤ tasks` (прогресс счётной фазы никогда не превышает 100%); принудительный
backpressure (K = 1 и буфер в один батч-слот — каждая отправка ждёт дренажа) не дедлокается и не
меняет итог. Формула `Beff` закреплена табличным
тестом границ (per-record при записях ≤ консьюмеры·C; потолок B при записях ≥ B·консьюмеры·C),
и малая таблица (записей < B) доставляется по одной записи в батче. Завершившийся контекст
(отмена и дедлайн — таблица) даёт частичный итог без паники; отмена ровно в момент первого
засчитанного таска (workers = 1) оставляет ровно одну завершённую задачу счётной фазы. GC-ручка
(ADR-014): итог не зависит от `SetGCPercent(0|40)`; после завершения конвейера процент рантайма
восстановлен (значения до/после в тесте).
