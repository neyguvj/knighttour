# monitoring: прогресс по фазам

## Ответственность

Пакет отслеживает и показывает прогресс подсчёта с разбивкой по фазам конвейера
(`gen A` → `gen B` → count-фаза). Монитор только агрегирует входящие данные;
собственных счётчиков поиска у него нет. Готовые подзадачи приносят статистику
через `ReportSubtask`, остальное публикуется по мере работы. На экран выводятся
время и ETA активной фазы, задачи, найденные пути, записи в таблицы, попадания
и промахи task-cache и отсечения по причинам.

## Публичный API

```go
type Monitor interface {
    Start(ctx context.Context)     // закрепляет часы; verbose — ещё горутину живой строки
    Finish()                       // закрывает активную фазу; verbose — финальный отчёт
    BeginPhase(name string)        // начинает новую активную фазу; только между фазами
    AddTasks(count int)            // дописывает задачи активной фазы, вызывается многократно
    ReportTaskCompleted()          // одна задача активной фазы завершена
    ReportPathsFound(count int)    // найденные пути (count-фаза — с учётом веса)
    // ReportSubtask складывает в активную фазу статистику одной готовой подзадачи:
    // записи в таблицу, попадания/промахи task-cache, отсечения по причинам.
    ReportSubtask(r *types.Result)
}

func NewMonitor() *RealMonitor      // verbose: живая строка раз в секунду и финальный отчёт
func NewFakeMonitor() *FakeMonitor  // тихо: только накопление статистики

// Снимки для тестов и бенчмарков; методы доступны обоим мониторам.
type PhaseStats struct {
    Tasks       uint64 // зарегистрированные задачи фазы
    Completed   uint64 // завершённые задачи
    Subtasks    uint64 // число вызовов ReportSubtask (нигде не печатается)
    PathsFound  uint64 // найденные пути (count-фаза, с учётом веса)
    CacheWrites uint64 // записи в таблицу (gen A / gen B)

    CacheHits   uint64 // попадания в task-cache (count-фаза)
    CacheMisses uint64 // промахи в task-cache (count-фаза)

    Pruned          uint64 // сумма отсечений по всем причинам
    PrunedDeadEnd   uint64
    PrunedNoCont    uint64
    PrunedDisconn   uint64
    PrunedEndpoints uint64

    PrunedForcedChain uint64 // фильтр записей в кэш: перегрузка или цикл цепочки

    Duration time.Duration // ноль, пока фаза не закрыта
}

func (m *monitor) Phase(name string) PhaseStats // сумма фаз с таким именем; ноль, если их не было
func (m *monitor) Totals() PhaseStats           // сумма всех записанных фаз
```

## Контракты

- **Общее ядро.** `RealMonitor` и `FakeMonitor` исполняют одну реализацию и
  различаются ровно полем `verbose`. Фейк не запускает горутину печати и ничего
  не выводит, но накапливает статистику идентично.
- **Переключение фаз.** Оркестратор вызывает `BeginPhase` строго между фазами:
  воркеры предыдущей фазы к этому моменту завершены. Поэтому дописывание новой
  фазы не конкурентно с сообщениями воркеров, а сообщения читают активную
  фазу через атомарный указатель.
- **Одноимённые фазы суммируются.** Повторный `BeginPhase("gen A")` дописывает
  новую запись; `Phase(name)` складывает все записи с этим именем.
- **Сообщения до первой фазы игнорируются.** Пока активной фазы нет, любой
  вызов `AddTasks`, `ReportTaskCompleted`, `ReportPathsFound` или
  `ReportSubtask` не делает ничего.
- **`ReportSubtask` — единственный поставщик статистики подзадач.** Поле
  `TotalPathsFound` внутри `Result` им игнорируется: count-фаза публикует
  взвешенные пути отдельно через `ReportPathsFound`.
- **Счётчики атомарны.** Все счётчики фазы — `atomic.Uint64`; суммарное число
  отсечений равно сумме по всем причинам.
- **Знаменатель прогресса.** `AddTasks` аддитивен и вызывается сколько угодно
  раз внутри фазы: порождающая сторона регистрирует задачи постепенно. Порядок «сначала
  `AddTasks`, потом завершение той же задачи» обеспечивает вызывающий. При его
  соблюдении `completed ≤ tasks`, и прогресс никогда не превышает 100%. При
  нарушении прогресс переваливает за сто процентов, а ETA застревает на `0s`.

## Формат вывода (verbose)

Живой вывод печатает одну строку раз в секунду только про активную фазу.
Предыдущая строка затирается ANSI-последовательностью `\x1b[2K\r`:

```
[1.234s] Phase gen B | Tasks: 1200/5041 (23.8%) | Paths 0 | Writes 447520 | Pruned 129334 | ETA 3.953s
```

`Finish` печатает финальный отчёт: заголовок `=== Final ===`, общее время,
затем по строке на каждую фазу и суммарное число путей. Разбивка отсечений
в скобках перечисляет только ненулевые причины в фиксированном порядке
`deadend, nocont, disconn, endpoints, chain`. В строках финального отчёта
сегменты статистики строчными буквами (`writes`, `hits`).

ETA — линейная оценка: время активной фазы умножается на отношение оставшихся
задач к завершённым. Если ни одна задача не завершена или общее их число
неизвестно, вместо ETA печатается `--`; при завершении всех задач — `0s`.
Сегмент `Writes` появляется только при ненулевых записях в таблицу. Сегмент
`Hits x/y` (попадания и промахи task-cache) печатается сразу после `Writes`,
когда хотя бы одно из двух значений ненулевое.

## Инварианты и edge cases

- Накладные расходы меньше процента: учёт сообщений выполняет только атомарные
  операции, а блокировка нужна лишь на дописывание фазы.
- Отмена контекста останавливает горутину мониторинга. Пропуск живой строки
  не влияет на результат подсчёта.
- `Finish` без `Start` не делает ничего и не паникует.
- Снимки аддитивны и не сбрасываются: один монитор на N прогонов даст
  N-кратные суммы. Для метрик «на прогон» монитор создают заново.
- Длительность фазы фиксируется при её закрытии — следующим `BeginPhase` или
  `Finish`. Чтобы прочитать длительность последней фазы, нужно вызвать
  `Start`, а затем `Finish`.

## Тесты

`monitoring/monitor_test.go` закрепляет:

- сообщения без активной фазы не делают ничего — `TestReportsWithoutPhaseAreNoop`;
- агрегацию по фазам и закрытие предыдущей фазы при `BeginPhase` — `TestPhaseAccumulation`;
- раскладку `ReportSubtask` по причинам отсечений — `TestReportSubtaskSumsByReason`,
  попадания и промахи task-cache — `TestReportSubtaskFoldsCacheHitsMisses`;
- табличную проверку `estimateRemaining` — `TestEstimateRemaining`, миллисекундную
  точность `fmtDur` — `TestFmtDurMillisecondPrecision`;
- живую строку: ANSI-префикс затирания, значения ETA `--` и `0s` — `TestReportFormatWithETA`,
  условность и порядок сегментов `Writes`/`Hits` — `TestLiveLineConditionalSegments`;
- финальный отчёт: строки фаз, разбивка только ненулевых причин, суммарные пути —
  `TestFinalReportFormat` и `TestRealMonitorPrintsFinalReport`;
- общность ядра: один сценарий на Real и Fake даёт совпадающие снимки —
  `TestMonitorsShareCountingLogic`; фейк печатает пусто — `TestFakeMonitorPrintsNothing`;
  оба монитора удовлетворяют интерфейсу — `TestFakeMonitorSatisfiesInterface`;
- накопление фейка по фазам (табличный тест) — `TestFakeMonitorRecordsPerPhase`;
- конкурентные вызовы под `-race` — `TestConcurrentReportsRace` и
  `TestFakeMonitorConcurrentReports`;
- `Finish` без `Start` без паники — `TestFinishWithoutStartDoesNotPanic`.
