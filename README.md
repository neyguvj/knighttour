# Knight Tour — Поиск всех открытых маршрутов коня

![Test Status](https://github.com/neyguvj/knighttour/actions/workflows/test.yml/badge.svg)

Реализация алгоритма подсчёта всех открытых маршрутов коня (knight's tours) на досках от 5×5 до 8×8 с использованием параллельных вычислений и продвинутых оптимизаций.

**Открытый маршрут** — это последовательность ходов коня, при которой он посещает каждую клетку доски ровно один раз (не возвращаясь в начальную клетку).

## Quick Start

```bash
# Быстрый запуск на доске 5×5 (по умолчанию)
go run main.go

# Запуск на доске 6×6 с параллелизмом
go run main.go -size 6 -workers 14

# С более глубоким предварительным разбиением подзадач
go run main.go -size 6 -workers 14 -precompute-depth 12
```

## Параметры командной строки

| Флаг | Тип | По умолчанию | Описание |
|------|-----|--------------|----------|
| `-size` | `int` | `5` | Размер доски (от 5 до 8) |
| `-workers` | `int` | число ядер CPU | Количество параллельных воркеров (1 = последовательный режим) |
| `-precompute-depth` | `int` | по размеру доски: `{5: 6, 6: 10, 7: 20, 8: 14}` | Глубина meet-in-the-middle разреза (от 1 до size²/2; глубже — дуал разреза обращённого тура) |
| `-tail-memo` | `int` | `0` (выключено) | Хвостовое мемо фазы счёта: хранить `f(cur,todo)` между формами одного воркера при `popcount(todo) ≤ K` |
| `-mode` | `string` | `class` | Режим подсчёта: `class` (ДП по классам форм) или `reversal` (task-cache + count-DFS с обращениями); победитель A/B-свода определит дефолт |
| `-gc-percent` | `int` | `40` | GOGC на время reversal-конвейера: пониженный GC держит пик task-cache ниже (`0` — не трогать GC рантайма); class mode значение игнорирует (ADR-014) |

## Как это устроено

Дальше — рассказ об алгоритме по порядку: от представления доски и сокращения пространства поиска через симметрию, к трёхфазному конвейеру генерации и счёта по классам форм, отсечению тупиковых ветвей и замерам. Детальные описания каждого компонента — в каталоге `specs/`.

### Структура графа

Всё состояние поиска — это одна 64-битная маска: один бит на клетку, 1 означает «посещена», 0 — «не посещена». Для доски до 8×8 (64 клетки) это помещается в одно машинное слово, поэтому копирование состояния — обычное присваивание, а само состояние — готовым ключом аккумуляторов. Битовые операции вынесены в отдельный пакет, а вызывающий код перебирает установленные биты через итератор, не обращаясь к битам напрямую.

Над маской лежит предвычисленный граф ходов коня. При старте для каждой клетки один раз строятся список соседей и побитовая маска этих соседей. Проверка «куда можно ходить из текущей клетки» сводится к пересечению маски соседей с маской непосещённых клеток — за O(1). Соседи хранятся в фиксированном порядке восьми возможных ходов коня; сортировка по эвристике Вонсдорфа сознательно не используется — замер показал, что она не меняет число узлов дерева поиска, а только добавляет стоимость сортировки в каждом узле (см. «Вывод»).

### Симметрия доски

Квадратная доска обладает группой симметрий D₄ — восемью преобразованиями: четыре поворота и четыре отражения. Это позволяет сократить пространство поиска в несколько раз.

Все восемь преобразований:

1. Без изменений (тождество)
2. Поворот на 90°
3. Поворот на 180°
4. Поворот на 270°
5. Отражение по горизонтали
6. Отражение по вертикали
7. Отражение по главной диагонали
8. Отражение по побочной диагонали

Поиск ведётся только из **канонических** стартовых позиций — по одному представителю на класс симметричных клеток. Результат из каждого представителя умножается на размер его орбиты: для «общих» клеток орбита равна 8, для угловых, реберных и диагональных — 4, для центра нечётной доски — 1.

### Канонизация состояния

Число продолжений маршрута зависит только от посещённой маски и текущей клетки, но не от того, где начался маршрут. Поэтому любую пару (маска, текущая клетка) приводят к минимальному виду среди восьми симметрий, и симметричные поддеревья — в том числе префиксы из разных стартовых орбит — сливаются в одну запись аккумулятора. Горячий путь работает через предвычисленные таблицы подстановки: без замыканий, делений и взятия остатка, а маска трансформируется перебором только установленных битов, а не всей доски.

### Генерация: две фазы, один аккумулятор

Алгоритм трёхфазный. В **фазе A** из канонических стартовых позиций DFS раскручивает префиксы до глубины `min(-precompute-depth, 5)`; достигнув её, префикс эмится в промежуточный аккумулятор как каноническая пара (маска, текущая клетка) с весом орбиты и дальше не раскручивается. Ветви на этом пути отсекает прунер (см. «Отсечение путей»), симметричные префиксы схлопываются в одну запись с суммарным весом.

Число канонических стартовых групп на досках 5–6 всего около шести, поэтому для загрузки воркеров **фаза B** берёт снимок промежуточного аккумулятора и каждая из тысяч записей независимо докручивается до целевой глубины `-precompute-depth`. Но на листьях фаза B уже ничего не сохраняет как подзадачи — она накапливает **веса классов форм дополнений** (см. следующий раздел). При `-precompute-depth ≤ 5` фаза B вырождается: классы эмются прямо из промежуточных записей.

Корректность двухфазной генерации: граф и прунер инвариантны относительно симметрий D₄, поэтому продолжения всех симметричных копий одного префикса изоморфны — докрутка канонического представителя с агрегированным весом воспроизводит ровно тот же набор листьев, что и однофазная генерация.

На нечётных досках дополнительно фильтруются старты: граф ходов коня двудольный, но с дисбалансом цветов (например, 13 против 12 на 5×5), поэтому открытый тур обязан начинаться на клетке «большинства». Старты другого цвета отсекаются ещё на этапе генерации.

### Аккумуляторы вместо кэша

Единственная разделяемая таблица в алгоритме — аддитивный аккумулятор «ключ → Σ весов»: 128 шардов под мьютексами, безаллокационный мультипликативный хэш по старшим битам. Два экземпляра: промежуточные префиксы фазы A (ключ — D4-каноническое размещение) и таблица M фазы B (ключ — класс формы). Чтение — только снапшотом между фазами; мемоизации «чти-при-промахе» нет нигде.

Писатели не долбят шарды напрямую: каждый воркер пишет через `LocalSink` — локальный буфер схлопывает дубликаты ключей (~6× на стенде) и догружает их в общий аккумулятор пачками по одному захвату лока на уникальный ключ.

Ключом и там и там служит одна и та же компарировая пара `(маска, конец)` — прежний отдельный кэш подзадач (с Get/Set/Each) и тип ключа класса форм удалены как дубликаты.

### Отсечение путей

После каждого хода DFS проверяет, не оказалась ли ветвь тупиковой. Проверка двухуровневая и всегда включена.

- **Локальный dead-end** за O(степени клетки): по инварианту родительский узел уже прошёл проверку, поэтому новую изолированную клетку мог создать только последний ход. Достаточно просмотреть непосещённых соседей только что посещённой клетки и проверить, не потеряли ли они всех соседей. Маски соседей не копируются — читается предвычисленная маска графа за O(1).
- **Глобальные проверки** (только если осталось более одной непосещённой клетки, на битовых масках):
  - у текущей клетки нет непосещённых соседей — ветвь мертва;
  - **связность** — оставшийся путь живёт только в непосещённых клетках, они обязаны образовывать одну компоненту. Проверяется «заливкой» от младшего бита с расширением фронта масками соседей; по ходу считается степень каждой клетки;
  - **эвристика концов** — гамильтов путь имеет ровно два конца. Если вершин степени 1 три и более — отсечь; если ровно две и ни одна не соседна с текущей клеткой — отсечь.

Ни одна проверка не отсекает ветвь, содержащую полный маршрут: связность обязательна (путь не может покинуть компоненту без возврата в посещённые клетки), а эвристика концов — необходимое условие существования гамильтова пути. Эквивалентность наивной реализации и корректность покрыты вероятностными тестами.

Замеры полного подсчёта (M4 Max): исторически отключение глобальных проверок (локальный dead-end вместо полного прунера) стоило ~3.2 мс на 5×5 и ~16.7 с на 6×6; текущий class-mode пайплайн с полным прунером — ~0.21 мс и ~69 мс соответственно (см. «Замеры»).

### Третья фаза: счёт через классы форм

Ответ на вопрос «сколькими способами можно покрыть ровно этот набор клеток путём, заканчивающимся вот здесь» зависит только от **формы** набора, а не от того, где он лежит на доске. Ход коня определяется разницей координат, а все пути заперты внутри формы — значит границы доски на ответ не влияют. Тот же вырез, сдвинутый в другое место или повёрнутый/отражённый, даёт ровно тот же ответ.

Поэтому фаза B вместо сохранения подзадач эмитит листьями веса в аккумулятор M по классам форм дополнений (D₄ ⋉ трансляции: 8 ориентаций, bbox к (0,0), лексикографический минимум пар «форма + конец»). Итог — точная перегруппировка суммы обращённого суффикса:

```
total = Σ_листьев weight · Σ_u h(U,u) = Σ_классам C  h(C) · M(C)
```

В **третьей фазе** каждая форма считается DP-перебором путей внутри неё ровно один раз (мемо общая для всех концов формы, прунер тот же), нулевые h просто не дают вклада. Мемо-таблица между формами не нужна — каждый класс запрашивается один раз по построению. Это и есть meet-in-the-middle: разрез `-precompute-depth` глубже половины доски дуален обращению тура, поэтому валидируется сверху половиной клеток.

Преимущество над прежней схемой с префикс-кэшем: нет экспоненциального хранилища корней (на 8×8 при глубине ≥12 оно требовало ~16 ГБ), нули не хранятся и не пересчитываются, а ограничение «двойная глубина ≤ числа клеток» снято. Подробности — `specs/shapecount.md`.

### Мониторинг

Прогресс выводится без блокировок (атомарные счётчики) — одна перезаписываемая строка раз в секунду, по активной фазе: `gen A`, `gen B`, затем `counting`. В строке — доля выполненных задач, найденные пути, число эмиссий в аккумуляторы и число отсечённых прунером ветвей, а также оценка оставшегося времени. По завершении печатается итог по каждой фазе, секция `Shapes:` (классы/формы/нули) и общее число путей. Накладные расходы — менее 1%.

## Замеры

Единственный источник — `BenchmarkCountAllToursClass` (`counter/benchmark_test.go`):
полный свип глубин meet-in-the-middle **по убыванию** для каждого размера доски.
5×5 и 6×6 — `make bench` (`-benchtime=10x`), 7×7 — дополнительно `make bench-deep`
(`BENCH_DEEP=1`, `-benchtime=1x`, один замер там стоит от минут до часов). Итоговое число
туров во всех строках совпадает с эталоном доски.

> Замеры: Apple M4 Max (14 ядер), workers=14, единый class-mode пайплайн,
> commit 41f31ce (2026-09-12).

Колонки — метрики самого бенчмарка (см. `specs/monitoring.md`): время прогона и его
разбивка по фазам (`gen A`, `gen B`, `counting`), эмиссии в аккумуляторы
(`writesA`/`writesB`), отсечённые прунером ветви (`prunedA`/`prunedB`) и итоги

## Вывод

Единый class-mode пайплайн держит время на плато: 5×5 — ~0.21 мс начиная с глубины 6 (дефолт и есть оптимум), 6×6 — оптимум ~69 мс на глубине 11 при плато 9–14 (дефолт 10 дороже примерно на 10%). На 7×7 плато 19–23 (~9.5 мин) с минимумом на 22–23; дефолт 20 выбран консервативно — он дороже минимума на единицы процентов, но заметно дешевле глубин 24+, где раздувается аккумулятор M (342М классов и 7.6Г эмиссий на глубине 24). Ниже 18 экспоненциально дорожает финальный DP по большим дополнениям — на глубине 9 это уже часы вместо минут, а глубина 6 не влезает в память. Поэтому глубина по умолчанию задаётся таблицей по размеру доски, а не формулой `size²/2`.

**Измеренные и отвергнутые оптимизации:**

- **Баланс цветов как критерий отсечения** — на 5×5/6×6 срабатывает 0 раз: инвариант выполняется автоматически вдоль любой легальной ветви DFS, а на нечётных досках старты уже фильтрует правило чётности.
- **Группировка классов форм на запись в аккумулятор** (хранить `State → концы` вместо последующей сортировки шарда): сортировка группировки стоит 0.33% CPU против ~20% у самого пути записи (`Accumulator.Add`/`Flush` — профиль 6×6 d18), а вложенное значение добавило бы по объекту с двумя срезами на каждую форму (на 7×7 d20 — 44.6M форм ≈ 150M мелких аллокаций и лишний указатель на форму в каждом GC-цикле) плюс merge-семантику под локом шарда.
- **Сортировка кандидатов по Вонсдорфу** — количество узлов дерева поиска не меняется вовсе (прунер локален и не зависит от порядка перебора), при этом время растёт на 10–20% из-за сортировки в каждом узле.
