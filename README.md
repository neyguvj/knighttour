# Knight Tour — Поиск всех открытых маршрутов коня

![Test Status](https://github.com/neyguvj/knighttour/actions/workflows/test.yml/badge.svg)

Реализация алгоритма подсчёта всех открытых маршрутов коня (knight's tours) на досках от 5×5 до 8×8 с использованием параллельных вычислений и продвинутых оптимизаций.

**Открытый маршрут** — это последовательность ходов коня, при которой он посещает каждую клетку доски ровно один раз (не возвращаясь в начальную клетку).

## Quick Start

```bash
# Быстрый запуск на доске 5×5 (по умолчанию)
go run main.go

# Запуск на доске 6×6 с параллелизмом
go run main.go -size 6 -workers 14

# С более глубоким предварительным разбиением подзадач
go run main.go -size 6 -workers 14 -precompute-depth 16
```

## Параметры командной строки

| Флаг | Тип | По умолчанию | Описание |
|------|-----|--------------|----------|
| `-size` | `int` | `5` | Размер доски (от 5 до 8) |
| `-workers` | `int` | число ядер CPU | Количество параллельных воркеров (1 = последовательный режим) |
| `-precompute-depth` | `int` | по размеру доски: `{5: 6, 6: 14, 7: 22, 8: 14}` | Глубина meet-in-the-middle разреза (от 1 до size²/2; глубже — дублирование дуала разреза обращённого тура) |
| `-gc-percent` | `int` | `40` | GOGC на время конвейера: пониженный GC держит пик task-cache ниже (`0` — не трогать GC рантайма, ADR-014) |

## Как это устроено

Дальше — рассказ об алгоритме по порядку: от представления доски и сокращения пространства поиска через симметрию, к двухфазной генерации и счёту обращений с ранним стопом, отсечению тупиковых ветвей и замерам. Детальные описания каждого компонента — в каталоге `specs/`. Конвейер один; вторая схема подсчёта (по классам форм) удалена вместе со своим DP-пакетом (ADR-016).

### Структура графа

Всё состояние поиска — это одна 64-битная маска: один бит на клетку, 1 означает «посещена», 0 — «не посещена». Для доски до 8×8 (64 клетки) это помещается в одно машинное слово, поэтому копирование состояния — обычное присваивание, а само состояние — готовым ключом таблиц. Битовые операции вынесены в отдельный пакет, а вызывающий код перебирает установленные биты через итератор, не обращаясь к битам напрямую.

Над маской лежит предвычисленный граф ходов коня. При старте для каждой клетки один раз строятся список соседей и побитовая маска этих соседей. Проверка «куда можно ходить из текущей клетки» сводится к пересечению маски соседей с маской непосещённых клеток — за O(1). Соседи хранятся в фиксированном порядке восьми возможных ходов коня; сортировка по эвристике Вонсдорфа сознательно не используется — замер показал, что она не меняет число узлов дерева поиска, а только добавляет стоимость сортировки в каждом узле (см. «Вывод»).

### Симметрия доски

Квадратная доска обладает группой симметрий D₄ — восемью преобразованиями: тождество, повороты на 90°/180°/270° и четыре отражения (горизонталь, вертикаль, главная и побочная диагонали). Это позволяет сократить пространство поиска в несколько раз.

Поиск ведётся только из **канонических** стартовых позиций — по одному представителю на класс симметричных клеток. Результат из каждого представителя умножается на размер его орбиты: для «общих» клеток орбита равна 8, для угловых, реберных и диагональных — 4, для центра нечётной доски — 1. На нечётных досках старты фильтруются дополнительно: граф ходов коня двудольный, но с дисбалансом цветов (13 против 12 на 5×5), поэтому открытый тур обязан начинаться на клетке «большинства»; старты другого цвета отсекаются ещё на этапе генерации.

### Канонизация размещения: маска + класс конца

Число продолжений маршрута зависит только от посещённой маски и текущей клетки, но не от того, где начался маршрут. Поэтому размещение `(маска, конец)` приводится к канонической форме, в которой симметричные поддеревья — в том числе префиксы из разных стартовых орбит — сливаются в одну запись таблицы. Форма двухчастная: ключом служит **каноническая маска** `K = min_t t(маска)`, а конец живёт в её значении **классом эквивалентности**: два конца одной маски неразличимы тогда и только тогда, когда их связывает стабилизатор `Stab(K) = {t ∈ D4 : t(K) = K}`. Класс задаётся тегом-репрезентантом (минимумом stab-орбиты), а размер орбиты пары — `orbitSize = 8 / |Stab(K, конец)|` — вычисляется на чтении из предвычисленной таблицы композиции и нигде не хранится.

Сведение конца к репрезентанту stab-орбиты поглощает неоднозначность выбора кадра: при нетривиальном стабилизаторе минимум маски достигается несколькими преобразованиями, но тег от этого не меняется — рассогласование tie-break исключено конструктивно. Писатель и читатель таблиц вызывают одну и ту же функцию канонизации, поэтому «мёртвость» ключа и его вес согласованы с симметризацией по построению. Горячий путь работает только на предвычисленных таблицах подстановки — без замыканий, делений и остатка, а маска трансформируется перебором установленных битов, а не всей доски (`specs/symmetry.md`).

### Генерация: две фазы

Алгоритм трёхфазный. В **фазе A** из канонических стартовых позиций DFS раскручивает префиксы до глубины `min(d, 5)`, где `d = -precompute-depth`; достигнув её, префикс эмится в промежуточную таблицу в форме «каноническая маска + класс конца» с весом орбиты и дальше не раскручивается. Ветви на этом пути отсекает прунер (см. «Отсечение путей»), симметричные префиксы схлопываются в один слот класса с суммарным весом.

Число канонических стартовых групп всего ~десять, поэтому для загрузки воркеров **фаза B** собирает записи промежуточной таблицы в worklist (обходом запечатанной таблицы в одну горутину после барьера писателей, развёрнуто — по одной задаче на класс), и каждая из тысяч его записей независимо докручивается до целевой глубины `d`, а её листья пишутся в task-cache. При `d ≤ 5` фаза B вырождается: эмиссия идёт прямо из промежуточных записей. Базовый случай спуска — гейт записи (ADR-030): перед записью листа прунер проверяет необходимое условие дополнения гамильтовым путём при зафиксированном конце; мёртвые размещения с нулевым числом дополнений не попадают ни в промежуточную таблицу, ни в task-cache. Один хук покрывает обе фазы.

Корректность двухфазной генерации: граф и прунер инвариантны относительно симметрий D₄, поэтому продолжения всех симметричных копий одного префикса изоморфны — докрутка канонического представителя с агрегированным весом воспроизводит ровно тот же набор листьев, что и однофазная генерация.

### Счёт: обращённый тур (reversal)

Ответ «сколько дополнений у префикса» считается не перебором до конца доски, а обращением суффикса: каждое дополнение `(T, t)` обращается в путь, покрывающий ровно остаток `U = full \ T` и кончающийся соседом `t`, поэтому число дополнений — сумма уже известных чисел замыканий остатка по соседям конца. Отсюда третья фаза: для каждой задачи task-cache (маска + класс конца) глубины `d` count-DFS раскручивает продолжения от конца и на уровне `size² − d` останавливается, отвечая суммой `W(K, класс) / orbitSize` по кандидатам `u` — канонический фрейм остатка считается один раз на вызов, а тег класса каждого соседа читает соответствующий слот гистограммы той же записи (нет остатка в таблице — все проверки этого вызова промахи, нет в гистограмме класса — промах только этой проверки). Эти веса лежат в том же кэше, потому что запись остатка с точностью до симметрии сама является задачей глубины `d`:

```
total = Σ_задач W(task) · f(task)
```

Деление веса класса на `orbitSize` точно: вес класса — сумма размеров орбит его членов. Выигрыш не в хранении, а в переиспользовании подзадач между задачами: count-DFS попадает в task-cache на ветках, уже посчитанных для других задач, и не раскручивает их заново (механика и основания — ADR-011). Ранний стоп законен, пока `2d ≤ size²`: более глубокий разрез дублирует дуаль разреза обращённого тура — поэтому глубина валидируется сверху половиной клеток. Весь конвейер работает под пониженным GOGC (`-gc-percent`, ADR-014): пик — живая task-cache, headroom над ней дорог.

### Кэш: одна таблица на обе роли

Разделяемые таблицы аддитивные, «маска → Σ весов по классам концов», и тип у них один — `cache.Cache`: 128 шардов с локом только для писателей, безаллокационный мультипликативный хэш по одной только маске — концы одной маски не разъезжаются по шардам (ADR-004). Экземпляра два: промежуточная таблица фазы A (короткоживущая) и task-cache — он живёт до конца счёта и не дренируется. Слот карты pointer-free (`uint64 → uint64`), конец в ключе не хранится: информативен только его класс, он живёт тегом в значении (ADR-034).

Значение упаковано вариабельно и тегировано по старшему биту. Одноклассовая маска целиком живёт в слоте карты словом `(rep:8 | W:56)`. Многоклассовая — ссылкой `(k:7 | idx:56)` на блок в append-only slab своего шарда: ёмкость блока — степень двойки `2^⌈log₂ k⌉`, рост записи дописывает пару в неиспользованный запас хвоста, а переезд через границу ёмкости дописывает в конец slab новый блок и отдаёт старый в корзину свободных того же класса — следующая запись с такой же ёмкостью берёт его оттуда. Плотность записи растёт с числом классов и не оплачивается фиксированной ёмкостью слота: раскладка не дороже парной базы ни при каком `k`, а на верхних границах ёмкости выигрывает до −60% (`specs/cache.md`). Нулей в таблице нет: и запись, и слот класса создаются только при положительном вкладе.

Чтение — по протоколу «write → seal → read»: контур останавливает писателей фазовым барьером и берёт запечатанную ручку `View`, безлоковую и неизменяемую; лок шарда берут только `Set` и батч-флеш. Писатели фазы A идут прямым `Set`, воркеры фазы B — собственным батч-писателем `Staging` (ADR-031): эмиссии буферизуются по шардам и сливаются под одним залом задетого шарда, а сложение коммутативно, так что итог к барьеру идентичен прямым записям. Таблица мала (глубина ≤ 5), поэтому освобождением промежуточной занимается обычный GC — пошардовый дренаж и копирующие снимки не нужны (ADR-018).

### Диспатч count-фазы и параллелизм фаз

Task-cache запечатывается после барьера генерации, и одна ручка даёт и мемо раннего стопа (`Get`), и обход-продюсер `All` — по живым map без локов и без копирующего снимка (механика прямого обхода ADR-013 сохранена). Продюсер складывает развёрнутые записи (24 Б: маска + тег класса + вес) в предвыделенный FIFO батч-канал, воркеры берут батчи и крутят count-DFS вне любых залов. Гранулярность батча адаптивна — от одной записи на крошечных таблицах (иначе весь task-cache уходит первому воркеру) до потолка в 16 на больших: так хвост обхода не запирается за чужими задачами (ADR-019). Буфер канала считается один раз на старте фазы — ноль аллокаций на запись, backpressure по целому слоту. Задачи регистрируются монитору до отправки батча, поэтому знаменатель прогресса точен и никогда не превышает 100%.

Сама механика горутин вынесена в домен-свободный пакет `workerpool` (ADR-033): `Pool.Run` спавнит `min(workers, n)` воркеров, снимающих индексы задач с одного атомарного курсора (контекст проверяется перед каждым снятием) и ждёт их барьером, `Fanout[T]` стримит значения по одному буферизованному каналу — продюсер на горутине вызывающего, закрытие по его возврате, консьюмеры дренируют. Ни политик, ни ошибок: формулы батча, ёмкости и клампы остаются у counter, пакет владеет только спавном, курсором, каналом и барьерами.

### Отсечение путей

После каждого хода DFS проверяет, не оказалась ли ветвь тупиковой. Проверка двухуровневая и всегда включена.

- **Локальный dead-end** за O(степени клетки): по инварианту родительский узел уже прошёл проверку, поэтому новую изолированную клетку мог создать только последний ход. Достаточно просмотреть непосещённых соседей только что посещённой клетки и проверить, не потеряли ли они всех соседей. Маски соседей не копируются — читается предвычисленная маска графа за O(1).
- **Глобальные проверки** (только если осталось более одной непосещённой клетки, на битовых масках):
  - у текущей клетки нет непосещённых соседей — ветвь мертва;
  - **связность** — оставшийся путь живёт только в непосещённых клетках, они обязаны образовывать одну компоненту. Проверяется «заливкой» от младшего бита с расширением фронта масками соседей; по ходу считается степень каждой клетки;
  - **эвристика концов** — гамильтов путь имеет ровно два конца. Если вершин степени 1 три и более — отсечь; если ровно две и ни одна не соседна с текущей клеткой — отсечь.

Третье применение того же прунера — **гейт записи** на листьях генерации (ADR-030): необходимое условие существования гамильтова пути из текущего конца по графу остатка проверяется обязательными цепочками — union-find рёбер степени 2. Проверка имеет силу только при зафиксированном конце (ровно одна вершина остатка степени 1) и прунит превышение обязательной степени и циклы обязательных рёбер; связность и локальные проверки на листе не повторяются — спуск родителя уже их прошёл. Безопасность: ключ с нулевым числом дополнений никогда не будет запрошен (дуальность обращения), поэтому его выбрасывание на записи не меняет итог, но оставляет task-cache заполненной только ключами с ненулевым потенциалом.

Ни одна проверка не отсекает ветвь, содержащую полный маршрут: связность обязательна (путь не может покинуть компоненту без возврата в посещённые клетки), а эвристика концов и обязательные цепочки — необходимые условия существования гамильтова пути. Эквивалентность наивной реализации и корректность покрыты вероятностными тестами. О том, сколько ветвей отсекается до того, как в них войдёт count-DFS, судите по колонкам `prunedA`/`prunedB` (в нём — гейт) в таблицах «Замеров».

### Мониторинг

Прогресс выводится без блокировок (атомарные счётчики) — одна перезаписываемая строка раз в секунду, по активной фазе: `gen A`, `gen B`, затем `counting`. В строке — доля выполненных задач, найденные пути, число эмиссий в таблицы (`Writes`), попадания/промахи task-cache (`Hits x/y`) и число отсечённых прунером ветвей, а также оценка оставшегося времени. По завершении печатается итог по каждой фазе; разбивка pruned перечисляет только ненулевые виды: `deadend`, `nocont`, `disconn`, `endpoints`, `chain` (гейт записи). Накладные расходы — менее 1%.

## Замеры

Единственный источник — `BenchmarkCountAllTours` (`counter/benchmark_test.go`): полный свип
глубин meet-in-the-middle **по убыванию** для каждого размера доски. Каждая глубина снималась
отдельным процессом, поэтому `peak RSS` честный на всех досках; 5×5/6×6 — `-benchtime=10x`,
7×7 — `1x` на точку (суммарно ~6 ч). Итоговое число туров во всех строках совпадает с эталоном доски.

> Замеры: Apple M4 Max (14 ядер), workers=14, GOGC конвейера 40; код 65eb198, прогоны 2026-09-29.

Колонки — метрики самого бенчмарка (`specs/benchmarks.md`): время прогона и его разбивка по
фазам (`gen A`, `gen B`, `counting`) в читаемых единицах, пик резидента на прогон, эмиссии в
промежуточную таблицу и task-cache (`writesA`/`writesB`), отсечённые прунером ветви генерации
(`prunedB` — в них уже сидят отсечения гейта записи) и попадания/промахи task-cache фазы счёта
(`hits`/`misses`). `taskEntries` — число класс-задач count-фазы (развёрнутый обход task-cache).
Фаза A везде ничтожна (мкс — ~десять стартовых групп), поэтому время прогона — это почти всегда
`gen B` + `counting`.

## Вывод

**Конвейер один, дефолты выбирает время.** Reversal стал штатной схемой по итогам A/B-свода с
классовой трубой (ADR-011); после удаления альтернативы (ADR-016) критерием выбора глубины стало
чистое время, а пик RSS фиксируется справочно (ADR-017). Дефолтная
глубина задаётся таблицей по размеру доски, а не формулой `size²/2`: выше оптимума `gen B`
раздувает task-cache (эмиссии растут экспоненциально), ниже — count-фаза дорожает по большим
остаткам.

| size | 5 | 6 | 7 | 8 |
|---|---|---|---|---|
| `-precompute-depth` | 6 | 14 | 22 | 14 |

- **5×5 — плато**: d2..d12 неразличимы над шумом повторов, измеренного минимума нет — дефолт 6.
- **6×6 — оптимум d14** (54.26 мс): подтверждён свипом текущей реализации, соседи дороже на
  +3.7% (d15) и +6.9% (d13).
- **7×7 — плато d21–d22**: по три прогона каждой глубины, полосы перекрываются полностью, дефолт 22
  не сдвигается — улучшать нечего, а выбор между этими двумя точками лежит внутри шума (на d22
  дороже `gen B` и дешевле count-фаза, суммарно одно и то же). Вся кривая d24..d6 растёт от плато
  в обе стороны, так что минимум внутренний.
- **8×8 — глубина 14 остаётся консервативным placeholder'ом**: доска вне штатных прогонов
  (ADR-015), точка не снималась.

Пониженный GOGC на время конвейера (`-gc-percent 40`, ADR-014) удешевляет именно глубокие точки:
пик — живая task-cache, headroom над ней дорог.

**Измеренные и отвергнутые оптимизации:**

- **Баланс цветов как критерий отсечения** — на 5×5/6×6 срабатывает 0 раз: инвариант выполняется
  автоматически вдоль любой легальной ветви DFS, а на нечётных досках старты уже фильтрует правило чётности.
- **Сортировка кандидатов по Вонсдорфу** — количество узлов дерева поиска не меняется вовсе
  (прунер локален и не зависит от порядка перебора), при этом время растёт на 10–20% из-за
  сортировки в каждом узле (ADR-009).
- **Чтение аккумуляторов копией-снимком в count-фазе** — снимок удваивал пиковую память процесса;
  вместо него прямой обход шардов запечатанной таблицы без локов и аллокаций (ADR-013).
- **Сочленения (Tarjan lowlink) в гейте записи** — добавляют к chain ещё +43 с `gen B` ради
  −0.3M записей: +20.1% полного времени против +1.3% у обязательных цепочек, отклонена числами;
  принятый набор гейта — только forced-chain (ADR-030).
- **Стратегии диспатча count-фазы: канал-пул и per-worker бины** — сравнение трёх стратегий на
  одном контроле (планы 11/12 против принятого общего стека с батч-претензией): канал-пул дал
  `cnt_ms` +14.5% (общий hchan дороже, чем снимает хвост), бины −4.9% — плато на head-of-line,
  не дотянувшее до гейта принятия (ADR-019).
