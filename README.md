# Knight Tour — Поиск всех открытых маршрутов коня

![Test Status](https://github.com/neyguvj/knighttour/actions/workflows/test.yml/badge.svg)

Реализация алгоритма подсчёта всех открытых маршрутов коня (knight's tours) на досках от 5×5 до 8×8 с использованием параллельных вычислений и продвинутых оптимизаций.

**Открытый маршрут** — это последовательность ходов коня, при которой он посещает каждую клетку доски ровно один раз (не возвращаясь в начальную клетку).

## Quick Start

```bash
# Быстрый запуск на доске 5×5 (по умолчанию)
go run main.go

# Запуск на доске 6×6 с параллелизмом
go run main.go -size 6 -workers 14

# С более глубоким предварительным разбиением подзадач
go run main.go -size 6 -workers 14 -precompute-depth 16
```

## Параметры командной строки

| Флаг | Тип | По умолчанию | Описание |
|------|-----|--------------|----------|
| `-size` | `int` | `5` | Размер доски (от 5 до 8) |
| `-workers` | `int` | число ядер CPU | Количество параллельных воркеров (1 = последовательный режим) |
| `-precompute-depth` | `int` | по размеру доски: `{5: 6, 6: 14, 7: 22, 8: 14}` | Глубина meet-in-the-middle разреза (от 1 до size²/2; глубже — дуал разреза обращённого тура) |
| `-gc-percent` | `int` | `40` | GOGC на время конвейера: пониженный GC держит пик task-cache ниже (`0` — не трогать GC рантайма, ADR-014) |

## Как это устроено

Дальше — рассказ об алгоритме по порядку: от представления доски и сокращения пространства поиска через симметрию, к двухфазной генерации и счёту обращений с ранним стопом, отсечению тупиковых ветвей и замерам. Детальные описания каждого компонента — в каталоге `specs/`. Конвейер один; вторая схема подсчёта (по классам форм) удалена вместе со своим DP-пакетом (ADR-016).

### Структура графа

Всё состояние поиска — это одна 64-битная маска: один бит на клетку, 1 означает «посещена», 0 — «не посещена». Для доски до 8×8 (64 клетки) это помещается в одно машинное слово, поэтому копирование состояния — обычное присваивание, а само состояние — готовым ключом аккумуляторов. Битовые операции вынесены в отдельный пакет, а вызывающий код перебирает установленные биты через итератор, не обращаясь к битам напрямую.

Над маской лежит предвычисленный граф ходов коня. При старте для каждой клетки один раз строятся список соседей и побитовая маска этих соседей. Проверка «куда можно ходить из текущей клетки» сводится к пересечению маски соседей с маской непосещённых клеток — за O(1). Соседи хранятся в фиксированном порядке восьми возможных ходов коня; сортировка по эвристике Вонсдорфа сознательно не используется — замер показал, что она не меняет число узлов дерева поиска, а только добавляет стоимость сортировки в каждом узле (см. «Вывод»).

### Симметрия доски

Квадратная доска обладает группой симметрий D₄ — восемью преобразованиями: четыре поворота и четыре отражения. Это позволяет сократить пространство поиска в несколько раз.

Все восемь преобразований:

1. Без изменений (тождество)
2. Поворот на 90°
3. Поворот на 180°
4. Поворот на 270°
5. Отражение по горизонтали
6. Отражение по вертикали
7. Отражение по главной диагонали
8. Отражение по побочной диагонали

Поиск ведётся только из **канонических** стартовых позиций — по одному представителю на класс симметричных клеток. Результат из каждого представителя умножается на размер его орбиты: для «общих» клеток орбита равна 8, для угловых, реберных и диагональных — 4, для центра нечётной доски — 1.

### Канонизация состояния

Число продолжений маршрута зависит только от посещённой маски и текущей клетки, но не от того, где начался маршрут. Поэтому любую пару (маска, текущая клетка) приводят к минимальному виду среди восьми симметрий, и симметричные поддеревья — в том числе префиксы из разных стартовых орбит — сливаются в одну запись промежуточной таблицы. Горячий путь работает через предвычисленные таблицы подстановки: без замыканий, делений и взятия остатка, а маска трансформируется перебором только установленных битов, а не всей доски.

### Генерация: две фазы

Алгоритм трёхфазный. В **фазе A** из канонических стартовых позиций DFS раскручивает префиксы до глубины `-precompute-depth`, но не глубже 5; достигнув её, префикс эмится в промежуточную таблицу как каноническая пара (маска, текущая клетка) с весом орбиты и дальше не раскручивается. Ветви на этом пути отсекает прунер (см. «Отсечение путей»), симметричные префиксы схлопываются в одну запись с суммарным весом.

Число канонических стартовых групп всего ~десять, поэтому для загрузки воркеров **фаза B** собирает записи промежуточной таблицы в worklist (обходом в одну горутину после барьера писателей), и каждая из тысяч его записей независимо докручивается до целевой глубины `-precompute-depth`, а её листья пишутся сырыми каноническими префиксами с весом напрямую в task-cache. При `-precompute-depth ≤ 5` фаза B вырождается: эмиссия идёт прямо из промежуточных записей.

Корректность двухфазной генерации: граф и прунер инвариантны относительно симметрий D₄, поэтому продолжения всех симметричных копий одного префикса изоморфны — докрутка канонического представителя с агрегированным весом воспроизводит ровно тот же набор листьев, что и однофазная генерация.

На нечётных досках дополнительно фильтруются старты: граф ходов коня двудольный, но с дисбалансом цветов (например, 13 против 12 на 5×5), поэтому открытый тур обязан начинаться на клетке «большинства». Старты другого цвета отсекаются ещё на этапе генерации.

### Счёт: обращённый тур (reversal)

Ответ «сколько дополнений у префикса» считается не перебором до конца доски, а обращением суффикса: каждое дополнение `(T, t)` обращается в путь, покрывающий ровно остаток `U = full \ T` и кончающийся соседом `t`, поэтому число дополнений — сумма уже известных чисел замыканий остатка по соседям конца. Отсюда третья фаза: для каждой записи task-cache `(маска, конец)` глубины `d` count-DFS раскручивает продолжения от конца и на уровне `size² − d` останавливается, отвечая суммой `W(D4-канон(U, u)) / orbitSize` по кандидатам `u` — а эти веса лежат в том же кэше, потому что запись остатка с точностью до симметрии сама является задачей глубины `d`:

```
total = Σ_задач W(task) · f(task)
```

Выигрыш не в хранении, а в переиспользовании подзадач между задачами: count-DFS попадает в task-cache на ветках, уже посчитанных для других задач, и не раскручивает их заново (механика и основания — ADR-011). Ранний стоп законен, пока `2d ≤ size²`: более глубокий разрез дублирует дуаль разреза обращённого тура — поэтому глубина валидируется сверху половиной клеток. Весь конвейер работает под пониженным GOGC (`-gc-percent`, ADR-014): пик — живая task-cache, headroom над ней дорог.

### Одна таблица на обе роли

Разделяемые таблицы аддитивные, «ключ → Σ весов», и тип у них один — `cache.Cache`: 128 шардов под RWMutex, безаллокационный мультипликативный хэш по одной только маске — концы одной маски не разъезжаются по шардам (ADR-004). Экземпляра два: промежуточная таблица фазы A (ключ — D4-каноническое размещение), короткоживущая, и task-cache — таблица с одновременными чтением и записью, которую count-фаза обходит напрямую под read-lock'ами шардов, без копирования (ADR-013); она живёт до конца счёта и не дренируется.

Писатели обеих генерационных фаз идут прямым `Set` — сложение коммутативно, нулевой вес не заводит запись. Worklist фазы B материализуется из промежуточной таблицы обходом после барьера писателей; таблица мала (глубина ≤ 5), поэтому её освобождением занимается обычный GC — пошардовый дренаж и копирующие снимки не нужны (ADR-018).

Ключом везде служит одна и та же компарировая пара `(маска, конец)` — `path.Path` (`specs/path.md`).

### Отсечение путей

После каждого хода DFS проверяет, не оказалась ли ветвь тупиковой. Проверка двухуровневая и всегда включена.

- **Локальный dead-end** за O(степени клетки): по инварианту родительский узел уже прошёл проверку, поэтому новую изолированную клетку мог создать только последний ход. Достаточно просмотреть непосещённых соседей только что посещённой клетки и проверить, не потеряли ли они всех соседей. Маски соседей не копируются — читается предвычисленная маска графа за O(1).
- **Глобальные проверки** (только если осталось более одной непосещённой клетки, на битовых масках):
  - у текущей клетки нет непосещённых соседей — ветвь мертва;
  - **связность** — оставшийся путь живёт только в непосещённых клетках, они обязаны образовывать одну компоненту. Проверяется «заливкой» от младшего бита с расширением фронта масками соседей; по ходу считается степень каждой клетки;
  - **эвристика концов** — гамильтов путь имеет ровно два конца. Если вершин степени 1 три и более — отсечь; если ровно две и ни одна не соседна с текущей клеткой — отсечь.

Ни одна проверка не отсекает ветвь, содержащую полный маршрут: связность обязательна (путь не может покинуть компоненту без возврата в посещённые клетки), а эвристика концов — необходимое условие существования гамильтова пути. Эквивалентность наивной реализации и корректность покрыты вероятностными тестами. Стоимость проверок — локальный ярус за O(степени) в узле; о том, сколько ветвей отсекается до того, как в них войдёт count-DFS, судите по колонкам `prunedA`/`prunedB` в таблицах «Замеров».

### Мониторинг

Прогресс выводится без блокировок (атомарные счётчики) — одна перезаписываемая строка раз в секунду, по активной фазе: `gen A`, `gen B`, затем `counting`. В строке — доля выполненных задач, найденные пути, число эмиссий в аккумуляторы (`Writes`), попадания/промахи task-cache (`Hits x/y`) и число отсечённых прунером ветвей, а также оценка оставшегося времени. По завершении печатается итог по каждой фазе; разбивка pruned перечисляет только ненулевые виды: `deadend`, `nocont`, `disconn`, `endpoints`. Накладные расходы — менее 1%.

## Замеры

Единственный источник — `BenchmarkCountAllTours` (`counter/benchmark_test.go`):
полный свип глубин meet-in-the-middle **по убыванию** для каждого размера доски.
5×5 и 6×6 — `make bench` (`-benchtime=10x`); 7×7 — гейт-прогоны `make bench-size N=7`,
два прохода на глубину, каждая в отдельном процессе (`-benchtime=1x`, часы). Итоговое число
туров во всех строках совпадает с эталоном доски.

> Замеры: Apple M4 Max (14 ядер), workers=14, `-benchtime=10x` (7×7 — гейт-прогоны `1x`, каждая глубина отдельным процессом), commit 895aa56 (2026-09-14).

Колонки — метрики самого бенчмарка (см. `specs/monitoring.md`): время прогона и его
разбивка по фазам (`gen A`, `gen B`, `counting`, в мс), эмиссии в аккумуляторы
(`writesA`/`writesB`), отсечённые прунером ветви (`prunedA`/`prunedB`) и попадания/промахи
task-cache фазы счёта (`hits`/`misses`). Peak RSS в `make bench` — накопленный максимум
общего процесса (не по глубинам), поэтому в таблицах 5×5/6×6 не приведён; честные пер-глубинные
пики — в ADR-016. Для 7×7 каждая глубина шла своим процессом, и колонки памяти там честные.
Фаза A везде ничтожна (десятые доли мс — ~десять стартовых групп), поэтому время прогона —
это почти всегда `gen B` + `counting`.

## Вывод

**Конвейер один, дефолты выбирает время.** Reversal стал штатной схемой по итогам
A/B-свода с классовой трубой (ADR-011: на 7×7 при d ≥ 18 быстрее до ×2.7 при вдвое ниже пике,
на 6×6 паритетен, но плоский по памяти; на 8×8 влезающий режим только один, ADR-015); после
удаления альтернативы (ADR-016) пересъёмка на единственном конвейере нашла минимумы времени
глубже прежних дефолтов, а критерий принятия стал «чистое время»: пик RSS фиксируется
справочно и больше не блокирует adopted (ADR-017). Таблица `{5: 6, 6: 14, 7: 22, 8: 14}`:

- **5×5 — плато**: d2..d12 неразличимы над шумом повторов, измеренного минимума времени нет —
  дефолт 6 остаётся.
- **6×6 — adopted d14**: −28.6% времени к прежнему дефолту 10; пик +3.5 МБ (19.3 против 15.8) —
  несущественно.
- **7×7 — adopted d22**: −24.4% времени к прежнему дефолту 20; пик ~10.6 ГБ (+106%) — теперь
  справочная метрика, стенду нужно ≥ ~11 ГБ свободной памяти на прогон. Пониженный GOGC=40
  (ADR-014) удешевляет именно эту точку: без него d22 стоит ~15.3 ГБ.
- **8×8 — глубина 14 остаётся консервативным placeholder'ом**: доска вне штатных прогонов
  (ADR-015), точка не снималась — при отсутствии замеров смена критерия ничего не меняет.

Глубина по умолчанию задаётся таблицей по размеру доски, а не формулой `size²/2`: выше
оптимума `gen B` раздувает task-cache (экспоненциальные эмиссии и пик RSS), ниже — дорожает
count-фаза по большим остаткам.

**Измеренные и отвергнутые оптимизации:**

- **Баланс цветов как критерий отсечения** — на 5×5/6×6 срабатывает 0 раз: инвариант выполняется автоматически вдоль любой легальной ветви DFS, а на нечётных досках старты уже фильтрует правило чётности.
- **Сортировка кандидатов по Вонсдорфу** — количество узлов дерева поиска не меняется вовсе (прунер локален и не зависит от порядка перебора), при этом время растёт на 10–20% из-за сортировки в каждом узле.
- **Чтение аккумуляторов копией-снимком в count-фазе** — снимок удваивал пиковую память процесса; вместо него прямой обход шардов под read-lock'ами без аллокаций (ADR-013).
