# Knight Tour — Поиск всех открытых маршрутов коня

![Test Status](https://github.com/neyguvj/knighttour/actions/workflows/test.yml/badge.svg)

Реализация алгоритма подсчёта всех открытых маршрутов коня (knight's tours) на досках от 5×5 до 8×8 с использованием параллельных вычислений и продвинутых оптимизаций.

**Открытый маршрут** — это последовательность ходов коня, при которой он посещает каждую клетку доски ровно один раз (не возвращаясь в начальную клетку).

## Quick Start

```bash
# Быстрый запуск на доске 5×5 (по умолчанию)
go run main.go

# Запуск на доске 6×6 с параллелизмом
go run main.go -size 6 -workers 14

# С более глубоким предварительным разбиением подзадач
go run main.go -size 6 -workers 14 -precompute-depth 12
```

## Параметры командной строки

| Флаг | Тип | По умолчанию | Описание |
|------|-----|--------------|----------|
| `-size` | `int` | `5` | Размер доски (от 5 до 8) |
| `-workers` | `int` | `1` | Количество параллельных воркеров (1 = последовательный режим) |
| `-precompute-depth` | `int` | `1` | Глубина предварительного разбиения подзадач (от 1 до size²/2) |

## Оптимизации

### 1. Битовые маски (uint64)
Состояние посещённых клеток — значение типа `State uint64`, один бит на клетку:
- Компактное хранение (до 64 клеток доски 8×8), копирование состояния — O(1)
- Все битовые операции инкапсулированы в пакете `state`: `Visit`, `Unvisit`, `Invert`, `Intersect`, `Union`
- Итератор `AllVisited() iter.Seq[int]` (range-over-func) скрывает перебор установленных битов от вызывающего кода
- Само состояние служит идеальным хэшем для кэша

### 2. Предвычисленный граф
Пакет `graph` при старте один раз строит для каждой клетки:
- Список соседей `[][]int` и побитовую маску соседей `[]State`
- Проверка смежности сводится к `mask & unvisited != 0` за O(1)

Соседи хранятся в фиксированном порядке возможных ходов коня — сортировка по Вонсдорфу сознательно не используется (см. «Измеренные и отвергнутые оптимизации»).

### 3. Симметрия доски (группа D₄)
Доска обладает 8 симметриями: 4 поворота и 4 отражения.
- `NewSymmetry(size)` один раз предрассчитывает LUT перестановок `[8][64]uint8`, канонические позиции, размеры орбит и канонические группы
- Поиск ведётся только из **канонических** стартовых позиций; результат умножается на размер орбиты (×8 для общих клеток, ×4 для углов/диагоналей, ×1 для центра нечётных досок)
- `Canonicalize(state, end)` приводит пару к лексикографически минимальному виду среди 8 трансформаций — нормализация ключа кэша, объединяющая симметричные поддеревья (в том числе префиксы из **разных** стартовых орбит)
- Горячий путь работает через чистые таблицы подстановки — без замыканий, делений и взятия остатка; `transformState` перебирает только установленные биты маски, а не всю доску

### 4. Пропуск стартов по чётности (нечётные доски)
Граф ходов коня на нечётной доске двудольный с дисбалансом цветов (например, 13 против 12 для 5×5), поэтому открытый тур обязан начинаться на клетке «большинства». `Graph.SholdSkip()` отсекает все старты с нечётным индексом ещё на этапе генерации подзадач.

### 5. Прунинг: dead-end + связность + эвристика концов (AdvancedPruner)
Двухуровневая проверка `ShouldPruneAfterVisit(last, unvisited)` — всегда включена:
- **Локальный dead-end** за **O(deg(last))** вместо полного скана доски: по инварианту родитель уже прошёл проверку, и посетить новую изолированную клетку мог только последний визит; маски соседей не копируются — читается предвычисленная маска графа за O(1)
- **Глобальные проверки** (только при `|unvisited| > 1`, на битовых масках):
  - у `last` нет непосещённых соседей → ветвь мертва;
  - **связность `G[unvisited]`** — оставшийся путь живёт только в непосещённых клетках, они обязаны образовывать одну компоненту: bitset flood-fill от младшего бита (расширение фронта ИЛИ-ем масок соседей), заодно считается степень каждой клетки
  - **эвристика концов** — гамильтов путь имеет ровно 2 конца; ≥3 вершин степени 1 → prune, ровно 2 и ни одна не соседна `last` → prune
- Эквивалентность наивной реализации и корректность (ни одна проверка не отсекает полный маршрут) покрыты вероятностными тестами

Замеры полного подсчёта (M4 Max): 5×5 — **3.20 мс → ~0.7 мс**, 6×6 — **16.7 с → ~1.0 с** против прунера только с dead-end. Порог по остатку (K=20) ускорял 5×5 на ~8%, но на 6×6 проигрывал ~2× — выбрано «всегда».

### 6. Кэширование с шардингом и симметрией
Потокобезопасный кэш мемоизации (`cache/`):
- **64 шарда**, каждый под собственным `sync.RWMutex`
- Аллокационно-бесплатный мультипликативный хэш; номер шарда — старшие 6 бит
- Ключ — каноническая пара `(visited bitboard, end)` **без start**: число продолжений маршрута зависит только от посещённой маски и текущей клетки, поэтому симметричные состояния сливаются в одну запись, а префиксы из разных стартовых орбит схлопываются в одну подзадачу
- Value — агрегированный вес `Σ count·orbitSize`: умножение на орбиту зашивается **при генерации** (единственный корректный момент, т.к. ключ не содержит start), `Set` накапливает веса (`+=`)
- Итоговый вклад подзадачи: `completions(key) × weight` — на этапе подсчёта ни `start`, ни `GetOrbitSize` не нужны
- `Each(ctx, workers, f)` — параллельный обход всех шардов (питает вторую фазу подсчёта)

Полезен на досках ≤6×6 (ускорение 2–3×); на 7×7 и выше доля попаданий менее 1% из-за экспоненциального пространства состояний.

### 7. Разбиение на подзадачи (precompute-depth)
Двухфазный параллельный алгоритм:
1. **Генерация подзадач:** DFS от каждой канонической стартовой группы — группы обрабатываются **параллельно** через `errgroup` с `SetLimit(workers)`; префиксы, достигшие заданной глубины, сохраняются в кэш с весом орбиты и дальше не раскручиваются (ветви отсекает тот же прунер)
2. **Подсчёт:** каждый элемент кэша обрабатывается воркером через `Cache.Each`; найденный результат умножается на вес записи (`Σ count·orbitSize`), агрегация — в общий `atomic.Uint64`

Обе фазы выполняет **единый горячий DFS** `dfs` по битовым маскам без колбэков и аллокаций: различие сводится к базовому случаю (`depth = totalCells, cache = nil` для полного подсчёта; `depth = precomputeDepth, cache ≠ nil` для генерации префиксов).

Мелкие подзадачи лучше распределяются между воркерами, а симметричные префиксы схлопываются в одну запись с суммарным весом.

### 8. Мониторинг
`RealMonitor` без блокировок (атомарные счётчики) перезаписывает одну строку прогресса раз в секунду:
```
[00:01:23] Tasks: 252/252 (100.0%) | Total paths 6637920 | Cached paths: 341
```
Накладные расходы — менее 1%; `FakeMonitor` используется в тестах.

### Измеренные и отвергнутые оптимизации
- **Баланс цветов как критерий отсечения:** на 5×5/6×6 срабатывает 0 раз — инвариант выполняется автоматически вдоль любой легальной DFS-ветви, а для нечётных досок старты фильтрует `SholdSkip`
- **Сортировка кандидатов по Вонсдорфу:** количество узлов дерева поиска не меняется вовсе (прунер локален и не зависит от порядка), при этом время растёт на 10–20% из-за сортировки в каждом узле

## Проверка кода

Полная проверка одной командой:

```bash
make check    # fmt → vet → test -race → fix (автофиксы) → lint
```

Отдельные цели Makefile:

| Команда | Что выполняет |
|---------|---------------|
| `make build` | `go build ./...` |
| `make fmt` | `go fmt ./...` |
| `make vet` | `go vet ./...` |
| `make test` | `go test -race ./...` — тесты с проверкой гонок данных |
| `make fix` | `go fix ./...` + `golangci-lint run --fix ./...` — автофиксы современных идиом |
| `make lint` | `golangci-lint run ./...` — статический анализ |
| `make bench` | Бенчмарки пакета `counter/` |
| `make clean` | `go clean -testcache` |
